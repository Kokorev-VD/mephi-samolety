# Методика идентификаторов

Версия: 0.3. Дата: 07.11.2026. Ответственный: Анохин Г.А. Методика действует для требований этой редакции.

## Область действия

Методика задаёт обозначения требований и связей в [текущей редакции](../README.md). Схема «тип-домен-номер» сохраняет идентификаторы ранее подготовленных Markdown-требований сессий. Это соглашение проекта; оно не объявляется обязательным форматом какого-либо стандарта.

В исходной [методике комплекта](../../notes/methodology/id-methodology.md) используются плоские номера `SR-001`, `SWR-001`. Они не переименовываются этой редакцией. При переносе редактор указывает соответствие между прежним и новым обозначением; оно должно подтверждаться смыслом требования. Совпадение номера не доказывает совпадение смысла.

## Форматы

| Объект | Обозначение |
|---|---|
| Документ | `DOC-NN`; для подсистем допускается суффикс `.N` |
| Системное требование | `SR-ДОМЕН-NNN` |
| Программное требование | `SWR-ДОМЕН-NNN` |
| Описательный проверочный кейс | `TC-ДОМЕН-NNN` |
| Зарегистрированное замечание | `DEF-NNN` |

Номер начинается с `001`; для SR, SWR и TC он выдаётся отдельно внутри каждого домена. В обозначении используются латинские буквы, цифры и обычный дефис. Маркеры требований действующего ТЗ, например `[TS.REQ.FUNC.SESSION.CREATE]`, сохраняются в исходном виде.

| Домен | Область | Владелец по плану |
|---|---|---|
| `AUTH` | Аутентификация и пользователи | Кокорев |
| `SES` | Сессии задач и планировщик | Анохин |
| `KNAP` | Ранцевые криптосистемы | Георгиев |
| `BDR` | Учебная бэкдор-атака | Минасов |
| `ELG` | Эль-Гамаль | Портнов |
| `CFG` | Конфигурации, модерация и инфраструктура | Самбьюи |
| `SYS` | Общие требования и интеграция | Редактор совместно с владельцами |

## Правила ведения

Автор выдаёт свободный ID в своём домене. Один ID обозначает одну проверяемую обязанность или неделимую реакцию на событие. При уточнении того же требования ID сохраняется. Для замены другим требованием указываются старый и новый ID; отменённый номер повторно не выдаётся. Перенос между файлами не меняет ID.

Каждое требование содержит формулировку, источник, приоритет и способ проверки. Общие значения этих полей можно задать перед группой требований. Приоритеты: обязательный, желательный, необязательный. Приоритет требования не заменяет состояние документа или факт его согласования.

В источнике указывается требование ТЗ, более высокого уровня или предметный сценарий. Если исходные документы расходятся, связь сопровождается пояснением; её нельзя выдавать за полное соответствие. Общее требование определяется один раз. В родительских документах и таблицах используются ссылки на его определение.

## Трассировка

Для подготовленных программных требований указываются реальные системные источники. Связи с TC добавляются после подготовки самих кейсов. До этого в таблице указывается описательный способ проверки без вымышленного номера TC.

Полную матрицу SR, SWR и TC ведёт Портнов. Автор домена передаёт ему свои определения и связи. Назначение номера кейсу не означает, что проверка выполнена. DEF присваивается только зарегистрированному замечанию фактической инспекции.
