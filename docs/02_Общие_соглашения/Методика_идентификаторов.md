# Методика идентификаторов

Версия 0.4 от 20.11.2026. Ответственный: Анохин Г.А. Методика действует для требований этой редакции.

## Область действия

Идентификатор (ID) — постоянное обозначение одной записи. По нему читатель может перейти от обещания заказчику к обязанности программы и далее к описанию проверки. Например, [`TS.REQ.FUNC.EVENT.PUBLISH`][TS.REQ.FUNC.EVENT.PUBLISH] требует показывать опубликованную работу в расписании её группы. [SR-CFG-008] описывает, что должен увидеть студент. [SWR-CFG-008] определяет действия программы при публикации, а [TC-CFG-008] описывает проверку этого перехода.

Буквы в начале системного или программного требования обозначают вид записи, средняя часть — область функций (домен), последние три цифры — порядковый номер внутри этой области. В техническом задании действуют собственные маркеры с точками. Оба способа обозначения используются в [текущей редакции](../README.md).

В исходной [методике комплекта](../../notes/methodology/id-methodology.md) используются плоские номера `SR-001`, `SWR-001`. Они не переименовываются этой редакцией. При переносе редактор указывает соответствие между прежним и новым обозначением; оно должно подтверждаться смыслом требования. Совпадение номера не доказывает совпадение смысла.

## Форматы

| Объект | Обозначение |
|---|---|
| Документ | `DOC-NN`; для подсистем допускается суффикс `.N` |
| Системное требование | `SR-ДОМЕН-NNN` |
| Программное требование | `SWR-ДОМЕН-NNN` |
| Описательный проверочный кейс | `TC-ДОМЕН-NNN` |
| Зарегистрированное замечание | `DEF-NNN` |

Номер начинается с `001`; для SR, SWR и TC он выдаётся отдельно внутри каждого домена. В обозначении используются латинские буквы, цифры и обычный дефис. Маркеры требований действующего ТЗ, например [`TS.REQ.FUNC.SESSION.CREATE`][TS.REQ.FUNC.SESSION.CREATE], сохраняются в исходном виде.

| Домен | Область | Владелец по плану |
|---|---|---|
| `AUTH` | Учётные записи, подтверждение группы через МИФИ и назначение преподавателю управляемых групп | Кокорев |
| `SES` | Сессии задач и планировщик | Анохин |
| `KNAP` | Ранцевые криптосистемы | Георгиев |
| `BDR` | Учебная бэкдор-атака | Минасов |
| `ELG` | Эль-Гамаль | Портнов |
| `CFG` | Шаблоны наборов задач, контрольные мероприятия, расписание групп и модерация | Самбьюи |
| `SYS` | Общие требования и интеграция | Редактор совместно с владельцами |

## Правила ведения

Исторический код домена `CFG` сохраняется при уточнении названия. Для требований к выдаче и обработке личной сессии применяется `SES`, в том числе когда сессия начата из расписания контрольных мероприятий. Автор выдаёт свободный ID в своём домене. Один ID обозначает одну проверяемую обязанность или неделимую реакцию на событие. При уточнении того же требования ID сохраняется. Для замены другим требованием указываются старый и новый ID; отменённый номер повторно не выдаётся. Перенос между файлами не меняет ID.

Каждое требование содержит формулировку, источник, приоритет и способ проверки. Общие значения этих полей можно задать перед группой требований. Приоритеты: обязательный, желательный, необязательный. Приоритет требования не заменяет состояние документа или факт его согласования.

В источнике указывается требование ТЗ, более высокого уровня или предметный сценарий. Если исходные документы расходятся, связь сопровождается пояснением; её нельзя выдавать за полное соответствие. Общее требование определяется один раз. В родительских документах и таблицах используются ссылки на его определение.

## Трассировка

Для подготовленных программных требований указываются реальные системные источники. Связи с TC добавляются после подготовки самих кейсов. До этого в таблице указывается описательный способ проверки без вымышленного номера TC.

Полную матрицу SR, SWR и TC ведёт Портнов. Автор домена передаёт ему свои определения и связи. Назначение номера кейсу не означает, что проверка выполнена. DEF присваивается только зарегистрированному замечанию фактической инспекции.
