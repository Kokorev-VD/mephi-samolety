## 1. Основание и назначение `[TS.INTRO]`

<a id="ts-intro-name"></a>
**Наименование `[TS.INTRO.NAME]`.** Полное наименование разработки — «Платформа для изучения и практики курса по криптографии в МИФИ». Краткое наименование — «Криптотренажёр mephi-12». Для курсовой работы Национального исследовательского ядерного университета «МИФИ» команда готовит проектную документацию на серверную часть платформы — программу, которая принимает запросы преподавателя и студентов, обрабатывает их и хранит данные. Комплект предъявляется 01.12.2026. Пометы в квадратных скобках обозначают положения этого задания и позволяют находить ссылки на них в других документах.

<a id="ts-intro-purpose"></a>
**Цель `[TS.INTRO.PURPOSE]`.** Преподаватель составляет работу для группы и определяет, когда студенты могут начать и до какого времени могут сдавать решения. Студент получает свои задания и видит результат по каждому из них. Преподавателю нужны результаты участников его работ в закреплённых за ним группах. Отдельно студенту доступны тренировочные задания и примеры с готовым разбором.

<a id="ts-intro-terms"></a>

### От задания к работе студента `[TS.INTRO.TERMS]`

**Задание, вариант и эталон.** Задание определяет, что надо сделать студенту. Вариант — конкретное условие этого задания. Преподаватель может подготовить задание «Назовите число сторон фигуры» и ввести два варианта. Вопрос «Сколько сторон у треугольника?» имеет правильный ответ «три», а вопрос «Сколько сторон у квадрата?» — «четыре». Преподаватель вводит и правильный ответ для каждого варианта. Этот сохранённый на сервере ответ называют *эталоном*. Одному студенту выдаётся условие выбранного варианта. Эталон остаётся доступным программе для сравнения.

**Модуль и тип.** Модуль — часть программы, которая умеет выдать условие и проверить ответ на него. Для текстового задания модуль выбирает подготовленный вариант и сравнивает ответ с эталоном. Для математического упражнения другой модуль может сам сформировать условие и проверить вычисления. *Тип задания* — обозначение, по которому система выбирает модуль с этими правилами. Предусмотрены ранцевые задачи, задачи по схеме Эль-Гамаля и текстовые задания преподавателя. Содержание математических упражнений определено в [требованиях к ранцевой задаче](#ts-req-func-prob-backpack-si) и [задаче Эль-Гамаля](#ts-req-func-prob-elgamal).

**Группа, мероприятие и позиция.** Учётная запись позволяет платформе узнать пользователя. Студент может сразу зарегистрироваться через `home.mephi.ru` или создать локальный профиль на платформе и позднее связать его со своей подтверждённой учётной записью на `home.mephi.ru`. Оттуда платформа получает номер учебной группы. У студента может быть одна подтверждённая группа. Администратор закрепляет за преподавателем группы, для которых тот может проводить работы. Контрольное мероприятие — работа, которую преподаватель составляет для одной из этих групп на определённую дату. *Позиция* — место задания в этой работе. Например, преподаватель может поставить первым текстовое задание, вторым и третьим — два задания одного математического типа. Ответ на третью позицию не заменяет ответ на вторую.

**Черновик, публикация и расписание.** Пока преподаватель составляет работу, она является черновиком и скрыта от студентов. Можно сохранить одно название и вернуться к подготовке позже. До публикации преподаватель добавляет хотя бы одно задание, выбирает одну из закреплённых за ним групп, задаёт два момента — открытие и закрытие работы — и решает, можно ли пройти её повторно. Публикация закрепляет эти условия. В расписании группы сразу появляется запись, даже если работа назначена на завтра. Сервер сам открывает доступ к началу работы в назначенный момент и закрывает его в момент окончания. Состав записи расписания и условия старта определяют [TS.REQ.FUNC.EVENT.VIEW](#ts-req-func-event-view) и [TS.REQ.FUNC.EVENT.START](#ts-req-func-event-start).

**Личная сессия и задача.** Когда студент начинает разрешённую работу, сервер создаёт для него личную сессию — запись одного прохождения с закреплёнными вариантами, временем старта и результатами. Каждая позиция мероприятия становится отдельной задачей этой сессии. У задачи есть свой идентификатор — значение, по которому система однозначно её находит. Два студента одной группы проходят одно мероприятие в разных сессиях. Даже если им выпадет один вариант, их ответы учитываются раздельно.

**Вердикт, состояние и попытка.** Вердикт — сохранённый ответ системы на вопрос, верно ли решена конкретная задача. Пока задача открыта, её состояние обозначается `NEW`. Верное решение переводит её в `SOLVED`, неверное — в `FAILED` с пояснением. Задача также может получить `FAILED` из-за просрочки. Тогда у неё нет предметного вердикта. Попытка — возможность представить решение задачи. Она расходуется в момент записи вердикта. Ошибка формы ответа не устанавливает его математическую или смысловую неправильность.

**Самостоятельная практика.** Для тренировки используется шаблон набора задач — именованный список типов, расположенных в нужном порядке и доступный определённой группе. По включённому для группы шаблону студент начинает личную тренировочную сессию. Результат такой работы не относится к контрольному мероприятию. Ещё один способ самоподготовки — редакционный пример, то есть отдельно запрошенное учебное условие или готовый разбор без записи в личную сессию.

<a id="ts-intro-scope"></a>
**Область применения `[TS.INTRO.SCOPE]`.** Платформа предназначена для контрольных мероприятий, практикума и лабораторных занятий. Клиентское приложение — программа, через которую преподаватель и студент работают с платформой. Сервер принимает запросы клиента, хранит данные и применяет правила доступа, времени и оценки. В состав серверной разработки входят операции для клиента, сохранение учебных данных и выполнение работы по расписанию, в том числе когда студент вышел из приложения. Согласованные термины собраны в [глоссарии проекта](../02_Общие_соглашения/Глоссарий.md).

<a id="ts-desc"></a>

## 2. Участники и ход работы `[TS.DESC]`

<a id="ts-desc-concept"></a>
**Концепция `[TS.DESC.CONCEPT]`.** В понедельник преподаватель публикует для своей группы работу на среду с 10:00 до 10:30. Студенты сразу видят название работы и оба времени. В среду в 10:00 студент может начать работу и получить собственные варианты. При старте в 10:00 у него есть 20 минут, при старте в 10:25 — пять минут, до 10:30. Начать в 10:30 уже нельзя. После закрытия работы студент может прочитать условие и записанный результат своей задачи. Другая группа не видит эту работу в расписании.

Состояние публикации относится ко всему мероприятию. Разрешение начать работу зависит от группы студента, времени и его предыдущих прохождений. Состояния `NEW`, `SOLVED` и `FAILED` относятся к задачам и к личной сессии. Например, один студент уже закончил работу, а второй ещё решает. Когда разрешено начать новую сессию, определяют [правила доступа и прохождения контрольного мероприятия](#правила-доступа-и-прохождения-контрольного-мероприятия).

<a id="ts-desc-arch"></a>
**Взаимодействие `[TS.DESC.ARCH]`.** Клиент преподавателя передаёт серверу состав, назначение и решение о публикации. Клиент студента читает расписание, предъявляет идентификатор мероприятия при старте и предъявляет идентификатор выданной задачи при сдаче решения. Сервер устанавливает пользователя по учётным данным, проверяет его право на действие и сохраняет данные мероприятия, назначения и индивидуальных сессий. Для каждой позиции сервер передаёт запрос на выдачу варианта или проверку решения модулю этого типа. Порядок обмена установлен в [правилах модулей](#ts-req-func-task-module). Когда время работы истекло, сервер учитывает это и при отключённом клиенте. Размещение частей программы и их действия после сбоя приведены в [архитектуре программного обеспечения (DOC-07)](../09_Архитектура_и_API/DOC-07_Архитектура.md).

<a id="ts-desc-limit"></a>
**Границы `[TS.DESC.LIMIT]`.** Задание определяет функции учебного сервера и наблюдаемые результаты операций. Критерии математической правильности относятся к учебным условиям, выданным системой. Учебные примеры служат для разбора свойств схем и не дают оснований оценивать стойкость сторонних систем. Требования к программе, описание обмена между клиентом и сервером и планы проверок входят в комплект курсовой работы. Условия его приёмки приведены в [разделе о контроле](#ts-test-accept).

## 3. Требования к системе `[TS.REQ]`

Требования раздела обязательны для целевой платформы. Для каждого результата, который зависит от нескольких подсистем, [системные требования DOC-05](../04_Системные_требования/DOC-05_Системные_требования.md) определяют, что увидит пользователь. [Сводные программные требования DOC-06](../07_Программные_требования/DOC-06_Программные_требования.md) и требования по подсистемам распределяют работу между частями программы. Идентификатор в квадратных скобках обозначает одно и то же положение во всех документах комплекта.

<a id="ts-req-func"></a>

### 3.1. Функциональные требования `[TS.REQ.FUNC]`

#### Подготовка и проведение контрольного мероприятия

<a id="ts-req-func-event-create"></a>
**Состав работы `[TS.REQ.FUNC.EVENT.CREATE]`.** Преподаватель должен иметь возможность создать свой черновик и самостоятельно выбрать задания и их порядок. В одну работу могут входить задания разных видов, несколько заданий одного вида и созданные преподавателем текстовые задания. Позиции одного вида дают отдельные задачи с независимыми результатами. Черновик можно сохранить без заданий, открыть позднее и менять до публикации, в том числе удалить последнее задание. В черновике преподаватель выбирает правило повторного прохождения (`repeatAllowed`) — «да» или «нет». Черновик с незаполненными полями можно сохранить. Перед публикацией преподаватель должен выбрать одно из двух значений.

<a id="ts-req-func-event-schedule"></a>
**Назначение `[TS.REQ.FUNC.EVENT.SCHEDULE]`.** Преподаватель назначает свою работу одной из групп, которыми его уполномочил управлять администратор. Для работы задаются дата и время открытия (`opensAt`) и закрытия (`closesAt`). Открытие должно предшествовать закрытию. Окно старта — промежуток от открытия включительно до закрытия исключительно. По часам сервера доступ открывается и закрывается автоматически. Знание идентификатора мероприятия не даёт студенту другой группы права начать работу.

<a id="ts-req-func-event-publish"></a>
**Публикация `[TS.REQ.FUNC.EVENT.PUBLISH]`.** По команде преподавателя сервер должен проверить его право на эту работу и выбранную группу. Для публикации необходимы хотя бы одно задание, назначенная группа, оба момента времени при `opensAt < closesAt` и явный выбор `repeatAllowed`. При ошибке преподаватель получает объяснение, может исправить свой черновик под прежним идентификатором, а в расписании запись не появляется. В частности, при пустом составе система предлагает добавить задание. Успешная публикация закрепляет порядок заданий, редакции их вариантов, группу, обе границы времени и правило повторного прохождения. Публикация и появление записи в расписании назначенной группы должны составлять одно завершённое действие, в том числе при сбое. Банк заданий — сохранённые преподавателем задания и варианты для составления работ. Позднейшее редактирование банка не изменяет условия и эталоны опубликованной работы.

<a id="ts-req-func-event-view"></a>
**Расписание `[TS.REQ.FUNC.EVENT.VIEW]`.** Сразу после публикации студент должен видеть в расписании своей подтверждённой группы название работы, дату и время открытия и закрытия, а также доступность старта. До открытия запись уже видна, но начать работу ещё нельзя. С момента закрытия новый старт недоступен. Правила повторного прохождения и чтения прежней работы установлены в [TS.REQ.FUNC.EVENT.START](#ts-req-func-event-start). Студенту недоступны черновики и мероприятия других групп. В расписание не входят условия индивидуальных вариантов, эталоны и другие данные проверки.

<a id="ts-req-func-event-start"></a>
**Начало личной работы `[TS.REQ.FUNC.EVENT.START]`.** Сервер разрешает новый старт только участнику подтверждённой группы опубликованного мероприятия при `opensAt ≤ t0 < closesAt`, где `t0` — серверное время создания сессии. Первый старт создаёт отдельную сессию, связанную со студентом и мероприятием. Если предыдущая сессия этого мероприятия завершена, ещё одно прохождение в пределах окна допускается при `repeatAllowed = true` («да»). Оно получает новый идентификатор. Условия и результаты прежней сессии сохраняются. При `repeatAllowed = false` («нет») студент может прочесть своё прежнее прохождение, но второй раз начать работу нельзя. При наличии любой активной личной сессии применяется [правило конфликта](#ts-req-func-session-create). Отказ в старте не создаёт задач или сессии.

#### Виды заданий и пользовательские варианты

<a id="ts-req-func-task-module"></a>
**Общие правила модулей `[TS.REQ.FUNC.TASK.MODULE]`.** Для подключения модуля устанавливается общий контракт — какие данные ему передаёт сервер и что тот возвращает. Модуль должен выдать условие варианта, а при получении решения — проверить его по этому условию. Система сохраняет тип и вариант при выдаче и направляет ответ тому же модулю. Модель допускает подключение дополнительных видов с этими операциями без изменения правил расписания, сроков, попыток и завершения личной сессии. Каждому виду соответствует устойчивое обозначение. При выдаче модуль предоставляет открытое условие и, когда необходимо, закрытые данные для последующей проверки. Тип `BACKPACK` обозначает ранцевую задачу, `EL_GAMAL` — задачу Эль-Гамаля, `CUSTOM_TEXT` — текстовое задание с вариантами преподавателя. Проверка текстового ответа описана в [TS.REQ.FUNC.TASK.ASSIGN](#ts-req-func-task-assign). Математические условия разобраны в [требованиях к ранцевым задачам](#ts-req-func-prob-backpack-si) и [схеме Эль-Гамаля](#ts-req-func-prob-elgamal).

<a id="ts-req-func-task-custom"></a>
**Задание преподавателя `[TS.REQ.FUNC.TASK.CUSTOM]`.** Преподаватель должен иметь возможность без программирования сформировать текстовое задание и ввести несколько вариантов. У задания есть название и как минимум один полностью заполненный вариант. Преподаватель может добавить ещё варианты для случайной выдачи. У каждого варианта обязательны текст условия и соответствующий ему правильный текстовый ответ. Преподавателю доступны собственные задания для включения в работу и перечень поддерживаемых видов. Такую задачу можно включить в контрольную работу вместе с математическими заданиями. Для выполнения студенту предоставляется текстовое поле.

<a id="ts-req-func-task-assign"></a>
**Выдача и проверка варианта `[TS.REQ.FUNC.TASK.ASSIGN]`.** Для каждой позиции с пользовательским заданием система должна случайно выбрать один из введённых преподавателем вариантов и закрепить его за студентом в данной сессии. Двум студентам может выпасть один вариант. При повторном открытии собственной работы студент видит прежнее условие. Клиент студента получает только назначенное условие. Эталон хранится на сервере и не передаётся студенту ни в составе задачи, ни при получении вердикта.

Система должна сравнивать введённый и правильный ответы как текст, удалив у обеих строк пробелы в начале и конце. Регистр букв и внутренние пробелы сохраняются. Например, у эталона «Ключ А» один пробел между словами. Пробелы перед словом «Ключ» и после буквы «А» допустимы в обеих строках. Ответ «ключ А» неверен из-за регистра. Ответ с двумя пробелами между словами также неверен. Оба предметных исхода учитываются по общему правилу попытки.

#### Учётные записи, группы и прохождение сессии

Клиент и сервер обмениваются запросами и ответами по протоколу HTTP. У каждого ответа есть числовой код состояния, по которому клиент отличает успех от отказа. После успешной регистрации или входа сервер выдаёт токен JWT (JSON Web Token) — подписанное удостоверение доступа к платформе. Клиент предъявляет его в последующих запросах. Сервер устанавливает учётную запись и проверяет права пользователя на выбранный объект. На платформе есть роли студента (`USER`), преподавателя (`TEACHER`) и администратора (`ADMIN`). Их полномочия определены в [TS.REQ.SEC.ROLES](#ts-req-sec-roles).

<a id="ts-req-func-auth-reg"></a>
**Регистрация и привязка `[TS.REQ.FUNC.AUTH.REG]`.** Студент может сразу зарегистрироваться через `home.mephi.ru`. Получив подтверждение его учётной записи из этого источника, платформа создаёт для неё один профиль. Другой путь начинается с локальной регистрации по адресу электронной почты, имени и паролю. Повторная локальная регистрация с занятым адресом отклоняется. Владелец локального профиля входит в него и может позднее привязать к нему свою подтверждённую учётную запись `home.mephi.ru`. Студент сохраняет прежний идентификатор профиля и историю прохождений. Одинаковый адрес почты не доказывает, что профили принадлежат одному человеку. Если подтверждение получить не удалось или та же внешняя учётная запись уже связана с другим профилем, операция отклоняется. Ошибка не должна создавать дубликат, объединять профили или менять ранее сохранённые связи, права и данные. При успешной регистрации пользователь получает токен платформы.

<a id="ts-req-func-auth-login"></a>
**Вход `[TS.REQ.FUNC.AUTH.LOGIN]`.** Студент с привязанной учётной записью при подтверждённом входе через `home.mephi.ru` получает токен своего профиля. Для локального входа используются адрес электронной почты и пароль. Допустимая длина адреса — от 4 до 120 символов включительно, пароля — от 8 до 255 включительно. Сервер проверяет пароль по хешу — сохранённому проверочному значению. При верных данных пользователь получает JWT своего профиля. Если подтвердить его личность не удалось, сервер возвращает HTTP 401. Успешный локальный вход сам по себе не подтверждает номер группы.

<a id="ts-req-func-auth-jwt"></a>
**Личность пользователя `[TS.REQ.FUNC.AUTH.JWT]`.** Для каждой защищённой операции система должна установить по действительному JWT идентификатор пользователя (`userId`) и полномочия (`authorities`). Указанный клиентом идентификатор задачи, группы или сессии выбирает объект операции. Он не удостоверяет права на этот объект.

<a id="ts-req-func-group-list"></a>
**Перечень групп `[TS.REQ.FUNC.GROUP.LIST]`.** Система должна предоставлять перечень учебных групп с идентификаторами, названиями и составом участников при наличии полномочий на соответствующие сведения.

<a id="ts-req-func-group-join"></a>
**Подтверждение учебной группы `[TS.REQ.FUNC.GROUP.JOIN]`.** Сервер устанавливает группу студента по номеру, полученному из `home.mephi.ru` для его подтверждённой внешней учётной записи. В профиле студента одновременно может быть одна действующая группа. Введённый вручную номер, выбор названия из списка и адрес электронной почты не дают членства. Если подтверждённого номера группы нет, студенту недоступны групповое расписание, шаблоны группы и старт по мероприятию или шаблону. Доступ к собственному профилю и истории прежних личных сессий сохраняется.

<a id="ts-req-func-config-view"></a>
**Шаблоны наборов задач `[TS.REQ.FUNC.CONFIG.VIEW]`.** Студент должен видеть только шаблоны своей группы. Для каждого шаблона указываются имя, порядок типов задач и признак включения. При самостоятельной практике студент может начать набор только по шаблону, включённому для его группы в момент создания. Если доступного шаблона с таким именем нет, набор не создаётся.

Идентификаторы учётных записей, мероприятий, сессий и задач имеют формат UUID — уникального идентификатора объекта, например `5a000000-0000-4000-8000-000000000001`. Один и тот же UUID указывает на один объект при создании, сдаче решения и чтении результата. Название работы или порядковый номер задачи не заменяет её идентификатор.

<a id="ts-req-func-session-create"></a>
**Создание сессии `[TS.REQ.FUNC.SESSION.CREATE]`.** Студент должен получить целиком сессию в состоянии `NEW`. В ответ входят идентификаторы набора и задач, время создания, тип, условие и состояние каждой задачи. Для самостоятельной практики порядок определяется включённым шаблоном подтверждённой группы, для контрольной работы — составом опубликованного мероприятия. По двум одинаковым типам выдаются две отдельные задачи. Последующие изменения исходных материалов сохраняют условия, уже выданные студенту. Если подготовка вариантов прервалась, незаконченный набор не сохраняется как активная сессия. Студент может иметь только одну активную сессию `NEW` во всех мероприятиях и практике вместе. При попытке начать вторую сессию, если остальные условия старта выполнены, сервер возвращает `409 ACTIVE_SESSION_EXISTS` — конфликт с уже активной сессией — и её идентификатор. Это правило действует и при двух одновременных запросах на старт. Разрешение повторного прохождения не допускает второй активной сессии.

<a id="ts-req-func-session-time"></a>
**Срок `[TS.REQ.FUNC.SESSION.TIME]`.** Серверное время создания личной сессии обозначается `t0`. У всех её задач общий предельный момент подачи решения — `D`. Для контроля `D = min(t0 + 20 минут, closesAt)`, то есть выбирается более ранний из двух моментов. Открытие и закрытие заданы в [назначении работы](#ts-req-func-event-schedule). Для самостоятельной практики `D = t0 + 20 минут`. Момент получения сервером полного запроса с решением обозначается `t_in`. Новый ответ владельца может пройти проверку, если `t_in < D` и соблюдены остальные [условия допуска](#ts-req-func-session-submit). При `t_in = D` или позднее принимать новый ответ к проверке нельзя. Планировщик — часть сервера, которая периодически находит и закрывает просроченные задачи. Плановый период его запуска — 60 секунд. Время этого просмотра не изменяет `D`.

На обработку своевременно полученного ответа отведён отдельный интервал до `L = t_in + 60 секунд`. Ожидание исполнителя, проверка и запись результата входят в этот интервал. Пока своевременный ответ владельца ожидает решения в пределах `L`, наступление `D` не препятствует его дальнейшему допуску и проверке. Вердикт можно записать строго до `L`. Если к моменту `L` записи нет, операция завершается техническим отказом без предметного вердикта. Новый ответ возможен, только пока задача открыта и новый запрос поступает до `D`.

<a id="ts-req-func-session-submit"></a>
**Отправка решения `[TS.REQ.FUNC.SESSION.SUBMIT]`.** Система должна принимать решение по UUID задачи (`statementId`), установить принадлежность задачи студенту и проверить состояние набора, срок и форму ответа. Сохранённый тип задаёт модуль, который проверяет решение по выданному условию. Допустим один окончательный вердикт на задачу. Верное решение даёт `SOLVED`. Решение, признанное неверным по правилам своего типа, даёт `FAILED` и пояснение. Например, у текстовой задачи условие может быть прочитано правильно, а введённый ответ не совпасть с эталоном. Ошибка формы означает, что ответ невозможно прочесть по правилам этого вида задания. Технический отказ означает, что серверу не удалось выполнить операцию. В обоих случаях без записанного вердикта попытка сохраняется. Подтверждение предметного результата выдаётся после согласованной записи вердикта, состояния задачи и состояния сессии. Пока хотя бы одна задача открыта, сессия остаётся `NEW`. После закрытия последней задачи сессия получает `SOLVED`, если все решены верно, либо `FAILED`, если хотя бы одна завершилась неуспешно.

<a id="ts-req-func-session-read"></a>
**Чтение собственной сессии `[TS.REQ.FUNC.SESSION.READ]`.** По идентификатору сессии владелец должен получить её состояние, исходные задачи и сохранённый результат каждой задачи. Чтение доступно и после `D`, в том числе после закрытия мероприятия или отказа в повторном прохождении. Если было несколько прохождений, по каждому идентификатору возвращается результат соответствующей сессии. Учитывается фактическая просрочка, даже если очередной фоновый проход ещё не состоялся. При отсутствии предметного вердикта в поле результата указывается `null` — специальное обозначение отсутствующего значения. `FAILED` с пустым результатом означает закрытие по сроку, `FAILED` с отрицательным вердиктом — неверное решение. Чтение не расходует попытку. Для чужой и отсутствующей сессии возвращается одинаковый отказ.

#### Математические упражнения и учебные разборы

В ранцевом упражнении сообщение представлено последовательностью выбранных и невыбранных элементов. Лёгкий ранец — закрытая исходная последовательность чисел, тяжёлый ранец — связанная с ней последовательность, используемая при шифровании. Модуль задаёт делитель, по которому берутся остатки. Множитель — число, участвующее в преобразовании последовательности. Обратным к нему называется число, произведение которого с множителем даёт остаток 1 по этому модулю. Взаимно простые числа имеют единственный общий положительный делитель — 1. Слово «модуль» в математическом условии означает число. В описании устройства программы оно обозначает часть программы, которая работает с определённым видом задания.

<a id="ts-req-func-prob-backpack-si"></a>
**Ранцевая задача на супервозрастающей последовательности `[TS.REQ.FUNC.PROB.BACKPACK.SI]`.** Система должна сформировать условие с частично скрытыми параметрами и проверить, что присланные значения согласуются с этим условием. Проверке подлежат элементы лёгкого ранца, модуль, взаимная простота множителя с модулем, тяжёлый ранец, обратный множитель, зашифрованное и расшифрованное сообщения. Для этого варианта каждый элемент лёгкого ранца строго больше суммы предшествующих. При неверном решении студент получает пояснение о величине, в которой обнаружено расхождение.

<a id="ts-req-func-prob-backpack-deg"></a>
**Ранцевая задача на степенях `[TS.REQ.FUNC.PROB.BACKPACK.DEG]`.** Основание степени — число, которое возводят в разные целые степени, получая элементы ранца. Система должна сформировать лёгкий ранец из степеней выбранного основания и выдать условие с сохранённым обозначением варианта. Решение должно проверяться по тем же группам величин, что и для супервозрастающего варианта, с учётом условия о степенях. Проверяется та задача, которую получил студент. Поля ответа не могут переключить проверку на другой вариант.

<a id="ts-req-func-prob-elgamal"></a>
**Эль-Гамаль `[TS.REQ.FUNC.PROB.ELGAMAL]`.** Это схема шифрования с открытым и закрытым ключами. Система должна выдавать условие с простым числом `p` (модулем), элементом `g` (основанием), закрытым показателем `x` и сообщением `m`. Студент определяет открытый ключ `y`, выбирает `k` — одноразовый показатель для шифрования сообщения, — получает две части зашифрованного сообщения `c1`, `c2` и восстанавливает исходное сообщение. Проверяются все перечисленные результаты. При математической ошибке в ответе надлежащей формы студент получает отрицательный вердикт с указанием первого неверного промежуточного значения.

<a id="ts-req-func-prob-backdoor"></a>
**Демонстрационный ранцевый пример `[TS.REQ.FUNC.PROB.BACKDOOR]`.** Бэкдор в этом учебном примере — специально предусмотренная скрытая особенность, из-за которой обещанная конфиденциальность сообщения нарушается даже при правильном выполнении вычислений. В режиме самостоятельного разбора система должна предоставлять готовый пример такого свойства ранцевой криптосистемы. Из представленного условия и пояснения студент должен суметь назвать, какое допущение о конфиденциальности нарушено, и отличить его от ошибки в вычислениях. Если за предусмотренное число попыток сформировать подходящий материал не удалось, система возвращает диагностический отказ. Демонстрация не входит в оцениваемый набор и не изменяет результат сессии.

<a id="ts-req-func-editorial"></a>
**Материалы для самоподготовки `[TS.REQ.FUNC.EDITORIAL]`.** По запросу должны предоставляться эталонная ранцевая задача выбранного варианта с полным решением, в том числе по заданным допустимым параметрам, готовый демонстрационный ранцевый пример, пошаговый разбор схемы Эль-Гамаля или самостоятельное задание по этой схеме. Результаты редакционных генераций выдаются без записи в базу данных. Состав и результаты собственной сессии после обращения за материалом сохраняются.

<a id="ts-req-func-mod-view"></a>
**Контроль прогресса `[TS.REQ.FUNC.MOD.VIEW]`.** Функция модерации должна предоставлять пользователю с ролью `ADMIN` обзор сессий всех студентов, включая состояния сессий и входящих в них задач. Пределы доступа для роли студента и роли администратора закреплены в [требовании о полномочиях](#ts-req-sec-roles). Получение обзора не изменяет ни результатов, ни оставшегося времени.

<a id="ts-req-func-history"></a>
**История `[TS.REQ.FUNC.HISTORY]`.** Студент должен иметь возможность просмотреть историю собственных решённых задач и сопоставить результат с выданным условием и сессией. Новый вход в учётную запись сохраняет доступ к прежним результатам. Повторное чтение истории не запускает проверку решений.

<a id="ts-req-int"></a>

### 3.2. Внешний интерфейс `[TS.REQ.INT]`

<a id="ts-req-int-rest"></a>
**Доступ к ресурсам `[TS.REQ.INT.REST]`.** Программный интерфейс приложения (API) задаёт доступные клиенту операции и формат обмена. В интерфейсе REST клиент выбирает ресурс по адресу, а действие — по методу HTTP. Сервер должен предоставлять этот интерфейс по базовому пути `/api` на порту 8083. Путь начинает адреса операций, порт указывает, куда клиент устанавливает соединение. Учётная запись, сессия и задача идентифицируются UUID. При отправке решения указывается UUID задачи, при чтении набора — UUID сессии. Параметр `configuration` в запросе на начало самостоятельной практики обозначает имя шаблона. При старте контрольной работы передаётся `assessmentId`. Требуется ровно один из параметров `assessmentId` и `configuration`. Их одновременная передача либо отсутствие обоих дают `400 INVALID_REQUEST` — неверная форма запроса. В представлении сессии `assessmentId` содержит UUID мероприятия либо `null` для самостоятельной практики. Результат тренировки не засчитывается за участие в мероприятии. JSON — текстовый формат обмена, в котором у полей есть имена и значения. При передаче в этом формате система должна сохранять точность учебных целых чисел. Временные отметки передаются с однозначной привязкой к всемирному координированному времени (UTC). Форматы запросов и ответов приведены в [справочнике API](../09_Архитектура_и_API/DOC-08_API_сессий.md).

<a id="ts-req-int-bearer"></a>
**Заголовок доступа `[TS.REQ.INT.BEARER]`.** Заголовок — служебное поле запроса HTTP. В заголовке `Authorization` клиент должен передать слово `Bearer` и выданный ему токен через пробел. Запись `Authorization: Bearer <JWT>` показывает место для значения токена. Для начала регистрации или входа не требуется ранее выданный токен платформы. Привязка внешней записи требует подтверждённого владельца локального профиля и подтверждения со стороны `home.mephi.ru`. Отсутствующий либо недействительный токен не позволяет получить данные защищённой операции.

<a id="ts-req-int-codes"></a>
**Результаты и ошибки `[TS.REQ.INT.CODES]`.** Успешное создание сессии даёт HTTP 201, чтение и оба предметных вердикта — HTTP 200. В ответе об ошибке обязателен машинный код, понятное человеку сообщение и время ошибки. Для операций сессий передаётся также идентификатор запроса. Ошибку параметров или формы тела следует обозначать `400`, неподтверждённую личность — `401`, недостаточные полномочия — `403`, отсутствие ресурса среди доступных пользователю — `404`. Для поздней отправки решения владельцем возвращается `410`. Отказы при конфликте состояния, превышении размера тела и технической невозможности проверки определены для каждой операции в DOC-08. Технический отказ не может возвращаться клиенту как подтверждённый неверный учебный ответ.

<a id="ts-req-rel"></a>

### 3.3. Надёжность `[TS.REQ.REL]`

<a id="ts-req-rel-autofail"></a>
**Завершение без участия студента `[TS.REQ.REL.AUTOFAIL]`.** После истечения общего срока система должна автоматически закрывать открытые задачи без своевременных ответов в обработке и пересчитывать итог набора. Для этого не требуется новый запрос от студента. У уже завершённой задачи сохраняется прежний результат.

<a id="ts-req-rel-persist"></a>
**Сохранность `[TS.REQ.REL.PERSIST]`.** При перезапуске приложения должны сохраняться учётные записи, подтверждённые связи с `home.mephi.ru`, учебные группы студентов, назначения групп преподавателям и шаблоны групп. Преподавателю после перезапуска должны быть доступны прежние черновики и банк пользовательских заданий с вариантами. У опубликованного мероприятия сохраняются состав, назначенная группа, открытие, закрытие, правило повторного прохождения и закреплённые редакции вариантов. Студент находит в расписании тот же идентификатор, даже если сервер был перезапущен после публикации и до первого старта. Для каждого прохождения сохраняются связь с мероприятием, принадлежность сессии, время создания, срок сдачи, закреплённые варианты, условия, состояния и определённые результаты. Для принятого ответа сохраняются полный ответ и исходный момент получения. После перезапуска его обработка может продолжиться в оставшейся части исходного интервала. Если вердикт уже записан, чтение возвращает его без повторной попытки. Если вердикта нет и `L` уже наступил, позднее вычисление не должно менять результат задачи. Окончательный технический отказ, сообщённый клиенту, исключает последующую запись вердикта той же отменённой операции.

<a id="ts-req-rel-sched"></a>
**Единое правило времени `[TS.REQ.REL.SCHED]`.** Допуск нового ответа, фоновое завершение и чтение состояния должны использовать один серверный срок `D`, определённый [для вида сессии](#ts-req-func-session-time). Если полный ответ получен до `D`, его можно обработать и после закрытия мероприятия, но записать результат нужно строго до исходного `L`. Пропущенный запуск планировщика, очередь исполнителя, отключение клиента и перезапуск приложения не сдвигают эти границы. При обращении владельца в `D` или позднее задача без своевременного ответа уже недоступна для решения, даже если планировщик ещё не запускался.

<a id="ts-req-rel-deploy"></a>
**Развёртывание и данные `[TS.REQ.REL.DEPLOY]`.** PostgreSQL — система управления базой данных (СУБД), которая хранит сведения платформы между запусками. Серверное приложение и СУБД запускаются в контейнерах — отдельных средах исполнения. Средства развёртывания должны запускать приложение после подтверждения готовности PostgreSQL. Базе предоставляется постоянный том — область хранения, содержимое которой сохраняется при перезапуске контейнеров. После повторного запуска сервер должен обслуживать запросы и выдавать сохранённые записи с прежними идентификаторами и сроками.

<a id="ts-req-sec"></a>

### 3.4. Безопасность и права `[TS.REQ.SEC]`

<a id="ts-req-sec-jwt"></a>
**Подпись токена `[TS.REQ.SEC.JWT]`.** Для защиты содержимого JWT от подмены сервер должен вычислять метку подлинности по общему секрету методом HMAC-SHA256. Срок действия в днях задаётся параметром окружения — значением, переданным приложению при запуске. Сервер проверяет подпись и срок действия перед предоставлением защищённого ресурса.

<a id="ts-req-sec-passwords"></a>
**Пароли `[TS.REQ.SEC.PASSWORDS]`.** Для вычисления и хранения проверочного хеша локального пароля платформа должна применять BCrypt — алгоритм хеширования паролей. При входе введённый пароль сверяют по сохранённому хешу. Во время передачи пароль должен быть защищён от чтения посторонним. Пароль и его хеш не включаются в представление профиля, в перечни групп и сообщения об ошибках.

<a id="ts-req-sec-roles"></a>
**Разграничение полномочий `[TS.REQ.SEC.ROLES]`.** Администратор (`ADMIN`) назначает каждому преподавателю набор управляемых групп. Только администратор может менять эти назначения. Ему доступен обзор сессий всех студентов. Преподаватель (`TEACHER`) создаёт свои черновики. Назначать и публиковать свои работы он может лишь для групп, которыми управляет. Он может смотреть результаты только по собственным работам в этих группах. Доступа к чужим работам, даже если они проводятся в той же группе, или к результатам вне закреплённых групп у него нет. Преподаватель не может назначить себе группу. Студент (`USER`) видит расписание и шаблоны своей подтверждённой группы, создаёт свои сессии и читает свои результаты. Сервер проверяет право на выбранный объект независимо от того, какой идентификатор передал клиент. Адрес электронной почты, его домен и переданные клиентом названия ролей не присваивают никаких полномочий.

<a id="ts-req-sec-secrets"></a>
**Секреты и параметры среды `[TS.REQ.SEC.SECRETS]`.** Секрет подписи JWT, срок действия токена, адрес и учётные данные подключения к базе должны передаваться через переменные среды. Значения секретов не включаются в распространяемые исходные тексты, документы и сообщения пользователю.

<a id="ts-req-perf"></a>

### 3.5. Производительность `[TS.REQ.PERF]`

Время отклика — интервал от отправки запроса клиентом до получения полного ответа. Для сравнения берут несколько измерений одного класса и располагают времена от меньшего к большему. 95-й процентиль (`p95`) — время на позиции, определённой по [правилу измерения](#ts-req-perf-measure). Для серии из ста запросов это 95-е значение. Пять самых долгих наблюдений могут его превышать.

<a id="ts-req-perf-crud"></a>
**Обычные операции `[TS.REQ.PERF.CRUD]`.** При одновременной работе 30 пользователей 95-й процентиль времени обычных операций должен быть не более 2 секунд. К этому классу относятся регистрация, вход, просмотр групп, шаблонов и расписания, чтение данных и обычная отправка решения. Время обычной отправки включает получение предметного ответа. Сценарии с намеренно задержанным или недоступным проверяющим проверяют надёжность отдельно.

<a id="ts-req-perf-gen"></a>
**Операции с генерацией `[TS.REQ.PERF.GEN]`.** При той же нагрузке 95-й процентиль времени операций с генерацией должен быть не более 5 секунд. К этому классу относятся создание набора со всеми его условиями и генерация учебных материалов, включая задания Эль-Гамаля с заданной разрядностью (длиной числа в битах) и демонстрационные примеры. Создание сессии учитывается один раз в классе генерации.

<a id="ts-req-perf-measure"></a>
**Условия измерения `[TS.REQ.PERF.MEASURE]`.** Для каждого класса отдельно задаётся серия не менее 100 запросов на прогретом стенде (сервер и база уже запущены и обслуживают запросы) при постоянном профиле нагрузки (сохраняются состав и соотношение операций) и 30 одновременно работающих пользователях. Для каждой серии фиксируются состав операций, размер выборки и измеренные времена от отправки запроса до получения полного ответа. Значения упорядочиваются по возрастанию, `p95` равен значению на месте `ceil(0,95 × N)` при нумерации мест с единицы. Здесь `N` — число наблюдений класса, `ceil` означает округление вверх до целого. Для 100 запросов берётся 95-е значение. Равенство установленному порогу допустимо. Предел `L` ограничивает право на запись одного вердикта и не служит показателем скорости массового обслуживания. Метод и ожидаемый результат измерения описываются в плане проверки требований (плане верификации).

## 4. Состав разработки и документации `[TS.DOC]`

<a id="ts-doc-set"></a>
**Комплект `[TS.DOC.SET]`.** Для курсовой работы принят порядок документирования по образцу авиационных документов ДО-178C/КТ-178C. Формальная инспекция в данном проекте означает рассмотрение конкретной редакции несколькими участниками по перечню вопросов, регистрацию замечаний и запись решения в протоколе. Реестр комплекта присваивает документам обозначения `DOC` с номером. В указателе DOC-00 и описании DOC-01 приводятся состав комплекта и назначение материалов. DOC-02 задаёт обязательства системы, DOC-03 регулирует управление версиями, DOC-04 определяет процедуру инспекции. DOC-05 содержит системные требования, в DOC-06 и DOC-06.1–DOC-06.6 формулируются общие требования к программе и обязанности отдельных подсистем. В DOC-07 описывается архитектура, в DOC-08 — внешний интерфейс. DOC-09 связывает требования с описательными случаями проверки (кейсами). DOC-10 содержит план проверок требований, DOC-11 — план интеграционных проверок, то есть проверок совместной работы нескольких частей системы. Решения состоявшихся инспекций оформляются в DOC-13.1–DOC-13.6. DOC-14 предусмотрен реестром для количественного анализа покрытия — подсчёта требований, для которых прослежены необходимые связи с требованиями других уровней и случаями проверки.

<a id="ts-doc-trace"></a>
**Трассировка `[TS.DOC.TRACE]`.** Трассировка — запись того, какое требование программы выполняет обещание системы и какой случай позволяет это проверить. Системное требование имеет обозначение SR, программное — SWR, описательный проверочный случай — TC. В последнем перечисляются исходные условия, действие и ожидаемый результат. Каждому системному требованию должны соответствовать хотя бы одно программное требование и один описательный проверочный кейс. Для каждого программного требования указываются хотя бы одно системное основание и один кейс проверки. Связи в матрице DOC-09 ведут к конкретным определениям SR, SWR и TC. Одинаковый номер, сходство названий или наличие записи в указателе сами по себе не подтверждают связь по смыслу.

<a id="ts-doc-tech"></a>
**Технологии `[TS.DOC.TECH]`.** Для серверной программы устанавливаются язык Kotlin 1.9.25 и платформа разработки Spring Boot 3.4.0. В её состав входят средства приёма запросов (Web), работы с данными (JPA), проверки доступа (Security), проверки входных полей (Validation) и наблюдения за приложением (Actuator). Данные хранятся в PostgreSQL 17. Для работы с токенами JWT применяется библиотека jjwt. Контейнеры запускает Docker, а Docker Compose задаёт их совместный запуск. Размещение и границы ответственности компонентов определены в DOC-07.

<a id="ts-doc-notest"></a>
**Объём верификации `[TS.DOC.NOTEST]`.** Курсовой комплект предусматривает формальные инспекции документов и описательные сценарии с условиями и ожидаемыми результатами. Тестовый код, выполнение прогонов и протоколы исполненных испытаний в эту работу не входят. Описания тестов и расчёт критериев служат исходными материалами для проверки документации.

## 6. Контроль и приёмка `[TS.TEST]`

<a id="ts-test-ver"></a>

### 6.1. Порядок контроля `[TS.TEST.VER]`

План DOC-10 должен описать исходные условия, действие и наблюдаемый результат для каждого требования. Отдельно рассматриваются штатное выполнение, неверный ввод, недостаточные полномочия, отказ до фиксации и восстановление. В DOC-11 связанные операции объединяются в сквозные сценарии — от подтверждения учётной записи и номера группы через `home.mephi.ru` до чтения результата, получения редакционных материалов или административного обзора. Для основного сценария описывают назначение группы преподавателю администратором, создание черновика, настройку окна и повторов, публикацию, появление записи в расписании, старт, выдачу вариантов, проверку ответа на границе закрытия и чтение результата. Повторное прохождение разбирают при обоих значениях `repeatAllowed`. Проверка производительности требует указать нагрузку, способ определения `p95` и критерий сравнения для каждого класса операций.

Формальная инспекция настоящего технического задания (ТЗ) проводится по DOC-04 и оформляется протоколом DOC-13.1. Программные требования, архитектура с API, трассировка с планами проверок предъявляются на соответствующие отдельные инспекции. Рецензент рассматривает чужую предметную область. Секретарь фиксирует фактических участников и предъявленную редакцию. Каждое принятое замечание регистрируется как дефект с идентификатором `DEF`, ответственным и сроком исправления. Ведущий подтверждает закрытие после проверки правки. Метод последующей проверки документа зависит от результата инспекции.

<a id="ts-test-accept"></a>

### 6.2. Критерии `[TS.TEST.ACCEPT]`

**Что должен увидеть пользователь по описанию целевой системы.** Для оценки полноты требований комиссия должна иметь возможность разобрать, в частности, следующие случаи с однозначным ожидаемым исходом.

| Условие | Ожидаемый результат |
|---|---|
| Студент регистрируется через `home.mephi.ru`. Другой студент создаёт локальный профиль и позднее привязывает подтверждённую учётную запись | Первый получает один профиль. У второго остаются прежний идентификатор и история. У каждого номер группы соответствует подтверждённым сведениям о нём. |
| Привязываемая внешняя учётная запись уже закреплена за другим профилем. В отдельном случае у студента с прежними прохождениями нет подтверждённой группы | При конфликте профили и их связи остаются раздельными. Без подтверждённого номера ручной выбор группы или указание адреса её участника не открывает групповое расписание, шаблоны и старт. Собственный профиль и история прежних сессий доступны. |
| Администратор назначил преподавателю первую группу. Преподаватель пробует назначить себе вторую и запросить чужую работу из первой | Оба действия отклоняются. Преподаватель может работать со своими мероприятиями для первой группы. Администратор сохраняет доступ к обзору сессий всех студентов. |
| В заполненном черновике преподаватель по очереди пропускает выбор повторов, указывает одинаковое открытие и закрытие, меняет их местами | Каждый раз черновик остаётся доступен автору под прежним идентификатором. В расписании записи нет. При выбранном «нет» и открытии раньше закрытия эти поля не препятствуют публикации. |
| Работа открыта с 10:00 до 10:30. Первый студент начинает ровно в 10:00, второй в 10:25, третий пробует начать ровно в 10:30 | Срок первого прохождения наступает в 10:20, второго — в 10:30. Третий студент получает отказ без создания сессии. Своевременное решение второго, полностью полученное в 10:29:59, может получить записанный вердикт строго до 10:30:59. |
| Студент снова запускает работу до закрытия | Пока есть активная сессия, возвращается `409 ACTIVE_SESSION_EXISTS` с её идентификатором. После завершения при разрешённом повторе выдаётся новая сессия, при запрещённом — доступно чтение прежнего прохождения. В момент закрытия и позднее новая сессия не создаётся даже при разрешённом повторе. |
| Преподаватель указал свою группу, открытие, закрытие и разрешение повторов. Он пробует опубликовать пустой черновик, затем добавляет задание и повторяет публикацию | В первый раз система просит добавить задание. Студенты работу не видят. При повторной публикации с тем же идентификатором работа появляется в расписании назначенной группы. |
| Преподаватель собрал смешанную работу, назначил группе и опубликовал до времени открытия | До публикации записи у студентов нет. Сразу после публикации своя группа видит будущее мероприятие, чужая группа его не видит. До открытия начать работу нельзя. |
| Преподаватель включил текстовую задачу с несколькими парами и задачу по криптографии | При прохождении студенту назначается вариант для каждой позиции. При повторном чтении текстовое условие прежнее. Эталона и неназначенных вариантов в ответе студенту нет. Правила проверки каждой задачи соответствуют её виду. |
| Обоим студентам случайно назначен один вариант, один из них вводит эталонный текст с пробелами по краям | Пробелы по краям строк не меняют вердикт. Совпадение вариантов допустимо. Ответ второго студента не изменяет первый результат. |
| Студент пытается получить шаблоны чужой группы, затем выбирает включённый шаблон своей | Чужие шаблоны не выдаются. По своему шаблону создаётся ровно один полный активный набор. |
| Часть задач решена, по одной своевременный ответ находится в обработке в момент `D` | Своевременный ответ может дать вердикт строго до `L`. Новый ответ владельца ровно в `D` отклоняется. Если результат не зафиксирован к `L`, предметного вердикта нет. |
| У владельца прервалось соединение после фиксации неверного решения | Чтение собственной сессии возвращает отрицательный результат ровно для той задачи, на которую был дан ответ. Чтение чужой сессии не раскрывает её существование. |
| Студент сравнивает два варианта ранцевой задачи, решает задачу Эль-Гамаля, затем запрашивает готовый пример | Решение каждого типа оценивается по своему условию. Готовый пример можно разобрать отдельно, состояния сессии и результаты задач сохраняются. |
| Студент и администратор запрашивают общий обзор сессий | Роль студента не даёт доступ к общему обзору. Пользователь с `ADMIN` видит сессии всех студентов. |
| На раздельных выборках обычных операций и операций с генерацией получены `p95` 2 и 5 секунд соответственно | Обе границы достигнуты и допустимы. Превышение порога хотя бы по одному классу означает невыполнение соответствующего требования к скорости. |

**Что предъявляется на приёмке курсовой работы.** К приёмке предъявляют обязательные документы версии 1.0 или выше с титульными сведениями, историей изменений и предусмотренным согласованием. Реестр документов задаёт приоритеты, по которым команда определяет обязательный порядок инспекции. Два таких приоритета — критический и высокий. Для документа любого из этих двух приоритетов должен быть предъявлен протокол формальной инспекции с решением «ПРИНЯТО» либо «ПРИНЯТО С ЗАМЕЧАНИЯМИ». В реестре DEF должны быть подтверждены закрытия в установленные сроки. Для полного комплекта проверяют оба правила [`TS.DOC.TRACE`][TS.DOC.TRACE], подсчитывая требования с действительными связями в DOC-09. Если в принятый состав включён отдельный отчёт DOC-14, его показатели должны соответствовать той же версии матрицы. Редакции документов в указателе, источниках и представленных для печати файлах совпадают.

#### Правила доступа и прохождения контрольного мероприятия

| Ситуация | Правило |
|---|---|
| Членство студента в группе | Номер группы поступает с `home.mephi.ru` для подтверждённой учётной записи. Групповой доступ появляется только при подтверждённом номере. Регистрация и привязка к существующему профилю определены в [TS.REQ.FUNC.AUTH.REG](#ts-req-func-auth-reg), порядок определения группы — в [TS.REQ.FUNC.GROUP.JOIN](#ts-req-func-group-join). |
| Доступ преподавателя | Администратор закрепляет за преподавателем группы. Преподаватель назначает только свои работы и только закреплённым группам. В этих пределах ему доступны результаты участников его работ. Право администратора читать все студенческие сессии установлено в [TS.REQ.SEC.ROLES](#ts-req-sec-roles). |
| Допуск к старту | Публикация сразу добавляет работу в расписание группы. Сервер разрешает старт с момента открытия включительно до момента закрытия исключительно. Преподавателю не нужно отдельно открывать или закрывать работу. См. [TS.REQ.FUNC.EVENT.PUBLISH](#ts-req-func-event-publish) и [TS.REQ.FUNC.EVENT.SCHEDULE](#ts-req-func-event-schedule). |
| Срок начатой сессии | На сдачу отводится до 20 минут от старта, но не дольше чем до закрытия мероприятия. Новый ответ, полностью полученный сервером ровно в предельный момент, уже опоздал. Своевременный ответ может завершиться после закрытия в пределах исходного срока обработки по [TS.REQ.FUNC.SESSION.TIME](#ts-req-func-session-time). |
| Повторное прохождение | Преподаватель до публикации обязательно выбирает, можно ли пройти мероприятие повторно. При разрешении новая сессия возможна до закрытия после завершения предыдущей. При запрете студент может прочитать прежнее прохождение. Пока у студента есть активная сессия, новая не создаётся. См. [TS.REQ.FUNC.EVENT.START](#ts-req-func-event-start) и [TS.REQ.FUNC.SESSION.CREATE](#ts-req-func-session-create). |
