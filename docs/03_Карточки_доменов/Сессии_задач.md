# Карточка домена: сессии задач

Версия 0.4 от 20.11.2026. Владелец домена — Анохин Г.А.

## Назначение и границы

Сессия задач — запись одного прохождения работы одним студентом. Она хранит выданные ему условия, время начала, ответы и результаты. Владелец сессии — студент, для которого она создана. Эта карточка определяет, когда он может сдать ответ и как узнать исход проверки.

Для контрольной работы преподаватель выбирает задания и их порядок, а также указывает, разрешено ли повторное прохождение. Каждое место задания в списке — **позиция**. Пока работа находится в черновике, она скрыта от студентов. Преподаватель публикует работу для одной из групп, которые назначил ему администратор, и задаёт дату и время открытия и закрытия. Состав закрепляется при публикации. Студент видит назначение в расписании группы, подтверждённой через его учётную запись МИФИ. Когда наступает время открытия, студент может начать работу и получить по каждой позиции отдельную задачу. Для самостоятельной практики источником набора служит **шаблон** — именованный список типов заданий, доступный группе. Правила подготовки определены в [`TS.REQ.FUNC.EVENT.CREATE`][TS.REQ.FUNC.EVENT.CREATE], [`TS.REQ.FUNC.EVENT.PUBLISH`][TS.REQ.FUNC.EVENT.PUBLISH] и [`TS.REQ.FUNC.CONFIG.VIEW`][TS.REQ.FUNC.CONFIG.VIEW].

**Тип задания** определяет правила выдачи условия и проверки решения. Их выполняет соответствующий модуль программы. В ранцевых задачах и упражнениях по схеме Эль-Гамаля модуль рассчитывает учебные параметры. Для текстового задания (`CUSTOM_TEXT`) преподаватель заранее вводит одну или несколько пар «условие — правильный ответ». Этот ответ называется эталоном. Для каждой позиции с таким заданием система случайно выбирает пару при старте сессии. Студент видит условие выбранного варианта при каждом открытии своей задачи. Разным студентам может выпасть один вариант. Сравнение ответа с эталоном описано в [`TS.REQ.FUNC.TASK.ASSIGN`][TS.REQ.FUNC.TASK.ASSIGN].

**Вердикт** — сохранённый результат содержательной проверки ответа одной задачи. Попытка расходуется при записи вердикта «верно» или «неверно». Общее состояние сессии учитывает все выданные задачи. Таблица [состояний задачи и сессии](../02_Общие_соглашения/Глоссарий.md#ответ-попытка-и-состояние) объясняет различия. Программная роль студента обозначается `USER`.

## Сценарии

| Операция владельца с ролью `USER` | Что получает студент |
|---|---|
| Начать контрольное мероприятие по идентификатору `assessmentId` из расписания | Личный набор по опубликованному составу для своей группы. Начать работу можно с момента открытия и строго до закрытия. Для просмотра прежней сессии используется её собственный идентификатор |
| Начать самостоятельную практику по имени шаблона | Полный набор задач в порядке, заданном выбранным шаблоном для группы студента. Если у студента уже есть незавершённая сессия (`NEW`), отказ содержит её идентификатор. Он позволяет открыть набор, когда ответ на создание потерян |
| Отправить решение по идентификатору задачи | При успешной обработке — сохранённый вердикт по конкретной задаче. Проверяющий использует её выданное условие и тип. На задачу допускается одна предметная попытка |
| Прочитать собственную сессию по идентификатору | Текущее состояние набора и каждой задачи, включая сохранённые вердикты. Чтение доступно и после общего срока. Чужая и отсутствующая сессии дают одинаковый отказ |

Если при старте контрольной потеряна связь, студент снова открывает расписание. Карточка содержит идентификатор его активной сессии по этой работе, а после её завершения — последней собственной сессии. По этому идентификатору можно открыть прежние условия и результаты. После завершения студент может начать новое прохождение, только если преподаватель разрешил повтор и окно ещё открыто. Новая сессия получает свой идентификатор и варианты. Закрытие мероприятия прекращает выдачу новых сессий. Студент может по-прежнему читать свои прежние результаты.

Практика и контроль различаются по записи сессии. В самостоятельной практике поле `assessmentId` равно `null` (связи с мероприятием нет). Результат такой работы остаётся личным результатом студента и не засчитывается за мероприятие, даже если оба набора имеют одинаковый состав.

При получении полного запроса сервер отмечает время его поступления и устанавливает принадлежность задачи подтверждённому отправителю. Для собственной задачи запрос регистрируется с исходным временем до ожидания в очереди. Попытка обратиться к чужой или отсутствующей задаче завершается отказом. Такое обращение не открывает операцию и не задерживает завершение чужой задачи.

Своевременная регистрация сохраняет возможность пройти проверки допуска и формы, пока действует предел обработки. Право начать предметную проверку получает один допустимый ответ на задачу. Если зарегистрированы два запроса, их тела сохраняют свою принадлежность. Второй запрос не может заменить ответ, уже находящийся на предметной проверке.

## Срок и попытка

Время создания набора на сервере обозначается `t0`, а граница приёма новых ответов — `D`. Все задачи одной сессии имеют общий срок. Для самостоятельной практики `D = t0 + 20 минут`. Для контрольной сервер выбирает более ранний момент: истечение 20 минут после старта или назначенное преподавателем время закрытия `closesAt`. Например, при старте в 10:25 и закрытии в 10:30 полный ответ должен поступить до 10:30. Ровно в 10:30 сдавать уже поздно.

Время получения полного запроса обозначается `t_in`. Предел записи вердикта по нему — `L = t_in + 60 секунд`. В этот интервал входят очередь, вычисление, возможное восстановление и запись результата. Сервер может закончить проверку ответа, поступившего до закрытия, и после закрытия, если успевает записать вердикт строго до `L`. Планировщик раз в 60 секунд ищет просроченные задачи. Расписание этих обходов не меняет `D` и `L`.

| Событие | Последствие для задачи |
|---|---|
| Полный запрос получен при `t_in < D` | Для зарегистрированного ответа владельца можно завершить допуск и проверку. Вердикт разрешено сохранить после `D`, если фиксация произошла строго до `L` |
| Полный запрос владельца получен при `t_in >= D` | Новый ответ на собственную задачу отклоняется по сроку, даже если фоновая проверка ещё не закрыла задачу |
| К моменту `L` вердикт не зафиксирован | Операция завершается техническим отказом. Результат, поступивший в `L` или позже, не записывается |
| Формат неверен или обработка завершилась техническим отказом без вердикта | Попытка сохраняется. Исправленный или новый запрос допустим только при собственном `t_in < D` и соблюдении остальных условий |
| Наступил `D`, у незавершённой задачи нет своевременного ответа владельца в обработке | Задача подлежит завершению по просрочке. Её состояние — `FAILED`, предметный результат отсутствует |

Попытка расходуется при фиксации вердикта «верно» или «неверно». Перезапуск и повторная отправка не продлевают общий срок `D` или предел `L` ранее принятой операции. Новый допустимый запрос получает собственное время поступления `t_in`. После перезапуска незавершённая операция продолжается по тем же входным данным до прежнего `L`. Если вердикт уже зафиксирован, студент читает его в своей сессии. После окончательного технического отказа та же операция уже не может записать вердикт.

## Итог сессии

Пока хотя бы одна задача не завершена, сессия остаётся `NEW`. Это относится и к своевременному ответу, который ещё проверяется. Когда последняя задача завершена, сессия получает `SOLVED`, если все задачи решены верно, либо `FAILED`, если хотя бы одна решена неверно или просрочена. Ранее сохранённые вердикты остальных задач остаются доступны.

У отдельной задачи состояние `FAILED` встречается в двух случаях. Неверное решение имеет сохранённый отрицательный вердикт с пояснением. Если истёк срок, а предметного вердикта не было, поле `result` равно `null`. Чтение различает эти исходы и не расходует попытку.
