# DOC-05. Требования к интеграции

Раздел [DOC-05](DOC-05_Системные_требования.md), версия 0.4 от 07.11.2026. Автор: Анохин Г.А. Приоритет всех требований — обязательный. Здесь определены свойства совместной работы частей системы. Имена полей, HTTP-коды и программные механизмы описываются ниже по иерархии.

## SR-SYS-001. Единая личность пользователя

Сессии, группы и конфигурации используют одну личность пользователя, установленную проверкой доступа. Иначе одна часть могла бы выбирать конфигурацию для одного человека, а другая сохранять результат от имени другого. Пользовательские параметры определяют объект операции, но не меняют её исполнителя. Передачу этих сведений между частями показывает [описание ответственности компонентов](../07_Программные_требования/DOC-06_Программные_требования.md#2-ответственность-и-связи).

**Требование.** Система должна использовать подтверждённую личность текущего пользователя при проверке принадлежности сессий и доступности конфигураций.

При создании набора по подтверждённому пользователю определяется его группа. При ответе тот же пользователь сопоставляется с владельцем сохранённой сессии. Подмена `userId` в теле не должна менять эти решения. Это системное обязательство раскрывается в [общем правиле передачи личности](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-001-передача-личности-пользователя) и в [получении пользователя обработчиком сессий](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-001-получение-пользователя).

Основание: `[TS.REQ.FUNC.AUTH.JWT]`, `[TS.REQ.FUNC.SESSION.SUBMIT]` в [ТЗ](../../02_Техническое_задание/Техническое_задание.tex).

Проверка: указание чужого пользователя в параметрах запроса не даёт доступа к его сессиям и конфигурациям. Данные аутентификации и владельца сессии сопоставляются однозначно.

## SR-SYS-002. Связность данных задачи

Идентификаторы связывают операции, выполняемые в разное время. Пользователь получает задачу при создании набора, отправляет её ID при ответе и позднее читает результат. На всех этапах речь должна идти об одном объекте. Сохранённая принадлежность задачи сессии одновременно используется для поиска результата и проверки доступа.

**Требование.** Система должна сохранять однозначные связи задачи с сессией и сессии с пользователем при создании набора, проверке ответа и получении результата.

Тип задачи или текст условия не заменяет её ID: в одном наборе могут быть задания одного типа, а данные разных пользователей могут иметь сходный вид. Связь устанавливается сохранёнными идентификаторами. Передаваемые поля разобраны в [контракте результата](../07_Программные_требования/Контракты_сессий.md#результат-и-отказы), а единое использование идентификаторов компонентами закреплено в [программном требовании общих ID](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-002-общие-идентификаторы).

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`, `[TS.REQ.FUNC.SESSION.SUBMIT]`.

Проверка: задача в результате создания и в результате её проверки относится к одной сессии и владельцу; операция над одной задачей не изменяет данные другой.

## SR-SYS-003. Согласованный состав набора

Конфигурация описывает состав нового набора и его доступность группе. Сессия фиксирует конкретные задания, которые уже выданы пользователю. Эти объекты связаны в момент создания, но дальнейшая проверка не должна заново определять условие по изменившимся настройкам. Граница между выбором состава и жизненным циклом набора проведена в [правиле создания сессии](Сессии_задач.md#sr-ses-001-создание-набора-по-конфигурации-группы).

**Требование.** Система должна формировать состав новой сессии по выбранной конфигурации, доступной группе пользователя на момент создания.

Если преподаватель изменил доступный состав после выдачи задач, проверяется прежнее выданное условие. Иначе студент мог бы получить вердикт по другому заданию. Система сохраняет состав и условия при создании, а недоступную конфигурацию отклоняет до подтверждения операции. Программная детализация находится в [сохранении состава](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-003-состав-созданной-сессии) и [формировании задач](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-004-формирование-задач).

Основание: `[TS.REQ.FUNC.CONFIG.VIEW]`, `[TS.REQ.FUNC.SESSION.CREATE]`.

Проверка: состав соответствует включённой конфигурации. Конфигурация другой группы или выключенная конфигурация не используется. Последующее изменение настроек не подменяет условия уже выданных задач.

## SR-SYS-004. Соответствие генерации и проверки

Генерация и проверка принадлежат одному предметному контракту. Генератор формирует условие определённого типа, а проверяющий должен интерпретировать именно это условие вместе с ответом. Домен сессий соединяет эти операции, сохраняя тип и условие задачи между выдачей и отправкой решения.

**Требование.** Система должна проверять ответ по тому же типу задачи и сохранённому условию, которые использовались при её выдаче.

Вызвать существующий проверяющий недостаточно: он должен соответствовать выбранной задаче. Клиент не может переключить этот выбор произвольным значением поля `type`. Если обработчик нужного типа недоступен, результат относится к техническому отказу. Форматы определены в [контракте предметного ответа](../07_Программные_требования/Контракты_сессий.md#предметный-ответ), передача данных — в [правиле вызова профильной проверки](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-010-передача-профильной-проверке).

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`, `[TS.REQ.FUNC.SESSION.SUBMIT]`; ответственность частей в DOC-05.

Проверка: решение одной задачи не проверяется с условием другой; обработчик неподдерживаемого типа не подменяется обработчиком другого типа.

## SR-SYS-005. Согласованность результата и состояния

Вердикт имеет значение для пользователя только вместе с сохранённым состоянием. При успешной доставке ответа система подтверждает не просто выполненное вычисление, а завершённую операцию над задачей и сессией. Это связывает предметную проверку, хранение и внешний интерфейс. Раздельное рассмотрение этих частей не должно приводить к противоречащим итогам.

**Требование.** Система должна выдавать подтверждённый результат предметной проверки только при сохранении соответствующего состояния задачи и связанного итога сессии.

Если после неверного решения завершились все задачи, должны сохраниться и отрицательный результат задачи, и `FAILED` сессии. Если запись не завершилась, нельзя сообщать операцию как подтверждённую. После потери соединения уже сохранённый результат доступен через [чтение сессии](Сессии_задач.md#sr-ses-014-получение-сохранённого-результата). Границу записи определяют [согласованное сохранение](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-005-согласованное-сохранение) и [фиксация вердикта](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-011-сохранение-вердикта).

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`, `[TS.REQ.REL.PERSIST]`.

Проверка: ошибка сохранения не возвращается как успешное завершение операции; после завершённой операции выдаваемый результат и сохранённые состояния согласованы.

## SR-SYS-006. Единое правило времени

Обработка ответа и планировщик наблюдают одни задачи, но запускаются по разным причинам. Обработчик реагирует на запрос пользователя, планировщик — на наступление времени. Для одной задачи их решения должны использовать один срок и одинаково учитывать своевременно полученный ответ. Собственная независимая трактовка срока у каждого компонента здесь недопустима.

**Требование.** Система должна применять общий серверный срок сессии при обработке ответов и при фоновом завершении задач.

Фоновая задержка не разрешает поздний запрос, а наступление общего срока не отменяет уже принятую своевременную проверку. Этот общий результат важнее порядка фактического запуска компонентов. Временная модель дана в [карточке домена](../03_Карточки_доменов/Сессии_задач.md#срок-и-попытка), условия завершения — в [обработке просрочки](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-017-завершение-по-просрочке), а защита своевременной операции — в [правиле её завершения](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-015-завершение-своевременной-проверки).

Основание: `[TS.REQ.REL.SCHED]`; уточнённое правило срока из [карточки домена](../03_Карточки_доменов/Сессии_задач.md).

Проверка: задержка планировщика не разрешает поздний ответ. Фоновая обработка не отменяет вердикт своевременно полученного ответа.

## SR-SYS-007. Сохранность данных сессии

Время создания, принадлежность и результаты являются данными сессии, а не временными сведениями интерфейса. Потеря этих данных при перезапуске меняла бы условия решения и делала невозможным получение прежнего итога. Поэтому сохранность охватывает не только состояние `SOLVED` или `FAILED`, но и сведения, по которым это состояние относится к конкретному набору.

**Требование.** Система должна сохранять принадлежность, состав, время создания и определённые результаты задач при перезапуске приложения.

Завершённый результат читается без повторного вычисления. Для принятого ответа без результата применяется другой путь: восстановление по сохранённой записи с прежним сроком обработки. Эти случаи разделены в [восстановлении принятого ответа](Сессии_задач.md#sr-ses-013-восстановление-принятого-ответа) и [получении готового результата](Сессии_задач.md#sr-ses-014-получение-сохранённого-результата). Программное хранение описывают [общая сохранность](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-008-сохранность-завершённых-данных) и [запись операции](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-021-запись-принятой-операции).

Основание: `[TS.REQ.REL.PERSIST]`.

Проверка: после перезапуска срок не начинается заново, завершённые результаты доступны и не пересчитываются. Незавершённый сохранённый ответ обрабатывается по SR-SES-013 с учётом прежнего срока обработки.

## SR-SYS-008. Совместимость обмена

Части системы должны одинаково понимать данные на внешней границе. При создании клиент получает ID, тип и условие задачи; при отправке использует их для выбора задачи и схемы ответа; после проверки сопоставляет результат с тем же заданием. Совместимость означает сохранение этого смысла на всём пути, а не только возможность разобрать отдельный JSON.

**Требование.** Система должна обмениваться данными пользовательских операций через REST-интерфейс с согласованными JSON-форматами запросов и результатов.

Поле `statementId` ссылается на ID задачи из выданного набора. Большие целые передаются без потери точности, а время однозначно задаёт серверный момент. Для работы клиента эти детали собраны в [операциях API](../07_Программные_требования/Контракты_сессий.md#операции) и [предметных форматах](../07_Программные_требования/Контракты_сессий.md#предметный-ответ). Программная обработка по этому контракту закреплена в [требовании форматов и категорий API](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-022-форматы-и-категории-api).

Основание: раздел `[TS.REQ.INT]`; область документирования системы.

Проверка: данные, выданные при создании сессии, позволяют однозначно выбрать задачу и сформировать ответ поддерживаемого типа; результат относится к этой задаче. Детальные поля определяет [программный контракт](../07_Программные_требования/Контракты_сессий.md).

## SR-SYS-009. Различение отказов

Для состояния задачи имеет значение причина отказа. Неверное решение даёт предметный итог и расходует попытку. Неверно оформленный запрос или технический сбой этого не устанавливает. Просрочка отдельно завершает возможность решения по времени. Если внешняя часть сведёт всё к одному отрицательному ответу, клиент и сервер потеряют различие между этими событиями.

**Требование.** Система должна отличать неверное предметное решение от отказа в допуске, ошибки формата и технического сбоя проверки.

Клиент определяет категорию по машинному коду, а текст сообщения использует как пояснение. Значение `isOk = false` относится только к сохранённому неверному предметному решению. Ошибки допуска и инфраструктуры передаются иначе, по [таблице ошибок](../07_Программные_требования/Контракты_сессий.md#коды-и-представление-ошибок). Сохранение категорий между компонентами раскрывает [общее программное требование результата операции](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-007-категория-результата-операции).

Основание: правила попытки и ошибок в карточке домена; SR-SES-003, SR-SES-009, SR-SES-010.

Проверка: только зафиксированный предметный вердикт «неверно» расходует попытку как неверное решение. Остальные категории сообщаются отдельно; просрочка учитывается по правилу срока. HTTP-коды и схема ошибок заданы в контракте сессий.

## Границы обмена между частями

Связь идентификаторов проверяется на всём пользовательском пути. При создании задачи система устанавливает её принадлежность сессии; при ответе использует эту же принадлежность для проверки владельца. Результат должен относиться к выбранной задаче. Несогласованность хотя бы на одном из этих переходов нарушает общий контракт даже при правильной работе отдельного проверяющего.

У конфигурации и созданной сессии разные обязанности. Конфигурация определяет доступный состав нового набора. Созданная сессия хранит уже выданные задачи и условия. Это разделение позволяет проверять ответ по тому условию, которое получил пользователь, независимо от дальнейшего изменения настроек группы.

Профильная проверка получает условие конкретной задачи и её ответ. Домен сессий отвечает за выбор допустимого обращения и сохранение результата; профильный домен — за правильность предметного вердикта. Требование к общему контракту не подменяет правила криптографического алгоритма и не назначает допустимые параметры за его владельца.

## Согласованность при сбоях

Для пользователя подтверждение результата должно означать согласованное изменение задачи и сессии. Успешный вызов предметного проверяющего сам по себе ещё не завершает операцию: результат необходимо сохранить. Если сохранение не подтверждено, система сообщает технический отказ, а не выдаёт неподтверждённый предметный итог как завершённую операцию.

Сохранность завершённых данных и восстановление прерванного вычисления рассматриваются отдельно. Для первого случая определены сохраняемые сведения и неизменность срока после перезапуска. Для второго перед вычислением сохраняется запись принятого ответа. После запуска приложения незавершённые записи продолжают обрабатываться в пределах прежнего срока. Результат фиксируется однократно вместе с состояниями задачи и сессии.

Общая проверка интеграции должна сопоставлять результат операции с данными всех участвующих частей. Для ответа это личность пользователя, принадлежность задачи, сохранённое условие, категория результата и итог сессии. Для контроля времени — общий срок и факт своевременного поступления ответа. Проверка только одного HTTP-ответа не показывает, сохранена ли согласованность этих сведений.
