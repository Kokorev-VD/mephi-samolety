# DOC-05. Общесистемная интеграция

Автор раздела — Анохин Г.А. Редакция 1.1 от 20.11.2026 входит в [DOC-05](DOC-05_Системные_требования.md). Все требования обязательны. Интеграция в этом разделе означает передачу одних и тех же данных между частями системы — от подтверждения личности до чтения сохранённого результата. Обозначения `TS` указывают на требования [технического задания](../02_Техническое_задание/DOC-02_Техническое_задание.md).

<a id="sr-sys-001"></a>

## SR-SYS-001. Единая личность пользователя

Подтверждённая личность — учётная запись, которую сервер определил при проверке доступа. Номер группы студента система получает только из подтверждённого профиля МИФИ на `home.mephi.ru` при регистрации или привязке профиля. Сессия — выданный студенту набор задач, а шаблон набора задаёт состав для его самостоятельной практики.

Система должна определять группу для выбора шаблона, расписания и старта контрольной, а также владельца личной задачи по одной и той же подтверждённой личности. При отсутствии подтверждённого номера группы групповой доступ закрыт. Преподавателю `TEACHER` доступны результаты участников его собственного мероприятия, если группа мероприятия всё ещё назначена ему администратором. Для роли `ADMIN` сохраняется общий просмотр сессий всех групп. Права доступа устанавливаются до выдачи сведений о конкретной задаче или сессии. Идентификатор пользователя, переданный в параметрах или теле запроса, не может изменить владельца операции.

При попытке прочитать чужую сессию пользователь получает тот же ответ, что и при отсутствии сессии. Студенты одной группы могут получить задания по общему шаблону, но каждый обращается только к собственному набору. Основание — [`TS.REQ.FUNC.AUTH.JWT`][TS.REQ.FUNC.AUTH.JWT] и [`TS.REQ.FUNC.SESSION.SUBMIT`][TS.REQ.FUNC.SESSION.SUBMIT].

<a id="sr-sys-002"></a>

## SR-SYS-002. Связность данных задачи

Идентификатор отличает одну запись от другой. У студента, выданного ему набора и каждой задачи внутри него разные идентификаторы. Вердикт означает результат проверки решения конкретной задачи.

Система должна поддерживать однозначную связь каждой задачи с выданной сессией и каждой сессии с её владельцем. Идентификатор задачи из первоначального набора должен обозначать ту же задачу при отправке ответа, в возвращённом вердикте и при последующем чтении.

Например, в набор могут входить две задачи одного типа с разными условиями. Ответ на вторую задачу изменяет результат только второй. Тип задания и порядковый номер в списке недостаточны для идентификации. Основание — [`TS.REQ.FUNC.SESSION.CREATE`][TS.REQ.FUNC.SESSION.CREATE] и [`TS.REQ.FUNC.SESSION.SUBMIT`][TS.REQ.FUNC.SESSION.SUBMIT].

<a id="sr-sys-003"></a>

## SR-SYS-003. Согласованный состав набора

Контрольное мероприятие — подготовленная преподавателем работа, назначенная группе. Позиция обозначает одно место в её составе. После публикации работы в расписании сохраняется та редакция каждого авторского варианта, в которой согласованы его условие и правильный ответ.

Для самостоятельной практики система должна формировать новую сессию по шаблону, включённому для группы студента в момент создания. Для контроля при публикации мероприятия закрепляются назначенная группа, границы окна, разрешение или запрет повторного прохождения, порядок позиций и редакции вариантов. Личная сессия и результат контроля связываются с назначенным мероприятием по его идентификатору. При успешной выдаче доступны все предусмотренные задачи. Когда одна из задач не сформирована, незавершённая часть набора не выдаётся как готовая сессия.

Отключение шаблона или изменение его состава после выдачи влияет на последующее создание наборов. Выданная сессия сохраняет первоначальные условия, типы и состав. Основание — [`TS.REQ.FUNC.CONFIG.VIEW`][TS.REQ.FUNC.CONFIG.VIEW] и [`TS.REQ.FUNC.SESSION.CREATE`][TS.REQ.FUNC.SESSION.CREATE].

<a id="sr-sys-004"></a>

## SR-SYS-004. Соответствие генерации и проверки

Система должна применять к решению правила того типа, к которому относится выданная задача, и сопоставлять решение с исходным сохранённым условием. Проверка по заново сгенерированному условию недопустима. Запрос пользователя и последующая смена настроек группы не могут подменить тип задачи.

Если правила для данного типа недоступны, система прекращает операцию с техническим отказом. Полученный в штатном случае предметный вердикт относится только к переданному решению этой задачи. Основание — [`TS.REQ.FUNC.SESSION.CREATE`][TS.REQ.FUNC.SESSION.CREATE], [`TS.REQ.FUNC.SESSION.SUBMIT`][TS.REQ.FUNC.SESSION.SUBMIT] и [SR-SES-004].

<a id="sr-sys-005"></a>

## SR-SYS-005. Согласованность результата и состояния

Подтверждение результата студенту допускается только после того, как система сохранила вердикт, соответствующее состояние задачи и состояние сессии с учётом остальных задач. Если обработчики двух последних задач завершились одновременно, итог должен учитывать оба результата.

Сбой записи до сохранения вердикта приводит к техническому отказу. Если данные сохранены, но соединение прервалось до доставки ответа, чтение сессии должно вернуть сохранённый вердикт вместе с согласованными состояниями. Основание — [`TS.REQ.FUNC.SESSION.SUBMIT`][TS.REQ.FUNC.SESSION.SUBMIT], [`TS.REQ.REL.PERSIST`][TS.REQ.REL.PERSIST] и [SR-SES-007].

<a id="sr-sys-006"></a>

## SR-SYS-006. Единое правило времени

Планировщик — часть системы, которая без запроса студента периодически проверяет сроки. Просрочкой называют завершение незаконченной задачи из-за истечения времени. Другая операция — проверка полученного решения — отсчитывает своё время от момента получения запроса.

Приём ответов и фоновое завершение должны использовать один общий срок набора. Для самостоятельной практики он наступает через 20 минут от серверного времени создания. Для контрольной работы берут более раннее из двух событий — истечение 20 минут от начала личной сессии или автоматическое закрытие мероприятия. У ответа, который сервер получил полностью до этого срока и допустил к предметной проверке, сохраняется право на фиксацию результата в пределах времени обработки. Начиная с общего срока новый ответ отклоняется, даже если фоновый цикл ещё не изменил состояние задачи.

ТЗ задаёт интервал фонового контроля 60 секунд. На первом цикле после наступления срока завершаются просроченные задачи без своевременного ответа в обработке. Отдельный 60-секундный предел обработки отсчитывается от получения конкретного ответа и продолжает действовать при пропуске фонового цикла. Подробные граничные условия заданы в [SR-SES-006], [SR-SES-011] и [SR-SES-012]. Основание — [`TS.REQ.FUNC.SESSION.TIME`][TS.REQ.FUNC.SESSION.TIME] и [`TS.REQ.REL.SCHED`][TS.REQ.REL.SCHED].

<a id="sr-sys-007"></a>

## SR-SYS-007. Сохранность данных сессии

После перезапуска система должна восстановить сессию с прежними идентификаторами, владельцем, составом, условиями и типами задач, временем создания и сохранёнными состояниями и вердиктами. Если общий срок уже наступил, к незавершённым задачам применяются те же правила просрочки, что и до перезапуска.

Для ответа, принятого, но ещё не завершённого, сохраняются данные, необходимые для продолжения проверки в пределах первоначального срока обработки. Для завершённой задачи достаточно прочитать зафиксированный результат. Основание — [`TS.REQ.REL.PERSIST`][TS.REQ.REL.PERSIST], [SR-SES-013] и [SR-SES-014].

<a id="sr-sys-008"></a>

## SR-SYS-008. Совместимость обмена

Клиент — программа, из которой студент работает с платформой. Операции с сессией должны использовать согласованный REST-интерфейс, в котором запрос относится к определённому ресурсу, например к одной сессии. Структурированные данные передаются в текстовом формате JSON. По идентификатору и типу выданной задачи клиент должен иметь возможность выбрать ресурс, сформировать решение нужного вида и сопоставить ответ сервера с исходной задачей. Целые величины произвольной длины и серверные отметки времени должны сохранять своё точное значение при передаче.

Форматы ресурсов, обязательные поля и представление ошибок определены в [контрактах сессий](../07_Программные_требования/Контракты_сессий.md). Совместимость оценивается по полному обмену для каждого поддерживаемого типа — выдача задачи, отправка решения, чтение результата. Основание — [`TS.REQ.INT`][TS.REQ.INT].

<a id="sr-sys-009"></a>

## SR-SYS-009. Различение отказов

Машинный код — постоянное обозначение причины отказа, которое может распознать программа. Оно сопровождает объяснение для студента. Состояние задачи `FAILED` означает, что задача завершилась без успеха.

Система должна сообщать о неверном предметном решении, отказе в допуске, ошибке формата и техническом сбое так, чтобы клиент мог различить их по ответу. Отрицательный предметный вердикт означает, что допустимое решение проверено, признано неверным и зафиксировано. Ошибки доступа, формы или обработки не должны создавать такой вердикт. Для отказа используется машинный код причины.

Просрочка завершает задачу по времени. При чтении просроченной задачи состояние `FAILED` сопровождается отсутствием предметного результата. Такое же состояние задачи после неверного решения сопровождается сохранённым отрицательным результатом. Основание — [SR-SES-003], [SR-SES-005], [SR-SES-006] и [SR-SES-008]–[SR-SES-010].

## Согласованность при сбоях

Рассмотрим сбой на границе фиксации. Студент отправил решение последней задачи своевременно. Предметная проверка окончена, но сеть оборвалась, и студент не знает её исхода. Система должна позволить ему вернуться к той же задаче, используя сведения о собственной сессии.

| Что успела сделать система | Наблюдаемый результат при восстановлении |
|---|---|
| Сохранила вердикт | Владелец читает прежний вердикт и соответствующий итог набора. Дополнительная попытка не требуется |
| Сохранила только принятый ответ, время обработки осталось | По исходным данным продолжается та же проверка. Другой ответ не подменяет принятый |
| Сохранила только принятый ответ, предел обработки достигнут | Вердикт отсутствует. До общего срока допустим новый запрос, начиная с общего срока задача подлежит завершению по просрочке |

Если студент получил подтверждение успеха, а после восстановления видит задачу без вердикта, нарушено [SR-SYS-005], даже если вычисление ответа было правильным. Если при восстановлении продлён срок, нарушены [SR-SYS-006] и [SR-SYS-007]. Критерием служат данные при повторном чтении и состояние всего набора.
