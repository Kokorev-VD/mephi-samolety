# DOC-05. Платформенные и предметные требования

Часть [системных требований](DOC-05_Системные_требования.md), редакция 1.1 от 20.11.2026. Все требования этого раздела обязательны. Редактор — Анохин Г.А. Владельцы предметных областей указаны в основном документе. Для каждого требования приведены основание в [DOC-02](../02_Техническое_задание/DOC-02_Техническое_задание.md) и признак, по которому можно проверить требование по описанию системы.

## Пользователи, группы и история

При регистрации студент получает учётную запись. Сервер выдаёт **токен доступа** — подписанную строку, которую клиент (программа студента) предъявляет при следующих запросах. Токен принятого в проекте формата JWT содержит идентификатор учётной записи и сведения о правах. В ответе сервер указывает код HTTP — числовой признак исхода запроса. Например, 401 означает, что личность подтвердить не удалось.

<a id="sr-auth-001"></a>

### SR-AUTH-001. Регистрация

Система должна создать локальную учётную запись по адресу электронной почты, имени и паролю и после успешной регистрации выдать токен доступа. Адрес должен содержать от 4 до 120 символов, пароль — от 8 до 255 символов, обе границы включены. Поля обязательны. Занятый адрес не может получить вторую учётную запись. Вместо локальной регистрации студент может сразу зарегистрироваться через подтверждённую учётную запись МИФИ на `home.mephi.ru`. Для привязки к существующему профилю нужны подтверждение его владельца и подтверждение университетской записи. При привязке сохраняются идентификатор локального профиля и прежняя личная история. Совпадение адресов электронной почты не даёт основания объединять профили. Для доступа к групповой работе система принимает номер группы только из подтверждённого университетского профиля.

При проверке граничных длин остальные поля берут допустимыми, адрес — синтаксически верным. Обе крайние допустимые длины принимаются, выход на один символ отклоняется. При ошибке новая запись и токен отсутствуют. Основание — [`TS.REQ.FUNC.AUTH.REG`][TS.REQ.FUNC.AUTH.REG].

<a id="sr-auth-002"></a>

### SR-AUTH-002. Вход по адресу и паролю

Система должна выдавать токен собственного профиля при успешном локальном входе по адресу и паролю либо при подтверждённом входе через связанную учётную запись `home.mephi.ru`. Локальный вход сам по себе не подтверждает номер группы. При неверной паре учётных данных доступ отклоняется с HTTP 401. Признак выполнения — по выданному токену доступна операция его владельца, а при отказе токен не выдан. Основание — [`TS.REQ.FUNC.AUTH.LOGIN`][TS.REQ.FUNC.AUTH.LOGIN].

<a id="sr-auth-003"></a>

### SR-AUTH-003. Подтверждение личности и прав

Регистрация и вход доступны без токена. Для остальных операций система должна проверять токен в заголовке запроса `Authorization`. Схема `Bearer` означает, что за этим словом в заголовке следует сам токен. Подлинность его содержимого подтверждает подпись HMAC-SHA256 с секретным ключом сервера. Срок действия в днях задаётся переменной окружения, то есть именованным параметром, который приложение получает при запуске. Поле `userId` обозначает пользователя, а список `authorities` — предоставленные роли, то есть наборы прав. Сервер учитывает оба поля только после успешной проверки подписи и срока.

Защищённая операция без действительного токена возвращает HTTP 401. Если пользователь подтверждён, но его роли не дают нужного права, система возвращает HTTP 403. В обоих случаях операция над защищённым ресурсом не выполняется. Основания — [`TS.REQ.FUNC.AUTH.JWT`][TS.REQ.FUNC.AUTH.JWT], [`TS.REQ.INT.BEARER`][TS.REQ.INT.BEARER], [`TS.REQ.SEC.JWT`][TS.REQ.SEC.JWT] и [`TS.REQ.SEC.ROLES`][TS.REQ.SEC.ROLES].

<a id="sr-auth-004"></a>

### SR-AUTH-004. Профиль текущего пользователя

Профиль — принадлежащие пользователю данные учётной записи и её подтверждённая связь с университетским профилем. При чтении собственной истории и привязке учётной записи `home.mephi.ru` система определяет пользователя по подтверждённому `userId`. Признак выполнения — привязка университетской записи одним студентом не меняет личность и историю другого. Основания — [`TS.REQ.FUNC.AUTH.JWT`][TS.REQ.FUNC.AUTH.JWT], [`TS.REQ.FUNC.GROUP.JOIN`][TS.REQ.FUNC.GROUP.JOIN] и [SR-SYS-001].

<a id="sr-auth-005"></a>

### SR-AUTH-005. Перечень учебных групп

Учебная группа объединяет студентов для назначения общей работы. Роль `USER` обозначает права студента на выполнение собственных задач. Просмотр справочника групп не изменяет профиль и не устанавливает членство ни в одной из групп.

Система должна выдавать перечень учебных групп пользователю, которому доступен справочник групп. Для каждой группы возвращаются её идентификатор, название и состав участников. Признак выполнения — для двух групп с разными составами клиент может определить название и участников каждой из них, при этом ответ не содержит паролей либо [хешей для их проверки](#sr-auth-008-защита-паролей). Основание — [`TS.REQ.FUNC.GROUP.LIST`][TS.REQ.FUNC.GROUP.LIST].

<a id="sr-auth-006"></a>

### SR-AUTH-006. Подтверждение группы студента

Система должна получать номер текущей группы студента из подтверждённого профиля `home.mephi.ru` при регистрации или при привязке к существующей локальной записи. Группа, введённая студентом или переданная клиентом, не является основанием доступа. Если связь с университетской записью не подтверждена или в подтверждённых сведениях нет номера группы, студенту недоступны групповые шаблоны, расписание и начало групповой работы. Собственный профиль и ранее сохранённая личная история остаются ему доступны.

Признак выполнения — у двух студентов разные подтверждённые номера групп. Каждый получает доступ к предложениям только своей группы. Подстановка номера другой группы либо отсутствие подтверждённой группы не открывает чужую работу. Источник сведений о группе не заменяет собственный токен пользователя. Основания — [`TS.REQ.FUNC.GROUP.JOIN`][TS.REQ.FUNC.GROUP.JOIN] и [`TS.REQ.FUNC.CONFIG.VIEW`][TS.REQ.FUNC.CONFIG.VIEW].

<a id="sr-auth-007"></a>

### SR-AUTH-007. Личная история решений

Предметный результат содержит вердикт — заключение о правильности решения конкретной выданной задачи. В личной истории студент может найти такой результат после нового входа в систему.

По запросу истории система должна вернуть студенту его собственные задачи с сохранённым предметным результатом. История включает верные и неверные решения поддерживаемых типов, связывает каждую запись с её задачей и сессией и остаётся доступной после срока сессии. Незавершённая задача и просрочка без вердикта не являются решением. Их состояние доступно при чтении самой сессии.

Признак выполнения — у двух студентов есть задачи одного типа. История каждого содержит его результаты, включая результат с потерянным ответом на исходную отправку. История пользователя без решений пуста. Чтение истории не меняет результат и попытку. Основания — [`TS.REQ.FUNC.HISTORY`][TS.REQ.FUNC.HISTORY], [`TS.REQ.REL.PERSIST`][TS.REQ.REL.PERSIST] и [SR-SES-014].

<a id="sr-auth-008"></a>

### SR-AUTH-008. Защита паролей

Защищённый канал сохраняет пароль в тайне при передаче от клиента серверу. Для хранения применяется BCrypt — способ получения хеша пароля. По хешу сервер может проверить предъявленный при входе пароль.

Система должна принимать пароль при регистрации и входе только по защищённому каналу. В учётной записи сохраняется хеш BCrypt, для входа предъявленный пароль сверяется с хешем. Из описания обмена и хранения должно следовать, что открытый пароль не остаётся в базе данных и не возвращается в ответах API. Правильный пароль позволяет войти после перезапуска, неверный отклоняется. Основания — [`TS.REQ.SEC.PASSWORDS`][TS.REQ.SEC.PASSWORDS] и [`TS.REQ.FUNC.AUTH.LOGIN`][TS.REQ.FUNC.AUTH.LOGIN].

<a id="sr-auth-009"></a>

### SR-AUTH-009. Назначение групп преподавателю

Роль `TEACHER` даёт преподавателю право готовить свои учебные материалы и работать с назначенными ему группами. Администратор с ролью `ADMIN` устанавливает, за какие группы отвечает каждый преподаватель. При назначении мероприятия система должна проверить принадлежность группы к этому перечню. При запросе результатов преподавателем система заново проверяет две связи: мероприятие принадлежит этому преподавателю, а его группа по-прежнему закреплена за ним. Права `USER` на собственные результаты сохраняют отдельное назначение.

Признак выполнения — администратор закрепил за преподавателем группу А. Преподаватель может назначить ей собственную работу и читать результаты её участников. Чужое мероприятие той же группы и самостоятельная практика группы не попадают в выдачу. Снятие назначения группы прекращает доступ преподавателя к результатам этой работы. Группа Б без назначения также недоступна. Общий просмотр администратора сохраняется. Основание — [`TS.REQ.SEC.ROLES`][TS.REQ.SEC.ROLES].

## Шаблоны наборов задач и модерация

Шаблон набора задач задаёт типы и порядок будущих заданий. Студент получает экземпляр набора со своими условиями и результатами — личную сессию. Контрольное мероприятие назначают группе, а самостоятельную практику студент начинает по доступному шаблону. Модерация означает просмотр учебного прогресса. Преподаватель с ролью `TEACHER` получает результаты своего мероприятия в закреплённой за ним группе. У администратора с ролью `ADMIN` есть общий обзор сессий.

<a id="sr-cfg-001"></a>

### SR-CFG-001. Шаблоны наборов учебной группы

Студенту с ролью `USER` система должна выдавать шаблоны наборов задач только его учебной группы. Шаблон задаёт имя и упорядоченный состав типов задач. В перечне указывают признак включения каждого шаблона. Студент может создать сессию только по включённому шаблону. Идентификатор другой группы не даёт доступа к её шаблонам.

Признак выполнения — группе назначены два шаблона, один из них выключен. Перечень содержит оба с различимыми признаками. Созданная по включённому шаблону сессия сохраняет заданные порядок и число вхождений каждого типа. Основания — [`TS.REQ.FUNC.CONFIG.VIEW`][TS.REQ.FUNC.CONFIG.VIEW], [`TS.REQ.FUNC.SESSION.CREATE`][TS.REQ.FUNC.SESSION.CREATE] и [SR-SYS-003].

Проверка границ включает прямой запрос по идентификатору другой группы и выключенный шаблон своей группы. Чужие шаблоны не выдаются. Выключенная запись видна с признаком отключения, но не разрешает новый старт. Для повторяющегося типа сопоставляются число и порядок отдельных позиций.

<a id="sr-cfg-002"></a>

### SR-CFG-002. Просмотр прогресса студентов

Система должна предоставлять администратору с ролью `ADMIN` общий просмотр сессий всех студентов, включая самостоятельную практику. У преподавателя с ролью `TEACHER` другая операция: по идентификатору своего мероприятия он получает результаты его участников только пока группа мероприятия закреплена за ним. Выдача не включает самостоятельную практику или чужие мероприятия той же группы. Просмотр показывает состояния наборов и задач, сохраняет их принадлежность и не даёт права решать вместо студента.

Признак выполнения — в закреплённой группе два преподавателя опубликовали по мероприятию. Первый получает результаты только своей работы. Когда администратор отзывает группу, преподаватель больше не получает эти результаты. У администратора и при двух назначениях, и после отзыва сохраняется общий обзор. Основания — [`TS.REQ.FUNC.MOD.VIEW`][TS.REQ.FUNC.MOD.VIEW], [`TS.REQ.SEC.ROLES`][TS.REQ.SEC.ROLES] и [SR-SES-003].

При проверке отдельно рассматриваются административный общий просмотр и преподавательская ведомость. Роль USER не получает общий перечень. После отзыва назначения группы преподаватель не получает её результаты; сохранённые сессии при этом не удаляются. Сопоставляются состояния и принадлежность записей до и после чтения.

<a id="sr-cfg-003"></a>

### SR-CFG-003. Состав контрольного мероприятия

Черновик — ещё не опубликованная работа преподавателя. Позиция обозначает место задания в составе работы. Авторское задание содержит введённые преподавателем условия и правильные ответы. Для подключаемого вида, например ранцевой задачи, условие выдаёт и решение проверяет программный модуль.

Преподаватель должен иметь возможность собрать собственный черновик контрольного мероприятия, вернуться к нему и изменить порядок позиций до публикации. Для готовящейся работы он выбирает, смогут ли студенты пройти её повторно. Выбор становится обязательным при публикации. Преподаватель может сохранить черновик с пустым списком позиций, в том числе после удаления последнего задания. Для одной позиции он выбирает авторское задание с подготовленными вариантами либо подключённый вид задания. В работе можно сочетать оба способа подготовки, несколько разных видов и повторные позиции одного вида. Конкретные условия студент получает в личной сессии.

Признак выполнения — у подготовленного мероприятия состав «ранцевая задача, Эль-Гамаль, Эль-Гамаль». В выданном студенту наборе три отдельные задачи в таком порядке. Две последние имеют разные идентификаторы, а ответ на одну не изменяет другую. Основания — [`TS.REQ.FUNC.EVENT.CREATE`][TS.REQ.FUNC.EVENT.CREATE], [SR-SYS-002] и [SR-SYS-003].

Для проверки границ сохраняют пустой черновик, затем возвращаются к нему и меняют порядок позиций. Неопределённое правило повтора в черновике отличается от явного запрета. Изменение банка авторских заданий после публикации проверяется по закреплению редакции в [SR-CFG-008].

<a id="sr-cfg-004"></a>

### SR-CFG-004. Назначение мероприятия группе

При публикации преподаватель должен назначить мероприятие одной из групп, закреплённых за ним администратором, и указать два момента по серверным часам: открытие `opensAt` и закрытие `closesAt`. Обязательное условие — `opensAt < closesAt`. Равные границы и закрытие раньше открытия отклоняются. Открытие и закрытие происходят автоматически. Само назначение не начинает личную сессию.

Признак выполнения — у назначения группы А с открытием в 10:00 и закрытием в 10:30 сохранены оба момента. При назначении чужой преподавателю группы либо неверного интервала в расписании не возникает опубликованной записи. Основание — [`TS.REQ.FUNC.EVENT.SCHEDULE`][TS.REQ.FUNC.EVENT.SCHEDULE].

При проверке назначения отдельно задаются равные границы окна и закрытие раньше открытия. В обоих случаях публикация не появляется в расписании, а черновик сохраняется. Успешное назначение проверяется для своей группы с действующим назначением преподавателю.

<a id="sr-cfg-005"></a>

### SR-CFG-005. Начало личной работы по назначению

Сервер должен разрешать новый старт только в опубликованном мероприятии подтверждённой группы студента при `opensAt <= t < closesAt`, где `t` — момент старта по серверным часам. До открытия и ровно с закрытия личный набор не создаётся. Сессия, выданная при разрешённом старте, связывается с мероприятием. Для чужого или неопубликованного мероприятия сведения о назначении не раскрываются.

Признак выполнения — при окне с 10:00 до 10:30 запрос в 09:59:59 отклоняется, первый старт в 10:00 разрешён, старт в 10:30 уже невозможен. Личная работа, начатая в 10:25, принимает новые ответы строго до 10:30. Практика по шаблону не создаёт участия в контрольном мероприятии. Основания — [`TS.REQ.FUNC.EVENT.START`][TS.REQ.FUNC.EVENT.START], [`TS.REQ.FUNC.EVENT.VIEW`][TS.REQ.FUNC.EVENT.VIEW] и [SR-SES-001].

Границы открытия и закрытия проверяются при выполненных остальных условиях допуска. Отдельно рассматриваются существующая активная сессия и ранее завершённое прохождение. Возможность повторного старта определяется опубликованным правилом [SR-CFG-008], а создание и срок личного набора — [SR-SES-001].

<a id="sr-cfg-006"></a>

### SR-CFG-006. Авторское задание с вариантами

Преподаватель должен иметь возможность создать текстовое задание без разработки программного модуля. У задания может быть один или несколько вариантов. Для каждого варианта он задаёт пару из условия и эталонного текстового ответа. Система должна сохранять принадлежность обоих значений одному варианту. Неполную пару нельзя использовать при выдаче. Для решения студент вводит текст в одно поле.

Признак выполнения — преподаватель ввёл две пары с разными условиями и ответами. При включении задания в мероприятие доступны подготовленные варианты. Перестановка вариантов не меняет соответствия внутри пар. Основание — [`TS.REQ.FUNC.TASK.CUSTOM`][TS.REQ.FUNC.TASK.CUSTOM].

При проверке сопоставляются одна полная пара, несколько полных пар и неполная пара. Перемещение варианта не меняет соответствия условия и эталона. Проверка касается полноты подготовки варианта, а не требования обязательной различности вариантов у разных студентов.

<a id="sr-cfg-007"></a>

### SR-CFG-007. Выбор и закрепление варианта

При выдаче личной сессии система должна случайно выбрать один подготовленный вариант для каждой позиции авторского задания и закрепить его за конкретной задачей. Студенту выдаётся условие. Эталон доступен системе проверки и не включается в ответы студенту, его историю или расписание.

Признак выполнения — у задания два разных варианта. Для каждого возможного выбора проверяющий сопоставляет решение с эталоном именно этой пары. При повторном чтении, повторном запросе и после перезапуска условие остаётся прежним. Случайный выбор не обещает, что два студента обязательно получат разные варианты. Основания — [`TS.REQ.FUNC.TASK.ASSIGN`][TS.REQ.FUNC.TASK.ASSIGN], [SR-SYS-002] и [SR-SYS-004].

При сравнении текстового решения система удаляет пробелы в начале и конце обеих строк и проверяет точное совпадение оставшихся символов. Регистр букв и пробелы внутри строки сохраняются. Если эталон содержит «Алый мак», крайние пробелы вокруг этих слов допустимы. Замена прописной буквы на строчную или вставка второго пробела между словами даёт отрицательный вердикт. Запись любого из двух предметных вердиктов расходует одну попытку.

Для проверки закрепления после первого чтения изменяют банк вариантов и рассматривают повторное чтение и восстановление. Выданное условие и связанный эталон остаются прежними. Отдельно проверяется отсутствие эталона в данных студента, истории и расписании.

<a id="sr-cfg-008"></a>

### SR-CFG-008. Публикация в расписании

Редакция варианта — сочетание условия и эталона, действовавшее при подготовке работы. Банк заданий хранит подготовленные преподавателем задания для повторного использования.

До явной публикации черновик отсутствует в расписании студентов. Для публикации требуются хотя бы одна позиция, закреплённая за преподавателем группа, корректные `opensAt` и `closesAt`, а также явный выбор `repeatAllowed` — разрешить или запретить повторное прохождение. При пустом составе система просит преподавателя добавить задание. При отсутствии любого обязательного значения публикация не происходит, тот же черновик остаётся доступным для правки. Успешная публикация закрепляет группу, обе границы, правило повтора, состав и редакции вариантов. Группа сразу видит название, время открытия и закрытия и доступность старта. Редактирование банка заданий не меняет опубликованные варианты. Просмотр расписания не выдаёт условия, эталоны или личную сессию.

Если `repeatAllowed` выключено, после завершения студент может читать прежний результат, а новую сессию этого мероприятия не получает. Если повторы включены, после завершения предыдущей сессии студент может начать отдельную сессию того же мероприятия до закрытия. Пока личная сессия активна, повтор или два одновременных старта не создают второй набор при любом значении настройки.

Признак выполнения — преподаватель назначил мероприятие на завтра и опубликовал сегодня. До публикации расписание группы его не содержит. После публикации видна запись на завтра, однако сегодняшнее чтение расписания оставляет личные сессии неизменными. Пользователи иной группы этого назначения не видят. Основания — [`TS.REQ.FUNC.EVENT.PUBLISH`][TS.REQ.FUNC.EVENT.PUBLISH] и [`TS.REQ.FUNC.EVENT.VIEW`][TS.REQ.FUNC.EVENT.VIEW].

Проверка публикации начинается с допустимых группы, времени открытия и времени закрытия. Для пустого состава запись расписания не возникает. Для непустого состава отдельно проверяются невыбранное правило повтора и явное false. Правило закрепления опубликованной редакции проверяется и до первого старта студента.

## Предметные учебные сценарии

<a id="sr-elg-001"></a>

### SR-ELG-001. Условие и результат задачи Эль-Гамаля

В задаче Эль-Гамаля студент шифрует сообщение и восстанавливает его по учебной схеме с открытым ключом. Система должна выдать условие, в котором `p` — простое число, по модулю которого выполняются операции, `g` — основание для вычисления степеней, `x` — учебный секретный показатель, а `m` — исходное сообщение. В математическом упражнении `x` входит в условие, чтобы студент мог выполнить расшифрование.

По этому же условию система должна проверить открытый ключ `y`, выбранный студентом одноразовый показатель шифрования `k`, обе части зашифрованного сообщения (шифртекста) `c1` и `c2`, а также восстановленное сообщение. Показатель `k` относится к одному шифрованию и не обозначает личную учебную сессию. Неверное, допустимое по форме решение даёт предметный вердикт с пояснением о первом неверном промежуточном значении.

Признак выполнения — согласованный ответ проходит все предметные проверки. Если раннее и более позднее значения неверны, пояснение указывает первое несоответствие. Пропуск обязательного поля обрабатывается по [SR-SES-009] до предметной проверки. Основания — [`TS.REQ.FUNC.PROB.ELGAMAL`][TS.REQ.FUNC.PROB.ELGAMAL] и [`TS.REQ.FUNC.SESSION.SUBMIT`][TS.REQ.FUNC.SESSION.SUBMIT].

<a id="sr-elg-002"></a>

### SR-ELG-002. Самоподготовка по схеме Эль-Гамаля

Редакционное задание предназначено для самостоятельной практики вне сессии с оценкой. В запросе на генерацию разрядность задаёт размер учебного числа в битах.

Система должна выдавать учебный пример с пошаговым разбором и, по запросу самостоятельной работы, условие без готового решения. Значение параметра разрядности должно быть положительным целым числом. Если задана нулевая или отрицательная разрядность, запрос отклоняется, учебный материал не выдаётся. Обе редакционные операции не записывают учебный пример в базу, не открывают сессию и не расходуют попытку решения.

Признак выполнения — по запросу разбора видны промежуточные значения и итог, а выдачи условия достаточно, чтобы студент сам составил ответ. После обоих обращений прежняя сессия и личная история остаются теми же. Основания — [`TS.REQ.FUNC.EDITORIAL`][TS.REQ.FUNC.EDITORIAL] и [`TS.REQ.FUNC.PROB.ELGAMAL`][TS.REQ.FUNC.PROB.ELGAMAL].

<a id="sr-bdr-001"></a>

### SR-BDR-001. Учебное упражнение с подготовленным примером

Платформа должна предоставить допущенному пользователю готовый учебный пример и его демонстрационный результат с пояснением. Пояснение показывает, почему получение защищаемых сведений участником без соответствующих прав нарушает ожидаемую конфиденциальность. Арифметически правильный расчёт сам по себе не гарантирует сохранения тайны. Эти материалы предназначены для самостоятельного чтения. Редакционное обращение не создаёт решённую задачу, не изменяет сессию и не расходует попытку.

Признак выполнения — по материалам одного подготовленного примера студент может назвать защищаемые сведения, ожидаемое ограничение доступа и показанное нарушение. Пояснение позволяет отличить этот исход от неверного промежуточного числа при решении задачи. До и после просмотра совпадают состав сессии и личная история, запись редакционной генерации в хранилище отсутствует. Основания — [`TS.REQ.FUNC.PROB.BACKDOOR`][TS.REQ.FUNC.PROB.BACKDOOR] и [`TS.REQ.FUNC.EDITORIAL`][TS.REQ.FUNC.EDITORIAL].

## Интерфейс, эксплуатация и производительность

<a id="sr-sys-010"></a>

### SR-SYS-010. Единый внешний интерфейс

REST API — доступные клиенту операции над ресурсами платформы через HTTP. Например, клиент запрашивает у сервера ресурс сессии по её идентификатору. JSON — текстовый формат структурированных данных, UUID — уникальный идентификатор ресурса. Базовый путь задаёт общее начало адресов операций, порт — номер сетевой точки подключения.

Внешний REST-интерфейс должен предоставлять операции под базовым путём `/api` на порту 8083. Для обмена структурированными данными применяется JSON, для идентификации ресурсов — UUID. При отказе клиент получает соответствующий HTTP-статус и JSON с машинным кодом, сообщением и временем события. Дополнительные поля для операций сессии определены в DOC-06.2.

Признак выполнения — неверная форма запроса даёт 400, отсутствие действительных учётных данных — 401, недостаточные права — 403, отсутствующий ресурс — 404. Категория отказа распознаётся по статусу и коду независимо от текста сообщения. Основания — [`TS.REQ.INT.REST`][TS.REQ.INT.REST], [`TS.REQ.INT.CODES`][TS.REQ.INT.CODES], [`TS.REQ.SEC.ROLES`][TS.REQ.SEC.ROLES] и [SR-SYS-008].

<a id="sr-sys-011"></a>

### SR-SYS-011. Параметры окружения

Секрет подписи `JWT_SECRET`, срок действия токена `ACCESS_TOKEN_LIFETIME` и параметры подключения к базе система должна получать из переменных окружения. Значения секретов не включаются в исходный код и файлы репозитория. Признак выполнения — конфигурация запуска ссылается на переменные по имени, описание рабочей поставки не содержит секретных значений. Срок токена задаётся в днях согласно [SR-AUTH-003]. Основания — [`TS.REQ.SEC.SECRETS`][TS.REQ.SEC.SECRETS] и [`TS.REQ.SEC.JWT`][TS.REQ.SEC.JWT].

При проверке конфигурации сопоставляют имена переменных и назначение параметров; действительные значения секретов в проверочные материалы не переносят. Подтверждение наличия ссылки на окружение не является проверкой фактического срока действия выданного токена.

<a id="sr-sys-012"></a>

### SR-SYS-012. Сохранность платформенных данных

PostgreSQL — система управления базами данных (СУБД), в которой платформа хранит сведения между запусками приложения.

Пользователи, подтверждённые номера их групп, назначения групп преподавателям, шаблоны наборов задач, авторские задания с вариантами, мероприятия, назначения, сессии и задачи должны сохраняться в PostgreSQL 17 и оставаться доступными после перезапуска. Незавершённые сессии продолжают обслуживаться с прежними сроками и учётом своевременных обращений. Фоновая обработка просрочки не требует повторного входа студента.

Признак выполнения — после запуска сохраняются учётная запись, состав группы, доступные ей шаблоны и расписание опубликованных мероприятий вместе с границами окон и правилами повторного прохождения. Подготовленный черновик остаётся черновиком. Владелец читает прежнюю сессию того же мероприятия с теми же идентификаторами, условиями и вердиктами. Проверка авторского варианта использует закреплённый эталон. Открытый ответ обрабатывается в пределах первоначального срока согласно [SR-SES-013]. Основания — [`TS.REQ.REL.PERSIST`][TS.REQ.REL.PERSIST], [`TS.REQ.REL.AUTOFAIL`][TS.REQ.REL.AUTOFAIL], [`TS.REQ.REL.SCHED`][TS.REQ.REL.SCHED] и [SR-SYS-007].

Проверка сохранности сопоставляет выбранный набор записей до остановки и после восстановления: UUID, связи, порядок позиций, редакции вариантов, состояния и вердикты. Для черновика сохраняется в том числе невыбранное правило повтора, для опубликованной работы — зафиксированное значение. Для незавершённой операции сопоставляются первоначальные отметки времени; новый срок не назначается.

<a id="sr-sys-013"></a>

### SR-SYS-013. Запуск и перезапуск серверной части

Docker Compose описывает совместный запуск приложения и базы в отдельных контейнерах — изолированных средах исполнения. Постоянный том — область хранения, данные которой сохраняются при перезапуске контейнера базы.

При развёртывании с Docker Compose приложение должно запускаться после успешной проверки готовности СУБД. База размещается на постоянном томе для сохранения данных между перезапусками контейнеров. Признак выполнения — в описании развёртывания указаны проверка готовности базы, зависимость запуска приложения от её результата и том данных. После штатного перезапуска со своим томом пользователю доступны прежние записи. Основание — [`TS.REQ.REL.DEPLOY`][TS.REQ.REL.DEPLOY].

Условия проверки различают отрицательный и положительный результаты готовности базы. Сохранность рассматривается при штатном перезапуске с тем же постоянным томом. Удаление тома и восстановление после повреждения носителя не входят в этот критерий.

<a id="sr-sys-014"></a>

### SR-SYS-014. Отклик обычных операций

Время отклика описывает, сколько клиент ждёт ответа. Для группы запросов используют 95-й процентиль (`p95`) — границу, в которую укладываются не менее 95 процентов наблюдений. Прогретый стенд — испытательная среда после запуска и выхода системы в обычный режим работы. Профиль нагрузки задаёт состав запросов и количество одновременно работающих пользователей.

При 30 одновременно работающих пользователях 95-й процентиль времени отклика обычных операций должен составлять не более 2 секунд. В этот класс входят регистрация, вход, просмотр групп и шаблонов, чтение данных и отправка решения со штатным предметным проверяющим. Время отклика считают от момента отправки запроса клиентом до получения полного ответа.

Для проверки задают прогретый стенд, неизменный профиль нагрузки и не менее 100 запросов данного класса. Полученные времена располагают по возрастанию и выбирают наблюдение с порядковым номером, равным округлённому вверх произведению 0,95 на число запросов. При ровно 100 наблюдениях 95-е значение, равное 2 секундам, удовлетворяет критерию. Большее значение не удовлетворяет. Искусственно вызванные отказы и специальные задержки очереди проверяются отдельно. Нормальная работа очереди входит во время отклика. Основания — [`TS.REQ.PERF.CRUD`][TS.REQ.PERF.CRUD] и [`TS.REQ.PERF.MEASURE`][TS.REQ.PERF.MEASURE].

Для воспроизводимой последующей проверки заранее описывают конфигурацию стенда, объём исходных данных и состав штатных запросов. Подготовка этих условий и расчёт ранга на примере не подтверждают фактический p95: заключение о выполнении показателя требует результатов измерения. В рамках документационного задания описывается проверка, а не заявляется её прогон.

<a id="sr-sys-015"></a>

### SR-SYS-015. Отклик операций генерации

При 30 одновременно работающих пользователях 95-й процентиль времени отклика операций генерации должен составлять не более 5 секунд. К этому классу относятся создание сессии с формированием задач и учебные запросы генерации. Измерительный интервал начинается отправкой запроса и заканчивается получением полного ответа.

Признак выполнения — для класса генерации в тех же условиях прогрева и нагрузки набрано не менее 100 собственных наблюдений. По правилу [SR-SYS-014] определяют отдельный 95-й процентиль. Значение ровно 5 секунд удовлетворяет критерию, превышение — нет. Быстрые операции чтения в эту выборку не включают. Предел обработки одного своевременного решения в [SR-SES-012] относится к другой обязанности системы. Основания — [`TS.REQ.PERF.GEN`][TS.REQ.PERF.GEN] и [`TS.REQ.PERF.MEASURE`][TS.REQ.PERF.MEASURE].

Состав и объём генерируемого материала фиксируются в условиях последующей проверки. Обычные операции и генерация не объединяются в одну выборку. Указание предела обработки одного ответа не заменяет отдельный критерий отклика генерации; фактическое соблюдение 5 секунд не утверждается без измерений.

<a id="sr-sys-016"></a>

### SR-SYS-016. Подключаемый вид задания

Платформа должна позволять добавлять программные модули с новыми видами заданий. Через общий интерфейс модуль формирует условие и данные для последующей проверки, а по сохранённому условию и ответу студента возвращает предметный вердикт либо сообщает о технической невозможности проверки. Система сохраняет связь выданной позиции с её видом. Правила доступа, времени, попытки и итога сессии одинаковы для подключённых видов.

Признак выполнения — в состав одной работы включены поставляемый вид и дополнительный учебный вид. Для обоих клиент получает условие. Каждый ответ обрабатывается соответствующим модулем по выданным данным, оба результата включаются в одну сессию. Неизвестный вид не подменяется другим и не приводит к выдаче частичного набора. Основания — [`TS.REQ.FUNC.TASK.MODULE`][TS.REQ.FUNC.TASK.MODULE] и [SR-SYS-004].
