# DOC-05. Требования к ранцевым задачам

Раздел [DOC-05](DOC-05_Системные_требования.md), рабочая версия 0.1 от 07.11.2026. Автор: Георгиев Д.Д. Все требования раздела имеют обязательный приоритет. Предметные основания: [карточка домена](../../notes/domains/backpack.md) и указанные ниже требования [ТЗ](../../02_Техническое_задание/Техническое_задание.tex). Состав и формат полей ответа приведены в [контракте сессий](../07_Программные_требования/Контракты_сессий.md#ранцевая-задача).

## SR-KNAP-001. Выбор варианта ранцевой задачи

Ранцевая криптосистема существует в двух учебных вариантах: на супервозрастающей последовательности и на последовательности степеней. Состав набора задаёт конфигурация группы, но конкретный математический вариант каждого ранцевого задания определяет система при генерации. Пользователь не передаёт серверу свой вариант: он получает условие уже выбранного вида и восстанавливает параметры именно этой криптосистемы. Порядок выбора конфигурации и создания набора определён в [создании сессии](Сессии_задач.md#sr-ses-001-создание-набора-по-конфигурации-группы), а роль предметных генераторов — в [выборе предметной проверки](Сессии_задач.md#sr-ses-004-выбор-предметной-проверки).

**Требование.** Система должна выбирать вариант ранцевой задачи, выдаваемой в сессии, из поддерживаемых вариантов — на супервозрастающей последовательности и на степенях — и формировать условие по схеме выбранного варианта.

Если конфигурация включает ранцевую задачу и задачу Эль-Гамаля, ранцевое условие строится одним из двух поддерживаемых вариантов, а задание Эль-Гамаля — собственной схемой своего домена. Неподдерживаемый вариант не подменяется другим и не создаёт частичной сессии: это соответствует [правилу сохранения полного набора](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-005-сохранение-созданного-набора).

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`, `[TS.REQ.FUNC.PROB.BACKPACK.SI]`; сценарий генерации карточки домена.

Проверка: в сессии появляются только задачи поддерживаемых вариантов; схема условия каждой задачи соответствует её варианту; выбор варианта определяется системой и не зависит от параметров пользователя.

## SR-KNAP-002. Частично скрытое условие

Учебная цель ранцевого задания — восстановить криптосистему по неполным данным. Поэтому условие не повторяет эталон: часть элементов лёгкого ранца скрыта, а множитель преобразования может отсутствовать вовсе. Студент достраивает недостающее, используя математические свойства последовательности, и затем завершает построение всех величин. Полное эталонное решение с открытыми данными выдаётся отдельно редакционной генерацией по SR-KNAP-008.

**Требование.** Система должна выдавать условие ранцевой задачи с частично скрытым лёгким ранцем; множитель преобразования может не включаться в условие. Условие должно быть достаточным для восстановления всех параметров криптосистемы.

Восстановление опирается на свойство последовательности: для супервозрастающего варианта каждый элемент строго больше суммы предыдущих, для варианта на степенях элементы являются степенями основания. Скрытие не должно делать задачу неразрешимой: по выданным фрагментам и тяжёлому ранцу восстанавливаются лёгкий ранец, модуль, множитель, обратный множитель, шифртекст и расшифрованное сообщение. Формат выданного условия входит в [представление задачи](../07_Программные_требования/Контракты_сессий.md#представление-сессии-и-задачи) контракта сессий.

Основание: `[TS.REQ.FUNC.PROB.BACKPACK.SI]`; сценарий генерации карточки домена.

Проверка: по выданному условию восстановимы лёгкий ранец, модуль, множитель, тяжёлый ранец, обратный множитель, шифртекст и расшифрованное сообщение.

## SR-KNAP-003. Состав ответа ранцевой задачи

Ответ на ранцевое задание — это не отдельное число, а восстановленная криптосистема целиком. Проверяющий сопоставляет каждую переданную величину с ожидаемой, поэтому пропуск поля делает проверку невозможной. Состав полей закреплён [контрактом сессий](../07_Программные_требования/Контракты_сессий.md#ранцевая-задача): размерность, вариант, исходное сообщение, лёгкий ранец, множитель, тяжёлый ранец, зашифрованное и расшифрованное сообщения, модуль и обратный множитель. Настоящий раздел подтверждает этот состав как владелец типа.

**Требование.** Ответ на ранцевую задачу должен содержать восстановленные значения всех величин криптосистемы: размерность, вариант, исходное сообщение, лёгкий ранец, множитель, тяжёлый ранец, зашифрованное и расшифрованное сообщения, модуль и обратный множитель. Указанный в ответе вариант не должен подменять вариант выбранной задачи.

Поля передаются в установленном контрактом виде: размерность — положительным целым числом, сообщения — списками логических значений, целые величины произвольной длины — десятичными строками, ранцы — списками таких строк. Ответ с полным набором полей допускается к предметной проверке; категория ошибки формы определяется [правилом ошибки формата](Сессии_задач.md#sr-ses-009-ошибка-формата) домена сессий. Значение поля варианта сверяется с вариантом сохранённого условия и не переключает проверку на другой тип.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`, `[TS.REQ.FUNC.PROB.BACKPACK.SI]`; поля предметного ответа в контракте сессий.

Проверка: ответ с полным набором величин допускается к предметной проверке; значение поля варианта не переключает проверку на другой вариант. Категории отказа до предметной проверки определяются SR-SES-009.

## SR-KNAP-004. Предметная проверка решения

Предметная проверка ранцевого задания проходит по всем восстановленным величинам, а не по итоговому сообщению. Каждая величина вычисляется из условия и сравнивается с переданной. Перечень охватывает длину и элементы сообщений и ранцев, сверхвозрастаемость лёгкого ранца, соотношение модуля с суммой лёгкого ранца, взаимную простоту множителя с модулем, тяжёлый ранец, обратный множитель, шифртекст и расшифрованное сообщение. Такой состав следует из [требования ТЗ к проверке восстанавливаемых величин](../../02_Техническое_задание/Техническое_задание.tex) и сценария проверки карточки домена.

**Требование.** Система должна проверять решение ранцевой задачи по всем восстановимым величинам: длине и элементам сообщения и ранцев, сверхвозрастаемости лёгкого ранца, соотношению модуля с суммой лёгкого ранца, взаимной простоте множителя с модулем, тяжёлому ранцу, обратному множителю, шифртексту и расшифрованному сообщению.

Расшифрованное сообщение проверяется расшифровкой жадным алгоритмом по супервозрастающей последовательности: элементы выбираются от старших к младшим, и результат сравнивается с переданным сообщением. Расхождение любой величины с ожидаемой приводит к неверному вердикту; полностью корректное решение — к верному. Результат операции и состояние задачи согласуются по [результату задачи](Сессии_задач.md#sr-ses-005-результат-задачи), а длительность проверки ограничена [пределом обработки](Сессии_задач.md#sr-ses-012-ограниченная-длительность-обработки) домена сессий.

Основание: `[TS.REQ.FUNC.PROB.BACKPACK.SI]`; сценарий проверки карточки домена.

Проверка: расхождение любой величины с ожидаемой приводит к неверному вердикту; полностью корректное решение — к верному.

## SR-KNAP-005. Диагностика неверного решения

Неверный ответ без пояснения не даёт студенту материала для работы над ошибкой. Предметная проверка сообщает, какая величина не прошла сравнение первой. Это пояснение относится к завершённой неверной попытке и не заменяет категорию отказа: транспортные и технические ошибки передаются отдельными кодами по [контракту ошибок](../07_Программные_требования/Контракты_сессий.md#коды-и-представление-ошибок).

**Требование.** При неверном решении система должна сообщать, какая величина не прошла проверку первой.

Диагностика указывает конкретную величину, например неверный тяжёлый ранец или нарушенную взаимную простоту множителя. Верный вердикт диагностикой не сопровождается: поле пояснения в положительном результате отсутствует. Текст пояснения не влияет на состояние задачи и попытку — они определяются требованиями домена сессий, а не формулировкой сообщения. Это применение общего [различения отказов](Интеграция.md#sr-sys-009-различение-отказов).

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]` (диагностическое сообщение при ошибке).

Проверка: сообщение указывает конкретную величину; верный вердикт не сопровождается диагностикой ошибки. Сообщение не заменяет категорию результата по SR-SYS-009.

## SR-KNAP-006. Вариант на степенях

Второй вариант ранцевой криптосистемы отличается построением лёгкого ранца: его элементы являются степенями выбранного основания. Такой ранец автоматически обладает сверхвозрастаемостью, что и позволяет применять общую схему проверки. Студент, решающий задание на степенях, сначала распознаёт структуру последовательности, затем восстанавливает остальные величины по той же цепочке, что и в супервозрастающем варианте.

**Требование.** Для варианта «на степенях» система должна строить лёгкий ранец из степеней выбранного основания и проверять решение по той же схеме величин, что и для супервозрастающего варианта.

Состав проверяемых величин совпадает со схемой SR-KNAP-004. Фактическое отсутствие проверки расшифрованного сообщения для этого варианта в текущей реализации отмечено в DOC-06.3 как известная особенность и вынесено на решение к следующей версии документа.

Основание: `[TS.REQ.FUNC.PROB.BACKPACK.DEG]`.

Проверка: элементы лёгкого ранца соответствуют степеням основания; состав проверок совпадает со схемой SR-KNAP-004.

## SR-KNAP-007. Повторный ответ после итогового состояния

После зафиксированного вердикта повторная отправка решения не создаёт новой попытки. Это правило домена сессий сформулировано в [требовании единственной попытки](Сессии_задач.md#sr-ses-008-одна-предметная-попытка); ранцевой домен применяет его к своему обработчику. Повтор может произойти из-за повторного нажатия, повторной отправки сетевого клиента или нового соединения — во всех случаях прежний результат сохраняется.

**Требование.** После итогового состояния задачи система должна отклонять повторный ответ ранцевой задачи без предметной проверки, сохраняя прежний результат.

Отклонение происходит до математического вычисления: проверяющий не запускается, а задача и сессия не изменяются. Внешняя категория отказа определена контрактом сессий (`TASK_FINALIZED`); для восстановления отображения студент использует [чтение сохранённого результата](Сессии_задач.md#sr-ses-014-получение-сохранённого-результата), а не повторную отправку.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; правило попытки карточки домена.

Проверка: повторная отправка не создаёт нового предметного вердикта и не изменяет состояние задачи; согласуется с SR-SES-008.

## SR-KNAP-008. Редакционная задача по варианту

Редакционная генерация предназначена для самоподготовки и подготовки методических материалов. В отличие от задания в сессии, она выдаёт эталон с полным решением: открытым лёгким ранцем, множителем, модулем, тяжёлым ранцем, обратным множителем и шифртекстом. По эталону студент прослеживает всю цепочку построения до расшифрованного сообщения.

**Требование.** Система должна выдавать редакционную (эталонную) ранцевую задачу выбранного варианта с полным решением — всеми величинами криптосистемы от лёгкого ранца до расшифрованного сообщения.

Вариант задаётся запросом; остальные параметры, не указанные явно, выбираются системой. Редакционные генерации не связаны с сессиями и не влияют на попытки и сроки — их единственная обязанность перед остальной системой описана в SR-KNAP-010.

Основание: `[TS.REQ.FUNC.EDITORIAL]`; учебный сценарий карточки домена.

Проверка: эталон содержит полный набор величин; вариант соответствует указанному в запросе.

## SR-KNAP-009. Редакционная задача с параметрами

Преподаватель может задать собственные параметры примера: размерность, вариант, сообщение, лёгкий ранец и множитель. Система строит эталон по этим данным, проверяя математическую допустимость. Взаимная простота множителя с модулем — необходимое условие обратного преобразования, поэтому её нарушение отклоняется до построения.

**Требование.** Система должна принимать параметры редакционной генерации — размерность, вариант, сообщение, лёгкий ранец, множитель — и отклонять запрос с множителем, не взаимно простым с модулем, сообщая причину.

При отказе задача не выдаётся: клиент получает диагностическое сообщение о причине. Отказ редакционной генерации не связан с сессиями и не расходует никаких попыток.

Основание: `[TS.REQ.FUNC.EDITORIAL]`; сценарий с параметрами карточки домена.

Проверка: генерация с корректными параметрами завершается эталоном; при невзаимно простом множителе — отказ с диагностикой и без задачи.

## SR-KNAP-010. Редакционные генерации без сохранения

Редакционные примеры не являются учебными попытками и не должны попадать в данные сессий. Каждый запрос создаёт новый пример на лету; сохранение сделало бы повторный запрос выдачей прежнего эталона и связало бы самоподготовку с хранилищем задач.

**Требование.** Система не должна записывать результаты редакционных генераций в базу данных.

Правило относится к результатам редакционных генераций и не затрагивает сохранение задач, созданных в сессиях по SR-KNAP-001.

Основание: `[TS.REQ.FUNC.EDITORIAL]`.

Проверка: повторный запрос даёт новый пример; сохранённые данные сессий не пополняются редакционными задачами.

## Пояснения к вариантам и попытке

Вариант задания и вариант в ответе студента имеют разное назначение. Первый выбирается системой при генерации и сохраняется вместе с условием; второй передаётся в теле ответа и сверяется с первым. Совпадение необходимо: ответ по схеме другого варианта не может проверить сохранённое условие.

Предметная попытка расходуется только завершённой проверкой с вердиктом. Неверная величина в ответе даёт отрицательный вердикт и завершает попытку; ошибка формы или технический сбой проверки обрабатываются правилами домена сессий без участия ранцевых алгоритмов. Диагностическое сообщение поясняет неверное решение, но не создаёт и не отменяет попытку.

Длительность предметной проверки входит в предел обработки принятого ответа, установленный доменом сессий. Ранцевая проверка по величинам конечна и не требует собственных таймеров: превышение предела обработки обработывается общим правилом технического завершения.

## Сочетания событий для проверки раздела

Приведённые сочетания раскрывают требования, а не вводят отдельные TC. При подготовке DOC-10 для них нужно задать исходное состояние, действие и наблюдаемый результат.

| Последовательность событий | Ожидаемый результат |
|---|---|
| Создан набор с ранцевой задачей; условие содержит скрытые элементы ранца | Условие восстанавливается до полного набора величин; вариант соответствует схеме |
| Ответ с полным набором величин, одна величина неверна | Отрицательный вердикт; диагностика указывает первую несовпавшую величину |
| Ответ с полным набором величин, все верны | Положительный вердикт; попытка завершена |
| Поле варианта в ответе указывает другой вариант | Ответ не допускается к проверке по чужой схеме; вариант сверяется с условием |
| Повторная отправка после зафиксированного вердикта | Отказ без предметной проверки; прежний результат сохранён |
| Редакционная генерация выполнена дважды с одними параметрами | Каждый запрос даёт новый пример; хранилище сессий не пополняется |
| Редакционная генерация с невзаимно простым множителем | Отказ с диагностикой; пример не выдаётся |
