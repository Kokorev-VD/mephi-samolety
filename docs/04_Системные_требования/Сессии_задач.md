# DOC-05. Требования к сессиям задач

Раздел [DOC-05](DOC-05_Системные_требования.md), рабочая версия 0.2 от 05.11.2026. Автор: Анохин Г.А. Все требования раздела имеют обязательный приоритет; статус — проект для согласования. Предметные основания: [карточка сессий](../03_Карточки_доменов/Сессии_задач.md) и указанные ниже требования [ТЗ](../../02_Техническое_задание/Техническое_задание.tex).

## SR-SES-001. Создание набора по конфигурации группы

Система должна создавать сессию текущего пользователя по конфигурации, включённой для его группы, и возвращать данные созданной сессии с задачами, соответствующими составу конфигурации.

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`, `[TS.REQ.FUNC.CONFIG.VIEW]`; сценарий создания набора.

Проверка: у пользователя есть группа с включённой конфигурацией и нет другой сессии `NEW`. Запрос создаёт его сессию в состоянии `NEW` с задачами выбранного состава. Недоступная конфигурация не должна приводить к созданию набора.

## SR-SES-002. Одна незавершённая сессия

При наличии у пользователя сессии `NEW` система должна отклонять создание новой сессии.

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`; ограничение активных сессий в карточке домена.

Проверка: последовательные и одновременные запросы одного пользователя не создают две незавершённые сессии. Если прежняя сессия просрочена, её состояние сначала приводится в соответствие с правилами завершения.

## SR-SES-003. Принадлежность и состояние сессии

Система должна допускать ответ к предметной проверке только для задачи собственной сессии текущего пользователя, если сессия находится в состоянии `NEW`.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; сценарий отправки ответа.

Проверка: обращение к задаче чужой или завершённой сессии отклоняется до предметной проверки; её данные и результаты не меняются. Срок и состояние самой задачи дополнительно проверяются по SR-SES-006, SR-SES-008 и SR-SES-011.

## SR-SES-004. Выбор предметной проверки

Для допустимого ответа система должна выбирать проверку по типу сохранённой задачи и передавать ей условие этой задачи и полученный ответ.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; ответственность криптографических доменов в карточке сессий.

Проверка: для каждого поддерживаемого типа вызывается соответствующая предметная проверка. Тип, указанный пользователем в ответе, не должен подменять тип выбранной задачи.

## SR-SES-005. Результат задачи

После завершённой предметной проверки система должна сохранить задаче `SOLVED` при верном ответе либо `FAILED` при неверном и вернуть результат, относящийся к этой задаче.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; сценарий проверки ответа.

Проверка: результат содержит идентификатор и тип проверенной задачи; сохранённое состояние соответствует вердикту. Технический сбой без вердикта обрабатывается по SR-SES-010.

## SR-SES-006. Общий срок сессии

Система должна ограничивать решение всех задач единым сроком: 20 минут от серверного времени создания сессии. По достижении срока незавершённые задачи без своевременного ответа в обработке должны завершаться с `FAILED`, а ранее определённые результаты — сохраняться.

Основание: сценарий срока в карточке домена; `[TS.REQ.FUNC.SESSION.TIME]` с уточнением общего срока, отмеченным в DOC-05.

Проверка: задачи одной сессии имеют один срок. Обновление страницы и повторы запроса его не меняют. После срока необработанные задачи получают `FAILED`; своевременно полученный ответ обрабатывается по SR-SES-011. Задержка фоновой обработки не разрешает новые ответы после срока.

## SR-SES-007. Итог сессии

После завершения всех задач система должна устанавливать сессии `SOLVED`, если все задачи имеют `SOLVED`, и `FAILED`, если хотя бы одна задача имеет `FAILED`.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; правило завершения в карточке домена.

Проверка: рассматриваются все верные ответы, наличие неверного ответа и наличие просрочки. Пока есть задача без итогового состояния, в том числе своевременный ответ в обработке, сессия остаётся `NEW`.

## SR-SES-008. Одна предметная попытка

Система должна допускать не более одной завершённой предметной проверки для каждой задачи; после получения итогового состояния повторный ответ не должен его изменять.

Основание: правило попытки в карточке домена.

Проверка: повторные и одновременные отправки не приводят к двум предметным вердиктам. Ответ после `SOLVED` или `FAILED` отклоняется, результат сохраняется. Исключения без расходования попытки определены в SR-SES-009 и SR-SES-010.

## SR-SES-009. Ошибка формата

Система должна отклонять запрос с некорректным форматом или отсутствующим обязательным полем до предметной проверки, сообщать причину и сохранять неиспользованную попытку.

Основание: правило обработки ошибок в карточке домена.

Проверка: неверно оформленный ответ не получает предметного вердикта. Исправленный ответ допускается, если новый запрос получен до срока и выполнены остальные условия. Состояние `NEW` сохраняется, пока задача не завершена по другому основанию; сама ошибка срока не продлевает.

## SR-SES-010. Технический сбой проверки

Если проверка не завершилась вердиктом из-за технического сбоя, система должна сообщить о сбое и сохранить неиспользованную предметную попытку.

Основание: правило технического сбоя в карточке домена.

Проверка: до срока возможен новый допустимый запрос. Если сбой своевременной проверки обнаружен после срока, новый ответ уже не принимается, а незавершённая задача закрывается по просрочке. Ошибка сервера не считается неверным предметным ответом.

## SR-SES-011. Момент приёма ответа

Система должна считать ответ своевременным, если полный запрос получен сервером строго до общего срока сессии, и сохранять право на его проверку после наступления этого срока.

Основание: решение Анохина от 05.11.2026; раздел «Срок и попытка» карточки домена.

Проверка: ответ получен за секунду до срока, а вердикт готов через секунду после него — вердикт принимается. Запрос, полученный точно в срок или позднее, отклоняется. Зафиксированное сервером время получения, а не время окончания проверки или часы пользователя, определяет своевременность.

Своевременность не отменяет проверок принадлежности, состояния и формата. Ожидание работы сервера не создаёт дополнительной попытки. Программные связи всех требований приведены в [DOC-06.2](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#6-трассировка-и-описательные-проверки).
