# DOC-05. Требования к сессиям задач

Автор раздела — Анохин Г.А. Редакция 1.1 от 20.11.2026 входит в [DOC-05](DOC-05_Системные_требования.md). Все требования обязательны. Основания приведены в [техническом задании](../02_Техническое_задание/DOC-02_Техническое_задание.md), в [таблице требований ТЗ и критериев](DOC-05_Системные_требования.md#4-охват-технического-задания-и-критерии) и в [карточке сессий](../03_Карточки_доменов/Сессии_задач.md).

Сессия — личный набор выданных студенту задач с их условиями, сроком и результатами. Сервер фиксирует момент создания набора `t0`. Для практики по шаблону срок `D = t0 + 20 минут`. Для контрольной работы срок `D = min(t0 + 20 минут, closesAt)`, где `closesAt` — момент её закрытия по серверным часам. Один срок `D` действует для всех задач сессии. Для отдельного решения `t_in` — момент получения сервером полного запроса, а `L = t_in + 60 секунд` — предел фиксации результата его обработки.

<a id="sr-ses-001"></a>

## SR-SES-001. Создание набора по шаблону группы

Шаблон набора задач задаёт типы заданий и их порядок для самостоятельной практики. Система должна создать студенту сессию по выбранному шаблону, если он включён для его группы и у него нет незавершённой сессии. Для контрольного мероприятия состав определяет преподаватель, а опубликованное назначение связывает работу с группой и расписанием. Студент начинает её отдельно, по идентификатору мероприятия. Его подтверждённая на `home.mephi.ru` группа должна совпадать с назначенной. Условие старта — `opensAt <= t < closesAt`, где `opensAt` — время открытия, а `t` — время запроса на старт по часам сервера.

При успешной выдаче студент получает весь набор в порядке, заданном источником его состава. Идентификатор каждой задачи позволяет адресовать ей отдельный ответ. Тип задачи определяет способ проверки, а условие сообщает студенту исходные данные. В начале сессия и её задачи имеют состояние `NEW` — работа ещё не завершена.

Если студенту не назначена группа или выбранный шаблон ей недоступен, набор не создаётся. При сбое генерации одной из задач частично сформированный набор также не должен появиться у студента.

<a id="sr-ses-002"></a>

## SR-SES-002. Одна незавершённая сессия

Для одного владельца система должна допускать не более одной сессии в состоянии `NEW`, в том числе при одновременном создании с двух устройств. Если студент повторяет запрос при действующей сессии или отправляет два запроса одновременно, система допускает только одну активную сессию. Ответ на повтор — отказ `409 ACTIVE_SESSION_EXISTS` с идентификатором уже созданного набора. После завершения контрольной работы при выключенном `repeatAllowed` доступен прежний результат. При включённом параметре отдельная новая сессия разрешена только до закрытия мероприятия. Существующий набор, его срок и решённые задачи сохраняются.

При обращении после общего срока учитывается фактическое состояние прежнего набора. Если у него остались только просроченные задачи без принятого ответа, система завершает их и определяет итог сессии перед созданием следующей. Если своевременный ответ ещё находится в пределах своей обработки, прежняя сессия остаётся активной.

<a id="sr-ses-003"></a>

## SR-SES-003. Принадлежность и состояние сессии

Предметная проверка устанавливает, соответствует ли решение правилам выданного задания. Её заключение «верно» или «неверно» называется вердиктом. К этой проверке система должна допускать только ответ студента на задачу его собственной сессии в состоянии `NEW`. Указание чужого идентификатора задачи не должно раскрывать её состояние, условие или результат. Правило действует и тогда, когда две задачи разных студентов имеют одинаковый тип.

Для собственной задачи действуют также ограничения по состоянию задачи, попытке, времени получения и форме запроса. Отказ до предметной проверки сохраняет данные владельца и не даёт вердикта.

<a id="sr-ses-004"></a>

## SR-SES-004. Выбор предметной проверки

Система должна проверять полученное решение по типу и условию, сохранённым для указанной задачи при создании сессии. Поля присланного решения не могут переключить проверку на другой тип. Если в наборе две задачи одного типа, каждая проверяется по собственному условию.

Обработчик — программная часть, которой поручена проверка задания выбранного типа. При отсутствии подходящего обработчика система сообщает о техническом отказе, то есть о невозможности выполнить проверку. Проверка по правилам другого типа дала бы вердикт по заданию, которое студент не получал.

<a id="sr-ses-005"></a>

## SR-SES-005. Результат задачи

При сохранении положительного вердикта система должна установить задаче состояние `SOLVED`. При сохранении отрицательного вердикта задача получает `FAILED`. В ответе студент получает идентификатор и тип именно этой задачи, признак правильности и, для неверного решения, предметное пояснение. По итогам операции прочитанное состояние задачи должно соответствовать выданному вердикту.

<a id="sr-ses-006"></a>

## SR-SES-006. Общий срок сессии

Для самостоятельной практики студенту отводится 20 минут от создания сессии. Для контрольной работы этот интервал заканчивается раньше, если раньше наступает `closesAt`. Система должна применять один срок `D` ко всем задачам набора. Работа, начатая в 10:25 при закрытии в 10:30, имеет `D = 10:30`. В момент `D` приём новых ответов прекращается. Повторное обращение и задержка фонового контроля срок не меняют.

Начиная с `D`, незавершённые задачи без своевременного допустимого ответа в обработке должны завершаться с `FAILED` по просрочке. Для них предметный результат отсутствует. Сохранённые ранее вердикты продолжают действовать. Для своевременного ответа применяются [SR-SES-011] и [SR-SES-012].

<a id="sr-ses-007"></a>

## SR-SES-007. Итог сессии

Система должна определять состояние сессии по всем задачам набора. Пока хотя бы одна из них имеет состояние `NEW`, сессия остаётся `NEW`. Это правило действует и при наличии уже зафиксированного неверного решения.

После завершения последней задачи сессия получает `SOLVED`, если каждая задача решена верно. При наличии хотя бы одной задачи в состоянии `FAILED` итог сессии — `FAILED`. И неверный ответ, и просрочка учитываются при определении этого итога.

<a id="sr-ses-008"></a>

## SR-SES-008. Одна предметная попытка

Предметная попытка — возможность получить один сохранённый вердикт по конкретной задаче. Число обращений к серверу само по себе не определяет, использована ли эта возможность.

Для каждой задачи система должна сохранять не более одного предметного вердикта. В момент его фиксации единственная попытка считается использованной независимо от правильности решения и доставки ответа клиенту.

Два одновременных запроса не могут завершиться разными вердиктами по одной задаче. Пока один ответ обрабатывается, следующий не заменяет его. После фиксации результата повторная отправка не запускает новую предметную проверку и не меняет сохранённые данные.

<a id="sr-ses-009"></a>

## SR-SES-009. Ошибка формата

Если запрос невозможно разобрать или состав полей не соответствует формату решения, система должна сообщить причину ошибки формата и сохранить неиспользованную предметную попытку. Например, при отсутствии обязательного поля студент получает сообщение о пропуске поля. Его решение ещё не прошло предметную проверку.

После исправления формы студент может отправить новый запрос при выполнении остальных условий допуска. Своевременность оценивается по получению исправленного запроса. Время первого обращения на него не переносится.

<a id="sr-ses-010"></a>

## SR-SES-010. Технический сбой проверки

Если при проверке или сохранении результата произошёл сбой и вердикт не зафиксирован, система должна сообщить о техническом отказе. Такая обработка не расходует попытку и не создаёт отрицательного предметного результата.

При сбое до `D` студент может повторить отправку, пока продолжается срок. Если к моменту сбоя наступил `D`, незавершённая задача без другого своевременного ответа завершается по просрочке. Если вердикт был сохранён до потери соединения, применяется [SR-SES-014].

<a id="sr-ses-011"></a>

## SR-SES-011. Момент приёма ответа

Система должна считать своевременным только ответ, полученный сервером полностью при `t_in < D`. При `t_in = D` и позднее новый ответ отклоняется. Начало передачи до `D` само по себе не даёт права на проверку.

Если своевременный ответ прошёл остальные условия допуска, его проверка может завершиться после `D` в пределах [SR-SES-012]. Пока такая проверка продолжается, система сохраняет задаче состояние `NEW`. Фоновая обработка просроченных задач не должна отменить принятый ответ.

<a id="sr-ses-012"></a>

## SR-SES-012. Ограниченная длительность обработки

Для принятого ответа система должна разрешать фиксацию вердикта строго до `L`. В 60 секунд от `t_in` входят ожидание, вычисление, восстановление после перезапуска и сохранение результата. Если в момент `L` сохранённого вердикта нет, операция завершается техническим отказом без расхода попытки.

Вердикт, поступивший в `L` или позднее, уже не изменяет задачу. Получение нового ответа возможно только при выполнении [SR-SES-011]. Если общий срок уже наступил, задача без вердикта завершается по просрочке.

<a id="sr-ses-013"></a>

## SR-SES-013. Восстановление принятого ответа

После перезапуска система должна продолжить обработку своевременного принятого ответа при наличии оставшегося времени до `L`. Используются прежние условие, решение и `t_in`. Утрата исходного сетевого соединения не требует повторной отправки решения студентом.

Если к восстановлению вердикт уже сохранён, он остаётся единственным. При восстановлении в `L` или позднее операция без сохранённого результата завершается по [SR-SES-012]. Срок сессии и предел обработки сохраняют свои первоначальные значения.

<a id="sr-ses-014"></a>

## SR-SES-014. Получение сохранённого результата

По идентификатору собственной сессии система должна возвращать студенту её текущее состояние, задачи и их сохранённые результаты. Чтение доступно после общего срока, перезапуска и потери ответа на исходный запрос. Чтение не вызывает повторную предметную проверку.

При отсутствии сохранённого вердикта у задачи нет предметного результата. Если студент обращается к чужой или отсутствующей сессии, ответ одинаков и не раскрывает чужие данные.

## Две границы времени на примере одной сессии

Сессия самостоятельной практики создана в 09:00:00. Сервер получил полный допустимый ответ на первую задачу в 09:19:55. На вторую задачу ответа нет.

| Момент | Событие и ожидаемый исход |
|---|---|
| 09:20:00 | Общий срок наступил. Новые ответы отклоняются, вторая задача подлежит завершению по просрочке. Первая задача остаётся в обработке |
| 09:20:54 | Если вердикт первой задачи сохранён в этот момент, студент получает предметный результат, хотя общий срок уже истёк |
| 09:20:55 | Если вердикт к этому моменту не сохранён, время обработки исчерпано. Задача завершается по просрочке без предметного вердикта. Поздняя запись результата недопустима |

Если то же задание выдано на контрольной в 10:25:00 при закрытии в 10:30:00, полный допустимый ответ в 10:29:55 можно зафиксировать строго до 10:30:55. Новый ответ в 10:30:00 отклоняется. Создать ещё одну сессию ровно при закрытии также нельзя даже при включённом `repeatAllowed`.

Две последние строки таблицы описывают разные исходы одной обработки. В обоих случаях итог сессии после завершения задач — `FAILED`, поскольку вторая задача просрочена. Различить исходы первой задачи можно чтением её сохранённого результата.
