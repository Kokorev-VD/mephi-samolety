# DOC-05. Требования к сессиям задач

Раздел [DOC-05](DOC-05_Системные_требования.md), версия 0.4 от 07.11.2026. Автор: Анохин Г.А. Все требования раздела имеют обязательный приоритет. Предметные основания: [карточка сессий](../03_Карточки_доменов/Сессии_задач.md) и указанные ниже требования [ТЗ](../../02_Техническое_задание/Техническое_задание.tex).

## SR-SES-001. Создание набора по конфигурации группы

Создание сессии превращает выбранную учебную конфигурацию в конкретный набор заданий одного пользователя. Конфигурация задаёт состав, а сессия хранит уже сформированные условия и результаты работы с ними. На этом переходе взаимодействуют проверка доступа, группа пользователя и генераторы криптографических задач; их обязанности разведены в [описании компонентов](../07_Программные_требования/DOC-06_Программные_требования.md#2-ответственность-и-связи). Пользователь выбирает доступный набор, а не передаёт серверу произвольный состав задач.

**Требование.** Система должна создавать сессию текущего пользователя по конфигурации, включённой для его группы, и возвращать данные созданной сессии с задачами, соответствующими составу конфигурации.

Если конфигурация включает ранцевую задачу и задачу Эль-Гамаля, в новой сессии сохраняются условия обоих заданий. Именно эти условия позднее используются при проверке, даже если настройки группы изменились. Создание считается законченным, когда полный набор сохранён и может быть возвращён пользователю. Программная последовательность раскрыта в [разделе создания сессии](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#2-создание-сессии), а случай ошибки генерации — в [правиле сохранения полного набора](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-005-сохранение-созданного-набора).

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`, `[TS.REQ.FUNC.CONFIG.VIEW]`; сценарий создания набора.

Проверка: у пользователя есть группа с включённой конфигурацией и нет другой сессии `NEW`. Запрос создаёт его сессию в состоянии `NEW` с задачами выбранного состава. Недоступная конфигурация не должна приводить к созданию набора.

## SR-SES-002. Одна незавершённая сессия

Ограничение относится к пользователю, а не к вкладке браузера или имени конфигурации. Без него можно было бы обходить общий срок, создавая несколько наборов и выбирая удобный для продолжения. Незавершённой считается сессия в состоянии `NEW`; наличие уже неверно решённой задачи не завершает весь набор, пока другие задачи ещё решаются. Это различие раскрывает [правило итога сессии](#sr-ses-007-итог-сессии).

**Требование.** При наличии у пользователя сессии `NEW` система должна отклонять создание новой сессии.

Два одновременных нажатия на создание набора должны приводить к одному и тому же ограничению, что и два последовательных обращения. Предварительная проверка наличия сессии сама по себе не защищает от параллельных запросов: проверку и создание нужно рассматривать совместно. Если прежний набор уже просрочен, сначала применяется [порядок завершения по сроку](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#4-контроль-срока-и-итог). Своевременный ответ в обработке сохраняет незавершённость набора до определения результата.

Основание: `[TS.REQ.FUNC.SESSION.CREATE]`; ограничение активных сессий в карточке домена.

Проверка: последовательные и одновременные запросы одного пользователя не создают две незавершённые сессии. Если прежняя сессия просрочена, её состояние сначала приводится в соответствие с правилами завершения.

## SR-SES-003. Принадлежность и состояние сессии

Идентификатор задачи указывает объект операции, но не подтверждает право пользователя работать с ним. Проверка должна пройти по цепочке «задача — сессия — владелец» и сопоставить владельца с личностью из механизма аутентификации. Эти сведения нельзя брать из переданного клиентом имени или `userId`. Общий принцип установлен в [требовании единой личности пользователя](Интеграция.md#sr-sys-001-единая-личность-пользователя).

**Требование.** Система должна допускать ответ к предметной проверке только для задачи собственной сессии текущего пользователя, если сессия находится в состоянии `NEW`.

Для собственного набора дополнительно проверяется состояние сессии. Завершённая сессия сохраняет результаты, но уже не принимает решения. Обращение к чужому заданию не должно запускать математический проверяющий и изменять данные. Внешний отказ задан в [контракте ошибок](../07_Программные_требования/Контракты_сессий.md#коды-и-представление-ошибок); доступ к результатам собственной завершённой сессии сохраняется через [операцию чтения](#sr-ses-014-получение-сохранённого-результата).

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; сценарий отправки ответа.

Проверка: обращение к задаче чужой или завершённой сессии отклоняется до предметной проверки; её данные и результаты не меняются. Срок и состояние самой задачи дополнительно проверяются по SR-SES-006, SR-SES-008 и SR-SES-011.

## SR-SES-004. Выбор предметной проверки

Домен сессий управляет жизненным циклом задачи, но не решает, верно ли выполнен криптографический расчёт. Для этого существуют предметные проверяющие. Сессия передаёт им сохранённое условие и ответ пользователя, а получает вердикт либо категорию отказа. Такой внешний контракт позволяет описывать криптографические домены как самостоятельные части без переноса их алгоритмов в системные требования.

**Требование.** Для допустимого ответа система должна выбирать проверку по типу сохранённой задачи и передавать ей условие этой задачи и полученный ответ.

Ответ на задачу Эль-Гамаля не должен попасть в проверяющий ранцевой задачи даже тогда, когда клиент указал в теле иной тип. Источник выбора — сохранённая задача. Содержимое и типы полей раскрыты в [предметном контракте ответа](../07_Программные_требования/Контракты_сессий.md#предметный-ответ), а порядок вызова — в [программном требовании передачи проверке](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-010-передача-профильной-проверке). Недоступность нужного обработчика означает технический отказ, а не неверное решение.

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; ответственность криптографических доменов в карточке сессий.

Проверка: для каждого поддерживаемого типа вызывается соответствующая предметная проверка. Тип, указанный пользователем в ответе, не должен подменять тип выбранной задачи.

## SR-SES-005. Результат задачи

Получение вердикта от математического проверяющего ещё не завершает пользовательскую операцию. Результат должен стать частью данных задачи и согласоваться с состоянием её сессии. Иначе пользователь мог бы увидеть успешный ответ, а после перезагрузки — другое состояние. Граница подтверждения определяется [требованием согласованности результата и состояния](Интеграция.md#sr-sys-005-согласованность-результата-и-состояния).

**Требование.** После завершённой предметной проверки система должна сохранить задаче `SOLVED` при верном ответе либо `FAILED` при неверном и вернуть результат, относящийся к этой задаче.

При верном ответе сохраняются `SOLVED` и положительный предметный результат. При неверном — `FAILED` и отрицательный результат с пояснением. Дальше пересчитывается итог сессии: отдельная ошибка не закрывает оставшиеся задачи. Повторное чтение возвращает уже сохранённый результат, не обращаясь к проверяющему. Различия полей результата и технического отказа приведены в [контракте результата](../07_Программные_требования/Контракты_сессий.md#результат-и-отказы).

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; сценарий проверки ответа.

Проверка: результат содержит идентификатор и тип проверенной задачи; сохранённое состояние соответствует вердикту. Технический сбой без вердикта обрабатывается по SR-SES-010.

## SR-SES-006. Общий срок сессии

Срок относится ко всему набору. Он отсчитывается от одного серверного времени создания сессии, поэтому получение новых данных, перезагрузка страницы или повтор запроса не создают новый интервал решения. Клиент может отображать оставшееся время, но допуск определяет сервер. Обозначения `t0`, `D` и `t_in` введены в [карточке домена](../03_Карточки_доменов/Сессии_задач.md#срок-и-попытка).

**Требование.** Система должна ограничивать решение всех задач единым сроком: 20 минут от серверного времени создания сессии. По достижении срока незавершённые задачи без своевременного ответа в обработке должны завершаться с `FAILED`, а ранее определённые результаты — сохраняться.

Нужно различать конец времени решения и момент фоновой записи просрочки. Планировщик может обновить хранилище позднее, но это не разрешает новые поздние ответы. При этом уже полученный своевременный ответ защищён от назначения просрочки, пока обрабатывается в допустимых пределах. Его поведение определяет [правило момента приёма](#sr-ses-011-момент-приёма-ответа), а окончание ожидания — [предел обработки](#sr-ses-012-ограниченная-длительность-обработки).

Основание: сценарий срока в карточке домена; `[TS.REQ.FUNC.SESSION.TIME]`. Все задачи набора получают время создания сессии как начало отсчёта своего срока.

Проверка: задачи одной сессии имеют один срок. Обновление страницы и повторы запроса его не меняют. После срока необработанные задачи получают `FAILED`; своевременно полученный ответ обрабатывается по SR-SES-011. Задержка фоновой обработки не разрешает новые ответы после срока.

## SR-SES-007. Итог сессии

Состояние сессии подводит итог всему набору и не копируется из последней обработанной задачи. Для этого система рассматривает состояния всех задач. Пока хотя бы одна задача не имеет итогового состояния, набор остаётся незавершённым. Остальные задачи сохраняют свои состояния и, если предметная проверка состоялась, зафиксированные вердикты. У завершённой по просрочке задачи состояние `FAILED`, но предметный вердикт отсутствует.

**Требование.** После завершения всех задач система должна устанавливать сессии `SOLVED`, если все задачи имеют `SOLVED`, и `FAILED`, если хотя бы одна задача имеет `FAILED`.

Если ранцевая задача решена неверно, а ответ на Эль-Гамаля ещё проверяется, итог сессии пока `NEW`. После завершения этой проверки набор получит `FAILED` из-за ранцевой задачи, даже при верном втором ответе. Успешный итог возможен только при успехе каждой задачи. Одинаковое агрегирование после ответа и планировщика закреплено в [общей функции итога](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-018-общая-функция-итога-сессии).

Основание: `[TS.REQ.FUNC.SESSION.SUBMIT]`; правило завершения в карточке домена.

Проверка: рассматриваются все верные ответы, наличие неверного ответа и наличие просрочки. Пока есть задача без итогового состояния, в том числе своевременный ответ в обработке, сессия остаётся `NEW`.

## SR-SES-008. Одна предметная попытка

Попытка означает предметный результат, зафиксированный для задачи. Она не равна числу HTTP-запросов: запрос может быть отклонён до проверки, а вычисление — прерваться без сохранения вердикта. Связь попытки с фиксацией нужна и для восстановления после сбоя. Термины используются одинаково в карточке, системных требованиях и [контракте принятой операции](../07_Программные_требования/Контракты_сессий.md#принятая-обработка-и-восстановление).

**Требование.** Система должна фиксировать не более одного предметного вердикта для каждой задачи; после получения итогового состояния повторный ответ не должен его изменять.

Повтор после сохранённого вердикта не даёт ещё одной возможности изменить результат. Одновременная отправка тоже не должна создать два независимых итога. Если же первая операция завершилась ошибкой формата или техническим отказом без вердикта, действует правило нового обращения в пределах общего срока. Эти случаи описаны в [обработке формата](#sr-ses-009-ошибка-формата) и [обработке технического сбоя](#sr-ses-010-технический-сбой-проверки).

Основание: правило попытки в карточке домена.

Проверка: повторные и одновременные отправки не приводят к двум предметным вердиктам. Ответ после `SOLVED` или `FAILED` отклоняется, результат сохраняется. Исключения без расходования попытки определены в SR-SES-009 и SR-SES-010.

## SR-SES-009. Ошибка формата

Проверка формата отвечает на вопрос, можно ли передать данные предметному алгоритму. Она проверяет наличие тела, обязательных полей и ожидаемые типы данных. Правильно оформленный, но математически неверный расчёт относится уже к предметной проверке. Структура обоих поддерживаемых видов решения определена в [контракте ответа](../07_Программные_требования/Контракты_сессий.md#предметный-ответ).

**Требование.** Система должна отклонять запрос с некорректным форматом или отсутствующим обязательным полем до предметной проверки, сообщать причину и сохранять неиспользованную попытку.

Например, отсутствующее обязательное поле не должно автоматически давать задаче `FAILED` как неверно решённой. Клиент получает категорию ошибки и может исправить запрос до общего срока. Время не начинается заново: исправленный запрос имеет собственный момент поступления. Если он получен после `D`, применяется [правило своевременности](#sr-ses-011-момент-приёма-ответа), независимо от времени первого обращения.

Основание: правило обработки ошибок в карточке домена.

Проверка: неверно оформленный ответ не получает предметного вердикта. Исправленный ответ допускается, если новый запрос получен до срока и выполнены остальные условия. Состояние `NEW` сохраняется, пока задача не завершена по другому основанию; сама ошибка срока не продлевает.

## SR-SES-010. Технический сбой проверки

Технический отказ означает, что система не получила и не зафиксировала предметный результат. Причиной может стать недоступность проверяющего, прерванное вычисление или невозможность сохранить результат. Такой отказ не устанавливает правильность ответа пользователя и не должен маскироваться под отрицательный вердикт. Внешние категории разделены в [таблице ошибок](../07_Программные_требования/Контракты_сессий.md#коды-и-представление-ошибок).

**Требование.** Если проверка не завершилась вердиктом из-за технического сбоя, система должна сообщить о сбое и сохранить неиспользованную предметную попытку.

Сохранённая попытка не даёт бессрочного права продолжать набор. До `D` пользователь может отправить новый допустимый ответ; после `D` такой запрос будет поздним. Если прежний своевременный запрос уже исчерпал [предел обработки](#sr-ses-012-ограниченная-длительность-обработки), его поздний результат не записывается. Порядок возобновления после перезапуска раскрыт в [требовании восстановления](#sr-ses-013-восстановление-принятого-ответа).

Основание: правило технического сбоя в карточке домена.

Проверка: до срока возможен новый допустимый запрос. Если сбой своевременной проверки обнаружен после срока, новый ответ уже не принимается, а незавершённая задача закрывается по просрочке. Ошибка сервера не считается неверным предметным ответом.

## SR-SES-011. Момент приёма ответа

Пользователь не управляет длительностью серверной очереди и математической проверки. Поэтому своевременность связывается с получением полного запроса сервером, а не с окончанием вычисления. Отметка времени на устройстве пользователя для такого решения не подходит: система использует собственное `t_in` и сравнивает его с общим сроком.

**Требование.** Система должна считать ответ своевременным, если полный запрос получен сервером строго до общего срока сессии, и сохранять право на его проверку после наступления этого срока.

Ответ, полученный до `D`, может завершиться вердиктом после `D`, если результат зафиксирован до `t_in + 60 секунд`. После этого предела поздний вердикт не сохраняется; действует [ограничение обработки SR-SES-012](#sr-ses-012-ограниченная-длительность-обработки). Запрос, полученный точно в `D`, уже не допускается. Эти события нельзя объединять в одну проверку состояния `NEW`: запись фоновой просрочки может ещё не выполниться. Регистрацию времени и защиту от планировщика связывают [учёт поступления](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-007-регистрация-времени-поступления) и [завершение своевременной проверки](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-015-завершение-своевременной-проверки).

Основание: раздел «Срок и попытка» карточки домена.

Проверка: ответ получен за секунду до срока, а вердикт готов через секунду после него — вердикт принимается. Запрос, полученный точно в срок или позднее, отклоняется. Зафиксированное сервером время получения, а не время окончания проверки или часы пользователя, определяет своевременность.

Своевременность не отменяет проверок принадлежности, состояния и формата. Ожидание работы сервера не создаёт дополнительной попытки. Программные связи всех требований приведены в [DOC-06.2](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#6-трассировка-и-описательные-проверки).

## SR-SES-012. Ограниченная длительность обработки

Право завершить своевременную проверку после общего срока не означает неограниченное ожидание. У принятой операции есть собственный предел, который включает очередь, вычисление и восстановление. Система должна иметь определённый исход и тогда, когда проверяющий завис или не смог вернуть ответ. Этот предел отличается от периода запуска фонового планировщика.

**Требование.** Система должна фиксировать результат обработки принятого ответа до момента «получение запроса + 60 секунд». Начиная с этого момента операция без сохранённого вердикта завершается техническим отказом без расходования предметной попытки.

Если результат не зафиксирован до `t_in + 60 секунд`, операция прекращается с техническим отказом. Вычисление, закончившееся позже, уже не меняет задачу. Далее учитывается общий срок: до `D` возможен новый запрос, после `D` задача закрывается по просрочке. Обе временные границы сопоставлены в [программном правиле предела обработки](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-020-предел-обработки).

Основание: правило ограниченной обработки в карточке домена; обработка технического сбоя по SR-SES-010.

Проверка: задержка проверяющего или очереди не оставляет задачу в бессрочном ожидании. После технического отказа повтор допустим до общего срока; после него задача завершается по просрочке. Вердикт, поступивший после прекращения обработки, не изменяет итог.

## SR-SES-013. Восстановление принятого ответа

После приёма своевременного ответа его дальнейшая судьба не должна зависеть только от памяти работающего процесса. До математического вычисления сохраняются входные данные и временные отметки. При перезапуске система различает операцию с уже записанным результатом и принятую операцию, которая ещё не закончилась.

**Требование.** После перезапуска система должна продолжать обработку сохранённого своевременного ответа, если его 60-секундный срок ещё не истёк, используя прежнее условие, ответ и время получения.

Операция без результата продолжается по тому же ответу и условию, если её собственный срок ещё действует. Истёкшая операция завершается техническим отказом; время поступления не заменяется временем запуска приложения. Уже записанный вердикт повторно не расходует попытку. Программная запись операции определена в [требовании сохранения принятого ответа](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-021-запись-принятой-операции), а получение готового итога — в [чтении результата](#sr-ses-014-получение-сохранённого-результата).

Основание: правило восстановления в карточке домена; `[TS.REQ.REL.PERSIST]`.

Проверка: перезапуск до фиксации результата не начинает заново срок сессии и обработки. Уже сохранённый вердикт не вычисляется повторно как новая попытка. Если срок обработки истёк, применяется SR-SES-012.

## SR-SES-014. Получение сохранённого результата

Сохранение результата и доставка HTTP-ответа — разные события. Соединение может пропасть после записи вердикта, и клиент останется без ответа, хотя задача уже завершена. Повторная отправка решения здесь непригодна: она должна быть отклонена как обращение к завершённой задаче. Для восстановления отображения используется отдельное чтение сессии.

**Требование.** Система должна предоставлять пользователю состояние собственной сессии и сохранённые результаты её задач по идентификатору сессии, в том числе после потери соединения или перезапуска.

Пользователь получает данные своего набора, состояния задач и их сохранённые предметные результаты. Срок ограничивает новые решения, но не закрывает чтение уже полученных итогов. Поэтому после перезапуска клиент может восстановить картину без математического пересчёта и новой попытки. Поля ответа описаны в [контракте чтения](../07_Программные_требования/Контракты_сессий.md#чтение-после-потери-ответа), а программная операция — в [требовании получения сессии](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-023-чтение-сессии-и-результата).

Основание: сохранность результатов по SR-SYS-007; сценарий восстановления карточки домена.

Проверка: вердикт сохранён, но ответ на запрос не доставлен клиенту. Чтение сессии возвращает тот же вердикт без новой предметной попытки. Получение результата после общего срока разрешено; чужая сессия недоступна.

## Пояснения к состояниям и попытке

Состояние `NEW` показывает отсутствие итогового результата. Оно не означает безусловного разрешения отправить ответ: дополнительно проверяются владелец, срок и наличие уже обрабатываемого ответа. Поэтому даже при задержке фонового завершения задача не получает дополнительного времени решения.

Предметная попытка завершается фиксацией результата проверки правильности. В неверно оформленном запросе такого результата нет; технический отказ также не устанавливает, правильно ли решена задача. Повтор после этих событий представляет новый запрос, своевременность которого проверяется заново. Он не наследует время поступления предыдущего запроса.

У своевременного допустимого ответа сохраняется право на завершение проверки. Состояние задачи в этот промежуток ещё не итоговое, но новая отправка не должна создавать вторую завершённую проверку. Внешнее обязательство системы состоит в сохранении единственного предметного результата; механизм согласования задаётся на программном уровне.

Просрочка и неверное решение приводят к одному итоговому состоянию `FAILED`, но основания различаются. Неверное решение связано с предметным вердиктом, а просрочка — с прекращением возможности решения по общему сроку. Это различие сохраняется в описании проверок и диагностике операции.

## Сочетания событий для проверки раздела

Приведённые сочетания раскрывают требования, а не вводят отдельные TC. При подготовке DOC-10 для них нужно задать исходное состояние, действие и наблюдаемый результат.

| Последовательность событий | Ожидаемый результат |
|---|---|
| Создан набор; один ответ неверный; остальные задачи ещё `NEW` | Задача завершена с `FAILED`, сессия остаётся `NEW` |
| Все задачи проверены верно | Задачи и сессия имеют `SOLVED` |
| Все задачи завершены, хотя бы одна неверно | Итог сессии `FAILED` |
| Некорректный запрос получен до срока; исправленный запрос тоже получен до срока | Первый запрос не расходует попытку; второй допускается при соблюдении остальных условий |
| Технический сбой произошёл до срока; новый запрос получен после срока | Новый ответ отклоняется, несмотря на сохранённую предметную попытку |
| Допустимый ответ получен до срока; пока он проверяется, наступает срок | Задача ожидает вердикт, планировщик не завершает её по просрочке |
| Своевременная проверка после срока закончилась техническим сбоем | Предметного вердикта нет; новый ответ не допускается, задача завершается по просрочке |
| Отправлен ответ на задачу с итоговым состоянием | Результат сохраняется без повторной предметной проверки |

Для общего срока важно рассматривать не только момент запроса, но и состояние других задач сессии. Завершение одной проверки не должно закрывать сессию, пока для другой задачи остаётся своевременный ответ в обработке. Аналогично окончание срока не изменяет уже определённые результаты.
