## 1. Назначение и состав

Документ определяет программные обязанности при создании сессии, обработке ответа, учёте срока и завершении задач. Он раскрывает [системные требования сессий](../04_Системные_требования/Сессии_задач.md), [требования интеграции](../04_Системные_требования/Интеграция.md) и [общие программные требования](DOC-06_Программные_требования.md).

| Логическая часть | Ответственность |
|---|---|
| Приём пользовательской операции | Получить подтверждённого пользователя, параметры и время поступления ответа |
| Создание сессии | Проверить конфигурацию и ограничение активных сессий, сформировать и сохранить набор |
| Обработка ответа | Проверить допуск, вызвать предметную проверку, сохранить результат |
| Контроль срока | Завершить просроченные задачи, учитывая своевременные ответы в обработке |
| Вычисление итога | Определить состояние сессии по состояниям её задач |
| Хранение | Согласовать изменения и сохранить данные для последующих операций |

Это распределение обязанностей; оно не задаёт имена классов, таблиц или число процессов. Для внешних участников используется [контракт операций](Контракты_сессий.md). Внутренняя последовательность и согласование параллельных действий определены ниже.

### Данные и их жизненный цикл

Сессия связывает владельца, время создания и состав задач. Для каждой задачи сохраняются принадлежность сессии, условие, тип и состояние. После выдачи набора условие и тип используются при проверке того же задания; они не восстанавливаются заново из текущей конфигурации группы.

Обработка ответа использует дополнительные сведения об операции: момент получения запроса и факт его незавершённой обработки. Эти сведения нужны для согласования с контролем срока и не вводят новое публичное состояние задачи. Пока предметный итог не определён, задача остаётся `NEW`.

Окончание обработки и изменение предметного состояния — связанные события. Вердикт завершает попытку и определяет состояние задачи. Ошибка формата и технический сбой без вердикта прекращают текущую обработку без расхода попытки; после срока к незавершённой задаче применяется правило просрочки. Поэтому снятие отметки об обработке также должно учитываться контролем срока.

## 2. Создание сессии

Приоритет всех программных требований документа — обязательный. Источники SR указывают на определения в DOC-05. Описания проверок находятся в разделе 6.

### SWR-SES-001. Получение пользователя

Обработчик создания и отправки ответа должен получать пользователя через компонент проверки доступа до обращения к его сессиям.

Источники: SR-SES-003, SR-SYS-001.

### SWR-SES-002. Выбор доступной конфигурации

Создание сессии должно получать состав выбранной конфигурации по группе подтверждённого пользователя и отклонять запрос при отсутствии группы или включённой конфигурации с указанным именем.

Источники: SR-SES-001, SR-SYS-003.

### SWR-SES-003. Защита от двух активных сессий

Проверка отсутствия сессии `NEW` и создание новой выполняются в транзакции под блокировкой строки пользователя, не допускающей две активные сессии при одновременных запросах.

Источник: SR-SES-002. Перед проверкой учитывается завершение просроченной сессии. Сессия с обрабатываемым своевременным ответом остаётся незавершённой.

### SWR-SES-004. Формирование задач

Создание должно получать условия у обработчиков типов, заданных выбранной конфигурацией, и сохранять состав сессии вместе с условиями, типами и принадлежностью задач.

Источники: SR-SES-001, SR-SYS-002, SR-SYS-003, SR-SYS-004. Последующее изменение конфигурации не должно подменять выданные условия.

### SWR-SES-005. Сохранение созданного набора

Компонент создания должен подтверждать операцию только после согласованного сохранения полного набора. Ошибка генерации или сохранения не должна оставлять пользователю частично созданную активную сессию.

Источники: SR-SES-001, SR-SYS-005. Сохранение набора выполняется одной транзакцией PostgreSQL; ошибка откатывает создание сессии и её задач.

### SWR-SES-006. Сохранение времени создания

При создании набора ПО должно зафиксировать серверное время создания сессии и использовать его для общего срока `D`, определённого в карточке домена. Время не изменяется при чтении, ошибках, перезапуске или повторном обращении.

Источники: SR-SES-006, SR-SYS-006, SR-SYS-007.

## 3. Обработка ответа

### SWR-SES-007. Регистрация времени поступления

ПО должно фиксировать время получения полного запроса сервером до ожидания предметной проверки и сохранять связь этой отметки с обрабатываемым ответом. Время запуска проверяющего не должно подменять время поступления.

Источники: SR-SES-011, SR-SYS-006. Сведения о своевременном запросе должны учитываться при согласовании с контролем срока. Отметка клиента не используется как основание допуска.

### SWR-SES-008. Проверка допуска

Обработка ответа должна проверять наличие задачи, принадлежность сессии текущему пользователю, состояния задачи и сессии и время поступления запроса до вызова предметного проверяющего.

Источники: SR-SES-003, SR-SES-008, SR-SES-011. Для своевременного ответа учитывается его зарегистрированная обработка; фоновая просрочка не должна преждевременно лишать его допуска.

### SWR-SES-009. Проверка формата

ПО должно проверять формат и обязательные поля ответа по схеме сохранённого типа задачи до предметного вердикта. Синтаксическую ошибку нельзя передавать как неверное решение.

Источники: SR-SES-009, SR-SYS-009. Набор и типы обязательных полей определены в контракте сессий.

### SWR-SES-010. Передача профильной проверке

ПО должно передавать проверяющему сохранённое условие выбранной задачи и полученный ответ, определяя обработчик по сохранённому типу задачи.

Источники: SR-SES-004, SR-SYS-004. Неизвестный тип или недоступный обработчик должны приводить к техническому отказу без предметного вердикта.

### SWR-SES-011. Сохранение вердикта

После завершённой предметной проверки ПО должно сохранить `SOLVED` при вердикте «верно» или `FAILED` при вердикте «неверно», вычислить соответствующее состояние сессии и только затем подтвердить результат операции.

Источники: SR-SES-005, SR-SES-007, SR-SYS-005. Результат содержит идентификатор и тип проверенной задачи по контракту.

### SWR-SES-012. Согласование одновременных обращений

ПО должно согласовывать обращения к одной задаче так, чтобы одновременно полученные ответы не приводили к двум завершённым предметным проверкам или перезаписи итогового результата.

Источник: SR-SES-008. Для фиксации используется короткая транзакция с блокировкой сначала строки сессии, затем задачи и записи операции; предметное вычисление выполняется вне этой транзакции. Повторное обращение к занятой задаче возвращает `CHECK_IN_PROGRESS`. При параллельном завершении разных задач итог вычисляется по согласованному набору их состояний под блокировкой сессии.

### SWR-SES-013. Сохранение итогового состояния

Для задачи в `SOLVED` или `FAILED` обработчик должен отклонять новый ответ, сохраняя существующий результат без повторной предметной проверки.

Источники: SR-SES-008, SR-SYS-005.

### SWR-SES-014. Отказ без расхода попытки

При ошибке формата или техническом сбое без вердикта ПО должно сообщать соответствующую категорию отказа и сохранять неиспользованную попытку. До срока задача остаётся `NEW`, если не завершена по другому основанию.

Источники: SR-SES-009, SR-SES-010, SR-SYS-009. После срока отсутствие допустимой незавершённой проверки приводит к завершению по просрочке; отказ не продлевает срок.

### SWR-SES-015. Завершение своевременной проверки

ПО должно принимать вердикт допустимого ответа с `t_in < D`, даже если проверка закончилась при `t >= D`. Регистрация и завершение такой проверки должны быть согласованы с фоновым контролем срока.

Источники: SR-SES-011, SR-SYS-006. Пока своевременный запрос проходит проверки допуска и формата либо предметную проверку, его задаче нельзя назначать итог по просрочке. Если запрос отклонён или проверка завершилась техническим сбоем после срока, защита от просрочки прекращается; новый ответ после срока не допускается.

## 4. Контроль срока и итог

### SWR-SES-016. Фоновый контроль

ПО должно выполнять фоновую обработку просроченных задач с плановым периодом 60 секунд и отдельно проверять срок при допуске каждого нового ответа.

Источники: SR-SES-006, SR-SYS-006; период задан `[TS.REQ.FUNC.SESSION.TIME]`. Период фоновой обработки не предоставляет пользователю дополнительное время между сроком и очередным запуском.

### SWR-SES-017. Завершение по просрочке

При обработке просрочки ПО должно переводить в `FAILED` только задачи `NEW`, срок которых наступил и для которых нет своевременного запроса в обработке. Итоговые результаты остальных задач должны сохраняться.

Источники: SR-SES-006, SR-SES-011. После отказа незавершённой проверки за пределами срока задача подлежит этому же правилу.

### SWR-SES-018. Общая функция итога сессии

Обработка ответа и контроль срока должны применять одно правило: пока есть задача без итогового состояния, сессия `NEW`; когда все задачи завершены, сессия `SOLVED`, только если все задачи `SOLVED`, иначе `FAILED`.

Источники: SR-SES-007, SR-SYS-005, SR-SYS-006.

### SWR-SES-019. Сохранность данных

Хранение должно сохранять идентификаторы, принадлежность, состав, условия, серверное время создания и определённые состояния сессии и задач между запусками приложения.

Источники: SR-SYS-002, SR-SYS-007. Принятые ответы сохраняются до вычисления и восстанавливаются по SWR-SES-021.

### SWR-SES-020. Предел обработки

ПО должно ограничивать всю обработку принятого ответа сроком `t_in + 60 секунд`. Результат может быть зафиксирован только до этого момента. По достижении срока незавершённая операция получает `CHECK_TIMEOUT`; её поздний результат отбрасывается без изменения задачи.

Источники: SR-SES-010, SR-SES-012. Ожидание очереди, вычисление и восстановление входят в один срок; повторный запуск его не продлевает. После отказа применяется общее правило срока сессии.

### SWR-SES-021. Запись принятой операции

До предметной проверки ПО должно сохранить запись операции с UUID, владельцем, задачей, ответом, `t_in`, сроком обработки и признаком незавершённости. Фиксация вердикта и завершение записи операции выполняются в одной транзакции с изменением состояний задачи и сессии.

Источники: SR-SES-008, SR-SES-013, SR-SYS-005, SR-SYS-007. При запуске приложения незавершённые операции с неистёкшим сроком продолжаются по сохранённым данным. Получение записи обработчиком согласуется блокировкой, исключающей две одновременно выполняемые обработки. Уже зафиксированный результат не создаёт новой предметной попытки. Операции с истёкшим сроком завершаются по SWR-SES-020.

### SWR-SES-022. Форматы и категории API

Приём операций должен применять обязательные поля, представление времени и целых чисел, предел тела и соответствие ошибок HTTP-кодам из контракта сессий. Повторяющийся параметр конфигурации отклоняется до создания набора.

Источники: SR-SES-009, SR-SYS-008, SR-SYS-009. Ошибки формата и превышения размера не запускают предметную проверку. Неизвестный тип в сохранённой конфигурации даёт технический отказ без частичной сессии.

### SWR-SES-023. Чтение сессии и результата

ПО должно предоставлять `GET /api/tasks/session/{sessionId}` для чтения собственной сессии с состояниями задач и сохранёнными предметными результатами. При отсутствии сессии у текущего пользователя возвращается `SESSION_NOT_FOUND`.

Источники: SR-SES-014, SR-SYS-002, SR-SYS-007, SR-SYS-008. Чтение не расходует попытку и доступно после общего срока. Перед формированием ответа состояние просроченных задач приводится к правилу SWR-SES-017 с сохранением своевременных обработок. Сохранённый вердикт возвращается без повторного вычисления.

## 5. Временные границы

Обозначения и длительность заданы в [карточке домена](../03_Карточки_доменов/Сессии_задач.md#срок-и-попытка).

| Ситуация | Ожидаемое действие |
|---|---|
| Запрос получен до `D`, проверка завершена до `D` | Сохранить предметный результат |
| Запрос получен до `D`, проверка завершена после `D` | Сохранить предметный результат; не заменять его просрочкой |
| Запрос получен точно в `D` или позже | Отклонить новый ответ по сроку |
| Своевременный запрос оказался некорректным до `D` | Сообщить ошибку; исправленный новый запрос возможен до `D` |
| Некорректный запрос или технический сбой обнаружены после `D` | Сообщить категорию отказа; завершить незавершённую задачу по просрочке, если нет другой допустимой проверки |
| Планировщик запущен во время своевременной проверки | Не назначать этой задаче `FAILED` по времени |
| Планировщик задержался | Отклонять новые поздние ответы независимо от состояния фоновой обработки |

### Согласование параллельных событий

Конкурировать могут два ответа на одну задачу, ответы на разные задачи одной сессии, ответ и контроль просрочки, а также два запроса создания набора. В каждом случае требуется сохранить определённый системой результат. Выбор блокировок или другого механизма не должен изменять правило одной попытки и общего срока.

Для одной задачи окончательный предметный вердикт определяется не более одного раза. Пока первый допустимый ответ обрабатывается, другое обращение не должно независимо завершать вторую предметную проверку. Если первый запрос закончился без вердикта до срока, возможность нового допустимого обращения сохраняется по общим правилам.

При параллельной проверке разных задач согласование необходимо на уровне сессии. Завершение последней задачи должно учитывать уже определённые результаты остальных. Сохранение одного вердикта не должно перезаписывать итог, вычисленный без учёта другой завершившейся задачи.

При конкуренции ответа и планировщика существенен момент поступления запроса. Своевременный запрос сохраняет право пройти проверки допуска и формата и, если они успешны, получить предметный вердикт. Ответ, поступивший после срока, этого права не получает даже при ещё не обновлённом состоянии задачи в хранилище.

### Переходы состояния задачи

| Исходное состояние и событие | Следующее состояние | Значение для попытки |
|---|---|---|
| `NEW`, допустимый ответ признан верным | `SOLVED` | Предметная попытка завершена |
| `NEW`, допустимый ответ признан неверным | `FAILED` | Предметная попытка завершена |
| `NEW`, ошибка формата до срока | `NEW`, если нет другого основания завершения | Попытка сохраняется |
| `NEW`, технический сбой без вердикта до срока | `NEW`, если нет другого основания завершения | Попытка сохраняется |
| `NEW`, наступил срок, своевременного запроса в обработке нет | `FAILED` | Завершение по сроку, без нового предметного вердикта |
| `NEW`, срок наступил во время своевременной проверки | `NEW` до завершения обработки | Ожидание единственного результата |
| `SOLVED` или `FAILED`, новый ответ | Прежнее итоговое состояние | Повторная проверка не допускается |

Для сессии используется агрегирование состояний задач по SWR-SES-018. Программная реализация не должна считать любой набор завершённых задач успешным: наличие хотя бы одной `FAILED` определяет итог `FAILED`. Это правило одинаково после предметной проверки и после фоновой обработки.

### Проверка длительной обработки

Для требования своевременности нужно рассматривать получение запроса, запуск проверяющего, наступление срока и сохранение вердикта как отдельные события. Условие `t_in < D` проверяется по первому из них. Задержка между событиями не изменяет сохранённую отметку времени и не разрешает вторую попытку.

Отдельно рассматривается своевременная обработка, завершившаяся отказом после срока. Предметный результат в этом случае отсутствует, но срок для нового запроса уже закончился. Требования сохраняют различие причин: технический сбой не становится неверным решением, а последующее завершение задачи происходит по просрочке.

## 7. Полнота описания подсистемы

Контракт задаёт создание, отправку ответа и чтение сессии, входные данные, результаты и категории отказов. Программные требования охватывают создание, предметную проверку, ограничение времени, параллельные обращения, сохранение и восстановление. Предел обработки и фоновый период имеют разные назначения, хотя оба составляют 60 секунд: первый ограничивает одну операцию, второй задаёт частоту фонового контроля общего срока.
