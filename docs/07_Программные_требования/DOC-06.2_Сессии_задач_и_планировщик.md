## 1. Назначение и состав

Документ определяет программные обязанности при создании сессии, обработке ответа, учёте срока и завершении задач. Он раскрывает [системные требования сессий](../04_Системные_требования/Сессии_задач.md), [требования интеграции](../04_Системные_требования/Интеграция.md) и [общие программные требования](DOC-06_Программные_требования.md).

| Логическая часть | Ответственность |
|---|---|
| Приём пользовательской операции | Получить подтверждённого пользователя, параметры и время поступления ответа |
| Создание сессии | Проверить конфигурацию и ограничение активных сессий, сформировать и сохранить набор |
| Обработка ответа | Проверить допуск, вызвать предметную проверку, сохранить результат |
| Контроль срока | Завершить просроченные задачи, учитывая своевременные ответы в обработке |
| Вычисление итога | Определить состояние сессии по состояниям её задач |
| Хранение | Согласовать изменения и сохранить данные для последующих операций |

Это распределение обязанностей; оно не задаёт имена классов, таблиц или число процессов. Для внешних участников используется [контракт операций](Контракты_сессий.md). Внутренняя последовательность и согласование параллельных действий определены ниже.

### Данные и их жизненный цикл

Сессия связывает владельца, время создания и состав задач. Для каждой задачи сохраняются принадлежность сессии, условие, тип и состояние. После выдачи набора условие и тип используются при проверке того же задания; они не восстанавливаются заново из текущей конфигурации группы.

Обработка ответа использует дополнительные сведения об операции: момент получения запроса и факт его незавершённой обработки. Эти сведения нужны для согласования с контролем срока и не вводят новое публичное состояние задачи. Пока предметный итог не определён, задача остаётся `NEW`.

Окончание обработки и изменение предметного состояния — связанные события. Вердикт завершает попытку и определяет состояние задачи. Ошибка формата и технический сбой без вердикта прекращают текущую обработку без расхода попытки; после срока к незавершённой задаче применяется правило просрочки. Поэтому снятие отметки об обработке также должно учитываться контролем срока.

## 2. Создание сессии

Приоритет всех программных требований документа — обязательный. Источники SR указывают на определения в DOC-05. Описания проверок находятся в разделе 6.

### SWR-SES-001. Получение пользователя

Обработчик сессий начинает работу с контекста доступа. Из него он получает пользователя, от имени которого выполняются создание и отправка ответа. Параметры операции описывают выбранную конфигурацию или задачу, но не определяют владельца. Это применение [общего контракта передачи личности](DOC-06_Программные_требования.md#swr-sys-001-передача-личности-пользователя) внутри подсистемы.

**Требование.** Обработчик создания и отправки ответа должен получать пользователя через компонент проверки доступа до обращения к его сессиям.

Далее при создании ищется группа этого пользователя, при ответе проверяется владелец сохранённой сессии. Неуспешная проверка доступа прекращает операцию до предметного вычисления. Пользовательский ID, присланный в теле, не заменяет контекст доступа. Внешние условия определены в [контракте операций](Контракты_сессий.md#операции), а проверка принадлежности задачи — в [порядке допуска ответа](#swr-ses-008-проверка-допуска).

Источники: SR-SES-003, SR-SYS-001.

### SWR-SES-002. Выбор доступной конфигурации

Имя конфигурации выбирает состав нового набора в пределах группы пользователя. Поиск по всему каталогу без учёта группы мог бы выдать недоступное задание. Поэтому управление сессиями сначала получает группу, а затем включённую для неё конфигурацию. Системное назначение такой границы дано в [согласованном составе набора](../04_Системные_требования/Интеграция.md#sr-sys-003-согласованный-состав-набора).

**Требование.** Создание сессии должно получать состав выбранной конфигурации по группе подтверждённого пользователя и отклонять запрос при отсутствии группы или включённой конфигурации с указанным именем.

Отсутствие группы и отсутствие включённой конфигурации прекращают создание до выдачи задач. Клиент получает `CONFIGURATION_NOT_FOUND`, поскольку для него нет доступного состава с указанным именем. После успешного выбора используются полученные данные конфигурации, а не повторные параметры клиента. Дальнейшее формирование описано в [генерации задач](#swr-ses-004-формирование-задач), формат параметра — в [контракте создания](Контракты_сессий.md#операции).

Источники: SR-SES-001, SR-SYS-003.

### SWR-SES-003. Защита от двух активных сессий

Два запроса одного пользователя могут одновременно пройти чтение «активной сессии нет». Если после этого каждый независимо создаст набор, будет нарушено системное ограничение. Поэтому проверка и создание рассматриваются как одна операция под блокировкой пользователя. Параллельность клиентских запросов не должна менять правило [одного незавершённого набора](../04_Системные_требования/Сессии_задач.md#sr-ses-002-одна-незавершённая-сессия).

**Требование.** Проверка отсутствия сессии `NEW` и создание новой выполняются в транзакции под блокировкой строки пользователя, не допускающей две активные сессии при одновременных запросах.

Первый запрос создаёт сессию, второй после получения доступа к данным видит уже существующий набор и получает отказ. Перед решением учитывается завершение старой просроченной сессии, но набор с обрабатываемым своевременным ответом остаётся незавершённым. Общая логика завершения описана в [вычислении итога](#swr-ses-018-общая-функция-итога-сессии), категория отказа — в [таблице ошибок API](Контракты_сессий.md#коды-и-представление-ошибок).

Источник: SR-SES-002. Перед проверкой учитывается завершение просроченной сессии. Сессия с обрабатываемым своевременным ответом остаётся незавершённой.

### SWR-SES-004. Формирование задач

Выбранная конфигурация становится конкретными заданиями через генераторы соответствующих типов. Для каждого задания сохраняются условие, тип и связь с создаваемой сессией. Эти данные нужны и для выдачи пользователю, и для будущего вызова проверяющего. Одно только сохранение имени конфигурации не заменяет сохранения выданного условия.

**Требование.** Создание должно получать условия у обработчиков типов, заданных выбранной конфигурацией, и сохранять состав сессии вместе с условиями, типами и принадлежностью задач.

Если набор содержит ранцевую задачу и Эль-Гамаля, к каждой относится свой генератор и полученное им условие. После выдачи эти условия не генерируются заново при проверке. Соответствие типов задано в [контракте предметного обработчика](DOC-06_Программные_требования.md#swr-sys-004-контракт-предметного-обработчика), а согласованное сохранение полного состава — в [следующем требовании](#swr-ses-005-сохранение-созданного-набора). Неподдерживаемый тип не заменяется другим заданием.

Источники: SR-SES-001, SR-SYS-002, SR-SYS-003, SR-SYS-004. Последующее изменение конфигурации не должно подменять выданные условия.

### SWR-SES-005. Сохранение созданного набора

Пользователь должен получить полный набор по выбранной конфигурации. Частично сохранённая сессия после отказа одного генератора мешала бы повторить создание и не соответствовала бы обещанному составу. Поэтому операция имеет общую границу подтверждения: либо сохранён весь набор, либо создание не считается завершённым.

**Требование.** Компонент создания должен подтверждать операцию только после согласованного сохранения полного набора. Ошибка генерации или сохранения не должна оставлять пользователю частично созданную активную сессию.

Ошибка генерации или записи откатывает создание сессии и её задач. На внешней границе возвращается технический отказ; ограничение активных сессий не должно блокировать пользователя из-за оставшегося частичного набора. Это частный случай [согласованного сохранения](DOC-06_Программные_требования.md#swr-sys-005-согласованное-сохранение). Для уже созданной сессии применяется другой путь — [фиксация результата отдельного ответа](#swr-ses-011-сохранение-вердикта).

Источники: SR-SES-001, SR-SYS-005. Сохранение набора выполняется одной транзакцией PostgreSQL; ошибка откатывает создание сессии и её задач.

### SWR-SES-006. Сохранение времени создания

От времени создания начинается общий интервал решения. Значение должно относиться к сессии и сохраняться вместе с ней, чтобы обработчик ответа, планировщик и восстановление использовали одну основу. Повторное чтение не означает нового создания, а перезапуск приложения не означает начала нового учебного набора.

**Требование.** При создании набора ПО должно зафиксировать серверное время создания сессии и использовать его для общего срока `D`, определённого в карточке домена. Время не изменяется при чтении, ошибках, перезапуске или повторном обращении.

Общий срок вычисляется по сохранённому `t0`; отдельное время создания каждой записи задачи не должно предоставлять ей другой интервал. Момент поступления ответа хранится отдельно и сравнивается с этим сроком. Связь временных величин приведена в [карточке домена](../03_Карточки_доменов/Сессии_задач.md#срок-и-попытка), а действия планировщика — в [завершении по просрочке](#swr-ses-017-завершение-по-просрочке).

Источники: SR-SES-006, SR-SYS-006, SR-SYS-007.

## 3. Обработка ответа

### SWR-SES-007. Регистрация времени поступления

Задача обработчика приёма — сохранить момент получения полного ответа до ожидания очереди и предметного вычисления. Иначе задержка внутри сервера могла бы превратить вовремя отправленное решение в позднее. Используется серверная отметка, связанная с конкретной операцией; время клиента не задаёт право на допуск.

**Требование.** ПО должно фиксировать время получения полного запроса сервером до ожидания предметной проверки и сохранять связь этой отметки с обрабатываемым ответом. Время запуска проверяющего не должно подменять время поступления.

Зафиксированное `t_in` сопровождает запрос при ожидании и восстановлении. По нему проверяются общий срок сессии и предел обработки. Сведения о принятой операции должны быть доступны контролю просрочки, чтобы он не закрыл задачу во время допустимой проверки. Хранение операции описано в [записи принятого ответа](#swr-ses-021-запись-принятой-операции), системное основание — в [правиле своевременности](../04_Системные_требования/Сессии_задач.md#sr-ses-011-момент-приёма-ответа).

Источники: SR-SES-011, SR-SYS-006. Сведения о своевременном запросе должны учитываться при согласовании с контролем срока. Отметка клиента не используется как основание допуска.

### SWR-SES-008. Проверка допуска

До вычисления необходимо установить, какой задаче адресован ответ и допустима ли работа с ней. Проверки связывают подтверждённого пользователя, сохранённую принадлежность и состояния задачи и сессии. Только после этого можно интерпретировать тело решения по нужному предметному типу. UUID сам по себе права доступа не даёт.

**Требование.** Обработка ответа должна проверять наличие задачи, принадлежность сессии текущему пользователю, состояния задачи и сессии и время поступления запроса до вызова предметного проверяющего.

Для чужой задачи используется отказ без раскрытия её данных. Для собственной задачи учитывается также поступление запроса относительно срока и наличие уже принятой обработки. Формат ответа не должен выбираться по произвольному клиентскому типу до установления задачи. Категории отказов приведены в [контракте ошибок](Контракты_сессий.md#коды-и-представление-ошибок), следующая стадия — в [проверке формата](#swr-ses-009-проверка-формата).

Источники: SR-SES-003, SR-SES-008, SR-SES-011. Для своевременного ответа учитывается его зарегистрированная обработка; фоновая просрочка не должна преждевременно лишать его допуска.

### SWR-SES-009. Проверка формата

Транспортный разбор и предметное решение отвечают на разные вопросы. Сначала устанавливается, содержит ли запрос все обязательные поля нужных типов. Затем математический проверяющий определяет правильность расчёта. Неверный JSON нельзя считать неправильным решением задачи: такой запрос ещё не содержит допустимого предметного ответа.

**Требование.** ПО должно проверять формат и обязательные поля ответа по схеме сохранённого типа задачи до предметного вердикта. Синтаксическую ошибку нельзя передавать как неверное решение.

Для ранцевого решения и Эль-Гамаля используются разные структуры из [предметного контракта](Контракты_сессий.md#предметный-ответ). Ошибка синтаксиса, отсутствующее поле или неверный тип дают `INVALID_REQUEST` без расхода попытки. Корректные по форме значения с неверными математическими связями передаются предметной проверке. Результаты этих стадий различаются по [общему правилу категории операции](DOC-06_Программные_требования.md#swr-sys-007-категория-результата-операции).

Источники: SR-SES-009, SR-SYS-009. Набор и типы обязательных полей определены в контракте сессий.

### SWR-SES-010. Передача профильной проверке

После допуска и проверки формата управление сессиями вызывает предметный обработчик. Выбор делается по сохранённому типу задачи, а проверка получает её сохранённое условие. Подмена этих данных значениями из пользовательского ответа изменила бы само задание. Обязательство соответствует [связи генерации и проверки](../04_Системные_требования/Интеграция.md#sr-sys-004-соответствие-генерации-и-проверки).

**Требование.** ПО должно передавать проверяющему сохранённое условие выбранной задачи и полученный ответ, определяя обработчик по сохранённому типу задачи.

Домен сессий не повторяет математические шаги профильного проверяющего и не выводит вердикт из текста исключения. Он получает явный предметный результат либо технический отказ. При отсутствии нужного обработчика операция не переводится в неверное решение. Дальнейший путь положительного или отрицательного вердикта определён в [сохранении результата](#swr-ses-011-сохранение-вердикта).

Источники: SR-SES-004, SR-SYS-004. Неизвестный тип или недоступный обработчик должны приводить к техническому отказу без предметного вердикта.

### SWR-SES-011. Сохранение вердикта

Вердикт вычисления нужно превратить в сохранённый результат задачи. В этой же операции учитывается состояние остальных задач сессии и закрывается запись обработки. Пока фиксация не завершена, внешний ответ не должен подтверждать результат как записанный. Такой порядок связывает вычисление с [общим контрактом сохранения](DOC-06_Программные_требования.md#swr-sys-005-согласованное-сохранение).

**Требование.** После завершённой предметной проверки ПО должно сохранить `SOLVED` при вердикте «верно» или `FAILED` при вердикте «неверно», вычислить соответствующее состояние сессии и только затем подтвердить результат операции.

Перед записью проверяется, что операция ещё допускает фиксацию: её предел времени не истёк и итог не был установлен другим завершением. В короткой транзакции сохраняются результат задачи и пересчитанное состояние набора. После потери соединения эти данные доступны через [чтение сессии](#swr-ses-023-чтение-сессии-и-результата), без нового вызова проверяющего и повторной предметной попытки.

Источники: SR-SES-005, SR-SES-007, SR-SYS-005. Результат содержит идентификатор и тип проверенной задачи по контракту.

### SWR-SES-012. Согласование одновременных обращений

Параллельные обращения создают риск двух результатов для одной задачи или неверного итога для всего набора. Для одной задачи нужно исключить две независимые фиксации. Для разных задач одной сессии нужно согласовать пересчёт агрегированного состояния. Здесь общая граница — данные сессии, а не отдельное клиентское соединение.

**Требование.** ПО должно согласовывать обращения к одной задаче так, чтобы одновременно полученные ответы не приводили к двум завершённым предметным проверкам или перезаписи итогового результата.

Предметное вычисление не удерживает долгую транзакцию. При фиксации строки блокируются в установленном порядке: сессия, задача, запись операции. После получения блокировки решение принимается по актуальным данным. Повтор для занятой задачи получает `CHECK_IN_PROGRESS`. Сценарии разных порядков событий описаны в [разборе параллельных событий](#согласование-параллельных-событий), а защита итогового состояния — в [правиле повторного ответа](#swr-ses-013-сохранение-итогового-состояния).

Источник: SR-SES-008. Для фиксации используется короткая транзакция с блокировкой сначала строки сессии, затем задачи и записи операции; предметное вычисление выполняется вне этой транзакции. Повторное обращение к занятой задаче возвращает `CHECK_IN_PROGRESS`. При параллельном завершении разных задач итог вычисляется по согласованному набору их состояний под блокировкой сессии.

### SWR-SES-013. Сохранение итогового состояния

После сохранения `SOLVED` или `FAILED` задача имеет итог, который нельзя пересмотреть новой отправкой решения. Это распространяется на повторное нажатие, повтор сетевого клиента и отдельное новое соединение. Сервер принимает решение по сохранённым данным, поэтому состояние интерфейса пользователя не влияет на запрет второй попытки.

**Требование.** Для задачи в `SOLVED` или `FAILED` обработчик должен отклонять новый ответ, сохраняя существующий результат без повторной предметной проверки.

Новый ответ отклоняется до профильного вычисления; существующий вердикт не заменяется и не записывается повторно как новая попытка. Для восстановления отображения используется [операция чтения результата](Контракты_сессий.md#чтение-после-потери-ответа). Если запрос получен после общего срока, приоритет категории отказа определяется [контрактом ошибок](Контракты_сессий.md#коды-и-представление-ошибок); ни один из отказов не изменяет прежний итог.

Источники: SR-SES-008, SR-SYS-005.

### SWR-SES-014. Отказ без расхода попытки

Отказ без предметного вердикта не должен расходовать возможность решения. Это правило относится к ошибке формата и техническому сбою проверки, но не отменяет общий срок сессии. Текущая обработка завершается соответствующей категорией, после чего возможность нового запроса оценивается по состоянию задачи и времени.

**Требование.** При ошибке формата или техническом сбое без вердикта ПО должно сообщать соответствующую категорию отказа и сохранять неиспользованную попытку. До срока задача остаётся `NEW`, если не завершена по другому основанию.

До `D` задача сохраняет `NEW`, если она не завершена по другому основанию. Новый исправленный или повторный запрос имеет собственное время поступления. После `D` незавершённая задача подлежит просрочке, даже если предметная попытка не была израсходована. Системный смысл разницы дан в [обработке технического сбоя](../04_Системные_требования/Сессии_задач.md#sr-ses-010-технический-сбой-проверки), а предел текущей операции — в [ограничении обработки](#swr-ses-020-предел-обработки).

Источники: SR-SES-009, SR-SES-010, SR-SYS-009. После срока отсутствие допустимой незавершённой проверки приводит к завершению по просрочке; отказ не продлевает срок.

### SWR-SES-015. Завершение своевременной проверки

Общий срок прекращает приём новых ответов, но уже полученный допустимый ответ может ещё находиться в обработке. Если фоновый компонент в этот момент назначит задаче просрочку, студент потеряет своевременно использованную возможность решения. Поэтому обработчик и планировщик должны учитывать одну запись принятой операции.

**Требование.** ПО должно принимать вердикт допустимого ответа с `t_in < D`, даже если проверка закончилась при `t >= D`. Регистрация и завершение такой проверки должны быть согласованы с фоновым контролем срока.

Для `t_in < D` проверка может зафиксировать вердикт после `D`, пока не истёк её собственный предел. Отказ в допуске, ошибка формата или техническое завершение снимают защиту от просрочки. Если общий срок к этому времени уже прошёл, задача закрывается по времени. Связанные действия определены в [контроле просрочки](#swr-ses-017-завершение-по-просрочке) и [пределе обработки](#swr-ses-020-предел-обработки).

Источники: SR-SES-011, SR-SYS-006. Пока своевременный запрос проходит проверки допуска и формата либо предметную проверку, его задаче нельзя назначать итог по просрочке. Если запрос отклонён или проверка завершилась техническим сбоем после срока, защита от просрочки прекращается; новый ответ после срока не допускается.

## 4. Контроль срока и итог

### SWR-SES-016. Фоновый контроль

Фоновый контроль обслуживает задачи независимо от действий пользователя. Он нужен, чтобы незавершённые наборы получили итог и без нового запроса. Его период не должен становиться частью разрешённого студенту интервала: между `D` и следующим запуском поздние ответы уже недопустимы.

**Требование.** ПО должно выполнять фоновую обработку просроченных задач с плановым периодом 60 секунд и отдельно проверять срок при допуске каждого нового ответа.

Обработчик каждого ответа самостоятельно применяет временное правило к `t_in`. Планировщик тем временем приводит сохранённые состояния к тому же правилу. Поэтому задержка фонового запуска влияет на момент обслуживания записи, но не выдаёт дополнительное время решения. Порядок выбора задач дан в [завершении по просрочке](#swr-ses-017-завершение-по-просрочке), общий контракт — в [едином правиле времени](../04_Системные_требования/Интеграция.md#sr-sys-006-единое-правило-времени).

Источники: SR-SES-006, SR-SYS-006; период задан `[TS.REQ.FUNC.SESSION.TIME]`. Период фоновой обработки не предоставляет пользователю дополнительное время между сроком и очередным запуском.

### SWR-SES-017. Завершение по просрочке

Назначение просрочки затрагивает только незавершённые задачи без своевременного запроса в обработке. Наличие старого `NEW` в хранилище ещё не означает, что можно записать `FAILED`: нужно учесть общий срок и принятую операцию. Уже завершённый вердикт не пересматривается планировщиком.

**Требование.** При обработке просрочки ПО должно переводить в `FAILED` только задачи `NEW`, срок которых наступил и для которых нет своевременного запроса в обработке. Итоговые результаты остальных задач должны сохраняться.

После выбора подходящих задач сохраняются их новые состояния и пересчитываются сессии. Для задачи со своевременной обработкой планировщик ждёт её исхода в пределах установленного времени. Если операция закончилась отказом после `D`, задача снова подпадает под правило просрочки. Само вычисление итога одинаково для всех путей и описано в [общей функции состояния сессии](#swr-ses-018-общая-функция-итога-сессии).

Источники: SR-SES-006, SR-SES-011. После отказа незавершённой проверки за пределами срока задача подлежит этому же правилу.

### SWR-SES-018. Общая функция итога сессии

Обработчик ответа и планировщик могут завершать разные задачи одного набора. Они не должны иметь разные способы определения успешности сессии. Итог выводится из полного согласованного набора состояний задач, а не из типа события, которое привело к последней записи.

**Требование.** Обработка ответа и контроль срока должны применять одно правило: пока есть задача без итогового состояния, сессия `NEW`; когда все задачи завершены, сессия `SOLVED`, только если все задачи `SOLVED`, иначе `FAILED`.

Если есть хотя бы одна задача без итога, сессия остаётся `NEW`. После завершения всех задач наличие хотя бы одной `FAILED` означает неуспех набора, даже когда последняя задача решена верно. Только все `SOLVED` дают успешную сессию. Системная формулировка находится в [итоге сессии](../04_Системные_требования/Сессии_задач.md#sr-ses-007-итог-сессии), а защита пересчёта при одновременных ответах — в [согласовании обращений](#swr-ses-012-согласование-одновременных-обращений).

Источники: SR-SES-007, SR-SYS-005, SR-SYS-006.

### SWR-SES-019. Сохранность данных

Сессия должна сохранять смысл после остановки процесса: тот же владелец, тот же набор условий и прежние временные границы. Одного итогового флага для этого недостаточно. При чтении и проверке нужны идентификаторы, принадлежность, тип и сохранённое условие каждой задачи.

**Требование.** Хранение должно сохранять идентификаторы, принадлежность, состав, условия, серверное время создания и определённые состояния сессии и задач между запусками приложения.

После восстановления данные не генерируются заново и срок не отсчитывается от запуска приложения. Завершённые результаты выдаются чтением. Для операции, не дошедшей до вердикта, используются отдельные сведения о принятом ответе. Системная цель закреплена в [сохранности данных](../04_Системные_требования/Интеграция.md#sr-sys-007-сохранность-данных-сессии), программные пути — в [восстановлении операции](#swr-ses-021-запись-принятой-операции) и [чтении сессии](#swr-ses-023-чтение-сессии-и-результата).

Источники: SR-SYS-002, SR-SYS-007. Принятые ответы сохраняются до вычисления и восстанавливаются по SWR-SES-021.

### SWR-SES-020. Предел обработки

Обработка своевременного ответа имеет конечный предел. В него входит не только математическое вычисление, но и ожидание очереди и продолжение после сбоя. Этот предел нужен, чтобы операция не оставалась бессрочно принятой и не удерживала задачу от завершения по общему сроку.

**Требование.** ПО должно ограничивать всю обработку принятого ответа сроком `t_in + 60 секунд`. Результат может быть зафиксирован только до этого момента. По достижении срока незавершённая операция получает `CHECK_TIMEOUT`; её поздний результат отбрасывается без изменения задачи.

Перед фиксацией проверяется и состояние операции, и её срок. После `t_in + 60 секунд` результат уже не записывается, даже если вычисление завершилось позднее. Техническое завершение не создаёт отрицательный предметный вердикт. Дальнейшее состояние задачи определяется [правилом отказа без расхода попытки](#swr-ses-014-отказ-без-расхода-попытки) и [правилом просрочки](#swr-ses-017-завершение-по-просрочке).

Источники: SR-SES-010, SR-SES-012. Ожидание очереди, вычисление и восстановление входят в один срок; повторный запуск его не продлевает. После отказа применяется общее правило срока сессии.

### SWR-SES-021. Запись принятой операции

Запись принятой операции связывает ответ пользователя с задачей и временем его получения. Она нужна, потому что память процесса и исходное сетевое соединение могут исчезнуть раньше фиксации результата. Для восстановления должны остаться сами входные данные и прежний предел обработки, а не только отметка «что-то выполнялось».

**Требование.** До предметной проверки ПО должно сохранить запись операции с UUID, владельцем, задачей, ответом, `t_in`, сроком обработки и признаком незавершённости. Фиксация вердикта и завершение записи операции выполняются в одной транзакции с изменением состояний задачи и сессии.

При перезапуске сохранённая незавершённая операция продолжается в оставшемся интервале. Готовый результат и закрытие записи фиксируются вместе с состояниями задачи и сессии. Если результат уже записан, повторная обработка не создаёт новой попытки. Если срок операции истёк, применяется [техническое завершение по пределу](#swr-ses-020-предел-обработки). Пользователь получает готовые данные через [чтение собственной сессии](#swr-ses-023-чтение-сессии-и-результата).

Источники: SR-SES-008, SR-SES-013, SR-SYS-005, SR-SYS-007. При запуске приложения незавершённые операции с неистёкшим сроком продолжаются по сохранённым данным. Получение записи обработчиком согласуется блокировкой, исключающей две одновременно выполняемые обработки. Уже зафиксированный результат не создаёт новой предметной попытки. Операции с истёкшим сроком завершаются по SWR-SES-020.

### SWR-SES-022. Форматы и категории API

Внешний контракт превращает системные категории в точные параметры, поля и HTTP-ответы. Разбор запроса должен следовать ему до обращения к предметному алгоритму. Иначе разные клиенты могли бы получать разный смысл одного и того же запроса, а ошибки формата смешивались бы с неверным решением.

**Требование.** Приём операций должен применять обязательные поля, представление времени и целых чисел, предел тела и соответствие ошибок HTTP-кодам из контракта сессий. Повторяющийся параметр конфигурации отклоняется до создания набора.

Повторяющееся имя конфигурации не выбирается произвольно из нескольких значений: запрос отклоняется. Большие целые передаются установленными строками без потери точности, время — в UTC, а размер тела ограничивается до предметной проверки. Подробности находятся в [операциях](Контракты_сессий.md#операции), [схемах решения](Контракты_сессий.md#предметный-ответ) и [машинных кодах ошибок](Контракты_сессий.md#коды-и-представление-ошибок). Эти правила не изменяют математический критерий правильности.

Источники: SR-SES-009, SR-SYS-008, SR-SYS-009. Ошибки формата и превышения размера не запускают предметную проверку. Неизвестный тип в сохранённой конфигурации даёт технический отказ без частичной сессии.

### SWR-SES-023. Чтение сессии и результата

Клиенту нужен самостоятельный способ получить уже сохранённое состояние. После потери ответа он не должен повторно решать задачу или вызывать проверяющий, чтобы узнать итог. Чтение по ID сессии проверяет владельца и возвращает те данные, которые уже связаны с этим набором в хранилище.

**Требование.** ПО должно предоставлять `GET /api/tasks/session/{sessionId}` для чтения собственной сессии с состояниями задач и сохранёнными предметными результатами. При отсутствии сессии у текущего пользователя возвращается `SESSION_NOT_FOUND`.

Операция доступна и после общего срока. Она показывает состояния задач и сохранённый `result`, а для просроченной задачи без предметного вердикта — `null` вместо выдуманного решения. Перед выдачей учитывается правило просрочки с защитой своевременных обработок. Назначение описано в [системном требовании чтения](../04_Системные_требования/Сессии_задач.md#sr-ses-014-получение-сохранённого-результата), поля ответа — в [контракте восстановления отображения](Контракты_сессий.md#чтение-после-потери-ответа).

Источники: SR-SES-014, SR-SYS-002, SR-SYS-007, SR-SYS-008. Чтение не расходует попытку и доступно после общего срока. Перед формированием ответа состояние просроченных задач приводится к правилу SWR-SES-017 с сохранением своевременных обработок. Сохранённый вердикт возвращается без повторного вычисления.

## 5. Временные границы

Обозначения и длительность заданы в [карточке домена](../03_Карточки_доменов/Сессии_задач.md#срок-и-попытка).

| Ситуация | Ожидаемое действие |
|---|---|
| Запрос получен до `D`, проверка завершена до `D` | Сохранить предметный результат |
| Запрос получен до `D`, проверка завершена после `D`, но до `t_in + 60 секунд` | Сохранить предметный результат; не заменять его просрочкой |
| Запрос получен точно в `D` или позже | Отклонить новый ответ по сроку |
| Своевременный запрос оказался некорректным до `D` | Сообщить ошибку; исправленный новый запрос возможен до `D` |
| Некорректный запрос или технический сбой обнаружены после `D` | Сообщить категорию отказа; завершить незавершённую задачу по просрочке, если нет другой допустимой проверки |
| Планировщик запущен во время своевременной проверки | Не назначать этой задаче `FAILED` по времени |
| Планировщик задержался | Отклонять новые поздние ответы независимо от состояния фоновой обработки |

### Согласование параллельных событий

Конкурировать могут два ответа на одну задачу, ответы на разные задачи одной сессии, ответ и контроль просрочки, а также два запроса создания набора. В каждом случае требуется сохранить определённый системой результат. Выбор блокировок или другого механизма не должен изменять правило одной попытки и общего срока.

Для одной задачи окончательный предметный вердикт определяется не более одного раза. Пока первый допустимый ответ обрабатывается, другое обращение не должно независимо завершать вторую предметную проверку. Если первый запрос закончился без вердикта до срока, возможность нового допустимого обращения сохраняется по общим правилам.

При параллельной проверке разных задач согласование необходимо на уровне сессии. Завершение последней задачи должно учитывать уже определённые результаты остальных. Сохранение одного вердикта не должно перезаписывать итог, вычисленный без учёта другой завершившейся задачи.

При конкуренции ответа и планировщика существенен момент поступления запроса. Своевременный запрос сохраняет право пройти проверки допуска и формата и, если они успешны, получить предметный вердикт. Ответ, поступивший после срока, этого права не получает даже при ещё не обновлённом состоянии задачи в хранилище.

### Переходы состояния задачи

| Исходное состояние и событие | Следующее состояние | Значение для попытки |
|---|---|---|
| `NEW`, допустимый ответ признан верным | `SOLVED` | Предметная попытка завершена |
| `NEW`, допустимый ответ признан неверным | `FAILED` | Предметная попытка завершена |
| `NEW`, ошибка формата до срока | `NEW`, если нет другого основания завершения | Попытка сохраняется |
| `NEW`, технический сбой без вердикта до срока | `NEW`, если нет другого основания завершения | Попытка сохраняется |
| `NEW`, наступил срок, своевременного запроса в обработке нет | `FAILED` | Завершение по сроку, без нового предметного вердикта |
| `NEW`, срок наступил во время своевременной проверки | `NEW` до завершения обработки | Ожидание единственного результата |
| `SOLVED` или `FAILED`, новый ответ | Прежнее итоговое состояние | Повторная проверка не допускается |

Для сессии используется агрегирование состояний задач по SWR-SES-018. Программная реализация не должна считать любой набор завершённых задач успешным: наличие хотя бы одной `FAILED` определяет итог `FAILED`. Это правило одинаково после предметной проверки и после фоновой обработки.

### Проверка длительной обработки

Для требования своевременности нужно рассматривать получение запроса, запуск проверяющего, наступление срока и сохранение вердикта как отдельные события. Условие `t_in < D` проверяется по первому из них. Задержка между событиями не изменяет сохранённую отметку времени и не разрешает вторую попытку.

Отдельно рассматривается своевременная обработка, завершившаяся отказом после срока. Предметный результат в этом случае отсутствует, но срок для нового запроса уже закончился. Требования сохраняют различие причин: технический сбой не становится неверным решением, а последующее завершение задачи происходит по просрочке.

## 7. Полнота описания подсистемы

Контракт задаёт создание, отправку ответа и чтение сессии, входные данные, результаты и категории отказов. Программные требования охватывают создание, предметную проверку, ограничение времени, параллельные обращения, сохранение и восстановление. Предел обработки и фоновый период имеют разные назначения, хотя оба составляют 60 секунд: первый ограничивает одну операцию, второй задаёт частоту фонового контроля общего срока.
