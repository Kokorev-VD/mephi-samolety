## 1. Назначение и состав

Личная сессия — выданный одному студенту набор конкретных задач с общим сроком решения. Она возникает, когда студент приступает к опубликованному контрольному мероприятию своей группы или начинает самостоятельную практику. Каждая задача получает собственное условие. Предметный обработчик проверяет ответ студента по этому условию и возвращает вердикт «верно» или «неверно». Подсистема сессий решает, можно ли принять ответ, сохраняет вердикт и подводит итог набора. Планировщик — фоновая часть программы, которая по серверным часам находит просроченные задачи и закрывает их, даже если студент отключился.

Правила этой подсистемы обязательны. В разделах 2–4 каждому правилу присвоен ID. Системные основания и контрольные случаи приведены в [таблице трассировки](#6-трассировка-и-описательные-проверки). Формы запросов и ответов определяет [приложение](Контракты_сессий.md). Смежные обязанности определены в [общих программных требованиях](DOC-06_Программные_требования.md).

### Данные и их жизненный цикл

UUID — уникальный идентификатор, по которому сервер находит конкретную запись. У пользователя, мероприятия, сессии, каждой задачи и каждой операции свои идентификаторы. Слово «операция» ниже означает обработку одного поступившего запроса с решением. Наименование операции и смысл её параметров приведены в [контракте сессий](Контракты_сессий.md#операции).

| Объект | Что хранится и для чего используется |
|---|---|
| Сессия | UUID, владелец, `assessmentId` контрольного мероприятия либо `null` для практики, серверное время создания, срок подачи решений `deadlineAt`, состав и состояние. Все задачи одного набора имеют общий срок |
| Задача | UUID, связь с сессией, выданное условие, тип, состояние и зафиксированный предметный результат, если он получен |
| Принятый ответ | Входные данные и срок конкретной операции. По этой записи обработчик может продолжить прерванную проверку, а планировщик определяет, какие задачи пока нельзя закрывать |

Для задачи `NEW` означает «итог ещё не определён», `SOLVED` — «зафиксировано верное решение», `FAILED` — «зафиксировано неверное решение или истёк срок». Во время проверки задача остаётся `NEW`. Для всей сессии `NEW` означает наличие хотя бы одной незавершённой задачи. Только после завершения последней задачи определяется [итог сессии](#swr-ses-018-общая-функция-итога-сессии). Отметка о принятом ответе относится к операции. Завершённая предметная попытка возникает при записи вердикта. Прекращение операции из-за ошибки формата или технического сбоя само по себе попытку не расходует.

### Время решения и время обработки

Серверное время создания сессии обозначено `t0`. Для самостоятельной практики срок подачи `D = t0 + 20 минут`. Для контроля `D = min(t0 + 20 минут, closesAt)`, где `closesAt` — момент закрытия опубликованной работы. В ответе сервера этот общий для задач срок передаётся как `deadlineAt`. Момент получения сервером полного запроса обозначен `t_in`. Запрос своевременен, если `t_in < D`. Для него действует отдельный предел фиксации результата `L = t_in + 60 секунд`. В момент `L` записывать вердикт уже поздно. Плановый период фонового контроля тоже равен 60 секундам. Это частота запуска планировщика, она не изменяет ни срок подачи, ни предел обработки. [Пример на часах](#согласование-параллельных-событий) показывает случай, когда оба срока наступают в разное время.

## 2. Создание сессии

Самостоятельная практика использует шаблон набора задач — упорядоченный перечень типов, доступный группе. Для контроля состав задан опубликованным преподавателем мероприятием. Проверку доступности и выбор источника состава описывают требования ниже. Одна транзакция хранилища объединяет запись сессии и всех её задач. Успешная фиксация делает их доступными вместе, а откат отменяет изменения этого создания.

<a id="swr-ses-001"></a>

### SWR-SES-001. Получение пользователя

При создании набора и при отправке решения обработчик должен получить личность пользователя от компонента проверки доступа до обращения к данным сессии. Если доступ не подтверждён, обработка запроса прекращается. Идентификатор в данных клиента не предоставляет права действовать от имени другого владельца.

<a id="swr-ses-002"></a>

### SWR-SES-002. Выбор доступного шаблона

Для самостоятельной практики компонент создания должен установить группу по подтверждённому университетскому профилю студента и найти среди шаблонов этой группы включённый шаблон с запрошенным именем. Из него компонент берёт состав набора. Для пользователя без группы, при отсутствии имени в группе и при отключённом шаблоне результат один — `CONFIGURATION_NOT_FOUND`. Сессия при этом не создаётся.

Для контроля клиент передаёт `assessmentId`. Компонент находит опубликованное мероприятие подтверждённой группы пользователя. Чужое, неопубликованное и отсутствующее мероприятие дают `404 ASSESSMENT_NOT_FOUND`. До открытия (`opensAt`) старт отклоняется с `409 ASSESSMENT_NOT_OPEN`, с момента закрытия (`closesAt`) — с `409 ASSESSMENT_CLOSED`. Внутри окна сервер проверяет активную сессию по [SWR-SES-003]. После завершения предыдущего прохождения этой работы новый набор выдаётся только при `repeatAllowed = true`. Если повторы запрещены, сервер возвращает `409 ASSESSMENT_RETAKE_DISABLED` с UUID прежней сессии в `details.sessionId`. При разрешённом старте формируется новый набор по закреплённому составу с тем же `assessmentId`. Ранее выданные наборы сохраняются. У практики `assessmentId = null`.

<a id="swr-ses-003"></a>

### SWR-SES-003. Защита от двух активных сессий

Компонент создания должен в одной транзакции заблокировать строку пользователя, учесть просрочку прежнего набора и проверить, осталась ли у этого пользователя сессия `NEW`. Внутри открытого окна контроля и при создании практики сессия `NEW` исключает выдачу второго набора независимо от `repeatAllowed`. Решение о повторном старте и запись нового прохождения выполняются под той же блокировкой. Второй параллельный запрос после снятия блокировки получает `ACTIVE_SESSION_EXISTS` с идентификатором действующей сессии.

Даже после общего срока прежняя сессия остаётся активной, пока у неё есть задача со своевременно полученным ответом в обработке. Порядок завершения такой задачи определяют [SWR-SES-015] и [SWR-SES-020].

<a id="swr-ses-004"></a>

### SWR-SES-004. Формирование задач

Для каждой позиции выбранного состава компонент создания должен запросить условие у модуля указанного типа. В сессии задачи следуют в порядке, заданном шаблоном. При повторе типа каждой позиции соответствует отдельная задача со своим UUID и выданным условием. Новая сессия и все её задачи получают состояние `NEW`. Последующие правки шаблона не изменяют состав набора и условия выданных задач. Если генератор для заданного типа отсутствует, создание завершается техническим отказом.

Модуль может сформировать условие вычислением или выбрать подготовленный вариант. Для позиции типа `CUSTOM_TEXT` он случайно выбирает одну из заданных преподавателем пар «условие — эталон». Выдача закрепляет выбор за задачей личной сессии. Студенту возвращается только условие. Остальные варианты и эталон выбранного варианта в ответ не включаются. Повторное чтение возвращает то же условие.

<a id="swr-ses-005"></a>

### SWR-SES-005. Сохранение созданного набора

Сессию и все её задачи компонент создания должен сохранить одной транзакцией PostgreSQL. Сообщить об успехе можно после фиксации полного состава. При ошибке генератора или записи транзакция откатывается. У пользователя не появляется частичный набор, который занимал бы место активной сессии.

<a id="swr-ses-006"></a>

### SWR-SES-006. Сохранение времени создания

При создании подсистема должна сохранить серверное время `t0` и общий срок `deadlineAt`. Для практики это `t0 + 20 минут`. Для контроля сервер выбирает более ранний из двух моментов — `t0 + 20 минут` или `closesAt`. Чтение сессии, повторный запрос, ошибка и перезапуск не меняют исходных временных границ. Время создания отдельных задач на них не влияет.

## 3. Обработка ответа

Проверки идут в два этапа. Допуск устанавливает, вправе ли этот пользователь решать задачу сейчас. Проверка формата устанавливает, можно ли прочитать решение по схеме выданного задания. Только затем предметный обработчик оценивает сам ответ. При конкуренции запросов блокировка даёт одному обработчику возможность работать с общей записью, пока другие ждут её освобождения. Это защищает запись единственного вердикта.

<a id="swr-ses-007"></a>

### SWR-SES-007. Регистрация времени поступления

Приёмный обработчик должен зафиксировать `t_in` в момент получения полного запроса. До очереди он сверяет подтверждённого отправителя с владельцем задачи. Для отсутствующей или чужой задачи возвращается `TASK_NOT_FOUND`, операция для этой задачи не открывается. Ответ владельца сохраняется с исходной отметкой по [SWR-SES-021]. Регистрация своевременного запроса владельца согласуется с планировщиком по `t_in`, чтобы планировщик учитывал его до закрытия задачи. После перезапуска обработчик продолжает проверки допуска и формата с прежним `t_in`. Время на устройстве клиента и начало математического вычисления на допуск не влияют.

<a id="swr-ses-008"></a>

### SWR-SES-008. Проверка допуска

До вызова проверяющего подсистема должна установить по сохранённым данным, что задача принадлежит сессии текущего пользователя, задача и сессия ещё допускают ответ, а запрос получен до `D`. Для отсутствующей и чужой задачи возвращается `TASK_NOT_FOUND`. После установления владельца сначала решается вопрос о сроке. При `t_in >= D` возвращается `SESSION_EXPIRED`, даже если задача уже имеет итог или планировщик ещё не обработал запись.

У своевременного запроса к завершённой задаче или сессии результат — `TASK_FINALIZED`. При незавершённой проверке другого допустимого ответа к той же задаче действует [SWR-SES-012].

<a id="swr-ses-009"></a>

### SWR-SES-009. Проверка формата

До предметного вычисления обработчик должен разобрать JSON и проверить обязательные поля и их типы по схеме сохранённой задачи. При ошибке формы он возвращает `INVALID_REQUEST`. При формально допустимой записи вычислений проверяющий получает ответ, даже если расчёт окажется неверным. Предел размера тела устанавливает [SWR-SES-022].

<a id="swr-ses-010"></a>

### SWR-SES-010. Передача профильной проверке

Подсистема должна выбрать проверяющий по типу сохранённой задачи и передать ему исходное выданное условие вместе с принятым ответом. Поля пользователя не изменяют условие или выбор проверяющего. Неизвестный тип и техническая недоступность обработчика завершают операцию без предметного вердикта.

Для `BACKPACK`, `EL_GAMAL`, `CUSTOM_TEXT` и подключаемых типов действуют одни правила времени и учёта попытки. Модуль `CUSTOM_TEXT` извлекает эталон закреплённого варианта. После удаления пробелов по краям обеих строк он сравнивает их с учётом регистра и всех внутренних пробелов. Равенство даёт положительный вердикт. Схему тела задаёт [приложение](Контракты_сессий.md#пользовательское-текстовое-задание).

<a id="swr-ses-011"></a>

### SWR-SES-011. Сохранение вердикта

При получении вердикта подсистема должна установить, что операция ещё открыта и время её фиксации не истекло. Дальше она записывает предметный результат с UUID и типом задачи, устанавливает задаче `SOLVED` для верного решения либо `FAILED` для неверного, пересчитывает состояние сессии и закрывает операцию. Все изменения фиксируются вместе. Подтверждение клиенту следует за фиксацией.

<a id="swr-ses-012"></a>

### SWR-SES-012. Согласование одновременных обращений

Подсистема должна атомарно предоставить право на предметную проверку одному допустимому ответу на задачу. Два зарегистрированных запроса с разными UUID не дают права на два одновременных вычисления по одной задаче. При ещё открытой проверке второй своевременный допустимый запрос получает `CHECK_IN_PROGRESS`, при уже зафиксированном результате до общего срока — `TASK_FINALIZED`. В обоих случаях тело ранее принятого ответа сохраняется.

Обработчик вычисляет вердикт вне транзакции записи. Для фиксации он открывает короткую транзакцию и блокирует по порядку строку сессии, строку задачи и запись операции. После получения блокировок он проверяет актуальные данные. При параллельном завершении разных задач одной сессии итог рассчитывается по их согласованным состояниям под блокировкой сессии.

<a id="swr-ses-013"></a>

### SWR-SES-013. Сохранение итогового состояния

Подсистема должна отклонить новую отправку решения для задачи `SOLVED` или `FAILED` до вызова проверяющего. При повторе запроса сохранённый результат и состояние задачи остаются прежними. Владелец получает результат отдельной операцией чтения.

<a id="swr-ses-014"></a>

### SWR-SES-014. Отказ без расхода попытки

При ошибке формата и при техническом отказе без зафиксированного вердикта обработчик должен вернуть причину отказа и сохранить предметную попытку. До `D` задача остаётся `NEW`, если у неё нет другого основания для завершения. Пользователь может подать исправленный ответ с новым `t_in`. Когда срок наступил, к оставшейся без своевременной обработки задаче применяется [SWR-SES-017].

Если запись вердикта откатилась и обработчик сообщает клиенту `500 INTERNAL_ERROR`, он должен сначала сохранить отмену операции. После доставки отказа прежний результат уже не может быть записан. При обрыве связи или остановке процесса судьбу ответа определяет хранилище. Открытая запись подлежит восстановлению по [SWR-SES-021], а зафиксированный результат доступен для чтения.

<a id="swr-ses-015"></a>

### SWR-SES-015. Завершение своевременной проверки

Для запроса владельца с `t_in < D` обработчик и планировщик должны сохранить возможность пройти допуск и проверку формата, а после успешного допуска — записать предметный вердикт, в том числе после `D`. Это правило действует и при закрытии контрольного мероприятия. Вердикт должен быть зафиксирован строго до `L`. Защита от просрочки действует с регистрации своевременного ответа подтверждённого владельца и включает ожидание в пределах [SWR-SES-020]. Обращение другого пользователя с UUID задачи не препятствует её закрытию. Если запрос отклонён или проверка завершилась техническим отказом, связанная с ним защита снимается. При этом учитываются остальные своевременные запросы владельца, если они ещё обрабатываются. После `D` новый запрос уже не допускается.

## 4. Контроль срока и итог

Контроль срока завершает задачу без предметного вердикта, когда прошёл [общий срок подачи ответа](#время-решения-и-время-обработки) и нет своевременной обработки. После каждого завершения пересчитывается состояние всего набора. Истечение времени и неверное решение имеют одно состояние задачи `FAILED`, но различаются по [сохранённому результату](Контракты_сессий.md#чтение-после-потери-ответа).

<a id="swr-ses-016"></a>

### SWR-SES-016. Фоновый контроль

Планировщик должен обрабатывать просроченные задачи с плановым периодом 60 секунд. Такой период задан требованием ТЗ [`TS.REQ.FUNC.SESSION.TIME`][TS.REQ.FUNC.SESSION.TIME]. Независимо от последнего запуска планировщика приёмный обработчик проверяет каждый новый ответ относительно `D`.

<a id="swr-ses-017"></a>

### SWR-SES-017. Завершение по просрочке

По достижении `D` подсистема должна закрывать по просрочке только задачу `NEW`, для которой нет своевременного запроса в обработке. Её состояние меняется на `FAILED`, поле `result` остаётся равным `null`. После изменения пересчитывается итог набора. Планировщик сохраняет прежние вердикты и учитывает защиту незавершённых операций по [SWR-SES-015].

<a id="swr-ses-018"></a>

### SWR-SES-018. Общая функция итога сессии

После предметной проверки и после закрытия задачи по сроку подсистема должна применять одинаковое правило к состояниям всех задач сессии.

| Состояния задач | Состояние сессии |
|---|---|
| Хотя бы одна задача остаётся `NEW` | `NEW`, включая сочетание `NEW` и `FAILED` |
| Все задачи завершены и каждая имеет `SOLVED` | `SOLVED` |
| Все задачи завершены, среди них есть `FAILED` | `FAILED` |

<a id="swr-ses-019"></a>

### SWR-SES-019. Сохранность данных

Между запусками приложения хранилище должно сохранять UUID и принадлежность сессии и задач, состав, условия и типы задач, `t0`, установленный срок подачи `deadlineAt`, текущие состояния и зафиксированные результаты. После запуска приложение использует те же условия и сроки. Для ответа, по которому ещё нет вердикта, используется запись операции по [SWR-SES-021].

<a id="swr-ses-020"></a>

### SWR-SES-020. Предел обработки

Вердикт можно записать только при времени фиксации строго меньше `t_in + 60 секунд`. По достижении этой границы подсистема должна закрыть незавершённую операцию с `CHECK_TIMEOUT`, отбросить поздний вердикт и сохранить неиспользованную попытку. В один интервал входят ожидание очереди, вычисление, фиксация и восстановление. Истечение интервала обработки не меняет `D`. Состояние задачи после отказа определяется [SWR-SES-014] и [SWR-SES-017].

<a id="swr-ses-021"></a>

### SWR-SES-021. Запись принятой операции

После сверки владельца по [SWR-SES-007] и до очереди подсистема должна записать в устойчивое хранилище UUID операции, подтверждённого пользователя, UUID собственной задачи из запроса, полный ответ, `t_in`, предел `t_in + 60 секунд` и признак незавершённости. Запись запроса нужна для учёта времени и восстановления. Право начать предметную проверку возникает после [SWR-SES-008] и [SWR-SES-009] и предоставляется на задачу по [SWR-SES-012]. Блокировка при получении записи не позволяет двум обработчикам одновременно продолжить одну операцию.

После перезапуска приложение должно найти открытые операции, в том числе ещё ожидавшие в очереди. До исходного предела обработчик продолжает работу по сохранённым данным с учётом правил допуска и формата. При истёкшем пределе действует [SWR-SES-020]. Закрытие операции, запись вердикта и новые состояния задачи и сессии принадлежат одной транзакции. Повторный запуск после фиксации использует записанный результат.

<a id="swr-ses-022"></a>

### SWR-SES-022. Форматы и категории API

Интерфейс должен применять список обязательных полей, точные типы, представление времени и целых чисел, ограничение размера и соответствие HTTP-статусов кодам из [приложения](Контракты_сессий.md). Создание принимает ровно один параметр из `configuration` и `assessmentId`. Отсутствие обоих, их сочетание, повтор или ошибка значения дают `400 INVALID_REQUEST`. Ошибки параметров, структуры тела и его размера прекращают обработку до предметной проверки. Неподдерживаемый тип задания в сохранённом шаблоне даёт технический отказ с откатом создания.

<a id="swr-ses-023"></a>

### SWR-SES-023. Чтение сессии и результата

По `GET /api/tasks/session/{sessionId}` подсистема должна предоставить владельцу его сессию и задачи с сохранёнными результатами, в том числе после закрытия мероприятия и после начала нового разрешённого прохождения. Чужая и отсутствующая сессии дают `SESSION_NOT_FOUND`. Перед выдачей подсистема приводит состояния к правилам просрочки и учитывает своевременные обработки. Чтение не вызывает предметного вычисления и не расходует попытку.

## 5. Временные границы

### Согласование параллельных событий

Пусть сервер создал сессию практики в 10:00:00 и получил полный ответ в 10:19:59. В 10:20:00 планировщик видит ещё открытую задачу. Регистрация запроса защищает её от просрочки, даже если проверяющий пока не приступил к вычислению. До 10:20:59 обработчик может зафиксировать вердикт. Если к 10:20:59 фиксации нет, операция завершается с `CHECK_TIMEOUT`, а задача — по просрочке без предметного результата. В той же сессии другой полный запрос, впервые полученный ровно в 10:20:00, уже опоздал.

Контрольное мероприятие закрывается в 11:00:00. Студент начинает в 10:57:00, поэтому его срок `D` — 11:00:00. Для ответа, полностью полученного в 10:59:59, запись вердикта разрешена строго до 11:00:59. В 11:00:00 новый ответ владельца получает `410 SESSION_EXPIRED`, а запрос на новый старт по мероприятию — `409 ASSESSMENT_CLOSED`. Прежнюю сессию можно читать в обоих случаях.

### Переходы состояния задачи

| Событие для задачи в состоянии `NEW` | Состояние и результат, доступные владельцу |
|---|---|
| Зафиксирован положительный вердикт | `SOLVED`, результат с `isOk = true` |
| Зафиксирован отрицательный вердикт | `FAILED`, результат с `isOk = false` и пояснением |
| До общего срока произошла ошибка формата или технический отказ без вердикта | `NEW`, `result = null`, если нет другого основания закрытия |
| Общий срок наступил во время своевременной обработки | `NEW`, пока обработка может дать вердикт |
| Общий срок наступил, своевременных обработок нет | `FAILED`, `result = null` |

### Проверка длительной обработки

При разборе временного случая фиксируют три момента по серверным часам — получение полного запроса, общий срок сессии и запись вердикта. Начало вычисления само по себе ещё не определяет исход. Например, проверяющий может вернуть верный ответ за секунду до предела, а транзакция записи получит блокировку уже на границе. Такой результат подпадает под [SWR-SES-020]. Клиент сможет прочитать состояние задачи по её сессии.

| [SWR-SES-005] | [SR-SES-001], [SR-SYS-005] | Ошибка при формировании последней задачи. Первая задача и незавершённая сессия не видны пользователю |
| [SWR-SES-006] | [SR-SES-006], [SR-SYS-006], [SR-SYS-007] | После повторного чтения и перезапуска срок практики по-прежнему отсчитывается от создания. Срок контрольной сессии также ограничивает `closesAt` опубликованной работы |
| [SWR-SES-007] | [SR-SES-011], [SR-SYS-006] | Перезапуск застал запрос в очереди. Сохранились сам ответ и время его полного получения |
| [SWR-SES-008] | [SR-SES-003], [SR-SES-008], [SR-SES-011] | Для чужой задачи и позднего запроса к собственной задаче получены соответствующие отказы до вычисления |

| [SWR-SES-010] | [SR-SES-004], [SR-SYS-004] | На проверку поступили условие и тип именно той задачи, UUID которой указан в запросе |
| [SWR-SES-011] | [SR-SES-005], [SR-SES-007], [SR-SYS-005] | После подтверждения видны записанный вердикт, соответствующее состояние задачи и пересчитанный итог набора |
| [SWR-SES-012] | [SR-SES-008] | Два ответа к одной задаче перекрылись во времени. Зафиксирован один предметный результат |
| [SWR-SES-013] | [SR-SES-008], [SR-SYS-005] | Повтор после фиксации получил отказ. Состояние и первый результат сохранились |
| [SWR-SES-014] | [SR-SES-009], [SR-SES-010], [SR-SYS-009] | После технического отказа до срока можно подать новый ответ, `D` сохранился |
| [SWR-SES-015] | [SR-SES-011], [SR-SYS-006] | После общего срока своевременный ответ по-прежнему может дать вердикт до своего предела |
| [SWR-SES-016] | [SR-SES-006], [SR-SYS-006] | Планировщик задержан. Новый ответ в момент общего срока отклонён |
| [SWR-SES-017] | [SR-SES-006], [SR-SES-011] | По сроку закрыты только задачи без итога и без своевременной обработки |
| [SWR-SES-018] | [SR-SES-007], [SR-SYS-005], [SR-SYS-006] | Одна задача `FAILED`, другая ещё `NEW`. Сессия получает `FAILED` только после завершения второй |
| [SWR-SES-019] | [SR-SYS-002], [SR-SYS-007] | После перезапуска совпадают владелец, состав, времена, условия и сохранённые вердикты |
| [SWR-SES-020] | [SR-SES-010], [SR-SES-012] | При попытке фиксации ровно на границе обработки вердикт отброшен |
| [SWR-SES-021] | [SR-SES-008], [SR-SES-013], [SR-SYS-005], [SR-SYS-007] | При восстановлении доступны прежние входные данные. До предела допускается одна фиксация, после предела — технический отказ |
| [SWR-SES-022] | [SR-SES-009], [SR-SYS-008], [SR-SYS-009] | Повтор параметра, превышение размера и неверная схема различаются в соответствии с таблицей ошибок |
| [SWR-SES-023] | [SR-SES-014], [SR-SYS-002], [SR-SYS-007], [SR-SYS-008] | После потери ответа владелец читает сохранённый результат. Чужой пользователь получает тот же отказ, что и для отсутствующей сессии |
