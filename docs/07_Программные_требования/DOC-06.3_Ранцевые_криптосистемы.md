## 1. Назначение и состав

Документ определяет программные обязанности домена ранцевых криптосистем при генерации условий, проверке решений, редакционных генерациях и хранении. Он раскрывает [системные требования ранцевых задач](../04_Системные_требования/Ранцевые_задачи.md) и подчиняется общим обязательствам [DOC-06](DOC-06_Программные_требования.md). Математические определения ранцевой криптосистемы приведены в [ТЗ](../../02_Техническое_задание/Техническое_задание.tex); здесь определяется, что делает программная часть домена.

| Логическая часть | Ответственность |
|---|---|
| Участие в сессиях | Предоставить генерацию и проверку ранцевых задач управлению сессиями по квалификатору конфигурации |
| Генерация условия | Построить условие выбранного варианта с частично скрытыми данными и сохранить его в составе сессии |
| Проверка решения | Проверить ответ по величинам криптосистемы и вернуть вердикт с диагностикой |
| Редакционные решатели | Построить эталонную задачу по варианту или с параметрами пользователя |
| Диспетчеризация | Выбрать решатель по варианту редакционного запроса |
| Хранение | Сохранять условия сгенерированных задач между запусками |

Это распределение обязанностей; оно не задаёт имена классов, таблиц или форматы внешних операций. Внешние операции сессий определены в [контракте](Контракты_сессий.md); справочник эндпоинтов — DOC-08.

### Условие и его состав

Условие ранцевой задачи — сохраняемый JSON-объект, сопровождающий задачу сессии. Он содержит вариант, выданные фрагменты лёгкого ранца, тяжёлый ранец и данные, достаточные для восстановления остальных величин. После выдачи условие не пересчитывается из конфигурации: проверка использует его сохранённую копию, что соответствует [составу созданной сессии](DOC-06_Программные_требования.md#swr-sys-003-состав-созданной-сессии).

Приоритет всех программных требований документа — обязательный. Источники SR указывают на определения в DOC-05; описания проверок приведены в разделе 7.

## 2. Участие в сессиях

### SWR-KNAP-001. Регистрация предметного обработчика

Управление сессиями получает задачи конфигурации через предметных обработчиков. Ранцевой домен предоставляет один обработчик, известный под квалификатором «Backpack»: конфигурация называет квалификатор, а управление сессиями передаёт ему генерацию и проверку. Так состав набора задаётся без знания внутренних алгоритмов домена. Это применение [общего контракта предметного обработчика](DOC-06_Программные_требования.md#swr-sys-004-контракт-предметного-обработчика) для ранцевого типа.

**Требование.** Обработчик ранцевых задач должен быть доступен управлению сессиями под квалификатором «Backpack» и вызываться для задач конфигураций с этим квалификатором.

Вызов генерации происходит при создании набора, вызов проверки — после допуска ответа. Обработчик не получает и не изменяет правила срока, попытки и принадлежности: они остаются у управления сессиями. Порядок вызова определён в [формировании задач](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-004-формирование-задач) и [передаче профильной проверке](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-010-передача-профильной-проверке).

Источники: SR-KNAP-001; SWR-SYS-004.

### SWR-KNAP-002. Случайный выбор варианта

Ранцевая часть конфигурации не различает учебные варианты: оба вида заданий обслуживаются одним квалификатором. Конкретный вариант каждого задания выбирается при генерации так, чтобы состав набора не предопределял тип всех ранцевых задач. Выбор не управляется параметрами пользователя и не зависит от предыдущих задач сессии.

**Требование.** При генерации задачи для сессии ПО должно выбирать вариант случайно из двух поддерживаемых.

Выбранный вариант фиксируется в сохранённом условии и далее используется проверкой без повторного выбора. Системное основание — [выбор варианта ранцевой задачи](../04_Системные_требования/Ранцевые_задачи.md#sr-knap-001-выбор-варианта-ранцевой-задачи).

Источник: SR-KNAP-001.

## 3. Генерация условия

### SWR-KNAP-003. Генерация сообщения

Сообщение определяет, какие элементы тяжёлого ранца суммируются при шифровании, и входит как в условие, так и в проверяемый ответ. Учебное сообщение должно быть коротким для ручного решения и содержать достаточно нулей, чтобы расшифровка жадным алгоритмом была наглядной.

**Требование.** Сгенерированное сообщение должно быть случайной последовательностью логических значений длиной от 3 до 5 с долей ложных значений не менее трети.

Сгенерированное сообщение сохраняется в условии и сравнивается с переданным в ответе. Параметры длины относятся к задачам в сессиях; редакционные генерации принимают сообщение пользователя по SWR-KNAP-013.

Источники: SR-KNAP-001, SR-KNAP-002.

### SWR-KNAP-004. Сокрытие параметров условия

Выдача полного набора данных превратила бы задание в чтение ответа. Поэтому условие скрывает большую часть лёгкого ранца, оставляя открытыми отдельные элементы, и может не содержать множитель. Степень сокрытия ограничена требованием восстанавливаемости: по условию должны однозначно достраиваться все величины криптосистемы.

**Требование.** В условии открытыми должны оставаться не более двух элементов лёгкого ранца; множитель преобразования может не включаться в условие.

Сокрытие выполняется при генерации и сохраняется вместе с условием: повторное чтение сессии выдаёт те же данные. Восстановление скрытого опирается на математические свойства последовательности варианта; полная проверка достроенных величин выполняется по SWR-KNAP-009. Системное основание — [частично скрытое условие](../04_Системные_требования/Ранцевые_задачи.md#sr-knap-002-частично-скрытое-условие).

Источник: SR-KNAP-002.

### SWR-KNAP-005. Супервозрастающий лёгкий ранец

Для супервозрастающего варианта лёгкий ранец обязан строго возрастать: каждый элемент больше суммы всех предыдущих. Это свойство используется и жадной расшифровкой, и проверкой ответа. Последовательность, переданная или построенная с нарушением свойства, не образует допустимую криптосистему данного варианта.

**Требование.** Для супервозрастающего варианта лёгкий ранец должен быть приведён к строго сверхвозрастающей последовательности заданной размерности.

Приведение выполняется при генерации; размерность соответствует параметрам задачи. Проверка ответа повторно устанавливает свойство для переданного ранца — см. SWR-KNAP-009.

Источники: SR-KNAP-001, SR-KNAP-004.

### SWR-KNAP-006. Лёгкий ранец на степенях

Вариант на степенях строит лёгкий ранец из последовательных степеней выбранного основания. Такая последовательность автоматически сверхвозрастает, что сохраняет применимость общей схемы проверки. Основание выбирается из фиксированного набора простых чисел.

**Требование.** Для варианта на степенях элементы лёгкого ранца должны строиться как степени выбранного основания.

Выбранное основание фиксируется в данных генерации и определяет ожидаемые элементы при проверке. Системное основание — [вариант на степенях](../04_Системные_требования/Ранцевые_задачи.md#sr-knap-006-вариант-на-степенях); известное отклонение в сопоставлении элементов приведено в разделе 8.

Источники: SR-KNAP-001, SR-KNAP-006.

### SWR-KNAP-007. Сохранение сгенерированной задачи

Построенное условие должно стать данными создаваемой сессии, а не промежуточным значением в памяти генератора. Вместе с условием сохраняются вариант и принадлежность задачи. Отказ генерации или сохранения обрабатывается общим правилом полного набора: частичная сессия не остаётся активной.

**Требование.** Построенная задача должна сохраняться вместе с вариантом и принадлежностью, а её условие — передаваться в состав создаваемой сессии до подтверждения операции создания.

Сохранённое условие затем используется при проверке без повторной генерации. Транзакционные границы операции создания определены [правилом сохранения набора](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-005-сохранение-созданного-набора) домена сессий; ранцевой обработчик участвует в ней как источник условия.

Источники: SR-KNAP-001, SR-KNAP-002; SWR-SYS-003, SWR-SES-004.

## 4. Проверка решения

### SWR-KNAP-008. Предварительная сверка ответа

До математического сравнения устанавливается, что ответ соответствует схеме ранцевого типа: передан полный набор полей, размерность — положительное число, сообщения — списки логических значений, целые величины — десятичные строки, ранцы — списки таких строк. Состав полей подтверждается настоящим документом как владелец типа в соответствии с [контрактом](Контракты_сессий.md#ранцевая-задача).

**Требование.** До предметного вердикта ПО должно сверить вариант и полноту обязательных полей ответа по схеме сохранённого варианта задачи; несоответствие должно приводить к отказу без предметной проверки.

Переданный вариант сравнивается с вариантом сохранённого условия: совпадение обязательно, подмена не допускается. Категория ошибки формы задаётся контрактом сессий (`INVALID_REQUEST`) и не расходует попытку; далее допустимый ответ передаётся математической проверке. Разделение стадий следует [правилу проверки формата](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-009-проверка-формата) домена сессий.

Источники: SR-KNAP-003; SR-SES-009, SWR-SES-009, SWR-SES-022.

### SWR-KNAP-009. Пошаговая проверка величин

Предметная проверка перебирает величины криптосистемы по установленному порядку: длину и элементы сообщений и ранцев, сверхвозрастаемость, соотношение модуля с суммой лёгкого ранца, взаимную простоту множителя, тяжёлый ранец, обратный множитель, шифртекст и расшифрованное сообщение. Расшифровка выполняется жадным алгоритмом по супервозрастающей последовательности; дополнительно устанавливается положительность элементов ранцев.

**Требование.** ПО должно проверять величины, перечисленные в SR-KNAP-004, поэтапно, включая расшифровку жадным алгоритмом по супервозрастающей последовательности и положительность элементов ранцев.

Вычисление конечно и не запускает собственных фоновых процессов. Его длительность входит в [предел обработки](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-020-предел-обработки) принятого ответа: поздний результат не фиксируется, а операция завершается технической категорией без расхода попытки. Для варианта на степенях состав фактически проверяемых величин уже перечня — см. раздел 8.

Источник: SR-KNAP-004; SR-SES-012.

### SWR-KNAP-010. Диагностика неверной величины

Первая несовпавшая величина определяет текст диагностики. Пояснение относится к завершённой неверной попытке и позволяет студенту найти ошибку в собственной цепочке вычислений. Дальнейшие величины после первого несовпадения не сравниваются: вердикт уже определён.

**Требование.** При первом несовпадении ПО должно возвращать вердикт «неверно» с указанием величины, не прошедшей проверку.

Диагностика передаётся в поле пояснения предметного результата; при верном решении поле отсутствует. Текст не участвует в определении категорий отказа — они различаются машинными кодами по [контракту ошибок](Контракты_сессий.md#коды-и-представление-ошибок).

Источник: SR-KNAP-005.

### SWR-KNAP-011. Защита итогового состояния

Повторное обращение к завершённой задаче не должно запускать математическую проверку. Решение принимается по сохранённым данным задачи, поэтому состояние клиента и повторные соединения не влияют на запрет второй попытки. Восстановление отображения выполняется чтением сессии.

**Требование.** Для задачи в итоговом состоянии обработчик должен отклонять новый ответ без повторной предметной проверки, сохраняя прежний результат.

Отказ выполняется до вычисления величин. Внешняя категория определена контрактом сессий (`TASK_FINALIZED`); порядок установлен [правилом повторного ответа](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-013-сохранение-итогового-состояния) домена сессий.

Источники: SR-KNAP-007; SR-SES-008, SWR-SES-013.

## 5. Редакционные генерации

### SWR-KNAP-012. Генерация по варианту

Редакционный запрос без дополнительных параметров выдаёт эталон выбранного варианта. Недостающие данные выбираются системой: основание — из фиксированного набора простых чисел, остальные параметры — по правилам варианта. Результат содержит полный набор величин и служит материалом для разбора решения.

**Требование.** Запрос выбранного варианта без дополнительных параметров должен строить эталон с полным решением; параметры, не указанные в запросе, выбираются ПО, в том числе основание — из фиксированного набора простых чисел.

Редакционная генерация не связана с сессиями: она не проверяет допуски и не расходует попытки. Состав выдачи соответствует [эталонной задаче](../04_Системные_требования/Ранцевые_задачи.md#sr-knap-008-редакционная-задача-по-варианту).

Источник: SR-KNAP-008.

### SWR-KNAP-013. Генерация с параметрами

Параметры преподавателя делают эталон воспроизводимым в методических целях: размерность, вариант, сообщение, лёгкий ранец и множитель задаются запросом. Система проверяет математическую допустимость до построения; нарушение взаимной простоты множителя с модулем делает обратное преобразование невозможным и отклоняется.

**Требование.** Запрос с параметрами должен использовать переданные размерность, вариант, сообщение, лёгкий ранец и множитель; взаимная простота множителя с модулем должна проверяться до построения эталона.

Отклонение сопровождается диагностикой причины; частично построенный эталон не выдаётся. Отказ редакционной генерации не влияет на сессии и попытки.

Источник: SR-KNAP-009.

### SWR-KNAP-014. Диспетчеризация по варианту

Редакционные запросы двух вариантов использует общий вход, поэтому перед построением выбирается решатель соответствующего варианта. Ошибка выбора привела бы к эталону другой криптосистемы при корректно указанном варианте. Требование фиксирует обязанность; фактическое отклонение текущей реализации для варианта на степенях приведено в разделе 8, п. 1.

**Требование.** Редакционный запрос должен направляться решателю соответствующего варианта.

Выбор выполняется по варианту запроса; результат диспетчеризации — эталон, соответствующий указанному варианту по составу величин.

Источники: SR-KNAP-008, SR-KNAP-009.

### SWR-KNAP-015. Генерация без сохранения

Редакционные примеры не являются попытками и не должны попадать в хранилище сессий. Результат строится на лету и возвращается напрямую; повторный запрос выполняет генерацию заново.

**Требование.** Результаты редакционных генераций не должны записываться в хранилище.

Правило не затрагивает сохранение задач, создаваемых в сессиях по SWR-KNAP-007.

Источник: SR-KNAP-010.

## 6. Хранение

### SWR-KNAP-016. Сохранность условий

Условия сгенерированных ранцевых задач должны переживать перезапуск приложения: вместе с вариантом и принадлежностью они образуют данные, по которым выполняется проверка и чтение результата. Списковые величины хранятся в текстовом представлении колонок и восстанавливаются без изменения значений.

**Требование.** Условия сгенерированных ранцевых задач должны сохраняться между запусками приложения вместе с вариантом и принадлежностью; списковые величины — в текстовом представлении; сохранённые условия доступны для просмотра истории.

Сохранённые условия читаются историей задач без повторной генерации. Общие границы сохранения и восстановления определены [правилом сохранности](DOC-06_Программные_требования.md#swr-sys-008-сохранность-завершённых-данных) DOC-06.

Источники: SR-SYS-007; SWR-SYS-008.

## 7. Трассировка и описательные проверки

## 8. Известные особенности

Фактическое поведение реализации, расходящееся с требованиями выше или требующее командного решения. Каждая позиция — кандидат DEF на формальной инспекции DOC-06.3 или вопрос к версии 1.0.

1. В диспетчеризации редакционных запросов для варианта на степенях фактически вызывается решатель супервозрастающего варианта; ветвь решателя степеней недостижима. SWR-KNAP-014 фиксирует обязанность, расхождение — предмет решения к v1.0.
2. Для варианта на степенях расшифрованное сообщение не проверяется (в коде отмечено как незавершённое). SR-KNAP-006 описывает схему целиком; фактический состав проверок уже — предмет уточнения к v1.0.
3. Приведение лёгкого ранца варианта на степенях сравнивает элементы со строковым представлением степеней основания.
4. Поле варианта в предметном ответе передаётся как наименование на русском языке; сверка варианта идёт по наименованию, а не по коду перечисления. Отражено в [контракте сессий](Контракты_сессий.md#ранцевая-задача) как строка варианта и подлежит отражению в DOC-08.
5. Редакционный контроллер помечен в коде как устаревший, но остаётся доступным; судьба его операций — вопрос к v1.0.
6. Арифметика (наибольший общий делитель, обратный элемент) реализована внутри домена; математическая библиотека домена Эль-Гамаля не используется. При чтении документов домены не смешиваются.

## 9. Условия следующей версии

Численные пределы размерности и длительности генерации не устанавливаются до решения владельца конфигураций.
