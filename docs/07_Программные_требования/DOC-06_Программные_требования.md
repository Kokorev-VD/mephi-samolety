## 1. Назначение и границы

Документ распределяет общие системные обязательства между логическими программными компонентами и определяет условия их совместной работы. Подсистемные требования уточняют эти обязательства; в текущую редакцию включён [DOC-06.2 по сессиям](DOC-06.2_Сессии_задач_и_планировщик.md).

Компонент здесь означает область ответственности ПО. Такое разделение не требует отдельных сервисов или применения единственного архитектурного стиля. Математические алгоритмы, модель хранения и полный справочник HTTP-операций не дублируются в общей части.

## 2. Ответственность и связи

| Компонент | Вход и результат | Ответственный за предметную часть |
|---|---|---|
| Проверка доступа | Учётные данные запроса; подтверждённый пользователь и полномочия либо отказ | Кокорев |
| Конфигурации | Пользователь и его группа; доступный состав набора либо отказ | Самбьюи |
| Управление сессиями | Запрос создания или ответа; сессия и предметный результат либо категория отказа | Анохин |
| Генераторы и проверяющие | Тип и настройки; условие. Сохранённое условие и ответ; предметный вердикт либо ошибка проверки | Владельцы криптографических доменов |
| Контроль срока | Сохранённые времена и сведения о принятых ответах; завершение просроченных задач | Анохин |
| Хранение | Данные и изменения состояния; согласованное сохранение и чтение | Анохин для правил сессий, Самбьюи для общей модели и инфраструктуры |

При создании набора управление сессиями получает пользователя и доступную конфигурацию, вызывает генераторы и сохраняет состав. При отправке ответа оно проверяет допуск, обращается к профильному проверяющему и сохраняет результат. Контроль срока использует те же данные времени и завершения; отдельного правила подсчёта итога у него нет.

### Последовательность создания набора

Компонент приёма операции передаёт управлению сессиями подтверждённого пользователя и имя конфигурации. Затем определяется группа пользователя и запрашивается доступный состав набора. Эти действия не заменяются доверием к переданному клиентом идентификатору группы.

По составу вызываются соответствующие генераторы. Полученные условия, типы и принадлежность задач образуют данные создаваемой сессии. Подтверждение выдаётся после сохранения полного набора. При отказе генерации или сохранения частичный набор не должен оставаться доступной активной сессией.

Ограничение одной активной сессии охватывает всю операцию создания. Отдельная предварительная проверка без согласования последующего сохранения недостаточна: два обращения могли бы одновременно увидеть отсутствие сессии. Конкретный механизм защиты выбирается при проектировании хранения, но программное обязательство уже определено.

### Последовательность обработки ответа

Приём запроса фиксирует серверное время его поступления. Управление сессиями устанавливает задачу, проверяет принадлежность, состояние и срок, затем проверяет формат по схеме сохранённого типа. Предметный обработчик получает только допустимый ответ с условием выбранной задачи.

После получения вердикта управление сессиями согласованно сохраняет результат задачи и вычисляет итог набора. Контроль срока использует те же правила завершения и сведения о своевременном запросе. Если ответ получен до срока, момент окончания вычисления не отменяет его своевременность.

Общие требования к обмену определяют смысл данных на этих переходах. Поля и HTTP-коды раскрываются в интерфейсных спецификациях; математические критерии правильности — в предметных подсистемах. Такое распределение позволяет уточнять внутреннее устройство части, сохраняя её обязательства перед остальными участниками.

## 3. Общие программные требования

Все требования ниже обязательны. Ссылки SR ведут к [системному разделу интеграции](../04_Системные_требования/Интеграция.md); проверки являются описательными.

### SWR-SYS-001. Передача личности пользователя

Входной компонент проверяет доступ и передаёт остальным частям подтверждённого пользователя. Дальнейшие операции используют этот результат как контекст выполнения. Имя конфигурации, UUID задачи и другие параметры остаются данными операции; они не назначают ей другого владельца. Системное основание такого разделения дано в [единой личности пользователя](../04_Системные_требования/Интеграция.md#sr-sys-001-единая-личность-пользователя).

**Требование.** Компоненты пользовательских операций должны получать личность пользователя из результата проверки доступа. Параметры тела и строки запроса не должны заменять подтверждённого владельца операции.

При создании сессии контекст используется для определения группы, при ответе — для проверки владельца задачи, при чтении — для отбора собственной сессии. Повторять логику выдачи полномочий в каждом предметном проверяющем не требуется. Порядок пользовательских операций определён в [обработке ответа](DOC-06.2_Сессии_задач_и_планировщик.md#3-обработка-ответа), а доступ по HTTP — в [контракте операций](Контракты_сессий.md#операции).

Источник: SR-SYS-001. Проверка: подстановка чужого идентификатора не изменяет пользователя, от имени которого выполняется операция.

### SWR-SYS-002. Общие идентификаторы

Создание, хранение, проверка и выдача результата обращаются к одному набору объектов. Программные компоненты должны передавать уже назначенные ID, а не создавать похожие идентификаторы при каждом преобразовании данных. Это особенно важно при формировании ответов и восстановлении после перезапуска, когда объект проходит через несколько представлений.

**Требование.** Компоненты должны сохранять и передавать идентификаторы пользователя, сессии и задачи без повторного назначения при обмене между ними.

ID задачи в выдаче используется как `statementId`, а результат содержит этот же ID как `problemId`. По связи с сессией определяется владелец. Формат передачи не должен менять принадлежность или связывать результат с соседней задачей одного типа. Поля описаны в [контракте результата](Контракты_сессий.md#результат-и-отказы), а системное обязательство — в [связности данных задачи](../04_Системные_требования/Интеграция.md#sr-sys-002-связность-данных-задачи).

Источник: SR-SYS-002. Проверка: задача в выдаче, проверке и хранилище имеет одну принадлежность и один идентификатор.

### SWR-SYS-003. Состав созданной сессии

Компонент конфигураций предоставляет доступный состав нового набора. После создания управление сессиями работает с сохранёнными задачами. Повторное получение текущей конфигурации во время проверки не должно менять ранее выданное условие. Поэтому данные выбора и данные уже созданного задания имеют разные роли в программе.

**Требование.** Управление сессиями должно сохранять состав и условия выданных задач по результату выбора доступной конфигурации; последующая проверка должна использовать эти сохранённые данные.

Сохранённые тип и условие передаются проверяющему без повторной генерации. Так ответ сопоставляется с тем заданием, которое получил пользователь. Порядок сохранения полного набора дан в [создании сессии](DOC-06.2_Сессии_задач_и_планировщик.md#2-создание-сессии), а последствия ошибки — в [согласованном сохранении](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-005-сохранение-созданного-набора). Системный смысл разделения раскрыт в [согласованном составе набора](../04_Системные_требования/Интеграция.md#sr-sys-003-согласованный-состав-набора).

Источники: SR-SYS-003, SR-SYS-004. Проверка: изменение конфигурации после создания не меняет условия уже выданной задачи.

### SWR-SYS-004. Контракт предметного обработчика

У генератора и проверяющего разные входы и результаты. Генерация создаёт условие по составу набора. Проверка получает уже сохранённое условие и ответ пользователя. Её результат должен отличать правильность решения от невозможности выполнить проверку: это определяет, возникает ли предметный вердикт и расходуется ли попытка.

**Требование.** Предметный обработчик должен различать генерацию условия и проверку ответа, а результат проверки — завершённый вердикт, ошибку формата или технический сбой без вердикта.

Проверяющий не должен самостоятельно назначать владельца, менять общий срок или закрывать всю сессию. Эти решения остаются у управления сессиями. Предметная часть отвечает за свой алгоритм и диагностику неверного расчёта. Подробное разделение видов ответа дано в [предметной схеме](Контракты_сессий.md#предметный-ответ) и [результате операции](Контракты_сессий.md#результат-и-отказы), а выбор обработчика — в [подсистемном требовании](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-010-передача-профильной-проверке).

Источники: SR-SYS-004, SR-SYS-009. Проверка: обработчик вызывается по сохранённому типу; сбой не возвращается как неверное решение. Форматы своих данных подтверждает владелец домена.

### SWR-SYS-005. Согласованное сохранение

Сохранение связывает результат одной задачи с агрегированным состоянием её набора. Если эти изменения подтвердить независимо, чтение может получить несовместимые сведения: задача завершена, а итог сессии вычислен без неё. Программная операция должна иметь общую границу фиксации, соответствующую [системному результату сохранения](../04_Системные_требования/Интеграция.md#sr-sys-005-согласованность-результата-и-состояния).

**Требование.** Изменение состояния задачи и вычисление соответствующего состояния сессии должны сохраняться как одна согласованная операция до выдачи подтверждённого результата.

Математическое вычисление выполняется до короткой транзакции записи. В транзакции проверяется допустимость фиксации, сохраняется вердикт и пересчитывается набор. После её завершения ответ может подтверждать результат клиенту. Порядок блокировки и конкуренция нескольких ответов раскрыты в [согласовании параллельных событий](DOC-06.2_Сессии_задач_и_планировщик.md#согласование-параллельных-событий); восстановление использует [сохранённую запись операции](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-021-запись-принятой-операции).

Источник: SR-SYS-005. Проверка: сбой сохранения не оставляет подтверждённый пользователю вердикт с противоречащим ему состоянием сессии.

### SWR-SYS-006. Общий серверный срок

Программные части не должны получать разные интервалы решения из собственных таймеров. Общий срок выводится из сохранённого времени создания сессии; своевременность отдельного запроса — из его времени поступления. Эти значения нужны и обработчику ответа, и фоновому контролю, и восстановлению после перезапуска.

**Требование.** Обработка ответов и контроль просрочки должны использовать одно сохранённое время создания сессии, один срок и зафиксированное сервером время получения ответа.

После перезапуска начало работы приложения не заменяет начало набора. После ожидания в очереди старт проверяющего не заменяет момент приёма. Отдельный предел обработки тоже продолжает отсчитываться от прежнего `t_in`. Обозначения даны в [карточке домена](../03_Карточки_доменов/Сессии_задач.md#срок-и-попытка), а программные обязанности разделены между [сохранением времени](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-006-сохранение-времени-создания), [регистрацией поступления](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-007-регистрация-времени-поступления) и [пределом обработки](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-020-предел-обработки).

Источники: SR-SYS-006, SR-SYS-007. Проверка: перезапуск не продлевает срок, а задержка планировщика не меняет допустимость ответа.

### SWR-SYS-007. Категория результата операции

Внешний интерфейс получает результаты от нескольких программных частей. Он должен сохранить их категорию, чтобы клиент отличал предметное решение от отказа выполнить операцию. Самого текста сообщения для этого недостаточно: одинаковые слова не определяют ни состояние задачи, ни возможность повторного ответа.

**Требование.** Компонент обработки запроса должен сохранять различие между предметным вердиктом и отказами при передаче результата внешнему интерфейсу.

Сохранённый неверный вердикт передаётся предметным результатом с `isOk = false`. Ошибка формата, нарушение доступа, просрочка и технический сбой передаются машинными кодами из [контракта ошибок](Контракты_сессий.md#коды-и-представление-ошибок). При преобразовании внутренних результатов нельзя превращать исключение проверяющего в отрицательный предметный ответ. Эти различия следуют из [системного требования категорий отказа](../04_Системные_требования/Интеграция.md#sr-sys-009-различение-отказов).

Источники: SR-SYS-008, SR-SYS-009. Проверка: неверное решение, нарушение доступа, ошибка формата, просрочка и технический сбой распознаются как разные категории; соответствие HTTP-кодам задано контрактом сессий и сохраняется в общем справочнике DOC-08.

### SWR-SYS-008. Сохранность завершённых данных

Состояние системы должно переживать завершение процесса приложения. В хранилище остаются не только конечные значения, но и принадлежность, условия и временные отметки, необходимые для их чтения. Иначе после восстановления нельзя было бы определить, кому принадлежит результат и по какому заданию он получен.

**Требование.** Хранение должно обеспечивать восстановление идентификаторов, принадлежности, условий, времени создания и завершённых результатов сессий после перезапуска приложения.

Готовый вердикт используется как сохранённый факт операции, без новой математической попытки. Принятая операция без вердикта восстанавливается по собственной записи, сохраняя предел времени. Это различие связывает [системную сохранность](../04_Системные_требования/Интеграция.md#sr-sys-007-сохранность-данных-сессии) с [восстановлением операции](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-021-запись-принятой-операции) и [чтением сессии](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-023-чтение-сессии-и-результата). Подтверждённый результат должен быть доступен клиенту даже после потери исходного соединения.

Источник: SR-SYS-007. Проверка: после восстановления выдаётся прежний итог и применяется прежний срок. Для принятого незавершённого ответа используются сохранённая операция и прежний срок обработки по DOC-06.2.

### Обязательства на границах подсистем

Безопасность задаёт подтверждённого пользователя и условия доступа; сессии используют этот результат. Конфигурации предоставляют доступный состав, по которому создаётся набор. Предметные обработчики различают вердикт и невозможность проверки; общий интерфейс сохраняет это различие при сообщении результата.

Задача, итог сессии и запись обработанного ответа сохраняются в одной транзакции. Незавершённая запись служит основанием восстановления. Время получения ответа, общий срок и предел обработки сохраняются при повторном запуске; вычислительная задержка не превращает своевременный ответ в поздний.

## 5. Связи и проверка редакции

Требования SR-SYS-001–SR-SYS-009 раскрыты восемью SWR-SYS выше. Для каждого указаны источник и ожидаемая проверка. Детализация SR-SES находится в DOC-06.2. Описательные кейсы DOC-10 связываются с этими требованиями в матрице DOC-09.

Проверка редакции охватывает единый контракт ошибок, точность целых чисел, доступ по владельцу, согласованность сохранения и восстановление принятого ответа. [DOC-05](../04_Системные_требования/DOC-05_Системные_требования.md#5-распределение-ответственности) задаёт распределение ответственности.
