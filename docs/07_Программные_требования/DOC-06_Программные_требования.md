## 1. Назначение и границы

Преподаватель готовит контрольное мероприятие — работу с заданным составом и порядком заданий, которую он назначает одной из закреплённых за ним учебных групп и публикует в расписании. Позиция описывает, какое задание получит студент. Когда студент приступает к работе, программа выдаёт ему собственные задачи и открывает личную сессию. Сессия связывает эти задачи с владельцем, общим сроком решения и результатами. Для самостоятельной практики состав сессии берут из **шаблона набора задач** — именованного перечня типов заданий в порядке выдачи. Такая сессия не засчитывается как участие в контрольном мероприятии.

Документ распределяет работу между программными компонентами. Компонент — часть программы, которой поручена определённая обязанность. Например, предметный обработчик проверяет вычисления студента и возвращает вердикт «верно» или «неверно». Управление сессиями устанавливает, чей это ответ и можно ли записать вердикт. В [общих требованиях](#3-общие-программные-требования) определены обязательства этих компонентов друг перед другом. Остальные [требования платформы](Программные_требования_платформы.md) и [модель сохраняемых данных](#приложение-а-модель-данных) также входят в DOC-06. Размещение компонентов описывает [архитектура ПО](../09_Архитектура_и_API/DOC-07_Архитектура.md).

## 2. Ответственность и связи

| Часть ПО | Решение и данные, которые получает следующая часть |
|---|---|
| Аутентификация и пользователи | Устанавливает личность и роли. Группу студента определяет по номеру в подтверждённом профиле НИЯУ МИФИ. Хранит назначения групп преподавателям, сделанные администратором. |
| Шаблоны и контрольные мероприятия | Сохраняет состав, при публикации закрепляет редакцию, выбранный режим повторов, группу и границы окна. Для контроля возвращает состав опубликованного мероприятия, для самостоятельной практики — доступного шаблона. |
| Управление сессиями | Ограничивает число активных наборов, создаёт задачи, принимает ответ и выбирает обработчик по сохранённому типу. Решает, можно ли записать вердикт. |
| Предметная подсистема | По запросу генерации возвращает условие. По запросу проверки получает выданное условие и ответ, возвращает вердикт либо сообщает причину, по которой проверка невозможна. |
| Контроль срока | Находит незавершённые задачи с истёкшим сроком. Учитывает своевременно принятые ответы и применяет общий для сессии порядок подведения итога. |
| Хранение | Связывает записи пользователя, сессии, задач и операций, обеспечивает совместную фиксацию связанных изменений и чтение после перезапуска. |

### Подготовка и публикация контрольного мероприятия

Преподаватель выбирает задания и указывает их порядок. В черновике он может отложить решение о повторных прохождениях (`repeatAllowed`). Для пользовательского задания он вводит один или несколько вариантов с эталонными ответами. Черновик можно сохранить пустым. Для публикации нужны хотя бы одно задание и явный выбор — разрешить повтор или запретить. При верно заданных группе и времени пустой состав проверяют первым. При публикации сервер проверяет, что администратор закрепил указанную группу за преподавателем, и сохраняет моменты открытия и закрытия. Сразу после публикации группа видит карточку мероприятия в расписании. Старт доступен с момента открытия и до момента закрытия по серверным часам. Преподаватель может видеть результаты своих мероприятий в закреплённых за ним группах. Подробнее см. [правила доступа и прохождения контрольного мероприятия](../02_Техническое_задание/DOC-02_Техническое_задание.md#правила-доступа-и-прохождения-контрольного-мероприятия).

Для каждого вида задания его программный модуль предоставляет две операции. Первая формирует условие или выбирает его из подготовленных вариантов. Вторая проверяет ответ по данным, закреплённым при выдаче. Так работают модуль ранцевых задач (`BACKPACK`), модуль шифрования по схеме Эль-Гамаля (`EL_GAMAL`) и модуль текстовых ответов с эталоном преподавателя (`CUSTOM_TEXT`). Реестр связывает название типа `type` с его модулем. Через реестр компонент мероприятий получает [виды заданий и схемы ответов](Программные_требования_платформы.md#swr-sys-015-единый-интерфейс-вида-задания). Схема определяет, какие поля клиент передаст и какого они должны быть типа. Закрытые данные для проверки остаются у сервера. Управление сессиями отвечает за права, срок, попытку и фиксацию вердикта.

### Последовательность создания набора

При самостоятельной практике управление сессиями находит включённый шаблон группы. Для контроля оно выбирает зафиксированный при публикации состав по `assessmentId` и проверяет группу и время старта. Если прежнее прохождение завершилось, новый набор разрешён только в открытом окне при закреплённом `repeatAllowed = true`. Прежние сессии и их вердикты сохраняются. Затем запрашивает условия в заданном порядке и сохраняет задачи вместе с их владельцем через связь с сессией. Повторение типа в шаблоне означает отдельное задание на каждой позиции. Подтверждение создания допускается, когда сохранён весь набор. Если генерация или запись оборвалась, пользователю не должна остаться частично созданная активная сессия. Ограничение одной активной сессии действует и при одновременном создании двумя запросами.

### Последовательность обработки ответа

Сервер отмечает время получения полного запроса. При регистрации управление сессиями связывает подтверждённого отправителя с владельцем задачи. Чужой или отсутствующий объект даёт одинаковый отказ 404. Такое обращение не создаёт открытой операции для запрошенной задачи. Для собственной задачи сервер сохраняет до ожидания в очереди тело ответа и сведения, по которым можно восстановить работу с исходной отметкой времени.

После проверки допуска и формата управление сессиями атомарно предоставляет право предметной проверки одному ответу на задачу. Если два ответа поступили параллельно, тело проигравшего запроса не заменит тело принятого. Пока идёт вычисление, второй допустимый ответ на ту же задачу получает `409 CHECK_IN_PROGRESS`. Предметный обработчик получает исходное условие и решение. При фиксации управление сессиями проверяет, действует ли ещё право на запись, и завершает операцию по [SWR-SYS-005] и [SWR-SYS-006]. После перезапуска для открытой операции сохраняются та же задача, ответ и предел обработки.

## 3. Общие программные требования

Все восемь требований обязательны. Для каждого в [таблице связей](#5-связи-и-проверка-редакции) указаны системные основания и признак, по которому можно проверить выполнение.

<a id="swr-sys-001"></a>

### SWR-SYS-001. Передача личности пользователя

Компоненты должны выполнять операции с сессией от имени пользователя, установленного при аутентификации. При создании управление сессиями проверяет, что шаблон самостоятельной практики или назначение контрольной работы доступно подтверждённой университетской группе студента. При отправке ответа и чтении оно сопоставляет его идентификатор с владельцем сохранённой сессии. Значения из строки запроса и тела не могут заменить подтверждённого пользователя.

<a id="swr-sys-002"></a>

### SWR-SYS-002. Общие идентификаторы

При выдаче задания, регистрации ответа и чтении результата компоненты должны сохранять идентификаторы задачи, сессии и пользователя и связи между ними. Идентификатор выданной задачи `id` передаётся в запросе как `statementId` и возвращается в предметном результате как `problemId`. Две задачи одного типа в одной сессии различаются по идентификаторам.

<a id="swr-sys-003"></a>

### SWR-SYS-003. Состав созданной сессии

При создании управление сессиями должно закрепить за сессией задачи включённого шаблона практики либо опубликованной контрольной работы и сохранить тип, порядок и выданное условие каждой задачи. Для проверки следует брать тип и условие из этой записи. Если после выдачи преподаватель изменил состав либо отключил шаблон, выданная задача сохраняет прежнее условие и тип проверки.

<a id="swr-sys-004"></a>

### SWR-SYS-004. Контракт предметного обработчика

Предметная подсистема должна различать два обращения. При генерации она по типу и настройкам формирует условие. При проверке она принимает сохранённое условие и решение, сообщает предметный вердикт, ошибку формата либо технический сбой без вердикта. Вызов проверяющего выбирает управление сессиями по сохранённому типу задачи. В его же ведении остаются принадлежность, допуск по времени и итог набора. Для поддерживаемых типов формы решений заданы в [контрактах сессий](Контракты_сессий.md#предметный-ответ).

<a id="swr-sys-005"></a>

### SWR-SYS-005. Согласованное сохранение

Транзакция объединяет несколько изменений хранилища. После фиксации читателю доступны все изменения вместе. При откате сохраняется состояние до этой записи.

Управление сессиями должно в одной транзакции записать вердикт, изменить состояние задачи, пересчитать состояние её сессии и завершить запись принятой операции. Вычисление выполняется до этой транзакции. В момент фиксации операция ещё должна оставаться допустимой. Внешний интерфейс выдаёт подтверждение только после успешной записи.

Сессия остаётся `NEW`, пока в ней есть незавершённая задача. Когда завершена последняя, набор получает `SOLVED`, если верно решены все задачи, либо `FAILED`, если хотя бы одна завершена неуспешно. Тот же расчёт применяется после фонового закрытия по сроку. Поэтому окончание последней незавершённой задачи само по себе не означает успешного решения набора.

<a id="swr-sys-006"></a>

### SWR-SYS-006. Общий серверный срок

Приём ответа и планировщик должны использовать один срок подачи `D` для всех задач сессии. Для практики он наступает через 20 минут после серверного времени создания `t0`. Для контрольного мероприятия действует более ранний из двух моментов — `t0 + 20 минут` или закреплённое при публикации время закрытия `closesAt`. Сервер возвращает этот срок в поле `deadlineAt`. Для ответа должно выполняться `t_in < D`, где `t_in` — время получения полного запроса сервером. В момент `D` новый ответ уже просрочен, независимо от времени последнего запуска планировщика.

У своевременно принятого ответа свой предел фиксации — строго до `t_in + 60 секунд`. Наступление `D` во время проверки не закрывает её досрочно. В момент достижения предела обработки незавершённая операция получает `CHECK_TIMEOUT`, дальнейшая фиксация вердикта исключена. Ожидание в очереди, расписание планировщика и перезапуск сохраняют исходные отметки времени. Если общего времени уже не осталось, задача без вердикта завершается по просрочке.

<a id="swr-sys-007"></a>

### SWR-SYS-007. Категория результата операции

Внешний интерфейс должен передавать клиенту категорию, установленную при обработке. Сохранённое неверное решение возвращается предметным результатом с `isOk = false` и завершает попытку. Ошибку формата, отказ в доступе, просрочку и техническую ошибку интерфейс передаёт соответствующим машинным кодом. Технический отказ без вердикта и ошибка формы ответа сохраняют попытку. До выдачи клиенту окончательного отказа обработчик закрывает операцию так, чтобы её прежний результат уже нельзя было записать. Если прервалась только связь с клиентом, открытая операция продолжает обрабатываться в исходный срок. Поля результата, структура ошибки и соответствие HTTP-статусам заданы в [контракте ошибок](Контракты_сессий.md#коды-и-представление-ошибок).

<a id="swr-sys-008"></a>

### SWR-SYS-008. Сохранность завершённых данных

После перезапуска хранилище должно вернуть прежние идентификаторы, принадлежность, состав, исходные условия, время создания, состояния и сохранённые предметные результаты. При чтении собственной сессии пользователю возвращается последний сохранённый результат каждой задачи без повторной проверки решения. Это правило действует и при потере ответа клиентом после успешной фиксации.

Если до сбоя принят ответ и вердикт ещё не записан, управление сессиями восстанавливает операцию по её записи с исходным телом и прежним пределом обработки. При истечении предела применяется [SWR-SYS-006]. Состав восстанавливаемых сведений приведён в [описании принятого ответа](#данные-принятого-ответа).

### Обязательства на границах подсистем

**Безопасность.** Операции с собственной сессией требуют аутентификации и роли `USER`. Компонент аутентификации проверяет JWT, переданный по схеме `Bearer` в заголовке `Authorization`. Управление сессиями отдельно устанавливает принадлежность конкретной задачи или сессии. Для постороннего пользователя обращение к чужой задаче или сессии даёт тот же ответ, что и обращение к отсутствующему объекту. Сведения для выбора шаблона определяет учётная запись. Основания — разделы [`TS.REQ.INT.BEARER`][TS.REQ.INT.BEARER] и [`TS.REQ.SEC`][TS.REQ.SEC] [технического задания](../02_Техническое_задание/DOC-02_Техническое_задание.md) и [SWR-SYS-001].

**REST-интерфейс.** Ресурсы сессий доступны через `/api` и идентифицируются по UUID. Операции создания, отправки решения и чтения используют согласованные JSON-представления. Большие целые в полях, заданных предметной схемой как десятичные строки, проходят через клиент и сервер без округления. Серверное время передаётся в UTC с миллисекундами. При потере ответа на отправку решения клиент может запросить свою сессию и сопоставить сохранённый результат с задачей по UUID. Основания — [`TS.REQ.INT.REST`][TS.REQ.INT.REST], [SR-SYS-008] и [контракт операций](Контракты_сессий.md#операции).

Самбьюи А.Ж. в редакции 1.2 уточнил логические структуры, ограничения связей и границы совместного сохранения для задачи 2.10. В редакцию 1.3 включено [приложение Б с физической моделью](Модель_данных.md): ER-диаграммы, таблицы, типы, ограничения и связи с API для задачи 3.9. Логическое описание ниже сохраняет предметные основания — [SWR-CFG-001–008](Конфигурации_и_модерация.md) и общие требования к идентификаторам, составу, срокам и сохранению [SWR-SYS-002]–[SWR-SYS-008]. Статус физической модели — проект для рассмотрения.

### Объекты и связи

Модель данных показывает, какие сведения сохраняются вместе и как по одной записи найти связанные с ней записи. Например, по задаче можно установить её сессию, а по сессии — учётную запись владельца. Общий тип `AbstractEntity` задаёт UUID (уникальный идентификатор записи) и время создания для семи перечисленных ниже сущностей. Имена в скобках обозначают соответствующие объекты в техническом описании.

1. **Пользователь (`User`).** У локальной записи есть уникальная электронная почта, имя и хеш локального пароля. Для подтверждённой университетской записи хранится устойчивый идентификатор `home.mephi.ru`, который однозначно связывает её с пользователем платформы. Группа студента определяется по номеру из доверенного профиля. Пользователю могут принадлежать несколько сессий, одновременно активна не более одной.
2. **Учебная группа (`UserGroup`).** Группа объединяет пользователей. У неё может быть несколько доступных шаблонов. Доступность определяется отдельно для каждой пары «группа — шаблон». Учебный номер группы используется при сопоставлении с университетским профилем.
3. **Назначение шаблона группе (`UserGroupProblemConfiguration`).** Запись связывает одну группу с одним шаблоном и хранит признак `enabled`. Отключение назначения меняет доступность шаблона для новых наборов этой группы.
4. **Шаблон набора задач (`ProblemConfiguration`).** Шаблон имеет имя и хранит упорядоченный список типов для генерации задач. Одно и то же значение может занимать несколько позиций. Группы получают доступ к шаблону через назначения.
5. **Сессия (`ProblemSession`).** Принадлежит одному студенту. Объединяет выданные ему задачи, хранит время создания, срок подачи `deadlineAt` и состояние. В контрольной сессии `assessmentId` указывает опубликованное мероприятие. При разрешённом повторе тот же студент получает новую сессию этого мероприятия с собственным UUID, сроком и результатами. Предыдущие прохождения остаются доступны по своим идентификаторам. Для самостоятельной практики `assessmentId = null`.
6. **Задача (`Problem`).** Задача принадлежит одной сессии. Её тип и условие определяются при выдаче. Состояние и зафиксированный результат используются для чтения и для подведения итога набора. При закрытии по просрочке предметный вердикт отсутствует.
7. **Ранцевая задача (`BackpackProblem`).** Предметная запись хранит параметры условия и сведения о результате ранцевой задачи. Принадлежность задачи пользователю и состояние его сессии определяются через `Problem` и `ProblemSession`. Требования к предметному хранению приведены в [DOC-06.3](DOC-06.3_Ранцевые_криптосистемы.md).

### Записи контрольных мероприятий и пользовательских заданий

Эти записи описывают целевую модель по требованиям к мероприятиям и выдаче вариантов. Они дополняют перечень Самбьюи. Одна логическая запись может быть представлена несколькими связанными записями хранения.

| Объект | Данные и связи |
|---|---|
| Пользовательское задание | Объединяет варианты задания типа `CUSTOM_TEXT`. Позиция состава ссылается на задание, для которого следует выбрать вариант. |
| Вариант задания | Хранит текст условия и соответствующий эталонный ответ. При выдаче студенту передают только условие. |
| Контрольное мероприятие | Хранит `assessmentId`, название, автора, упорядоченные позиции и выбор преподавателя `repeatAllowed`. В состоянии `DRAFT` неуказанный выбор сохраняется как неопределённый. Для публикации обязательно явное `true` или `false`. Публикация фиксирует состав, редакции вариантов и выбор повторов вместе с назначением и состоянием `PUBLISHED`. |
| Назначение мероприятия группе | Связывает мероприятие с одной учебной группой. Хранит `opensAt` и `closesAt`: первое значение строго меньше второго. Для студента назначение видно с момента публикации. Начать можно с `opensAt` включительно и до `closesAt` исключительно. |
| Группа преподавателя | Связывает учётную запись с ролью `TEACHER` и конкретную учебную группу. Изменять набор связей вправе администратор. Сервер использует действующие назначения для публикации и просмотра преподавателем результатов своих мероприятий. |
| Закрепление варианта | Связывает позицию выданного набора с личной сессией и выбранным вариантом. Обработчик выбирает вариант из опубликованной редакции. Условие и эталон для этой выдачи сохраняются до проверки. Повторное чтение или последующее изменение задания не заменяет вариант. |
| Зафиксированный вердикт | Принадлежит конкретной задаче личной сессии. Содержит идентификатор задачи, тип и итог предметной проверки. Подсистема сессий сохраняет вердикт вместе с состояниями задачи и набора. |

### Состав и ограничения логических структур

**Позиция** — отдельное место упорядоченного списка, а не уникальный тип задания. **Опубликованная редакция** — закреплённые при публикации сведения, по которым формируются все последующие прохождения мероприятия. Она отделена от изменяемого банка преподавателя. **Выданный вариант** — конкретная пара условия и закрытых данных проверки, закреплённая за задачей одной личной сессии.

| Структура | Сохраняемые сведения и ограничения |
|---|---|
| Назначение шаблона | Ссылки на существующие группу и шаблон, отдельное для этой пары значение `enabled`. Одна пара не получает двух противоречащих назначений. Отключение влияет на новый старт, сохраняя прежние задачи |
| Позиции шаблона или мероприятия | Принадлежность одному составу, место в порядке, код `type`; для `CUSTOM_TEXT` — ссылка на авторское задание. Внутри состава места различаются. Повторяющиеся типы и повторное использование упражнения не объединяют позиции |
| Черновик | UUID `assessmentId`, автор, название, позиции и трёхзначный выбор `repeatAllowed`: `null`, `true` или `false`. Пустой список допустим. Полная замена черновика сохраняет UUID; пропуск выбора в ней означает `null` |
| Опубликованная редакция | Тот же UUID мероприятия и автор, состояние `PUBLISHED`, одна группа, обе границы окна, непустой порядок позиций и явное логическое `repeatAllowed`. Для каждой текстовой позиции закрепляются все полные пары вариантов включённой редакции задания; конкретная пара выбирается при старте. Последующая правка банка не заменяет эту редакцию |
| Выданная задача | Собственный UUID, ссылка на сессию, место в выданном порядке, сохранённый тип и условие, состояние и вердикт. Для текстовой позиции сохраняется выбранная пара из опубликованной редакции. Несколько студентов могут получить одинаковую пару, но задачи у них разные |
| Личная сессия | Собственный UUID, один владелец, время создания, `deadlineAt`, состояние и полный состав задач. Для контроля — связь с одним `assessmentId`; для практики — `null`. Порядок выдачи сохраняется независимо от последующей правки шаблона |

Для названия шаблона, передаваемого параметром `configuration`, сохраняется возможность однозначно выбрать доступный шаблон в подтверждённой группе по [контракту создания сессии](../09_Архитектура_и_API/DOC-08_API_сессий.md#1-создание-сессии). Способ физического обеспечения этого ограничения здесь не предписывается.

Группа может иметь от нуля назначенных шаблонов; один шаблон может назначаться разным группам. У шаблона хранится упорядоченный список позиций без введения здесь нового ограничения его минимального размера. Черновик мероприятия содержит ноль или больше позиций, опубликованная работа — одну или больше. Одно авторское задание содержит один или больше полных вариантов и может использоваться в разных позициях. Опубликованное мероприятие связано ровно с одной группой и с нулём или больше личных сессий; каждая сессия содержит собственные задачи. Ноль прохождений допустим до первого старта студента.

Повторные прохождения одного студента связываются с тем же мероприятием разными UUID сессий. Поэтому пара «студент — мероприятие» не является уникальной для всей истории. Ограничение одной активной сессии пользователя применяется отдельно и при параллельном старте, по [SWR-SES-003](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-003). Запрет повтора по опубликованному `repeatAllowed = false` проверяется по истории прохождений и не стирает её. Текущая активная сессия мероприятия и последняя завершённая определяются по сохранённым связям; поле `sessionId` в расписании не заменяет остальные записи истории.

Назначение группы преподавателю хранится отдельно от автора мероприятия и членства студента. Отзыв назначения не меняет UUID или результаты уже созданных прохождений, но последующий запрос преподавателя проходит проверку действующего допуска. Сохранённая связь с автором сама по себе не даёт права чтения после отзыва. Основания — [правила групп и доступа](../02_Техническое_задание/DOC-02_Техническое_задание.md#правила-доступа-и-прохождения-контрольного-мероприятия).

### Совместная фиксация и неизменность опубликованных данных

Публикация сохраняет одной транзакцией состояние `PUBLISHED`, группу, обе границы окна, выбранный режим повторов, порядок позиций и редакции авторских вариантов. Проверка состава выполняется в этой же транзакции по [SWR-CFG-004](Конфигурации_и_модерация.md#swr-cfg-004) и [SWR-CFG-008](Конфигурации_и_модерация.md#swr-cfg-008). Не допускается состояние, при котором карточка уже видна в расписании, а состав или эталоны ещё читаются из изменяемого банка. Ошибка публикации сохраняет прежний черновик без частичного назначения.

При одновременной правке банка и публикации закрепляется согласованная редакция: условие и эталон каждой пары относятся к одной сохранённой версии. Последующая правка банка действует для будущих публикаций. После публикации состав, окно и выбор повторов этой работы не заменяются редактированием черновика. При одновременной правке мероприятия и публикации результат определяется порядком их фиксации; правка уже опубликованного мероприятия отклоняется.

Создание личного набора сохраняет сессию, все задачи, порядок и закреплённые варианты одной транзакцией по [SWR-SES-005](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-005) с составом по [SWR-SYS-003]. Если набор не удалось сформировать целиком, частично созданная активная сессия не остаётся. Пара условия и закрытого эталона принадлежит конкретной выданной задаче. Повторное чтение, восстановление сервера или изменение авторского банка не запускают новый выбор варианта. Закрытые эталоны и приватный контекст не входят в расписание, публичное условие, историю, ведомость преподавателя или административный обзор.

### Данные принятого ответа

Для восстановления одного снимка сессии недостаточно. Задача в состоянии `NEW` может ещё ждать ответа, а может уже иметь ответ, принятый в обработку. В первом случае по достижении `D` её можно закрыть по просрочке. Во втором требуется учесть исходный срок обработки принятого ответа.

По [SWR-SES-021] до передачи принятого запроса в очередь сохраняются UUID операции, владелец, идентификатор задачи, полный ответ, время его получения, предел обработки и признак незавершённости. Физическое размещение этих сведений определяет модель хранения. Пока операция открыта, новое обращение к той же задаче не заменяет принятый ответ. Запись результата завершает операцию по [SWR-SYS-005]. После перезапуска ранее сохранённый вердикт выдаётся по [SWR-SYS-008].

Сохранённые `deadlineAt`, момент полного получения ответа `t_in` и предел обработки `L = t_in + 60 секунд` имеют разный смысл. Для контроля `deadlineAt = min(createdAt + 20 минут, closesAt)`. При восстановлении ни срок подачи, ни исходный предел принятого ответа не отсчитываются заново. Предметный вердикт, состояния задачи и сессии и завершение операции записываются совместно. Принятому ответу не требуется новый UUID сессии или новый выбор варианта. Порядок допуска и обработки сохраняется по DOC-06.2.

Сохранённое состояние и его представление при чтении различаются, если очередной фоновый проход ещё не состоялся. По [контракту чтения](../09_Архитектура_и_API/DOC-08_API_сессий.md#3-чтение-состояния-и-восстановление-после-обрыва-связи) просрочка учитывается уже в ответе. Для этого нужны не только `deadlineAt`, но и сведения о своевременно принятых незавершённых ответах с исходными пределами обработки. Сохранённый вердикт не подменяется просрочкой. Тот же порядок представления применяется в ведомости преподавателя и административном обзоре; чтение не выполняет предметную проверку и не расходует попытку.

### Связи структур с API и проверка полноты

Полные форматы и ошибки определены в [DOC-08](../09_Архитектура_и_API/DOC-08_Справочник_API.md). Таблица показывает, какие данные обеспечивают уже заданные операции; она не вводит новые эндпоинты.

| Данные | Операции чтения и записи | Что сопоставляют при проверке документации |
|---|---|---|
| Назначения шаблонов и позиции | Каталог шаблонов группы; создание сессии по `configuration` | `enabled` отдельно для группы, сохранение числа и порядка повторяющихся типов |
| Банк и опубликованные пары | Создание и изменение `/api/custom-tasks`; публикация мероприятия | Правка банка после публикации не меняет пару при последующем старте, чтении и проверке |
| Черновик и опубликованная редакция | Создание, замена и публикация `/api/assessments` | Один UUID; пустой состав и отсутствие выбора повтора не дают частичной публикации |
| Группа, окно и история прохождений | Расписание; старт по `assessmentId` | Видимость до открытия, отдельный UUID каждого повтора, прежние прохождения сохраняются |
| Сессии, задачи и операции ответов | Чтение сессии; ведомость `/results`; административный обзор | Одинаковое определение просрочки, исходные сроки после перезапуска, отсутствие эталонов в публичном представлении |

Для документарной сверки рассматривают две публикации одного авторского задания с правкой банка между ними, два прохождения одной работы при разрешённом повторе, отказ повтора при запрете и два одновременных старта пользователя. После штатного перезапуска сопоставляют UUID, связи, порядок, опубликованные и выданные пары, сроки и сохранённые вердикты. Наличие этих сценариев описывает способ проверки модели и не подтверждает испытания программного обеспечения.
