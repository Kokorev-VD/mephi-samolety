# DOC-06.2. Контракты сессий задач

Приложение к [DOC-06.2](DOC-06.2_Сессии_задач_и_планировщик.md), версия 0.9, редакция от 07.11.2026. Ответственный: Анохин Г.А. Здесь определены операции, форматы данных, категории отказов и правила восстановления домена сессий.

## Операции

| Операция | Вход | Нормальный результат |
|---|---|---|
| `POST /api/tasks/session` | Параметр строки запроса `configuration`: имя конфигурации | `201 Created`, созданная сессия с задачами |
| `PUT /api/tasks/submit` | Параметр строки запроса `statementId`: UUID задачи; тело JSON с решением её типа | `200 OK`, вердикт с идентификатором и типом задачи |
| `GET /api/tasks/session/{sessionId}` | UUID собственной сессии в пути | `200 OK`, состояние сессии и сохранённые результаты задач |

Операции выполняются от имени подтверждённого пользователя с ролью `USER`. Идентификатор владельца не берётся из тела запроса. Время получения полного запроса сервером используется по SWR-SES-007; предметный допуск определяется в DOC-06.2. JSON передаётся в UTF-8 с типом содержимого `application/json`.

Создание принимает ровно один непустой параметр `configuration`. Имя сопоставляется с конфигурацией группы с учётом регистра. Повторяющийся параметр отклоняется с `400 Bad Request`; несколько наборов одним запросом не создаются. Для отправки ответа требуется ровно один корректный UUID `statementId`.

Предельный размер тела ответа — 1 МиБ, то есть 1 048 576 байт до разбора JSON. Превышение даёт `413 Payload Too Large` и не расходует предметную попытку. Отсутствующее тело, некорректный JSON, неверный тип поля и отсутствие обязательного поля дают `400 Bad Request`.

## Представление сессии и задачи

| Поле сессии | Содержание |
|---|---|
| `id` | UUID сессии |
| `createdAt` | Серверное время создания |
| `state` | `NEW`, `SOLVED` или `FAILED` |
| `userId` | UUID владельца |
| `problems` | Список задач сессии |

| Поле задачи | Содержание |
|---|---|
| `id` | UUID задачи; передаётся в `statementId` при отправке ответа |
| `statement` | Строка, содержащая JSON условия соответствующего типа |
| `type` | Тип, определяющий генератор и проверяющий |
| `state` | Состояние задачи |
| `sessionId` | UUID содержащей её сессии |
| `result` | Сохранённый предметный результат либо `null`, если вердикт не зафиксирован |

Выдаваемые идентификаторы и принадлежность должны соответствовать сохранённым данным. Время передаётся строкой UTC в формате RFC 3339 с миллисекундами и суффиксом `Z`. Поле `createdAt` задаёт начало общего срока. Сравнение со сроком выполняется на сервере; часовой пояс устройства пользователя не участвует в допуске ответа.

## Предметный ответ

Структура тела определяется сохранённым типом задачи. Транспортный разбор JSON предшествует предметной проверке. Значение поля `type` в решении не может переключить проверку на другой тип задачи.

В сессиях поддерживаются `BACKPACK` и `EL_GAMAL`. Для каждого типа назначены генератор и проверяющий с форматом ответа ниже. Наличие другого типа в конфигурации считается ошибкой настройки: создание набора завершается техническим отказом, частичная сессия не сохраняется.

### Ранцевая задача

Все перечисленные поля обязательны и не допускают `null`. `power` передаётся положительным целым JSON-числом, `type` — строкой варианта, совпадающей с вариантом сохранённого условия. `message` и `decodedMessage` — массивы JSON-значений `true` и `false`. Остальные целые значения передаются десятичными строками; поля ранцев — массивами таких строк.

| Поле | Предметное значение |
|---|---|
| `power` | Размерность задачи |
| `type` | Обозначение варианта ранцевой задачи |
| `message` | Исходное сообщение как список логических значений |
| `lightBackpack` | Лёгкий ранец, список целых чисел |
| `omega` | Множитель преобразования |
| `hardBackpack` | Тяжёлый ранец, список целых чисел |
| `encodedMessage` | Зашифрованное сообщение |
| `decodedMessage` | Восстановленное сообщение как список логических значений |
| `module` | Модуль преобразования |
| `reverseOmega` | Обратный множитель |

### Эль-Гамаль

Все поля решения обязательны, не допускают `null` и передаются десятичными строками:

| Поле | Предметное значение |
|---|---|
| `y` | Открытый ключ |
| `k` | Одноразовый параметр шифрования |
| `c1` | Первая часть шифротекста |
| `c2` | Вторая часть шифротекста |
| `decryptedMessage` | Восстановленное сообщение |

Десятичная строка содержит `0` либо ненулевое целое без ведущих нулей, перед которым допускается знак минуса. Пробелы, знак плюса, дробная часть и экспоненциальная запись не допускаются. Такой формат сохраняет точность больших целых на стороне клиента. Правильность математических связей между значениями определяет предметная проверка; синтаксически корректный, но неверный расчёт даёт предметный вердикт `isOk = false`.

## Результат и отказы

| Поле предметного результата | Содержание |
|---|---|
| `problemId` | UUID проверенной задачи |
| `isOk` | `true` при верном решении, `false` при неверном |
| `problemType` | Сохранённый тип задачи |
| `errorMessage` | Непустая строка при неверном решении; `null` при верном |

`isOk = false` означает завершённую проверку неправильного решения. Отсутствие прав, ошибка формата, просрочка, недоступность проверяющего и ошибка сохранения передаются отдельными категориями отказов. При верном ответе `errorMessage` имеет значение `null`; при неверном содержит пояснение предметной ошибки.

Состояние задачи и попытки определяется требованиями DOC-06.2, а не формулировкой диагностического сообщения. При техническом сбое нельзя сообщать, что решение неверно, если предметного вердикта не было.

## Как клиент проходит операции

Создание набора начинается с имени конфигурации. Ответ содержит сессию и список задач; клиент сохраняет её `id`, чтобы позднее читать тот же набор. Каждое задание имеет собственный `id`, который используется как `statementId` при отправке решения. Отождествлять эти два идентификатора нельзя: первый обозначает набор, второй — выбранную задачу внутри него.

Клиент выбирает схему тела по выданному типу задачи. Он передаёт предметные значения в установленном формате, а сервер берёт условие из сохранённых данных. Правильность формы запроса проверяется до математического вердикта. Поэтому `400 INVALID_REQUEST` означает, что решение не было допущено к предметной проверке, а `200 OK` с `isOk = false` означает завершённую неверную попытку.

После получения результата клиент может обновить отображение через чтение сессии. Этот же путь используется при потере соединения: неизвестность на стороне клиента не доказывает, что сервер не сохранил вердикт. Повторная отправка решения не заменяет чтение, поскольку задача могла уже завершиться. Подробный порядок раскрывает [чтение после потери ответа](#чтение-после-потери-ответа).

## Учебный пример решения Эль-Гамаля

Пусть выданное условие задаёт `p = 23`, `g = 5`, `x = 6`, `m = 13`. Для выбранного в решении `k = 3` получаются `y = 8`, `c1 = 10`, `c2 = 9`, а восстановленное сообщение равно `13`. Числа служат примером чтения формата; условия конкретной задачи берутся из её сохранённого `statement`.

Тело ответа на эту задачу имеет вид:

```json
{
  "y": "8",
  "k": "3",
  "c1": "10",
  "c2": "9",
  "decryptedMessage": "13"
}
```

Числа заключены в кавычки, поскольку контракт использует десятичные строки для целых произвольной длины. Поле `isOk` в результате, напротив, имеет логический тип. Если эти значения признаны верными, сохраняется `SOLVED`; неверный расчёт в корректно оформленном теле приводит к `FAILED` с отрицательным предметным результатом. Отличие формы и смысла ответа описано в [проверке формата](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-009-проверка-формата) и [передаче профильному проверяющему](DOC-06.2_Сессии_задач_и_планировщик.md#swr-ses-010-передача-профильной-проверке).

## Смысл связей в передаваемых данных

`statementId` обозначает идентификатор задачи, полученный в поле `id` этой задачи при создании набора. Это не текст условия и не отдельный идентификатор, который клиент должен назначать самостоятельно. Сервер устанавливает принадлежность по сохранённой задаче и её сессии.

Поле `sessionId` связывает задачу с набором, а `userId` в представлении сессии обозначает владельца. Наличие этих значений в выдаче не меняет источник полномочий: операция выполняется от имени подтверждённого пользователя. Сервер сопоставляет переданный идентификатор задачи со своими данными принадлежности.

У `statement` и тела решения разное назначение. Первое передаёт выданное условие; второе содержит ответ пользователя по предметной схеме. Проверка использует сохранённое условие, поэтому клиентский ответ не должен заменять его другим заданием. Конкретный состав решения подтверждается владельцем соответствующего типа.

Для результата проверки идентификатор и тип позволяют сопоставить вердикт с задачей. Диагностический текст поясняет неверное решение; при отсутствии профильного пояснения возвращается «Решение неверно». Он не должен служить единственным признаком категории отказа: нарушение доступа и техническая ошибка отличаются от предметного `isOk = false` независимо от языка сообщения.

## Коды и представление ошибок

| HTTP | Код ошибки | Условие |
|---|---|---|
| `400` | `INVALID_REQUEST` | Неверные параметры, JSON, типы или обязательные поля |
| `401` | `UNAUTHENTICATED` | Нет действительных данных аутентификации |
| `403` | `ACCESS_DENIED` | У пользователя нет роли `USER` |
| `404` | `TASK_NOT_FOUND` | Задача не найдена среди задач текущего пользователя |
| `404` | `SESSION_NOT_FOUND` | Сессия не найдена среди сессий текущего пользователя |
| `404` | `CONFIGURATION_NOT_FOUND` | У группы нет включённой конфигурации с таким именем |
| `409` | `ACTIVE_SESSION_EXISTS` | Уже есть незавершённая сессия |
| `409` | `TASK_FINALIZED` | Задача или сессия уже имеет итоговое состояние |
| `409` | `CHECK_IN_PROGRESS` | Для задачи уже обрабатывается допустимый ответ |
| `410` | `SESSION_EXPIRED` | Новый ответ получен в момент общего срока или позднее |
| `413` | `PAYLOAD_TOO_LARGE` | Тело ответа превышает 1 МиБ |
| `500` | `INTERNAL_ERROR` | Ошибка настройки или сохранения данных |
| `503` | `CHECK_UNAVAILABLE` | Проверяющий недоступен либо произошёл технический сбой проверки |
| `503` | `CHECK_TIMEOUT` | Обработка не завершилась за 60 секунд |

Для чужой задачи используется та же ошибка `TASK_NOT_FOUND`, что и для отсутствующей: интерфейс не раскрывает существование чужих заданий. Отсутствие группы при создании набора даёт `CONFIGURATION_NOT_FOUND`, поскольку доступная конфигурация не может быть выбрана.

Тело ошибки содержит строковые поля `code`, `message`, `timestamp` и `requestId`. `timestamp` передаётся в том же UTC-формате, что и `createdAt`; `requestId` — UUID серверной операции. Поле `message` предназначено для человека, а клиент определяет категорию по `code`. При `ACTIVE_SESSION_EXISTS` дополнительное поле `details.sessionId` содержит UUID собственной активной сессии; по нему клиент может восстановить её данные, если ответ на создание был потерян. Текст исключения, стек вызовов и служебные данные хранилища в ответ не включаются.

Проверки доступа предшествуют раскрытию данных задачи. После установления собственной задачи проверяется время: при `t_in >= D` возвращается `SESSION_EXPIRED` независимо от фонового обновления состояния. Для своевременного повторного ответа на уже завершённую задачу или сессию возвращается `TASK_FINALIZED`. Ни одна из этих ошибок не запускает вторую предметную попытку.

## Принятая обработка и восстановление

Перед запуском проверяющего сохраняются UUID операции, пользователь, задача, полный ответ, `t_in` и срок обработки `t_in + 60 секунд`. Для одной задачи может существовать только одна незавершённая операция предметной проверки. Принятые данные не заменяются телом повторного запроса.

При перезапуске незавершённые операции продолжаются в пределах прежнего срока. Если результат уже сохранён, повторная фиксация не выполняется. Если срок обработки закончился, операция получает `CHECK_TIMEOUT` без нового предметного вердикта. В пределах общего срока пользователь может отправить новый ответ; после общего срока незавершённая задача закрывается по просрочке.

## Чтение после потери ответа

Получение сессии возвращает сохранённые состояния и поле `result` каждой задачи. Для `SOLVED` оно содержит вердикт с `isOk = true`; для неверного решения — вердикт с `isOk = false`. У задачи, завершённой по просрочке без предметного вердикта, `result` равно `null`.

Клиент использует чтение, если соединение прервано до доставки ответа или требуется восстановить отображение после перезапуска. Чтение доступно после срока и не повторяет предметную проверку. Чужая сессия и отсутствующая сессия дают один ответ `SESSION_NOT_FOUND`.
