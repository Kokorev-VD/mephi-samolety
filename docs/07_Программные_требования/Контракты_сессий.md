# DOC-06.2. Контракты сессий задач

Приложение к [DOC-06.2](DOC-06.2_Сессии_задач_и_планировщик.md), проект 0.8 от 05.11.2026. Ответственный: Анохин Г.А. Точные HTTP-коды, формат ошибок и предметные поля подлежат согласованию с владельцами API, безопасности и криптографических доменов. Это приложение не заменяет полный DOC-08.

## Операции

| Операция | Вход | Нормальный результат |
|---|---|---|
| `POST /api/tasks/session` | Параметр строки запроса `configuration`: имя конфигурации | Созданная сессия с задачами |
| `PUT /api/tasks/submit` | Параметр строки запроса `statementId`: UUID задачи; тело JSON с решением её типа | Вердикт с идентификатором и типом задачи |

Операции выполняются от имени подтверждённого пользователя с правом решения задач. Идентификатор владельца не берётся из тела запроса. Время получения полного запроса сервером используется по SWR-SES-007; предметный допуск определяется в DOC-06.2.

Создание принимает одно имя конфигурации. Поведение при повторяющихся одноимённых параметрах запроса должно быть единым в API; до согласования этого случая он не считается поддержанным способом выбора нескольких наборов.

## Представление сессии и задачи

| Поле сессии | Содержание |
|---|---|
| `id` | UUID сессии |
| `createdAt` | Серверное время создания |
| `state` | `NEW`, `SOLVED` или `FAILED` |
| `userId` | UUID владельца |
| `problems` | Список задач сессии |

| Поле задачи | Содержание |
|---|---|
| `id` | UUID задачи; передаётся в `statementId` при отправке ответа |
| `statement` | Строка, содержащая JSON условия соответствующего типа |
| `type` | Тип, определяющий генератор и проверяющий |
| `state` | Состояние задачи |
| `sessionId` | UUID содержащей её сессии |

Выдаваемые идентификаторы и принадлежность должны соответствовать сохранённым данным. Представление `createdAt` должно однозначно задавать момент серверного времени. Точное строковое представление времени и его часовая зона требуют общего решения для DOC-08; локальное время без правила интерпретации для этого недостаточно.

## Предметный ответ

Структура тела определяется сохранённым типом задачи. Транспортный разбор JSON предшествует предметной проверке. Значение поля `type` в решении не может переключить проверку на другой тип задачи.

В текущем проекте контракта рассмотрены `BACKPACK` и `EL_GAMAL`. Другие типы не включаются в сессию без определения генератора, формата ответа и правил проверки их владельцем.

### Ранцевая задача

Ниже приведён состав полей для согласования с Георгиевым. Обязательность каждого поля и его применение в разных вариантах ранцевых задач должны быть подтверждены в подсистемном документе; перечень не устанавливает единую схему для всех вариантов.

| Поле | Предметное значение |
|---|---|
| `power` | Размерность задачи |
| `type` | Обозначение варианта ранцевой задачи |
| `message` | Исходное сообщение как список логических значений |
| `lightBackpack` | Лёгкий ранец, список целых чисел |
| `omega` | Множитель преобразования |
| `hardBackpack` | Тяжёлый ранец, список целых чисел |
| `encodedMessage` | Зашифрованное сообщение |
| `decodedMessage` | Восстановленное сообщение как список логических значений |
| `module` | Модуль преобразования |
| `reverseOmega` | Обратный множитель |

### Эль-Гамаль

Поля решения для согласования с Портновым:

| Поле | Предметное значение |
|---|---|
| `y` | Открытый ключ |
| `k` | Одноразовый параметр шифрования |
| `c1` | Первая часть шифротекста |
| `c2` | Вторая часть шифротекста |
| `decryptedMessage` | Восстановленное сообщение |

Для больших целых чисел нужно согласовать передачу JSON-числом либо строкой и правила точности клиента. Произвольные разрядности и диапазоны здесь не назначаются. Криптографические ограничения определяет владелец соответствующего домена.

## Результат и отказы

| Поле предметного результата | Содержание |
|---|---|
| `problemId` | UUID проверенной задачи |
| `isOk` | `true` при верном решении, `false` при неверном |
| `problemType` | Сохранённый тип задачи |
| `errorMessage` | Диагностика неверного решения, если предусмотрена предметной проверкой |

`isOk = false` означает завершённую проверку неправильного решения. Отсутствие прав, ошибка формата, просрочка, недоступность проверяющего и ошибка сохранения не должны маскироваться этим результатом. Для них требуются отдельные категории отказов, согласованные в DOC-08.

Состояние задачи и попытки определяется требованиями DOC-06.2, а не формулировкой диагностического сообщения. При техническом сбое нельзя сообщать, что решение неверно, если предметного вердикта не было.

## Что передать владельцу DOC-08

До выпуска справочника нужно подтвердить HTTP-коды и схему ошибок, формат серверного времени, передачу больших целых чисел, обязательность предметных полей и обработку повторяющихся параметров. Имена операций, связи идентификаторов и категории результатов связываются с требованиями DOC-06.2; окончательное согласование интерфейсов не предполагается состоявшимся.
