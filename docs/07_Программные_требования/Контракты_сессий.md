# DOC-06.2. Контракты сессий задач

Приложение к [требованиям подсистемы сессий и планировщика](DOC-06.2_Сессии_задач_и_планировщик.md). Редакция 1.0 от 20.11.2026. Ответственный — Анохин Г.А.

В этом приложении «клиент» означает программу, через которую студент работает с платформой. Клиент начинает личную сессию, отправляет решение одной задачи и читает состояние набора. Контракт описывает запрос и возможные ответы сервера для каждого действия. Представление сессии, задачи или результата для обмена называют объектом передачи данных (DTO). Контракт определяет поля этого объекта и допустимые значения. Полное внутреннее состояние приложения остаётся на сервере.

## Операции

В записи запроса первое слово — метод HTTP, дальше указан путь. Метод `POST` используется для создания сессии, `PUT` — для отправки решения, `GET` — для чтения. Заполнители в фигурных скобках заменяются конкретными значениями. UUID — уникальный идентификатор объекта. Код 201 сообщает о создании ресурса, 200 — об успешной обработке запроса. Конкретную причину отказа определяют по [таблице ошибок](#коды-и-представление-ошибок).

Все три операции требуют подтверждённой личности и роли `USER`, дающей студенту доступ к собственной работе. Сервер определяет владельца по [проверенному токену доступа](Программные_требования_платформы.md#swr-auth-003-проверка-токена-и-роли). Данные передаются в JSON — текстовом формате объектов с именованными полями и массивов значений. Для JSON используются кодировка UTF-8 и тип содержимого `application/json`.

| Запрос | Данные от клиента | Успешный ответ |
|---|---|---|
| `POST /api/tasks/session` | Ровно один параметр. `assessmentId` — UUID мероприятия из записи в расписании студента, `configuration` — имя шаблона из списка для его группы | `201 Created`. Созданная сессия со всеми задачами |
| `PUT /api/tasks/submit` | Один параметр запроса `statementId` с UUID задачи и тело с решением | `200 OK`. Сохранённый вердикт для указанной задачи |
| `GET /api/tasks/session/{sessionId}` | UUID сессии в пути | `200 OK`. Собственная сессия с состояниями и результатами задач |

По `assessmentId` сервер находит опубликованное мероприятие группы пользователя и проверяет серверное время. Новая сессия допустима с момента открытия `opensAt` включительно до момента закрытия `closesAt` исключительно. Внутри окна при действующей сессии `NEW` новая не создаётся. Завершённое прохождение можно повторить, только если преподаватель выбрал `repeatAllowed = true` до публикации. Повтор получает собственные UUID сессии и задач. Прежнюю сессию владелец может прочитать по её UUID и после закрытия. Успешная выдача закрепляет за сессией идентификатор этого мероприятия. По имени шаблона создаётся практика без связи с контролем. Одновременная передача `configuration` и `assessmentId`, отсутствие обоих параметров, повтор или неверная запись значения дают `400 INVALID_REQUEST`.

Имя шаблона в параметре `configuration` сравнивается с учётом регистра. Сервер ищет шаблон среди включённых для группы пользователя. Для отправки решения отсутствие, повтор или неверная запись `statementId` также дают `400 INVALID_REQUEST`.

На тело решения отводится 1 МиБ (1 048 576 байт). Размер определяется до разбора JSON. При большем размере возвращается `413 PAYLOAD_TOO_LARGE`. Пустое тело, ошибка JSON, отсутствие обязательного поля, недопустимый тип или `null` в обязательном поле дают `400 INVALID_REQUEST`. В обоих случаях предметная попытка сохраняется.

## Представление сессии и задачи

Сессия — личный набор студента, а задача — один конкретный экземпляр задания внутри него. Первый объект ответа описывает сессию. В его массиве `problems` находятся объекты задач, по одному на каждую выданную позицию. Значение `null` обозначает отсутствие значения, например ещё не записанный результат. Подробнее о [состояниях задачи и сессии](DOC-06.2_Сессии_задач_и_планировщик.md#данные-и-их-жизненный-цикл).

| Поле сессии | Тип и значение |
|---|---|
| `id` | UUID созданной сессии |
| `assessmentId` | UUID опубликованного мероприятия для контрольной сессии, `null` для самостоятельной практики |
| `createdAt` | Серверное время создания набора. Дата и время по всемирному координированному времени (UTC) в формате RFC 3339 с миллисекундами и суффиксом `Z`, например `2026-11-20T12:00:00.000Z` |
| `deadlineAt` | Срок подачи ответа для всех задач, в том же формате UTC, что и `createdAt`. Для практики — через 20 минут после создания, для контроля — более ранний из `createdAt + 20 минут` и `closesAt`. Новый ответ в этот момент уже опоздал. |
| `state` | Состояние набора. Принимает `NEW`, `SOLVED` или `FAILED` |
| `userId` | UUID владельца |
| `problems` | Массив задач именно этой сессии |

| Поле задачи | Тип и значение |
|---|---|
| `id` | UUID, который клиент передаёт в `statementId` |
| `statement` | Строка с JSON выданного условия |
| `type` | Сохранённый тип задачи. Определяет схему решения |
| `state` | Состояние задачи из того же перечня `NEW`, `SOLVED`, `FAILED` |
| `sessionId` | UUID сессии, к которой принадлежит задача |
| `result` | Объект предметного результата либо `null`, если вердикт не был зафиксирован |

### Смысл связей в передаваемых данных

Для запроса чтения клиент использует `id` сессии. Для отправки решения он выбирает одну запись из `problems` и берёт `id` задачи. Ответ на решение содержит этот же UUID в поле `problemId`. Так клиент может сопоставить ответ со строкой задачи, даже если в наборе несколько задач одного типа.

Для всех задач набора применяется срок из `deadlineAt`. Срок определяется на сервере, часовой пояс клиента на него не влияет. Сервер определяет владельца задачи по её связи с сессией. Полученные из клиента идентификаторы не заменяют проверку владельца.

## Предметный ответ

Каждый подключённый тип задаёт схему решения. Для `BACKPACK` и `EL_GAMAL` передают расчётные величины, для `CUSTOM_TEXT` — текст ответа. При создании набор с неподдерживаемым типом отклоняется целиком с `500 INTERNAL_ERROR`. При отправке решения схему диктует сохранённый тип задачи. Клиент не может передать новое условие или выбрать другого проверяющего полем своего ответа.

Для больших целых используется **десятичная строка**. Допустимы `"0"` и строка из цифр с ненулевой первой цифрой, перед которой для отрицательного целого стоит знак минуса. Записи `"-0"`, `"+2"`, `"02"`, `"2.0"`, `"2e3"` и пробелы не допускаются. Строковое представление сохраняет точное значение при обмене. Предметный проверяющий отдельно оценивает математические связи между корректно записанными значениями.

### Ранцевая задача

Студент передаёт параметры [ранцевого шифрования](DOC-06.3_Ранцевые_криптосистемы.md#как-устроена-ранцевая-задача). Сообщение указывает, какие веса нужно сложить. Лёгкий и тяжёлый ранцы — два связанных списка весов. Названия полей ниже описывают части одного решения.

В решении `BACKPACK` обязательны все поля таблицы. Ни одно из них не принимает `null`.

| Поле | Представление и смысл |
|---|---|
| `power` | Положительное целое JSON-число, размерность задачи |
| `type` | Строка с вариантом ранца, совпадающим с вариантом выданного условия |
| `message` | Массив логических значений `true` и `false`, исходное сообщение |
| `lightBackpack` | Массив десятичных строк, элементы лёгкого ранца |
| `omega` | Десятичная строка, множитель преобразования |
| `hardBackpack` | Массив десятичных строк, элементы тяжёлого ранца |
| `encodedMessage` | Десятичная строка, зашифрованное сообщение |
| `decodedMessage` | Массив логических значений, восстановленное сообщение |
| `module` | Десятичная строка, модуль преобразования |
| `reverseOmega` | Десятичная строка, обратный множитель |

### Эль-Гамаль

В этом учебном шифре простое число `p` задаёт модуль, то есть число, по которому берут остатки, а `g` — основание для возведения в степень. По заданному закрытому показателю `x` вычисляют открытый ключ `y`. Для шифрования сообщения `m` используется отдельный одноразовый показатель `k`. Результат шифрования состоит из двух чисел `c1` и `c2`. Проверяются и эти числа, и сообщение, полученное после расшифрования. Закрытый показатель выдан в составе учебного условия, чтобы студент мог выполнить весь расчёт.

В решении `EL_GAMAL` пять обязательных полей. Каждое содержит десятичную строку. Значение `null` не допускается.

| Поле | Значение |
|---|---|
| `y` | Открытый ключ |
| `k` | Одноразовый параметр шифрования |
| `c1` | Первая составляющая шифротекста |
| `c2` | Вторая составляющая шифротекста |
| `decryptedMessage` | Восстановленное сообщение |

### Учебный пример решения Эль-Гамаля

Для условия с `p = 23`, `g = 5`, `x = 6`, `m = 13` пользователь выбрал `k = 3`. Тело корректного ответа имеет следующий вид.

```json
{
  "y": "8",
  "k": "3",
  "c1": "10",
  "c2": "9",
  "decryptedMessage": "13"
}
```

Замена `"13"` числом `13` нарушит тип поля и даст ошибку формата. Строка `"12"` типу соответствует, но математически неверна для этого условия. В таком случае клиент получит предметный результат с `isOk = false`.

### Пользовательское текстовое задание

В редакторе преподаватель вводит условие варианта как обычный текст и отдельно задаёт правильный ответ. У выданных задач всех видов одинаковые внешние поля. Поле `statement` содержит строку с сериализованным JSON, то есть с текстовой записью значения в формате JSON. У типа `CUSTOM_TEXT` внутреннее значение само является строкой. В ответе сервера возможен такой фрагмент объекта задачи.

```json
{"type":"CUSTOM_TEXT","statement":"\"Сколько бит в байте?\""}
```

Клиент разбирает внешний объект, берёт строку из `statement` и разбирает её как JSON. Теперь он может показать студенту текст «Сколько бит в байте?» без кавычек. Ответ передаётся как обычный JSON-объект `{"answer":"8"}`; второй слой сериализации для него не нужен.

При публикации фиксируется редакция вариантов из задания преподавателя. При выдаче задачи `CUSTOM_TEXT` модуль случайно выбирает одну пару из этой редакции для указанной позиции. Студент получает только условие выбранного варианта. Два студента могут получить одинаковый вариант. Прочие варианты и эталонный ответ отсутствуют в представлении сессии и в ответе на проверку. В качестве решения клиент передаёт объект с обязательным строковым полем `answer`. Пример тела решения:

```json
{"answer":"  Северный ветер  "}
```

Проверяющий удаляет пробелы по краям ответа и закреплённого эталона и сравнивает оставшиеся строки. Для эталона `Северный ветер` ответ из примера верен. Строки `северный ветер` и `Северный  ветер` дадут отрицательный вердикт. Если `answer` отсутствует, равно `null` или имеет числовой тип, возвращается `400 INVALID_REQUEST` без расходования попытки.

## Результат и отказы

| Поле результата | Тип и правило заполнения |
|---|---|
| `problemId` | UUID проверенной задачи |
| `problemType` | Сохранённый тип этой задачи |
| `isOk` | Логическое значение. `true` при верном решении, `false` при неверном |
| `errorMessage` | Для `true` — `null`. Для `false` — непустая строка с пояснением |

Оба предметных исхода возвращаются с HTTP 200. При отсутствии профильного пояснения к неверному решению сервер возвращает «Решение неверно». Отказ доступа, ошибка формы, просрочка и технический сбой возвращаются в формате ошибки из следующего раздела. При таком отказе сервер не выдаёт предметный вердикт.

## Коды и представление ошибок

| HTTP | Значение `code` | Условие |
|---|---|---|
| 400 | `INVALID_REQUEST` | Нарушены правила параметров, JSON или обязательных полей |
| 401 | `UNAUTHENTICATED` | Сервер не смог подтвердить личность |
| 403 | `ACCESS_DENIED` | У подтверждённого пользователя отсутствует роль `USER` |
| 404 | `TASK_NOT_FOUND` | Задачи с таким UUID нет среди собственных |
| 404 | `SESSION_NOT_FOUND` | Сессии с таким UUID нет среди собственных |
| 404 | `ASSESSMENT_NOT_FOUND` | При старте контроля мероприятие отсутствует, ещё не опубликовано или назначено другой группе |
| 409 | `ASSESSMENT_NOT_OPEN` | Старт в своей группе запрошен до `opensAt` |
| 409 | `ASSESSMENT_CLOSED` | Сервер получил запрос на старт в момент `closesAt` или позднее |
| 409 | `ASSESSMENT_RETAKE_DISABLED` | Окно открыто, у студента нет сессии `NEW`, но он уже завершил прохождение этого мероприятия и `repeatAllowed = false` |
| 404 | `CONFIGURATION_NOT_FOUND` | У пользователя нет группы или у группы нет включённого шаблона с указанным именем |
| 409 | `ACTIVE_SESSION_EXISTS` | Пользователь уже имеет незавершённый набор |
| 409 | `TASK_FINALIZED` | Своевременный запрос адресован задаче или сессии, которая уже завершилась |
| 409 | `CHECK_IN_PROGRESS` | По этой задаче ещё обрабатывается ранее принятый допустимый ответ |
| 410 | `SESSION_EXPIRED` | Новый ответ к собственной задаче получен ровно в общий срок или позже |
| 413 | `PAYLOAD_TOO_LARGE` | Размер тела больше 1 МиБ |
| 500 | `INTERNAL_ERROR` | Ошибка настройки либо сохранения |
| 503 | `CHECK_UNAVAILABLE` | Проверяющий недоступен или произошёл технический сбой во время его работы |
| 503 | `CHECK_TIMEOUT` | К моменту `t_in + 60 секунд` результат не зафиксирован |

Сначала сервер проверяет доступ. По чужой задаче он возвращает тот же ответ, что и по отсутствующей. Для собственной задачи `SESSION_EXPIRED` имеет приоритет перед отказом по состоянию. Порядок запуска планировщика не влияет на выбор этой ошибки.

В теле ошибки четыре обязательных строковых поля. Поле `code` предназначено для выбора действия клиентом, `message` поясняет причину человеку, `timestamp` содержит время в том же UTC-формате, что и `createdAt`, а `requestId` — UUID серверной операции. Стек вызовов, текст исключения и служебные данные хранилища клиенту не выдаются. У ошибки `ACTIVE_SESSION_EXISTS` есть дополнительное поле `details.sessionId` с UUID собственной активной сессии. В ошибке `ASSESSMENT_RETAKE_DISABLED` поле `details.sessionId` содержит UUID прежней собственной сессии этого мероприятия.

## Как клиент проходит операции

1. При успешном старте клиент сохраняет `id` сессии и показывает выданные условия. Если ответ на старт контрольной потерян, клиент читает своё расписание через `GET /api/users/me/schedule`. Из карточки этой работы он берёт `sessionId` своей активной или последней завершённой сессии и открывает её через `GET /api/tasks/session/{sessionId}`. Запрос на новый старт используется, когда студент намерен начать прохождение. При самостоятельной практике повторный запрос при наличии действующей сессии даёт `ACTIVE_SESSION_EXISTS` с её идентификатором в `details.sessionId`.
2. Для выбранной задачи клиент отправляет `PUT` с её UUID и телом по соответствующей схеме. При `400 INVALID_REQUEST` можно исправить тело и отправить его до общего срока. Предметный ответ с `isOk = false` завершает попытку.
3. Если после отправки соединение прервалось, клиент читает сессию по её UUID, чтобы узнать, что зафиксировал сервер.

## Принятая обработка и восстановление

«Принятый ответ» — запрос с решением владельца, который сервер уже зарегистрировал для обработки. Получение запроса ещё не означает, что решение верно или что вердикт сохранён. Сервер различает [время подачи и предел обработки](DOC-06.2_Сессии_задач_и_планировщик.md#время-решения-и-время-обработки). Например, при подаче за одну секунду до `closesAt` предельное время записи вердикта наступит через 59 секунд после закрытия. Новый ответ владельца в момент `deadlineAt` получит `410 SESSION_EXPIRED`.

При полном получении запроса сервер отмечает `t_in`. До очереди он сверяет подтверждённого отправителя с владельцем задачи. Чужой или отсутствующий UUID даёт `404 TASK_NOT_FOUND` и не открывает операцию для этой задачи. Для собственной задачи сервер записывает в устойчивое хранилище UUID операции, владельца, UUID задачи, полный ответ, `t_in`, предел `t_in + 60 секунд` и признак незавершённости.

Своевременно зарегистрированный ответ владельца защищает задачу от просрочки во время ожидания, допуска и проверки формата. При отказе защита по этому запросу снимается. Право начать предметную проверку подсистема предоставляет атомарно для задачи. Если два допустимых запроса зарегистрированы до срока, при идущей проверке второй получает `409 CHECK_IN_PROGRESS`, после фиксации итога до общего срока — `409 TASK_FINALIZED`. Повторный запрос и перезапуск приложения не заменяют исходные данные и не отодвигают предел.

После перезапуска сервер должен продолжить обработку открытой записи по сохранённому ответу, пока исходный предел не достигнут. Если вердикт уже зафиксирован, сервер выдаёт его при чтении. Если предел наступил до фиксации, операция завершается с `CHECK_TIMEOUT`. Пока общий срок не истёк, пользователь может отправить новый ответ. После общего срока задача без своевременной обработки закрывается по просрочке.

Если при записи вердикта произошёл откат, сервер сообщает клиенту `500 INTERNAL_ERROR` только после сохранения отмены операции. Прежний вердикт после такого отказа уже не появится. Если вместо ответа клиент обнаружил разрыв соединения, он читает собственную сессию. При открытой записи сервер продолжит обработку в пределах исходного времени, при уже сохранённом вердикте вернёт результат чтением.

## Чтение после потери ответа

Потеряться может HTTP-ответ сервера с вердиктом даже тогда, когда сам вердикт уже записан. Для восстановления клиент читает личную сессию по её UUID. Обозначение `D` ниже означает общий срок подачи решений.

Операция чтения доступна владельцу до и после `D`. Перед выдачей сервер учитывает просрочку и сохраняет право на завершение своевременного ответа в обработке. Клиент различает исходы по сочетанию `state` и `result`.

| Задача в ответе на чтение | Что произошло |
|---|---|
| `NEW`, `result = null` | Предметного вердикта пока нет. Своевременный запрос может ещё обрабатываться |
| `SOLVED`, в результате `isOk = true` | Зафиксирован верный ответ |
| `FAILED`, в результате `isOk = false` | Зафиксирован неверный ответ. Причина приведена в `errorMessage` |
| `FAILED`, `result = null` | Задача завершена по сроку без предметного вердикта |

Чтение выдаёт сохранённые результаты без повторного вызова проверяющего и без расхода попытки. Пользователь, запросивший чужую сессию, получает `404 SESSION_NOT_FOUND`, как и при отсутствии указанного UUID.
