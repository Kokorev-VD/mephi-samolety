# DOC-06. Программные требования платформы

Часть [сводных программных требований](DOC-06_Программные_требования.md), редакция 1.0 от 20.11.2026. Все требования раздела обязательны. Системные основания для них определены в [DOC-05](../04_Системные_требования/Платформенные_и_предметные_требования.md). Раздел устанавливает обязанности компонентов, когда данные или результат переходят от одной подсистемы к другой. Параметры вызовов, состав ответов и коды отказов приведены в [справочнике API](../09_Архитектура_и_API/DOC-08_Справочник_API.md).

## Учётная запись и доступ

Учётная запись хранит сведения об одном пользователе. При регистрации сервер создаёт такую запись, при входе проверяет, что представившийся пользователь ею владеет. Эта проверка называется аутентификацией. Для следующих запросов сервер выдаёт токен доступа JWT — подписанное сообщение с идентификатором пользователя, его ролями и временем действия. Роль задаёт набор разрешённых действий. Студент с ролью `USER` работает со своими задачами. Преподаватель с ролью `TEACHER` проводит контрольные мероприятия в группах, которые закрепил за ним администратор. Для [просмотра сессий всех студентов](#swr-cfg-002-чтение-сессий-всех-студентов) требуется роль `ADMIN`.

Хеш пароля — значение, по которому можно проверить предъявленный пароль. Для хранения хеша используется [алгоритм BCrypt](#swr-auth-008-передача-и-хранение-пароля). Числа 400, 401, 403 и 404 далее обозначают статусы ответа HTTP, протокола обмена клиента с сервером. Их [значения для платформы](#swr-sys-009-маршрутизация-и-представление-ошибок) зависят от причины отказа.

<a id="swr-auth-001"></a>

### SWR-AUTH-001. Создание учётной записи

Компонент регистрации поддерживает локальную учётную запись и регистрацию с подтверждением личности на `home.mephi.ru`. Для локальной записи он проверяет имя, формат и длину электронной почты (4–120 символов) и длину пароля (8–255 символов), включая границы. После успешной регистрации сервер выдаёт JWT. Локальная запись без университетской привязки даёт доступ к собственным операциям, для которых не нужна учебная группа. Групповые права студент получает по [подтверждённому университетскому профилю](#swr-auth-006).

Основание — [SR-AUTH-001]. При двух запросах локальной регистрации на один свободный адрес создаётся только одна запись. По занятому адресу новый пользователь не получает токен и данные владельца. При регистрации через университетский сервис компонент должен получить подтверждение внешней личности, связанное с начатой этим клиентом операцией. Для одной внешней личности хранится не более одной связи, в том числе при одновременной регистрации. Повторная внешняя регистрация даёт HTTP 409. Совпадение электронной почты не подтверждает владение записью и не объединяет профили.

<a id="swr-auth-002"></a>

### SWR-AUTH-002. Выдача токена при входе

Для локального входа компонент должен найти учётную запись по адресу электронной почты и сверить пароль с её хешем. Успешная сверка даёт право на выдачу JWT. Для незарегистрированного адреса и неверного пароля возвращается HTTP 401 без токена. При входе через `home.mephi.ru` компонент находит пользователя по подтверждённому внешнему идентификатору. Университетский пароль платформа не получает.

Основание — [SR-AUTH-002]. При успешном входе выданный токен позволяет обратиться к прежней истории собственных решений. При отказе клиент не получает доступа к этим данным.

<a id="swr-auth-003"></a>

### SWR-AUTH-003. Проверка токена и роли

Без JWT компонент доступа должен пропускать только локальную регистрацию и вход, а также предусмотренное для внешней регистрации или входа подтверждение личности. Для привязки университетской личности к существующей записи требуется действующий токен этой записи. Для защищённых операций он извлекает токен из заголовка `Authorization: Bearer`, проверяет подпись HMAC-SHA256 и срок действия. HMAC-SHA256 позволяет серверу проверить с общим секретным ключом, что данные токена подлинны и не были изменены. Срок выдаваемого токена определяется параметром окружения в днях. После проверки компонент передаёт идентификатор `userId` и роли `authorities` обработчику операции и проверяет требуемую роль до выдачи защищённых данных.

Основание — [SR-AUTH-003]. Отсутствие действительного токена даёт HTTP 401. При действительном токене и недостаточных правах возвращается HTTP 403. В обоих случаях состояние защищённого ресурса сохраняется.

<a id="swr-auth-004"></a>

### SWR-AUTH-004. Выбор собственного профиля

При чтении собственной истории и при привязке университетской учётной записи прикладной обработчик должен определять локального пользователя по проверенному JWT. Номер группы студента берётся из подтверждённого университетского профиля. Членство в одной группе не даёт одному студенту доступа к чужому профилю или решениям. Привязку начинает владелец после локального входа. Сервер связывает полученное от `home.mephi.ru` подтверждение с этой незавершённой операцией и тем же локальным пользователем. Подтверждение можно применить только один раз. При уже существующей связи с другой записью он возвращает HTTP 409 без изменения обеих записей. Неподтверждённая личность даёт HTTP 401, временная недоступность источника — HTTP 503. В обоих случаях прежняя связь сохраняется. Параметры трёх операций описаны в разделе [об учётной записи и входе](../09_Архитектура_и_API/DOC-08_Справочник_API.md#учётная-запись-и-вход).

Основание — [SR-AUTH-004]. Привязка университетского профиля к существующей записи не переносит её решения другому владельцу. Сохранённые сессии доступны тому же пользователю по прежним идентификаторам.

<a id="swr-auth-005"></a>

### SWR-AUTH-005. Выдача списка групп

Обработчик перечня групп должен возвращать для каждой доступной группы её UUID, название и идентификаторы участников согласно [справочнику API](../09_Архитектура_и_API/DOC-08_Справочник_API.md). Студент с ролью `USER` видит только свою подтверждённую группу, а без неё — пустой список. Для `TEACHER` выдаются только назначенные администратором группы, для `ADMIN` — все группы. Пароли и хеши в ответ не входят.

Основание — [SR-AUTH-005]. Для двух групп с разным составом список возвращает участников каждой под UUID соответствующей группы.

<a id="swr-auth-006"></a>

### SWR-AUTH-006. Определение учебной группы по университетскому профилю

При регистрации студента или привязке его университетской учётной записи обработчик должен получить номер учебной группы из подтверждённого профиля `home.mephi.ru` и сопоставить его с учебной группой платформы. Имя группы, введённое в форме или переданное в запросе студента, не устанавливает членства. Студент не может самостоятельно вступать в группы. Успешная привязка определяет доступные шаблоны и контрольные мероприятия по установленной группе. Владелец ранее созданных сессий и результатов сохраняется.

Основание — [SR-AUTH-006]. Если университетская личность подтверждена, но для неё нельзя установить учебную группу, запись сохраняется без групповых прав. В ответе завершения подтверждения поля `groupId` и `groupNumber` равны `null`. Студент видит пустое расписание. Для недоступного мероприятия действует `404 ASSESSMENT_NOT_FOUND`, для практики — правило выбора доступного шаблона [SWR-SES-002].

<a id="swr-auth-007"></a>

### SWR-AUTH-007. Отбор личной истории

Обработчик истории должен отобрать задачи через сессии подтверждённого пользователя и включить только задачи с записанным предметным вердиктом. Каждая запись связывает результат с выданной задачей и её сессией. История охватывает положительные и отрицательные вердикты поддерживаемых типов и доступна после истечения срока. Чтение не вызывает предметную проверку.

Основание — [SR-AUTH-007]. После обрыва соединения уже сохранённый результат входит в историю. Для `FAILED` с пустым `result` причиной завершения была просрочка без вердикта, поэтому такой записи в истории решений нет. При отсутствии собственных результатов обработчик выдаёт пустой список.

<a id="swr-auth-008"></a>

### SWR-AUTH-008. Передача и хранение пароля

При локальной регистрации и входе пароль должен передаваться по защищённому каналу. Компонент регистрации передаёт в хранилище хеш BCrypt. Компонент входа сверяет предъявленный пароль с сохранённым хешем. Открытый пароль не хранится в записи пользователя. Ни пароль, ни его хеш не выдаются в ответах API.

Основание — [SR-AUTH-008]. Перезапуск не требует повторной регистрации. Сохранённый хеш позволяет войти по правильному паролю и отклонить вход с неверным.

<a id="swr-auth-009"></a>

### SWR-AUTH-009. Закрепление учебных групп за преподавателем

Администратор с ролью `ADMIN` назначает учебные группы пользователю с ролью `TEACHER`. Сервер хранит связь преподавателя с каждой назначенной группой. При чтении перечня групп, публикации мероприятия и чтении результатов обработчик сверяет роль и действующее назначение, в том числе при прямом запросе по UUID группы. Преподаватель без назначения не может опубликовать работу для этой группы. Преподаватель вправе читать результаты только собственного мероприятия в группе с действующим назначением этому преподавателю. В результатах мероприятия отдельно представлены сессии каждого прохождения, включая повторные, и сохранённые вердикты по его задачам. После прекращения назначения сведения группы преподавателю больше не выдаются. Право администратора читать сессии всех студентов установлено в [SWR-CFG-002](#swr-cfg-002).

Основание — [SR-AUTH-009]. После изменения назначений преподаватель видит только свой обновлённый перечень. Студент и преподаватель не могут сами назначать группы преподавателю. Для контроля доступа проверяют и результаты: после отзыва назначения преподаватель не может прочитать результаты ранее опубликованной им работы этой группы. Сессии студентов и их результаты продолжают храниться.

## Шаблоны набора задач, контрольные мероприятия и модерация

Шаблон набора задач — именованный перечень видов заданий в порядке выдачи. По нему студент может начать самостоятельную практику. Для контрольного мероприятия преподаватель составляет работу, назначает её конкретной группе и публикует в расписании. Позиция — одно место в составе работы. Вариант — конкретное условие задания для этой позиции с данными для его проверки. Личная сессия связывает выданные варианты с конкретным студентом и его результатами.

Состояние `DRAFT` обозначает неопубликованный черновик, доступный преподавателю для редактирования. `PUBLISHED` обозначает опубликованное мероприятие с закреплённым составом. Факт публикации позволяет группе увидеть назначение в расписании. Возможность начать работу сервер проверяет отдельно. Допуск определяют [правила доступа и прохождения контрольного мероприятия](../02_Техническое_задание/DOC-02_Техническое_задание.md#правила-доступа-и-прохождения-контрольного-мероприятия).

<a id="swr-cfg-001"></a>

### SWR-CFG-001. Выборка шаблонов своей группы

Обработчик каталога должен сверять запрошенную группу с группой подтверждённого пользователя. Пользователю с ролью `USER` доступны только шаблоны набора задач его группы. Для каждого назначения обработчик возвращает имя шаблона, список типов задач в заданном порядке и признак `enabled` именно для этой группы. Отключённые шаблоны остаются видны в каталоге группы. Компонент создания сессии принимает только включённый шаблон.

Основание — [SR-CFG-001]. Если группе назначены включённый и отключённый шаблоны, каталог различает оба. Создание по включённому шаблону сохраняет число позиций, включая повторяющиеся типы. Запрос каталога чужой группы не раскрывает её шаблоны.

<a id="swr-cfg-002"></a>

### SWR-CFG-002. Чтение сессий всех студентов

Обработчик модерации должен допускать к общему перечню сессий только роль `ADMIN`. Он читает сессии всех студентов с их владельцами, состояниями сессий и состояниями отдельных задач. Обращение к перечню не запускает предметную проверку и не предоставляет права отправить решение за владельца. Преподавательская роль сама по себе не предоставляет доступа к этому перечню.

Основание — [SR-CFG-002]. Если сессии есть у двух студентов из разных групп, в общем перечне модератора видны обе. При обращении только с ролью `USER` сервер отказывает до выдачи перечня.

<a id="swr-cfg-003"></a>

### SWR-CFG-003. Состав контрольного мероприятия

При создании контрольного мероприятия обработчик должен сохранить черновик `DRAFT` с уникальным `assessmentId` и составом, заданным преподавателем. Поле `repeatAllowed` хранит выбор преподавателя о повторном прохождении. В черновике его можно отложить. При создании или полной замене черновика пропуск поля и `null` означают, что выбор ещё не сделан. Значения `true` и `false` явно разрешают или запрещают повтор. Другие типы дают HTTP 400. Черновик допускает пустой список позиций. При редактировании своего черновика преподаватель может изменить состав и этот выбор. Для каждой позиции преподаватель выбирает подключённый программный вид либо своё авторское задание с готовыми вариантами. В одной работе допускаются позиции разных видов и несколько позиций одного вида. Преподаватель может просмотреть свои мероприятия и заменить состав своего черновика. Если к моменту записи правки его работа уже опубликована, обработчик отклоняет правку и сообщает автору о публикации. При выдаче личного набора подсистема сессий получает позиции выбранного мероприятия в заданном порядке. Создание черновика не открывает студентам сессии.

Основание — [SR-CFG-003]. Для мероприятия из ранцевой задачи и задачи Эль-Гамаля преподаватель видит обе позиции в заданном порядке. При формировании личного набора этим позициям соответствуют две задачи своих типов.

<a id="swr-cfg-004"></a>

### SWR-CFG-004. Назначение конкретной группе

При публикации обработчик должен проверить роль `TEACHER` и действующее назначение указанной группы этому преподавателю. Публикация требует двух величин — времени открытия `opensAt` и времени закрытия `closesAt`, причём `opensAt < closesAt`. Сервер сравнивает их со своими часами. Переход в `PUBLISHED`, запись группы, границ, значения `repeatAllowed`, порядка позиций и редакций заданий выполняются в одной транзакции. Опубликованные параметры определяют правила всех прохождений этой работы. При отказе черновик сохраняется, в расписании новая запись не появляется. Разные мероприятия одной группы различаются по `assessmentId`.

Основание — [SR-CFG-004]. Публикация на группу, которую администратор не закреплял за преподавателем, не создаёт назначения. Равные границы окна также исключают публикацию.

<a id="swr-cfg-005"></a>

### SWR-CFG-005. Начало личной сессии по мероприятию

По `assessmentId` подсистема должна проверить публикацию и принадлежность работы группе студента, затем определить по серверным часам, открыт ли старт. Окно открывается и закрывается автоматически. До `opensAt` сервер возвращает `409 ASSESSMENT_NOT_OPEN`, с момента `closesAt` — `409 ASSESSMENT_CLOSED`. Внутри окна действует ограничение одной сессии `NEW` на студента. При наличии такой сессии студент получает `409 ACTIVE_SESSION_EXISTS` и её UUID. Если прежнее прохождение этой работы завершилось, при `repeatAllowed = false` сервер возвращает `409 ASSESSMENT_RETAKE_DISABLED` с UUID прежней сессии в `details.sessionId`. При `repeatAllowed = true` успешный старт создаёт отдельную сессию с новыми UUID сессии и задач для того же мероприятия. Сессии и ответы предыдущих прохождений сохраняются и доступны владельцу по их UUID.

Для начала контроля запрос содержит идентификатор мероприятия. Параметр `configuration` относится к самостоятельной практике по шаблону своей группы. В запросе должен быть ровно один из этих параметров. Для практики `assessmentId` созданной сессии равен `null`. Результат такой сессии не может быть зачтён как участие в мероприятии.

Основание — [SR-CFG-005]. Ровно в момент открытия студент своей группы может начать работу при соблюдении остальных условий. На границе закрытия новый старт уже невозможен. Любой отказ в создании сохраняет прежние задачи и результаты.

<a id="swr-cfg-006"></a>

### SWR-CFG-006. Авторское задание с готовыми ответами

Редактор авторских заданий должен позволять преподавателю ввести варианты без программирования. Для каждого варианта он сохраняет пару строк `statement` и `expectedAnswer` — условие и готовый текстовый ответ. Каждый вариант, доступный для выдачи, имеет оба значения. Преподаватель может выбрать сохранённое задание из своего перечня для позиции вида `CUSTOM_TEXT`. Ответ студента передаётся строкой `answer`. Подсистема сессий вызывает проверку через тот же интерфейс, что и для программно добавленного вида задания.

Для изменения своего задания преподаватель передаёт название и варианты по `PUT /api/custom-tasks/{customTaskId}` в той же форме, что и при создании. Компонент сохраняет новую редакцию для будущих публикаций. Мероприятия, уже опубликованные к моменту изменения, продолжают использовать закреплённую редакцию, даже если ни один студент ещё не начал работу.

Проверяющий получает ответ студента и эталон выданного варианта. У каждой из двух строк он удаляет пробелы по краям и затем сравнивает строки целиком. Регистр букв и внутренние пробелы сохраняются. Например, эталон «Красная книга» и ответ с теми же словами принимаются при любом числе пробелов по краям обеих строк. Ответ с маленькой начальной буквой или с двумя пробелами между словами даёт отрицательный вердикт.

Основание — [SR-CFG-006]. Для проверки используют два варианта с разными эталонами. Вердикт относится к эталону того варианта, который получил студент.

<a id="swr-cfg-007"></a>

### SWR-CFG-007. Выбор и закрепление авторского варианта

Для каждой позиции с авторским заданием обработчик выдачи должен случайно выбрать одну из пар той редакции задания, которая была закреплена при публикации, и связать выбор с этой позицией в личной сессии. Последующие изменения банка вариантов не меняют ни опубликованное задание, ни уже выданную пару. Открытое условие входит в набор студента. Основание для проверки и эталонный ответ хранятся на сервере. Их нельзя получить в составе условия, через повторное чтение сессии или через личную историю.

Основание — [SR-CFG-007]. После перезапуска чтение возвращает прежнее условие, а проверка использует прежний эталон без нового случайного выбора. Повторяющиеся позиции одного вида имеют собственные привязки к вариантам. При случайном выборе один вариант может встретиться повторно.

<a id="swr-cfg-008"></a>

### SWR-CFG-008. Публикация в расписании группы

Компонент расписания должен включить назначенное группе контрольное мероприятие в расписание студентов этой группы после явного действия преподавателя по публикации. Обработчик публикации проверяет сохранённый список позиций в той же транзакции, в которой закрепляет состав и переводит мероприятие в состояние `PUBLISHED`. Если список пуст, обработчик возвращает отказ с указанием добавить хотя бы одно задание. При корректных параметрах назначения проверка пустого состава выполняется первой и даёт `409 ASSESSMENT_EMPTY`, даже если режим повторов ещё не выбран. Для непустого состава без выбора `repeatAllowed` сервер возвращает `409 ASSESSMENT_RETAKE_POLICY_REQUIRED` и просит преподавателя разрешить либо запретить повтор. В обоих случаях сохраняются состояние `DRAFT` и прежний идентификатор, запись расписания не создаётся. При успехе опубликованное значение `repeatAllowed` всегда равно `true` или `false`. С момента публикации студент своей группы видит мероприятие, оба момента окна и разрешение на повторное прохождение, в том числе до открытия. Чтение расписания не создаёт личную сессию и не выдаёт условия или эталоны. Условия доступны студенту в его личном наборе после допуска к началу работы. Поле `canStart` учитывает открытое окно, наличие активной сессии и возможность повтора. Если у студента были прохождения этого мероприятия, `sessionId` указывает на его собственную активную сессию мероприятия либо, при её отсутствии, на последнюю завершённую. Остальные сессии доступны владельцу по своим UUID.

Основание — [SR-CFG-008]. Проверку выполняют для двух групп. Сразу после публикации назначенная группа видит запись о мероприятии в расписании. В расписании другой группы эта запись отсутствует. Перед открытием из расписания нельзя получить индивидуальные условия или эталонные ответы.

## Предметные компоненты

Предметный компонент отвечает за содержание учебного задания. Для сессионной работы он выдаёт условие и проверяет решение, а для самоподготовки может предоставить отдельный пример с разбором. **Шифрование** — преобразование исходного сообщения в шифротекст с использованием ключа. **Расшифрование** восстанавливает сообщение с соответствующим ключом. В учебной задаче студент показывает промежуточные результаты обоих преобразований.

<a id="swr-elg-001"></a>

### SWR-ELG-001. Условие и проверка решения Эль-Гамаля

В учебном условии схемы Эль-Гамаля `p` — простое число, по которому считают остатки, `g` — основание, `x` — закрытый показатель, `m` — исходное сообщение. По запросу создания задачи генератор должен вернуть студенту условие с этими четырьмя величинами. Из закрытого показателя получают открытый ключ. Для конкретного шифрования студент выбирает отдельный одноразовый показатель. Для ответа допустимой формы предметный обработчик берёт то же сохранённое условие. Он последовательно проверяет открытый ключ `y`, допустимость выбранного студентом показателя `k`, компоненты шифротекста `c1` и `c2` и восстановленное сообщение `decryptedMessage`. Обработчик передаёт в подсистему сессий один предметный вердикт. При несоответствии он указывает первое ошибочное значение в этой последовательности.

Основание — [SR-ELG-001]. Если неверны открытый ключ и одна из компонент шифротекста, пояснение указывает на ключ. Отсутствие обязательного поля отклоняется при разборе формы до предметного вычисления. Состояние задачи и общий итог фиксирует подсистема сессий по [SWR-SES-011].

<a id="swr-elg-002"></a>

### SWR-ELG-002. Самостоятельное задание и разбор

Компонент самоподготовки должен по положительному целому параметру разрядности `bitLength` сформировать отдельный учебный пример с математически допустимыми параметрами. Нулевое или отрицательное значение разрядности отклоняется с HTTP 400. При запросе самостоятельной работы клиент получает условие с `p`, `g`, `x`, `m`. При запросе разбора клиент получает условие, промежуточные результаты с пояснениями и итог. Ответ выдаётся без записи задачи или результата в базу. Условие и ответ редакционного примера не заменяют данные задачи, уже выданной студенту в сессии.

Основание — [SR-ELG-002]. При последовательном запросе условия и разбора прежняя сессия, её попытки и личная история сохраняются. Условия применения `bitLength` определяет справочник API.

<a id="swr-bdr-001"></a>

### SWR-BDR-001. Выдача готового демонстрационного примера

Обработчик учебной демонстрации должен выдать допущенному пользователю подготовленный пример вместе с относящимся к нему демонстрационным результатом и пояснением. В пояснении указывается, какое допущение о конфиденциальности нарушено в примере и почему этот вывод сохраняется при правильном выполнении вычислений. Если готовый пример получить не удалось, обработчик возвращает отказ без оценки решения студента. Просмотр не создаёт сессию, задачу с предметным вердиктом или запись результата в базе.

Основание — [SR-BDR-001]. Связь результата с примером проверяют по описанию учебного материала. В обоих исходах сохраняются прежний состав сессии, доступные попытки и личная история студента.

## Общие службы и условия эксплуатации

Сервер принимает запросы клиентов через REST-интерфейс — набор HTTP-операций над ресурсами платформы, например группами и сессиями. UUID однозначно обозначает ресурс. Документы JSON передают значения его полей. PostgreSQL — система управления базой данных, в которой сохраняются записи платформы. Docker Compose задаёт порядок запуска приложения и базы. **Постоянный том** — место хранения файлов базы, которое остаётся доступным после перезапуска контейнера.

Производительность оценивают по времени от отправки запроса до получения полного ответа. Показатель p95 (95-й процентиль) — длительность на границе, в которую укладываются не менее 95 процентов измерений упорядоченной выборки. Для обычных операций и генерации задач используются [отдельные выборки и пределы](#swr-sys-013-время-ответа-обычных-операций).

<a id="swr-sys-009"></a>

### SWR-SYS-009. Маршрутизация и представление ошибок

Сервер должен предоставлять операции по базовому пути `/api` на порту 8083. Интерфейс принимает и выдаёт структурированные данные в JSON и использует UUID для идентификаторов ресурсов. При отказе общий обработчик возвращает HTTP-статус и JSON с полями машинного кода, понятного сообщения и времени события. Для операций сессии действуют дополнительные поля из приложения к DOC-06.2.

Основание — [SR-SYS-010]. Неверная форма запроса получает 400, неподтверждённая личность — 401, недостаток прав — 403, отсутствующий ресурс — 404. Подтверждённый отрицательный учебный вердикт остаётся успешной обработкой запроса с предметным результатом.

<a id="swr-sys-010"></a>

### SWR-SYS-010. Получение параметров при запуске

Компонент настройки приложения должен получить секрет для подписи из `JWT_SECRET`, срок действия токена в днях из `ACCESS_TOKEN_LIFETIME` и параметры подключения к СУБД из переменных окружения. Компонент токенов и компонент хранения используют назначенные им параметры. В исходных текстах и файлах рабочей поставки в репозитории указывают имена переменных без значений секретов.

Основание — [SR-SYS-011]. В описании запуска прослеживаются источники параметров подписи, срока и подключения. Выданный токен имеет установленный срок действия.

<a id="swr-sys-011"></a>

### SWR-SYS-011. Восстановление записей и обслуживания сессий

Компонент хранения должен сохранять в PostgreSQL 17 учётные записи платформы и их связь с подтверждённой университетской личностью, членство по номеру группы из профиля, назначения групп преподавателям, шаблоны набора задач и их назначения, авторские задания с редакциями вариантов, черновики и опубликованные контрольные мероприятия. Для публикации сохраняются назначенная группа, моменты открытия и закрытия, явное значение `repeatAllowed`, порядок позиций и закреплённые редакции их содержимого. Для личных сессий сохраняются связи прежних и последующих прохождений с мероприятием, сроки подачи ответов, выданные задачи со своими вариантами, открытые операции и зафиксированные вердикты.

После запуска обработчики читают прежние данные по тем же UUID. Преподаватель может продолжить работу над своим черновиком. В расписании группы остаётся опубликованное мероприятие, в том числе до первого старта. При первом старте после восстановления задачу формируют по редакции, закреплённой при публикации. Для уже открытых сессий возобновляется контроль срока, а для принятых ответов действует порядок [SWR-SES-021]. Повторный вход студента для фоновой обработки просрочки не требуется.

Основание — [SR-SYS-012]. После перезапуска совпадают принадлежность студента к группе, доступные шаблоны и состояния выданных задач. Для открытой операции сохраняются первоначальное время получения, предел обработки и входные данные.

<a id="swr-sys-012"></a>

### SWR-SYS-012. Готовность базы и постоянный том

Описание развёртывания Docker Compose должно связывать запуск приложения с успешной проверкой готовности PostgreSQL. Файлы данных СУБД размещаются на постоянном томе, который повторно подключается при штатном перезапуске контейнеров.

Основание — [SR-SYS-013]. Пока СУБД ещё не готова принимать запросы, условие запуска приложения не выполнено. При штатном перезапуске с тем же томом доступны ранее зафиксированные данные.

<a id="swr-sys-013"></a>

### SWR-SYS-013. Время ответа обычных операций

При 30 одновременно работающих пользователях на прогретом стенде сервер должен обеспечивать 95-й процентиль времени отклика обычных операций не более 2 секунд. К классу относятся регистрация, вход, запросы групп и шаблонов, чтение данных и отправка ответа с обычной предметной проверкой. Время считают от отправки запроса клиентом до получения полного ответа. Обычное ожидание в очереди входит в измерение.

Основание — [SR-SYS-014]. Для класса берут не менее 100 штатных измерений, упорядочивают длительности по возрастанию и сравнивают с пределом значение на позиции `ceil(0.95*N)`, считая от единицы. Здесь `N` — число измерений класса. При 100 наблюдениях сравнивают 95-е значение. Искусственные задержки и специально вызванные отказы рассматриваются отдельно.

<a id="swr-sys-014"></a>

### SWR-SYS-014. Время ответа при генерации

При той же нагрузке в 30 пользователей на прогретом стенде сервер должен обеспечивать для операций генерации 95-й процентиль не более 5 секунд. Создание сессии с формированием задач входит в этот класс вместе с учебными запросами генерации. Для него собирают собственную выборку не менее чем из 100 штатных измерений. Точки начала и окончания измерения и правило выбора ранга заданы в [SWR-SYS-013].

Основание — [SR-SYS-015]. Сравнивают с 5 секундами значение на позиции `ceil(0.95*N)` в выборке генерации. Результат ровно на границе удовлетворяет требованию. Двухсекундный предел применяется к отдельной выборке обычных операций. Предельное время фиксации своевременно поступившего ответа на задачу по [SWR-SES-020] отсчитывается независимо от расчёта процентиля.

<a id="swr-sys-015"></a>

### SWR-SYS-015. Единый интерфейс вида задания

Каждому программно зарегистрированному виду задания должны соответствовать две операции. При выдаче модуль формирует вариант и передаёт подсистеме сессий отдельно условие для студента и закрытые данные для проверки. При проверке он принимает ответ и закреплённые данные этого варианта и возвращает предметный вердикт с предусмотренной для него диагностикой. Ошибка выполнения модуля без вердикта передаётся как технический отказ. Состояниями задачи и сессии управляет подсистема сессий.

Реестр выбирает модуль по устойчивому идентификатору вида выданной задачи. Через него обслуживаются ранцевые задачи, задачи Эль-Гамаля и авторские задания. Новый программный вид подключается регистрацией модуля с идентификатором, схемой ответа и обеими операциями. По `GET /api/task-types` каталог передаёт для каждого вида поля `type`, `title` и `solutionSchema`. Последнее описывает форму студенческого ответа в машиночитаемом виде. Закрытые данные для проверки и эталоны в каталог не входят. Подсистема сессий использует тот же порядок выдачи и проверки для всех зарегистрированных видов.

Основание — [SR-SYS-016]. Для добавленного вида проверяют весь путь от его позиции в мероприятии до вердикта в личной сессии. Студент получает только открытое условие. При отправке решения используется серверный контекст именно этой позиции. При отсутствии необходимого модуля набор не подтверждается как полностью созданный.
