# DOC-13.5. Протокол формальной инспекции архитектуры и API

## Результаты сверки

**Группы и доступ к результатам.** Номер учебной группы студента сервер получает при регистрации или привязке подтверждённой учётной записи МИФИ. Группы преподавателю назначает администратор. Если администратор снимает назначение после публикации, преподаватель при следующем запросе результатов своей работы для этой группы получает HTTP 404. Правило доступа задано в DOC-07, раздел 2. Код ответа указан в DOC-08, «Результаты контрольного мероприятия». Подтверждение группы и отзыв назначения разобраны в карточках [TC-AUTH-004](../10_Верификация_и_тестирование/DOC-10_План_верификации.md#tc-auth-004) и [TC-AUTH-005](../10_Верификация_и_тестирование/DOC-10_План_верификации.md#tc-auth-005).

**Закрытие работы.** В карточке TC-SES-017 студент начинает работу в 10:55, а в 11:00 она закрывается. Сервер отклоняет новый ответ, полученный ровно в 11:00, с кодом 410 `SESSION_EXPIRED`. Если полный допустимый ответ получен в 10:59:59.900, вердикт по нему можно записать в 11:00:02. Ровно в 11:00:59.900 срок записи уже истёк. DOC-07, раздел 5, и DOC-08, «Сессии задач», раздел 2, дают тот же результат. Связь с системными требованиями SR-SES-011 и SR-SES-012 указана в [таблице соответствия DOC-10](../10_Верификация_и_тестирование/DOC-10_Верификация_сессий.md#соответствие-карточек-требованиям).

**Возврат после обрыва связи.** Если студент потерял ответ на запрос старта, в расписании он находит идентификатор своей сессии и открывает её запросом чтения. После завершения сессии новый запрос старта при открытой контрольной и разрешённых повторах создаёт отдельное прохождение. Такое различие явно описано в DOC-08, «Расписание студента» и «Сессии задач», раздел 1. Карточка TC-CFG-005 проверяет условия повторного старта.

## Замечания к разбору

### 1. Состояние просроченной задачи в ведомости преподавателя

В DOC-07, раздел 5, и DOC-08, «Сессии задач», раздел 3, студент при чтении своей сессии сразу видит просрочку. В DOC-08, «Результаты контрольного мероприятия», описан состав ведомости преподавателя, но не указано, на какой момент определять состояние задач.

Например, работа закрылась в 10:30, студент ничего не отправил, фоновая проверка запланирована на 10:30:30. В 10:30:01 студент уже увидит у задачи `FAILED` (срок истёк) и `result = null` (вердикта нет). В ведомости преподавателя по тексту допустимо показать прежнее `NEW` — задача ещё открыта. От этого зависит, какую работу преподаватель сочтёт незавершённой.

Предложение редактору DOC-08 — установить в описании ведомости тот же момент определения состояния, что и при чтении студентом. Для повторной сверки нужны два случая между закрытием и ближайшей фоновой проверкой. При отсутствии ответа обе стороны видят просрочку. Если своевременный ответ ещё обрабатывается в пределах отведённых 60 секунд, обе стороны видят открытую задачу до записи вердикта либо истечения срока обработки.

### 2. Условия проверки публикации пустой контрольной

В [карточке TC-CFG-008](../10_Верификация_и_тестирование/DOC-10_План_верификации.md#tc-cfg-008) случай «ноль и одно задание» предлагает передать группу и время открытия пустой работы. Ожидается код 409 `ASSESSMENT_EMPTY`. По DOC-08, «Назначение группе и публикация», при пропуске времени закрытия сервер вернёт 400 ещё до проверки состава. Далее карточка ожидает успешную публикацию после добавления задания, хотя в описанных действиях преподаватель ещё не выбрал правило повторного прохождения.

Предложение владельцу DOC-10 — во всех запросах этого случая указывать допустимые `groupId`, `opensAt` и `closesAt`. Для пустого состава ожидается 409 `ASSESSMENT_EMPTY`. После добавления задания при невыбранном правиле ожидается 409 `ASSESSMENT_RETAKE_POLICY_REQUIRED`. После явного выбора, например `repeatAllowed = false`, ожидается 200 и карточка появляется в расписании назначенной группы. Для двух параллельных запросов в конце той же карточки выбор повтора также должен быть задан заранее.
