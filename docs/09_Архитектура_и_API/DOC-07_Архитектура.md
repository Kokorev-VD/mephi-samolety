## 1. Назначение и границы

Документ описывает архитектуру ПО криптотренажёра mephi-12: состав программных компонентов, их размещение по слоям, связи и развёртывание. Он показывает, где в системе размещаются обязательства, определённые [DOC-06](../07_Программные_требования/DOC-06_Программные_требования.md) и подсистемными требованиями, и не вводит новых требований. Математические алгоритмы, форматы операций и состав требований здесь не дублируются — на них даются ссылки.

Источником фактов об реализации служат карточки доменов Спринта 1 (`notes/domains/*.md`) и каталог эндпоинтов (`notes/api/endpoints.md`), сверенные с кодом `mephi-12/backend`. Технологии зафиксированы [ТЗ](../../02_Техническое_задание/Техническое_задание.tex): Kotlin 1.9.25, Spring Boot 3.4.0 (Web, JPA, Security, Validation), PostgreSQL 17, Docker/docker-compose.

## 2. Общий облик системы

Система — монолитное серверное приложение со слоистой структурой и одной внешней зависимостью: реляционной базой данных. Все компоненты выполняются в одном процессе; отдельные сервисы, брокеры сообщений и внешние хранилища не используются. Разделение на слои определяет направление зависимостей: внешний запрос проходит слои сверху вниз, предметные вычисления не обращаются к приёму операций.

| Слой | Назначение | Основные элементы |
|---|---|---|
| Приём операций | HTTP-приём, аутентификация, авторизация, разбор параметров, единое представление ошибок | Контроллеры, `JwtFilter`, `SecurityConfig`, `ExceptionResolver` |
| Оркестрация | Пользовательские сценарии: coordination доступа, конфигураций, генерации и проверки | `AuthService`, `UserService`, `GroupConfigService`, `ProblemDecorator`, `HistoryService` |
| Предметные домены | Генерация условий и математическая проверка решений | Ранцевые решатели и проверяющий, Эль-Гамаль с математической библиотекой, бэкдор-генератор |
| Хранение | Сохранение и чтение данных, согласованность изменений | JPA-сущности, Spring Data-репозитории, конвертеры списковых величин |
| Фоновый контроль | Завершение просроченных задач по расписанию | `ProblemAutoFailScheduler` |

### Последовательность создания набора

Приём операции передаёт в оркестрацию подтверждённого пользователя и имя конфигурации. Оркестрация через компонент конфигураций получает доступный состав набора, затем для каждого квалификатора вызывает генератор предметного домена. Условия, типы и принадлежность задач сохраняются вместе с сессией; подтверждение выдаётся после сохранения полного набора. Порядок закреплён [SWR-SES-002–005](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#2-создание-сессии).

### Последовательность обработки ответа

Приём фиксирует время получения запроса. Управление сессиями проверяет допуск (принадлежность, состояния, срок), затем формат по схеме типа. Допустимый ответ передаётся предметному проверяющему вместе с сохранённым условием; вердикт согласованно сохраняется с состоянием задачи и итогом сессии. Категории результата различаются машинными кодами [контракта сессий](../07_Программные_требования/Контракты_сессий.md#коды-и-представление-ошибок). Порядок закреплён [SWR-SES-007–015](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#3-обработка-ответа).

### Фоновый контроль и чтение

Планировщик выполняется в процессе приложения с периодом 60 секунд и приводит просроченные незавершённые задачи к `FAILED`, учитывая принятые своевременные ответы; агенты внешних очередей отсутствуют. Чтение собственной сессии возвращает сохранённые состояния и результаты без повторной проверки. Обязательства определены [SWR-SES-016–019 и SWR-SES-023](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#4-контроль-срока-и-итог).

## 4. Размещение и исполнение

Все компоненты выполняются в одном процессе приложения; единственный внешний исполнитель — СУБД. Предметные вычисления выполняются синхронно в рамках обработки запроса; собственные потоки доменов не создаются. Фоновый контроль использует средство планирования платформы и разделяет хранилище с остальными компонентами, поэтому согласование параллельных действий выполняется транзакциями и блокировками данных, а не обменом сообщениями.

Расширение состава задач выполняется подключением нового предметного обработчика под собственным квалификатором: конфигурация называет квалификатор, оркестрация вызывает обработчик, остальные компоненты не изменяются. Требование к такому подключению задано [контрактом предметного обработчика](../07_Программные_требования/DOC-06_Программные_требования.md#swr-sys-004-контракт-предметного-обработчика).

## 5. Развёртывание

Развёртывание выполняется docker-compose из двух служб: контейнер СУБД и контейнер приложения, стартующий после готовности СУБД.

| Элемент | Значение |
|---|---|
| Контейнер СУБД | PostgreSQL 17 (alpine), база `mephi12`, порт 5432, контроль готовности `pg_isready`, том данных `mephi12-data` |
| Контейнер приложения | Сборка Gradle на JDK 17, исполнение на OpenJDK 17, порт 8083, базовый путь `/api` |
| Параметры окружения | `JWT_SECRET`, `ACCESS_TOKEN_LIFETIME`, `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD` |
| Схема базы | Создаётся средствами JPA по описанию сущностей |

Обязательства развёртывания заданы [ТЗ, `TS.REQ.REL.DEPLOY`]: старт приложения только после готовности СУБД и сохранность данных между перезапусками томом данных. Секреты передаются только переменными окружения и не включаются в код или репозиторий ([`TS.REQ.SEC.SECRETS`]).

## 7. Известные ограничения реализации

Ограничения зафиксированы [ТЗ, п. 2.3](../../02_Техническое_задание/Техническое_задание.tex) и карточками доменов; они не меняют описанную архитектуру, а помечают различия между ней и текущим кодом.

1. Схема базы создаётся режимом обновления JPA-описания; инструменты миграции не применяются.
2. Правило доступа к функции модерации фактически не отличает роли: эндпоинт просмотра сессий доступен любой роли `USER`, а выдача роли `ADMIN` через API невозможна.
3. Настройка CORS разрешает все источники с передачей учётных данных; область применения системы — учебная.
4. Управление группами и конфигурациями на уровне API не покрывает создание, изменение и удаление — выполняется средствами СУБД.
5. Средство наблюдения (Actuator) входит в зависимости, но не настроено; собственные метрики и зонды готовности приложения не экспортируются.
