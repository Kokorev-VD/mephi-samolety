## 1. Назначение и границы

Архитектура программного обеспечения (ПО) описывает, какая часть платформы принимает решение, где оно исполняется и какие данные переживают перезапуск. **Контрольное мероприятие** — составленная преподавателем работа для одной учебной группы. При публикации преподаватель закрепляет состав работы, разрешение на повторное прохождение и два момента — открытие и окончание. После этого студент видит карточку мероприятия в расписании, а в разрешённое время может начать свою **сессию** — личный набор задач с общим сроком решения. Для самостоятельной практики набор можно получить по **шаблону** — именованному перечню типов задач в заданном порядке. Результаты практики сохраняются отдельно от участия в мероприятии.

На устройстве пользователя работает **клиент** — приложение, которое показывает задания и отправляет решения. **Сервер** принимает запросы клиента, устанавливает, кому принадлежит задача, и записывает результаты в PostgreSQL — систему управления базой данных. Клиент и сервер общаются через **REST API** — программный интерфейс для работы с ресурсами сервера. Клиент по сетевому протоколу HTTP указывает операцию и адрес ресурса. Сервер возвращает код состояния и, когда это предусмотрено, данные. Внешние операции перечислены в [указателе API](DOC-08_Справочник_API.md#указатель-операций).

Один и тот же результат должен правильно сохраняться как при обычной отправке решения, так и при сбое. Запрос студента может запустить **предметную проверку** — сравнение ответа с условиями конкретного задания. Её **вердикт** сообщает, верен ли ответ. **Планировщик** — часть сервера, которая периодически завершает просроченные задачи. При перезапуске сервер возобновляет прерванные операции по записям в базе. Все три пути используют одни и те же данные. То, что в каждом случае видит студент, определяют [требования к сессиям](../04_Системные_требования/Сессии_задач.md).

## 2. Слои и компоненты

**Компонент** — часть программы с определённой обязанностью. Компоненты со сходными задачами образуют **слой**. На внешней границе сервер принимает HTTP-запрос и проверяет JWT — подписанную строку с идентификатором и правами пользователя. Так устанавливается личность отправителя (аутентификация). После этого прикладной слой решает, разрешено ли ему действие с конкретной записью. Предметный компонент определяет правильность решения учебной задачи. Слой хранения записывает связанные изменения в **транзакции**. При успешном завершении все её изменения становятся видимы вместе. При отмене сохраняется состояние до начала записи.

Для связи записей используется **UUID** — уникальный идентификатор в форме строки, например `312c6ab8-5c12-46ae-a8bf-942d3c45c125`. В запросе идентификатор указывает, какую запись надо найти, а право на неё устанавливается отдельно. **Контекст пользователя** содержит подтверждённые данные отправителя, прежде всего его идентификатор и роль. Роль `USER` даёт права студента. `TEACHER` позволяет создавать свои упражнения и контрольные, а для назначения работы или чтения результатов требуется также действующее закрепление группы за преподавателем. `ADMIN` назначает эти группы и может просмотреть сессии всех пользователей. Права на конкретную группу сервер проверяет по действующим назначениям. [Правила доступа и прохождения](../02_Техническое_задание/DOC-02_Техническое_задание.md#правила-доступа-и-прохождения-контрольного-мероприятия).

В составе работы **позиция** — место задания в упорядоченном списке. **Тип** определяет, как выдать условие (данные, которые увидит студент) и как проверить его решение. Эту работу выполняет **предметный модуль**. Закрытые данные проверки, например эталонный текст, остаются на сервере.

| Компонент | Данные на его границе | За что отвечает |
|---|---|---|
| REST-интерфейс и аутентификация | Запрос клиента, заголовок `Authorization`, параметры и тело | Подтвердить пользователя и роль, отметить время получения полного запроса с решением. Вернуть данные или ошибку в форме, определённой API. |
| Учётные записи и группы | Локальные учётные данные либо подтверждение личности из личного кабинета МИФИ. Для связи с существующим профилем — также личность вошедшего пользователя | Зарегистрировать профиль, выполнить вход или привязать внешний профиль к тому же владельцу. Определить учебную группу по надёжно подтверждённому номеру. Отдельно хранить назначения, сделанные администратором для преподавателя. |
| Шаблоны наборов задач и модерация | Группа, имя шаблона, признак включения | Предоставить доступный группе упорядоченный состав задач. Модерация — просмотр сессий всех студентов для контроля учебного прогресса. Для неё проверяется право `ADMIN`. |
| Мероприятия и расписание | Преподаватель передаёт состав, правило повтора, группу и границы времени. Студент запрашивает собственное расписание | Сохранить авторство черновика, проверить назначение группы, опубликовать работу и вернуть карточку расписания. Для выдачи передать закреплённый состав и срок. Показать преподавателю результаты его работы в закреплённой за ним группе. |
| Управление сессиями | Контекст пользователя, мероприятие или шаблон для начала работы, UUID задачи или сессии для решения и чтения | Создать набор, решить вопрос о допуске ответа, выбрать обработчик, сохранить вердикт и рассчитать итог набора. |
| Предметные обработчики | Тип и настройки для генерации, сохранённое условие и ответ для проверки | Сформировать условие или вернуть предметный вердикт. Об ошибке формы либо невозможности проверки сообщить отдельно. |
| Хранение | Сущности пользователя и набора, записи операций | Обеспечить принадлежность данных, согласованную запись и чтение. По состоянию записи можно отличить прерванное вычисление от завершённого. |

Управление сессиями обращается к предметному модулю за условием и передаёт ему ответ на проверку. Модуль с типом `BACKPACK` обслуживает ранцевые задачи, модуль `EL_GAMAL` — задачи по схеме Эль-Гамаля. Модуль `CUSTOM_TEXT` выбирает подготовленный преподавателем вариант для каждой позиции и сравнивает текст ответа с эталоном именно этого варианта. Компонент выдачи возвращает условие без эталона. Реестр — каталог подключённых модулей. По устойчивому идентификатору `type` в нём находятся модуль, схема решения (перечень полей и типов данных), операции выдачи и проверки. Выдача возвращает открытое условие и закрытые данные проверки. При подключении нового модуля расписание продолжает пользоваться тем же реестром. Правила срока и фиксации остаются общими. Редакционной операцией называется выдача учебного примера для самостоятельного разбора, вне сессии студента. Среди материалов есть [готовая демонстрация со скрытым свойством](DOC-08_Справочник_API.md#учебная-демонстрация-со-скрытым-свойством). Её просмотр не создаёт задачу с попыткой решения. Границы предметных обязанностей приведены в [сводных программных требованиях](../07_Программные_требования/DOC-06_Программные_требования.md#2-ответственность-и-связи).

### Подготовка мероприятия и расписание группы

Компонент мероприятий сохраняет работу преподавателя в состоянии `DRAFT` (черновик), и запоминает `repeatAllowed` — разрешён ли повтор после завершения. Черновик доступен автору и может быть пустым, правило повтора в нём можно пока оставить незаполненным. Для публикации преподаватель указывает закреплённую за ним группу и моменты открытия и окончания. Открытие должно предшествовать окончанию. В одной транзакции компонент проверяет право автора на эту группу и наличие хотя бы одной позиции. Затем проверяет, что преподаватель явно разрешил или запретил повтор. При незаполненном условии работа остаётся черновиком. При успехе компонент закрепляет порядок и редакции заданий, правило повтора и обе границы времени, затем записывает `PUBLISHED` (опубликована). При одновременной правке и публикации в расписание может попасть только сохранённый непустой состав.

Публикация сразу показывает карточку расписания студентам с подтверждённой группой. Окно старта открывается автоматически в момент начала, закрывается в момент окончания. Студенту видны оба момента, текущая доступность старта и идентификатор его последней сессии, если такая была. Проверка перед созданием учитывает действующие на тот момент права и время. Компонент результатов проверяет роль преподавателя, авторство и текущее назначение группы при каждом чтении. Отзыв назначения прекращает доступ к результатам этой группы. Для администратора сохраняется отдельный общий просмотр.

Для `CUSTOM_TEXT` хранилище связывает задачу личной сессии с выбранным вариантом и эталоном на момент выдачи. Студенту доступны только условие и его собственный сохранённый результат. При повторном чтении или восстановлении обработки система использует прежний вариант. Сравнение текстов после удаления пробелов по краям сохраняет регистр букв и пробелы внутри строки.

## 3. Размещение и исполнение

**Узел** — среда, в которой исполняется программа или хранятся её данные. На устройстве пользователя расположен клиент. Серверное приложение и базу данных размещают в двух **контейнерах**, изолированных средах выполнения. Описанные выше серверные компоненты работают внутри приложения. **Порт** обозначает точку подключения к серверу, а **путь** указывает ресурс внутри его интерфейса. Запрос идёт от клиента к приложению, с базой данных работает приложение.

| Участник обмена | Где выполняется и как взаимодействует с остальными |
|---|---|
| Клиент | Обращается к REST API серверного приложения по базовому пути `/api`, порт 8083. Передаёт JWT в заголовке запроса `Authorization`, после слова `Bearer`. |
| Сервер | Контейнер приложения. Программа написана на языке Kotlin 1.9.25 и использует платформу Spring Boot 3.4.0 для серверных приложений. В одном процессе работают приём запросов, управление сессиями, предметные компоненты, планировщик и обработка открытых операций при запуске. |
| Хранилище | Контейнер PostgreSQL 17 с постоянным томом — областью хранения, которая сохраняется при перезапуске контейнера. Приложение обращается к нему при проверке принадлежности, регистрации входящего ответа, изменении набора и чтении результатов. |
| Личный кабинет МИФИ (`home.mephi.ru`) | Внешний источник удостоверенной личности и подтверждённого номера учебной группы. Сведения о связи с локальным профилем, полномочия платформы и результаты обучения хранит сервер платформы. |

Docker Compose управляет запуском связанных контейнеров. Сначала он проверяет готовность PostgreSQL принимать подключения, затем запускает приложение. Настройки серверного приложения включают параметры подключения к базе данных, секрет подписи JWT (закрытое значение для проверки подлинности токена) и срок действия токена. Эти значения приложение получает из переменных окружения — именованных настроек, переданных процессу при его запуске. Условия развёртывания определены в [TS.DESC.ARCH](../02_Техническое_задание/DOC-02_Техническое_задание.md#ts-desc-arch), [TS.REQ.REL.DEPLOY](../02_Техническое_задание/DOC-02_Техническое_задание.md#ts-req-rel-deploy), [TS.REQ.SEC.SECRETS](../02_Техническое_задание/DOC-02_Техническое_задание.md#ts-req-sec-secrets) и [TS.DOC.TECH](../02_Техническое_задание/DOC-02_Техническое_задание.md#ts-doc-tech) [технического задания](../02_Техническое_задание/DOC-02_Техническое_задание.md).

Локальная регистрация и вход с паролем доступны отдельно. Для входа или регистрации через кабинет МИФИ сервер связывает одноразовое подтверждение с начатым обращением и его назначением. Для привязки дополнительно проверяет, что обращение завершает тот же вошедший владелец профиля. Одна внешняя личность может быть связана только с одним локальным профилем, в том числе при одновременных обращениях. Совпадение адресов электронной почты не подтверждает связь. Без подтверждённого номера группы доступны самостоятельные действия вне группы. [Операции регистрации, входа и привязки](DOC-08_Справочник_API.md#учётная-запись-и-вход).

Обработка ответа может дождаться свободного исполнителя в приложении. На время такого ожидания данные ответа уже находятся в PostgreSQL. Повторный запуск получает их оттуда вместе с исходным временем поступления. Очередность исполнения и период фоновой работы не задают пользователю новый срок.

## 4. Состояние и границы записи

Состояние задачи `NEW` означает, что задача открыта, `SOLVED` — что сохранён верный ответ, `FAILED` — что зафиксирован неверный ответ либо истёк срок задачи. Поле `result` хранит вердикт, а `null` означает его отсутствие. Ход обработки запроса сохраняют отдельной записью. Для неё «открыта» означает, что окончательный исход ещё предстоит записать. Чтение задачи различает [четыре сочетания состояния и результата](DOC-08_API_сессий.md#3-чтение-состояния-и-восстановление-после-обрыва-связи).

У хранилища три группы данных с разным назначением. Состав первой группы позволяет решить, какой набор пользователь может начать сейчас. По второй можно воспроизвести то, что он действительно получил. По третьей приложение определяет, какое действие остаётся завершить после сбоя.

| Данные | Когда записываются и что по ним восстанавливается |
|---|---|
| Профиль, подтверждённая группа студента, назначения преподавателя, мероприятие или шаблон | До создания сессии. Для контрольной сервер получает назначение группе, открытие и окончание, разрешение на повтор, состав и редакции вариантов. Для практики получает шаблон, включённый для подтверждённой группы, и порядок типов задач. |
| Сессия и задачи | При создании одной транзакцией сохраняются UUID владельца, UUID набора, серверное время создания набора `t0`, фактический срок приёма ответов `deadlineAt`, ссылку на мероприятие для контрольной, позиции задач с их UUID, типами и условиями. Далее здесь хранятся состояния и зафиксированные предметные результаты. |
| Операция ответа | После установления владельца, до ожидания обработчика сохраняются UUID операции, владелец, UUID задачи, полное тело, время получения `t_in`, предел `t_in + 60 секунд` и признак незавершённости. Запись приёма ещё не даёт права принять предметный вердикт. |

### Создание сессии

Параметр `assessmentId` содержит UUID мероприятия, а `configuration` — имя шаблона. Клиент выбирает один из них при [создании сессии](DOC-08_API_сессий.md#1-создание-сессии). В запросе с `assessmentId` сервер выбирает опубликованное мероприятие подтверждённой группы студента и проверяет, что наступило открытие и ещё не наступило окончание. В запросе с `configuration` он выбирает шаблон для самостоятельной практики. Такое занятие сохраняется с `assessmentId = null`. При записи результата нельзя перенести его в контрольное мероприятие на основании совпадения состава. Для создания приложение в транзакции блокирует строку пользователя. Такая блокировка удерживает запись и заставляет одновременное создание для того же пользователя ждать. Затем приложение учитывает просрочку его прежних задач и проверяет, остался ли набор `NEW`. Если остался, возвращается `ACTIVE_SESSION_EXISTS` с UUID этого набора. Точные условия отказов приведены в [справочнике ошибок](DOC-08_API_сессий.md#4-ошибки). Если активной сессии нет, для контрольной сервер проверяет и предыдущие прохождения того же мероприятия. Завершённое прохождение при запрете повтора даёт `ASSESSMENT_RETAKE_DISABLED` с собственным UUID для чтения. При разрешённом повторе создаётся другая сессия, а прежний результат сохраняется. При допустимом старте управление сессиями получает состав для выбранного режима и обращается к модулю каждой позиции за условием. Одинаковый тип в двух позициях создаёт две задачи с отдельными UUID. Условия выдаются после фиксации полного набора. Ошибка генерации или записи отменяет создание целиком. Если два клиента одновременно начали создание для одного пользователя, второй увидит результат первого после освобождения блокировки.

### Приём и предметная проверка

Приёмный компонент отмечает `t_in`, когда получен полный запрос. Управление сессиями проверяет, входит ли задача в сессию подтверждённого пользователя. Для чужой и отсутствующей задачи ответ одинаков — `404 TASK_NOT_FOUND`. Такое обращение не создаёт операции для чужой задачи и не мешает планировщику закрыть её. Для собственной задачи приложение регистрирует получение так, чтобы планировщик успел учесть своевременный запрос до решения о просрочке. Обозначим момент прекращения приёма новых ответов через `D`. Для практики `D = t0 + 20 минут`, для мероприятия `D` равен более раннему из `t0 + 20 минут` и момента окончания работы. Сервер выдаёт его как `deadlineAt`. Если `t_in >= D`, новый ответ получает `410 SESSION_EXPIRED`, в том числе при уже закрытой собственной задаче.

До вызова предметного обработчика управление сессиями проверяет срок, состояние и соответствие тела сохранённому типу. Если одновременно поступили два допустимых ответа на одну задачу, право предметной проверки получает только один из них. Пока это право занято, другой своевременный допустимый запрос получает `409 CHECK_IN_PROGRESS`. После фиксации результата повторный своевременный запрос получает `409 TASK_FINALIZED`. Новый запрос не заменяет тело уже принятого. Для задач одного типа конкретный исход определяют UUID и условие выбранной задачи.

### Фиксация вердикта

Предметный обработчик вычисляет вердикт вне транзакции фиксации. Затем управление сессиями открывает короткую транзакцию и блокирует записи в порядке «сессия, задача, операция». Под блокировкой оно заново устанавливает, открыта ли операция и можно ли завершить фиксацию строго до `t_in + 60 секунд`. При успехе вместе записываются вердикт, состояние задачи, пересчитанное состояние сессии и завершение операции. Внешнее подтверждение отправляется после фиксации.

Блокировка сессии существенна, когда одновременно заканчиваются *разные* задачи. Если из двух открытых задач одна решена верно, а вторая неверно, после обеих записей состояние набора должно быть `FAILED`. Пока хотя бы одна задача открыта, сессия имеет состояние `NEW`, независимо от уже записанных неудач. Возможный сбой транзакции не оставляет подтверждённого результата без соответствующего состояния набора.

Если обработчик возвращает клиенту окончательный технический отказ после отката записи, до выдачи отказа должна быть зафиксирована отмена операции. Позднее вычисление не получит права завершить её вердиктом. Обрыв клиентского соединения сам по себе отмену не означает. Правила регистрации, блокировок и восстановления определены в [DOC-06.2](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#3-обработка-ответа).

## 5. Срок, чтение и восстановление

Планировщик с периодом 60 секунд ищет незавершённые задачи. По достижении `D` задача без своевременного запроса в обработке получает `FAILED` с `result = null`. Для запроса своего владельца с `t_in < D` сохраняется возможность пройти допуск и проверку формы, даже если ответ ещё ожидает вычисления. Если запрос отклонён, планировщик учитывает другие своевременные обращения по той же задаче. Предметную попытку завершает только записанный вердикт. Закрытие контрольной после получения полного своевременного запроса сохраняет исходный предел обработки. По достижении `t_in + 60 секунд` незавершённая операция закрывается с `CHECK_TIMEOUT`. До `D` пользователь может подать новый ответ, если задача открыта. После `D` задача без иной своевременной обработки закрывается по просрочке.

При чтении управление сессиями сначала устанавливает владельца. Чужая и отсутствующая сессии одинаково дают `404 SESSION_NOT_FOUND`. Состояние своей сессии приводится к тем же правилам просрочки, что и при фоновом проходе. Поэтому результат чтения после `D` не зависит от того, успел ли сработать планировщик. Открытая своевременная операция может дать `NEW` с `result = null`. Уже завершённая по сроку задача даёт `FAILED` с `null`, а неверно решённая — `FAILED` с сохранённым отрицательным вердиктом. Чтение не запускает вычисление и не расходует попытку.

При запуске приложение ищет незавершённые операции. Обработчик блокирует выбранную запись от одновременного продолжения двумя исполнителями. До исходного предела он использует сохранённое тело, время и состояние допуска, включая запросы, которые на момент остановки ждали в очереди. Истечение предела закрывает такую операцию без вердикта. Если транзакция вердикта уже завершена, операция также закрыта, и владельцу доступен записанный результат.

## 6. Сквозные сценарии

**От выбора шаблона до результата.** Студент с ролью `USER` создаёт сессию из двух задач, предусмотренных доступным шаблоном. Сервер возвращает UUID набора и разные UUID задач. Студент отправляет верный ответ на первую. Предметный обработчик получает выданное условие, а после записи вычисленного вердикта задача становится `SOLVED`. Вторая задача остаётся `NEW`, как и сессия. Если по второй задаче истёк срок без ответа, планировщик или чтение после `D` учтёт просрочку. Владелец увидит у первой задачи сохранённый положительный вердикт, у второй — `FAILED` без предметного результата, у набора — `FAILED`.

**Перезапуск до и после фиксации.** Все моменты примера указаны по одним серверным часам. Для набора самостоятельной практики, созданного в 10:00:00, полный ответ владельца пришёл в 10:19:59. Предел обработки — 10:20:59. Проверяющий закончил вычисление, но сервер остановился до транзакции записи. При запуске в 10:20:10 открытая операция позволяет продолжить обработку и успеть зафиксировать вердикт. При запуске в 10:20:59 права на запись уже нет. Операция завершается по пределу обработки, задача без иной своевременной операции закрывается по просрочке. Если же перед остановкой транзакция успела завершиться, при любом времени перезапуска владелец прочитает тот же вердикт. Эти случаи различаются по данным PostgreSQL, даже если клиент в каждом случае увидел лишь обрыв соединения.
