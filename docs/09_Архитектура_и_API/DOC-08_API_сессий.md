Сессия — личный набор задач студента с общим сроком решения. Клиентское приложение может создать набор, отправить решение одной из его задач и прочитать состояние всего набора. Сервер устанавливает студента по JWT — подписанному токену, который клиент передаёт в заголовке `Authorization: Bearer <JWT>`. Для этих трёх операций требуется роль `USER` (права студента). Владелец операции определяется токеном. Формат обмена — `application/json` (данные JSON) в кодировке UTF-8. Запись методов и путей, значение HTTP-статусов, формат UUID и обозначения JSON разобраны в [правилах чтения операций](DOC-08_Справочник_API.md#как-читать-запись-операции).

**Шаблон набора задач** задаёт типы и порядок задач для самостоятельной практики. **Контрольное мероприятие** — работа, которую составляет преподаватель. Уже у черновика есть свой идентификатор. После публикации мероприятие видно в расписании назначенной группы, а начать личную сессию можно в разрешённое время. В обоих случаях сессия и каждая из её задач получают свои идентификаторы. Какой запрос сервер допускает к проверке и когда сохраняет вердикт (результат «верно» или «неверно»), определяют [требования к приёму ответа](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md#3-обработка-ответа).

## 1. Создание сессии

`POST /api/tasks/session`

В строке запроса передают ровно один из двух параметров. Для контрольной работы требуется `assessmentId` — UUID опубликованного мероприятия из [расписания](DOC-08_Справочник_API.md#расписание-студента). Для самостоятельной практики используется `configuration` — непустое имя шаблона набора задач, включённого для группы пользователя, с учётом регистра. Передача обоих параметров, отсутствие обоих, повтор параметра или неверная запись его значения дают `400 INVALID_REQUEST`.

Для старта контрольной сервер проверяет роль студента, подтверждённую учебную группу и публикацию для этой группы. Если группа не подтверждена либо мероприятие чужое, отсутствует или скрыто в черновике, ответ одинаков — `404 ASSESSMENT_NOT_FOUND`. Затем сервер проверяет свои часы. До назначенного открытия `opensAt` запрос даёт `409 ASSESSMENT_NOT_OPEN`, в момент окончания `closesAt` и позже — `409 ASSESSMENT_CLOSED`. Старт возможен в момент открытия и строго до окончания. Расписание и правило повторного прохождения определены при [публикации работы](DOC-08_Справочник_API.md#назначение-группе-и-публикация). Имя шаблона самостоятельной практики не предоставляет доступ к контрольной.

При успехе сервер возвращает `201 Created` и объект сессии со всем набором задач. Число в ответе обозначает статус HTTP. При отказе вслед за ним в справочнике указан машинный код причины. Все пары перечислены в [таблице ошибок](#4-ошибки). Поле `assessmentId` связывает личную работу с её мероприятием. Состав и редакция вариантов взяты из публикации. При ошибке формирования любой позиции частичная сессия не выдаётся.

В ответах на создание и чтение сессии используются одинаковые поля.

| Поле сессии | Тип и значение |
|---|---|
| `id` | Строка UUID. Этот идентификатор нужен для чтения сессии |
| `assessmentId` | Строка UUID мероприятия для контрольной работы. У самостоятельной практики значение равно `null` |
| `createdAt` | Время создания по серверным часам. Строка RFC 3339 в UTC (всемирное координированное время), с миллисекундами и суффиксом `Z`, например `2026-11-20T12:00:00.000Z` |
| `deadlineAt` | Момент прекращения приёма новых ответов, в том же формате. Для практики наступает через 20 минут после `createdAt`. Для контрольной берётся более ранний из двух моментов — через 20 минут после `createdAt` или в `closesAt` мероприятия |
| `state` | Строка состояния сессии. Пока хотя бы одна задача открыта, сессия имеет состояние `NEW`. Когда все задачи закрыты, сессия получает `SOLVED` при успехе каждой задачи и `FAILED` при наличии хотя бы одной неудачи |
| `userId` | Строка UUID владельца |
| `problems` | Массив объектов задач |

| Поле задачи | Тип и значение |
|---|---|
| `id` | Строка UUID. Этот идентификатор передают в параметре `statementId` |
| `sessionId` | Строка UUID родительской сессии, совпадает с её `id` |
| `statement` | Строка, внутри которой записан JSON выданного условия |
| `type` | Строковый идентификатор подключённого типа задания. Определяет форму условия и решения |
| `state` | Строка. `NEW` — задача открыта, `SOLVED` — верное решение сохранено, `FAILED` — сохранено неверное решение или задача закрыта по сроку |
| `result` | Сохранённый [объект вердикта](#2-отправка-решения). Если вердикт отсутствует, значение поля равно `null` |

У студента может быть только одна незавершённая сессия, то есть набор хотя бы с одной открытой задачей. В открытое время мероприятия или при создании сессии практики сервер сначала проверяет, осталась ли такая сессия. Если да, возвращается `409 ACTIVE_SESSION_EXISTS`. Клиент берёт собственный UUID из `details.sessionId` и читает прежний набор. Если при создании практики ответ потерян, повторный запрос при наличии активной сессии вернёт этот конфликт.

Если соединение оборвалось при старте контрольной и UUID ещё не получен, клиент сначала читает `GET /api/users/me/schedule`. В карточке мероприятия он находит `sessionId` своей активной или последней сессии и читает её через `GET /api/tasks/session/{sessionId}`. Повторный `POST` после завершения прежней сессии при разрешённом повторе создаёт новое прохождение. Эту операцию пользователь выбирает, когда действительно хочет начать работу заново.

Если активной сессии нет, первый старт открытого мероприятия создаёт новый набор. После завершения прежнего прохождения этого же мероприятия новый набор создаётся только при `repeatAllowed = true`. У него другой UUID и отдельный результат. Предыдущая работа сохраняется. При `repeatAllowed = false` повтор получает `409 ASSESSMENT_RETAKE_DISABLED` с UUID собственной завершённой сессии в `details.sessionId`. Одновременные запросы старта проходят ту же проверку до создания набора.

## 2. Отправка решения

`PUT /api/tasks/submit`

В строке запроса передают ровно один параметр `statementId` со значением UUID выбранной задачи. Тело содержит объект решения. Допустимый размер тела до разбора JSON — не более 1 048 576 байт (1 МиБ). Сервер выбирает предметную схему по сохранённому типу задачи. Обязательные поля определены для каждого модуля его схемой `solutionSchema` из [каталога типов](DOC-08_Справочник_API.md#каталог-типов-и-банк-преподавателя). Для трёх типов ниже обязательны все перечисленные поля, и каждое должно иметь значение, отличное от `null`. Десятичная строка — строка с целым числом, записанным десятичными цифрами; точные правила записи приведены сразу под таблицей. Назначение параметров криптографических задач объяснено в [контракте ранцевого ответа](../07_Программные_требования/Контракты_сессий.md#ранцевая-задача) и [контракте ответа Эль-Гамаля](../07_Программные_требования/Контракты_сессий.md#эль-гамаль).

| Тип задачи | Поля решения | Представление в JSON |
|---|---|---|
| `BACKPACK` | `power` | Положительное целое число |
| `BACKPACK` | `type` | Строка варианта из сохранённого ранцевого условия |
| `BACKPACK` | `message`, `decodedMessage` | Массивы логических значений |
| `BACKPACK` | `lightBackpack`, `hardBackpack` | Массивы десятичных строк |
| `BACKPACK` | `omega`, `module`, `reverseOmega`, `encodedMessage` | Десятичные строки |
| `EL_GAMAL` | `y`, `k`, `c1`, `c2`, `decryptedMessage` | Десятичные строки |
| `CUSTOM_TEXT` | `answer` | Строка ответа на выбранный для этой позиции вариант |

Для каждого дополнительного подключённого типа форму решения задаёт его модуль. Для `CUSTOM_TEXT` сервер сравнивает со скрытым эталоном строки после удаления пробелов с обоих концов. Регистр и внутренние пробелы сохраняются. Публичный ответ на чтение задачи содержит выданное условие и результат проверки. Сервер хранит эталонный ответ вне студенческой выдачи.

Десятичная строка содержит `0` либо целое число без ведущих нулей. Для отрицательного числа перед цифрами ставится минус. Пробелы, плюс, дробная часть и экспоненциальная запись недопустимы. Преобразование длинной строки в число с плавающей точкой на клиенте может исказить решение.

Сервер сравнивает момент получения полного запроса с полем `deadlineAt`. В этот момент и позднее новый ответ получает `410 SESSION_EXPIRED`. Если полный ответ владельца получен раньше, на его обработку отводится 60 секунд с момента получения. Вердикт можно сохранить строго до конца этих 60 секунд, в том числе после окончания контрольной. Ни закрытие мероприятия, ни ожидание обработчика, ни перезапуск сервера не меняют исходный предел обработки.

При верном и при неверном решении сервер возвращает `200 OK` и объект вердикта. Клиент находит тот же объект в поле `result` при следующем чтении сессии.

| Поле вердикта | Тип и значение |
|---|---|
| `problemId` | Строка UUID проверенной задачи, равна переданному `statementId` |
| `problemType` | Строка сохранённого типа задачи |
| `isOk` | Логическое значение. При `true` задача решена и получает `SOLVED`. При `false` попытка также завершается, задача получает `FAILED` |
| `errorMessage` | При `true` равно `null`. При `false` содержит непустое пояснение, по умолчанию «Решение неверно» |

### Как передаётся текстовый вариант

При подготовке упражнения преподаватель записывает фразу в поле `statement` выбранного варианта, например «Сколько бит в байте?». При выдаче задачи одноимённое поле имеет общую для предметных модулей форму — строку с сериализованным JSON. Для `CUSTOM_TEXT` само условие внутри этой строки является JSON-строкой. Ниже приведён один элемент массива `problems` в полученном студентом JSON.

```json
{
  "id": "b72e684c-4beb-4e15-b94b-11f3d52bc50b",
  "sessionId": "c8959f02-0477-435f-8d8f-b94bb1f94db8",
  "type": "CUSTOM_TEXT",
  "statement": "\"Сколько бит в байте?\"",
  "state": "NEW",
  "result": null
}
```

Клиент сначала разбирает JSON сессии. Тогда значение `statement` ещё содержит пару кавычек вокруг вопроса. Он разбирает это значение как JSON и получает текст для экрана «Сколько бит в байте?». В параметре `statementId` строки запроса клиент передаёт UUID задачи `b72e684c-4beb-4e15-b94b-11f3d52bc50b`. Тело решения передаётся отдельным JSON-объектом.

```json
{"answer":"8"}
```

## 3. Чтение состояния и восстановление после обрыва связи

`GET /api/tasks/session/{sessionId}`

В путь подставляют UUID собственной сессии. Ответ `200 OK` содержит объект сессии из раздела 1. Операция доступна и после общего срока. Планировщик — фоновая часть сервера, которая периодически закрывает задачи с истёкшим сроком. Даже до его очередного запуска сервер при чтении учтёт просрочку задач без своевременного ответа. Если принятый до срока ответ ещё обрабатывается в пределах отведённых 60 секунд, задача остаётся открытой. При повторном чтении сервер возвращает актуальное состояние, сохраняя зафиксированный вердикт. Чтение не расходует попытку и не запускает повторную проверку.

Если после отправки решения клиент потерял соединение, сначала надо прочитать сессию и найти задачу по её `id`.

| Что вернулось при чтении | Что видит пользователь |
|---|---|
| `SOLVED`, результат с `isOk = true` | Сохранён верный ответ |
| `FAILED`, результат с `isOk = false` | Сохранён неверный ответ. Причина содержится в `errorMessage` |
| `FAILED`, `result = null` | Задача закрыта по истечении срока без предметного вердикта |
| `NEW`, `result = null` | Итог ещё не определён. Ранее принятый ответ может оставаться в обработке, в том числе после общего срока. Клиент может прочитать состояние повторно |

Предметная попытка завершается при сохранении вердикта. После ошибки формата или технического отказа без вердикта исправленный ответ можно подать, пока задача открыта и общий срок допускает новый запрос.

## 4. Ошибки

При отказе ответ содержит объект со строками `code`, `message`, `timestamp` и `requestId`. Клиент выбирает действие по `code`, а `message` показывает пользователю. Поле `timestamp` имеет тот же формат, что `createdAt`. Поле `requestId` содержит UUID серверной операции. При `ACTIVE_SESSION_EXISTS` и `ASSESSMENT_RETAKE_DISABLED` ответ дополнительно содержит объект `details` с UUID собственной сессии в строковом поле `sessionId`. Сервер не включает в сообщение стек вызовов и внутренние данные хранилища.

| HTTP | `code` | Когда возвращается |
|---|---|---|
| 400 | `INVALID_REQUEST` | Некорректный или повторённый параметр, отсутствующее тело решения, неверный JSON, пропущенное обязательное поле или ошибка его типа |
| 401 | `UNAUTHENTICATED` | Отсутствуют действительные данные аутентификации |
| 403 | `ACCESS_DENIED` | У пользователя нет роли `USER` |
| 404 | `CONFIGURATION_NOT_FOUND` | Нет группы или для неё нет включённого шаблона с указанным именем |
| 404 | `ASSESSMENT_NOT_FOUND` | Студент не может увидеть мероприятие по указанному UUID |
| 404 | `TASK_NOT_FOUND` | Задача с таким ID отсутствует у текущего пользователя |
| 404 | `SESSION_NOT_FOUND` | Сессия с таким ID отсутствует у текущего пользователя |
| 409 | `ACTIVE_SESSION_EXISTS` | При создании обнаружилась собственная незавершённая сессия |
| 409 | `ASSESSMENT_NOT_OPEN` | Мероприятие своей группы опубликовано, но момент открытия ещё не наступил |
| 409 | `ASSESSMENT_CLOSED` | Старт видимого мероприятия запрошен в момент его окончания или позднее |
| 409 | `ASSESSMENT_RETAKE_DISABLED` | В открытое время студент с завершённым прохождением этой работы запросил новое, а преподаватель запретил повтор |
| 409 | `TASK_FINALIZED` | До общего срока пришёл ответ на уже закрытую задачу или сессию |
| 409 | `CHECK_IN_PROGRESS` | До общего срока поступил ещё один ответ на задачу, по которой идёт проверка |
| 410 | `SESSION_EXPIRED` | Полный запрос с новым решением получен в момент общего срока сессии или позднее |
| 413 | `PAYLOAD_TOO_LARGE` | Тело решения превышает 1 МиБ |
| 500 | `INTERNAL_ERROR` | Ошибка настройки или сохранения данных, в том числе неподдерживаемый тип задачи в шаблоне |
| 503 | `CHECK_UNAVAILABLE` | Предметный обработчик недоступен или его работа завершилась техническим сбоем |
| 503 | `CHECK_TIMEOUT` | К границе 60 секунд от получения полного запроса вердикт не зафиксирован |

Сервер сначала устанавливает доступ к запрошенному объекту. Для чужого и отсутствующего объекта ответ одинаков. У собственной задачи момент поступления проверяется до проверки итогового состояния. Поэтому отправка решения после общего срока даёт `410` даже для уже закрытой задачи. Прочитать её сохранённый результат можно по-прежнему. После закрытия видимого мероприятия запрос нового старта возвращает `409 ASSESSMENT_CLOSED`, даже если повтор был запрещён или у студента сохранилась начатая работа. Её состояние по-прежнему можно прочитать.

## 5. Пример от создания до чтения результата

В этом примере `Sem4` — имя шаблона самостоятельной практики, включённого для группы студента. В 12:00 UTC студент с ролью `USER` отправляет `POST /api/tasks/session?configuration=Sem4`. Сервер возвращает `201 Created`. В объекте сессии `id` равен `312c6ab8-5c12-46ae-a8bf-942d3c45c125`, `createdAt` равен `2026-11-20T12:00:00.000Z`, `deadlineAt` — `2026-11-20T12:20:00.000Z`, а `assessmentId` равен `null`. В массиве `problems` одна задача типа `EL_GAMAL` с идентификатором `a626ae49-2020-4ca2-94ed-d5aef1193ee3`. В условии `p = 23` — простой модуль, `g = 5` — основание, `x = 6` — учебный показатель, `m = 13` — исходное сообщение. Назначение пяти полей решения и расчёт этих значений показаны в [примере из контракта Эль-Гамаля](../07_Программные_требования/Контракты_сессий.md#учебный-пример-решения-эль-гамаля).

Клиент подставляет идентификатор **задачи** в `statementId` операции `PUT /api/tasks/submit` и передаёт решение в теле запроса.

```json
{
  "y": "8",
  "k": "3",
  "c1": "10",
  "c2": "9",
  "decryptedMessage": "13"
}
```

Полный запрос поступает в 12:19:59.500. Сервер сохраняет вердикт в 12:20:02.000, когда общий срок уже истёк, а срок обработки ещё идёт. Соединение разрывается до доставки ответа. Клиент выполняет `GET /api/tasks/session/{sessionId}`, подставив идентификатор **сессии** из ответа на создание. В полученном объекте сессия и её единственная задача имеют состояние `SOLVED`. Клиент берёт сохранённый вердикт из поля `result` этой задачи.
