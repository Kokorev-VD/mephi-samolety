## Как обращаться к платформе

**API** — программный интерфейс, через который приложение пользователя (клиент) обращается к серверу платформы. Преподаватель составляет **контрольное мероприятие** — работу с упорядоченным перечнем заданий, — назначает его учебной группе и указывает время открытия и окончания. Публикация делает карточку работы видимой в расписании. В разрешённое время студент начинает **сессию** — получает личный набор задач, в котором каждая задача имеет свой идентификатор. Сессия связывает выданные условия и полученные результаты с одним студентом. Одинаковая позиция в составе работы у двух студентов даёт две отдельные задачи.

### Как читать запись операции

Интерфейс использует REST. Каждая операция обращается по сетевому протоколу HTTP к определённому ресурсу — например, расписанию или сессии. Полная запись состоит из метода и пути. `GET` запрашивает данные, `POST` передаёт данные для создания объекта или выполнения действия, `PUT` передаёт данные для изменения или обработки. В записи `GET /api/tasks/session/{sessionId}` вместо `{sessionId}` клиент подставляет идентификатор нужной сессии. В записи `?configuration=Sem4` после знака вопроса указаны имя параметра и его значение. Порт 8083 — сетевая точка подключения к серверу, `/api` — общая начальная часть пути.

**Тело** — передаваемые данные запроса или ответа. Платформа использует формат JSON. Объект в фигурных скобках содержит пары «имя поля — значение», массив в квадратных скобках содержит упорядоченные элементы. Тип поля задаёт форму записи. В поле числового типа значение записывается без кавычек (например, `"power": 3`). В поле для десятичной строки цифры заключаются в кавычки (например, `"y": "8"`). Так передаются учебные целые числа произвольной длины. `true` и `false` — логические значения «да» и «нет», `null` обозначает отсутствие значения. Идентификаторы (ID) ресурсов имеют вид UUID — уникальных строк, например `312c6ab8-5c12-46ae-a8bf-942d3c45c125`. Даты и время обмена передаются в UTC (всемирное координированное время), а суффикс `Z` в записи времени означает нулевое смещение от UTC.

После успешного входа клиент получает `accessJwt` — строку с подписанным сервером токеном JWT (JSON Web Token). Токен удостоверяет личность пользователя. Для защищённого запроса клиент передаёт его в заголовке HTTP `Authorization: Bearer <JWT>`. Роль `USER` позволяет выполнять действия студента. Роль `TEACHER` позволяет вести свой банк упражнений и составлять контрольные. Назначать работу группе и читать её результаты преподаватель может при действующем закреплении этой группы. Роль `ADMIN` позволяет назначать группы преподавателям и просматривать сессии всех пользователей. Сервер проверяет права на группу при обращении. [Правила доступа и прохождения мероприятия](../02_Техническое_задание/DOC-02_Техническое_задание.md#правила-доступа-и-прохождения-контрольного-мероприятия).

В ответ на запрос сервер возвращает трёхзначный код состояния HTTP. `200 OK` означает успешное выполнение операции, `201 Created` — создание нового объекта. Неверное тело или некорректный параметр запроса дают 400. Код 409 указывает, что операция вступила в конфликт с текущим состоянием данных. Отсутствующие, истёкшие или недействительные учётные данные дают 401, недостаточные полномочия — 403, отсутствующий ресурс — 404. Объект ошибки содержит `code` (строковый машинный код), `message` (пояснение для пользователя) и `timestamp` (строку серверного времени UTC). Проверка полномочий предшествует выдаче данных объекта. По состоянию собственной сессии и при отправке решения применяются дополнительные коды и правила из [каталога ошибок сессий](DOC-08_API_сессий.md#4-ошибки). В других разделах справочника отказ описан для той операции, в которой он возникает.

95-й процентиль времени ответа — граница, в которую укладываются не менее 95 % запросов данной категории. При 30 одновременно работающих пользователях эта граница для обычных операций не должна превышать 2 секунд, для операций генерации — 5 секунд. При формировании условий по запросу создания сессии применяется граница для генерации. Чтение сохранённой сессии относится к обычным операциям.

## От авторского вопроса до личной сессии

### Каталог типов и банк преподавателя

Преподаватель (`TEACHER`) и студент (`USER`) могут получить публичные описания подключённых типов через `GET /api/task-types`. Ответ 200 содержит массив объектов. В каждом `type` — устойчивый строковый код типа, `title` — его отображаемое название, `solutionSchema` — публичная схема тела решения. Преподаватель использует код при составлении контрольной. Клиент студента находит по тому же коду схему полей ответа. Например, `CUSTOM_TEXT` означает текстовое упражнение с вариантами, `BACKPACK` и `EL_GAMAL` обозначают другие учебные модули.

Схема `solutionSchema` описывает тело ответа **студента**. Правила подготовки задания **преподавателем** относятся к самому модулю. Например, для текстового задания автор вводит варианты по описанию ниже, а студент передаёт одно поле `answer`. В `solutionSchema` тип верхнего значения — `object` (объект с именованными полями). По именам в `properties` клиент строит поля формы, по списку `required` отмечает обязательные. Описание поля задаёт название `title` и тип `type`, например `string` (строка), `integer` (целое), `boolean` (логическое значение) или `array` (массив). У массива `items` описывает тип одного элемента. Для составного объекта действуют те же правила `properties` и `required`. Если модуль ограничивает набор допустимых значений, их передают в `enum`. Этот перечень описывает форму ответа для всех студентов и не подсказывает верное значение конкретного варианта. Таким образом клиент может сформировать ответ на задачу подключённого типа, которого ещё не было при разработке его форм. Проверка на сервере остаётся обязательной.

Например, в каталоге текстового задания студент увидит следующее описание формы. Оно одинаково для всех вариантов и не содержит эталонов, приватного контекста или сведений о том, какие варианты задал преподаватель.

```json
{
  "type": "CUSTOM_TEXT",
  "title": "Текстовый ответ",
  "solutionSchema": {
    "type": "object",
    "properties": {
      "answer": {"title": "Ваш ответ", "type": "string"}
    },
    "required": ["answer"]
  }
}
```

В `POST /api/custom-tasks` преподаватель передаёт строку `title` и массив `variants` с одним или несколькими вариантами. Для каждого нужны две заполненные строки — `statement` с условием и `expectedAnswer` с эталонным ответом. Например, для одного упражнения преподаватель передаёт следующие данные.

```json
{
  "title": "Единицы информации",
  "variants": [
    {
      "statement": "Сколько бит в одном байте?",
      "expectedAnswer": "8"
    },
    {
      "statement": "Сколько байтов в двух кибибайтах?",
      "expectedAnswer": "2048"
    }
  ]
}
```

При успехе сервер отвечает 201 и выдаёт UUID созданного упражнения в поле `customTaskId`. Отсутствующее условие, эталон неверного типа или пустой список вариантов дают 400. Доступ к своему банку требует `TEACHER`. Допускается задание с одним заполненным вариантом. Через `GET /api/custom-tasks` преподаватель получает 200 и массив своих упражнений для составления контрольной. У каждого элемента есть UUID `customTaskId`, название `title` и список `variants` в той же форме, в какой его вводил автор. При пустом банке возвращается `[]`. Студенческие операции не открывают доступ к авторскому банку или эталонам.

Для изменения собственного упражнения преподаватель передаёт `PUT /api/custom-tasks/{customTaskId}`. Тело имеет ту же схему, что при создании, и заменяет название и весь список вариантов. Успешный ответ 200 содержит исправленное упражнение с полями `customTaskId`, `title` и `variants`. До публикации преподаватель может исправить условие или эталон. Если упражнение уже вошло в опубликованную работу, изменение банка действует только для будущих публикаций. Повторное чтение студентом уже выданной задачи возвращает прежнее условие, а проверка использует прежний эталон. Неизвестное или чужое упражнение даёт 404, отсутствие роли преподавателя — 403.

### Черновик контрольного мероприятия

`POST /api/assessments` требует роль `TEACHER`. В теле обязательны строковое название `title` и упорядоченный массив позиций `items`. Поле `repeatAllowed` задаёт правило повтора. Значение `true` разрешает повторное прохождение после завершения предыдущего, `false` запрещает. В черновике поле можно опустить или передать `null`, если преподаватель ещё не сделал выбор. Любое иное значение даёт 400. Для сохранения черновика без заданий клиент передаёт `"items": []`. Если поле `items` пропущено или содержит значение другого типа, сервер отвечает 400. В каждой позиции требуется строковый идентификатор зарегистрированного типа `type`. Для `CUSTOM_TEXT` преподаватель указывает UUID своего упражнения в `customTaskId`. Для математической позиции в приведённом ниже запросе достаточно кода типа. Модуль использует обычные правила генерации. Дополнительные настройки позиции зависят от описания конкретного модуля. Поле `solutionSchema` описывает только ответ студента. Параметр `bitLength` в операции самостоятельной генерации Эль-Гамаля относится к той операции. Одинаковый тип допускается на разных позициях. Клиент их не объединяет.

В примере создано упражнение с UUID `7d3c4781-6c9c-493d-9162-044fb753ca60`. Преподаватель включает этот вопрос в первую позицию, а задание Эль-Гамаля — во вторую.

```json
{
  "title": "Контрольная работа по цифровым представлениям",
  "repeatAllowed": false,
  "items": [
    {
      "type":"CUSTOM_TEXT",
      "customTaskId":"7d3c4781-6c9c-493d-9162-044fb753ca60"
    },
    {"type":"EL_GAMAL"}
  ]
}
```

В ответе 201 поле `assessmentId` содержит UUID созданного мероприятия, а состояние `DRAFT` означает, что перед нами черновик, скрытый от студентов. Неизвестный тип или параметры, не соответствующие типу позиции, дают 400. Метод `GET /api/assessments` возвращает 200 и перечень собственных мероприятий с полями `assessmentId`, `title`, `state`, `repeatAllowed`, `items`. Для опубликованной работы также указываются `groupId`, `opensAt`, `closesAt`. В состоянии `DRAFT` преподаватель может заменить состав через `PUT /api/assessments/{assessmentId}`, передав название, полный массив позиций и, если выбор сделан, логическое значение `repeatAllowed`. Как и при создании, пропуск поля или `null` означает, что у сохранённой редакции черновика правило повтора ещё не выбрано. Чтобы удалить последнее задание, клиент передаёт пустой массив `items`. Ответ 200 отражает сохранённый состав того же черновика. Если преподаватель отправляет правку своей работы после её публикации, сервер отвечает 409 с кодом `ASSESSMENT_ALREADY_PUBLISHED` и сообщает, что работу уже опубликовали. Это правило действует и при одновременной правке и публикации, если первой была сохранена публикация. Состав опубликованной работы сохраняется. Неизвестный или чужой черновик даёт 404.

### Назначение группе и публикация

`POST /api/assessments/{assessmentId}/publish` назначает свою работу одной группе. UUID черновика берётся из ответа на создание. Для контрольной из примера это `320b6de1-755f-4f05-8081-e677fb868d33`. Сервер проверяет роль `TEACHER`, авторство работы и действующее назначение учебной группы. Отсутствие роли даёт 403, чужая или неизвестная работа либо недоступная группа — 404. Тело содержит обязательные `groupId` (UUID группы), `opensAt` и `closesAt` (моменты открытия и окончания, выбранные преподавателем). Клиент переводит обе даты в UTC и передаёт строки RFC 3339 с миллисекундами и суффиксом `Z`. Пропуск поля, неверная дата или `closesAt` не позже `opensAt` дают 400, расписание не меняется.

Сервер проверяет список позиций, сохранённый под этим `assessmentId`. Если в нём нет заданий, корректный запрос публикации получает HTTP 409 с кодом `ASSESSMENT_EMPTY`. В поле `message` сервер предлагает добавить хотя бы одно задание. При корректной группе и времени пустой состав проверяется первым, даже если правило повтора ещё не выбрано. Для непустой работы с незаполненным `repeatAllowed` сервер возвращает `409 ASSESSMENT_RETAKE_POLICY_REQUIRED` и предлагает разрешить или запретить повтор. Явное `false` удовлетворяет этому условию. При любом из этих отказов работа сохраняет состояние `DRAFT` и отсутствует в расписании. Преподаватель дополняет черновик через `PUT /api/assessments/{assessmentId}` и снова вызывает `POST /api/assessments/{assessmentId}/publish` с прежним идентификатором.

Для контрольной из примера преподаватель выбирает 25 ноября 2026 года, с 10:00 до 10:30 по Москве (UTC+03:00). Запрос публикации содержит следующий объект.

```json
{
  "groupId": "aab71c03-036d-44bf-9055-20ba3312077a",
  "opensAt": "2026-11-25T07:00:00.000Z",
  "closesAt": "2026-11-25T07:30:00.000Z"
}
```

Успешная публикация возвращает 200. Объект мероприятия содержит `assessmentId`, состояние `state = PUBLISHED`, название `title`, состав `items`, назначенную группу `groupId`, обе границы времени и сохранённое `repeatAllowed`. Публикация закрепляет порядок позиций, редакции вариантов с эталонами и правило повтора. При отказе сохраняется прежнее состояние. Повтор публикации уже опубликованной работы даёт `409 ASSESSMENT_ALREADY_PUBLISHED`.

#### Пример последовательности отказов и публикации

Во всех запросах публикации следующего примера преподаватель имеет доступ к группе и передаёт все три поля из объекта выше: `groupId`, `opensAt`, `closesAt`. Между запросами он изменяет тот же собственный черновик. Отказы не меняют его `assessmentId` и не создают запись расписания.

| Сохранённый черновик перед запросом публикации | Ожидаемый ответ и состояние |
|---|---|
| `items = []`, выбор `repeatAllowed` отложен | `409 ASSESSMENT_EMPTY`; остаётся `DRAFT` |
| Через `PUT /api/assessments/{assessmentId}` сохранена одна допустимая позиция; `repeatAllowed` пропущен или равен `null` | `409 ASSESSMENT_RETAKE_POLICY_REQUIRED`; остаётся `DRAFT` |
| Тем же `PUT` сохранены название, одна позиция и явное `repeatAllowed = false` | `200`; становится `PUBLISHED`, карточка видна назначенной группе |

Пропуск `closesAt` не проверяет пустой состав: такой запрос получает 400 из-за отсутствующего обязательного поля. Для рассмотрения параллельной правки и публикации также заранее задаются допустимое назначение, непустой состав и явный режим повторов. Это пример контракта API, а не отчёт об исполнении [TC-CFG-008](../10_Верификация_и_тестирование/DOC-10_План_верификации.md#tc-cfg-008).

### Расписание студента

`GET /api/users/me/schedule` с ролью `USER` не принимает параметров или тела. Ответ 200 — массив опубликованных работ подтверждённой группы студента. Если группа не подтверждена или подходящих работ нет, возвращается `[]`. Карточка содержит UUID работы `assessmentId`, название `title`, UUID группы `groupId`, моменты `opensAt` и `closesAt`, логические значения `repeatAllowed` и `canStart`. Первое показывает, разрешил ли преподаватель повтор. Второе показывает, может ли именно этот студент начать новую сессию сейчас. Сервер проверяет назначение, свои часы, наличие незавершённой сессии и предыдущих прохождений. При запросе старта проверка выполняется снова. Если у студента уже была сессия этой работы, `sessionId` содержит UUID его активной сессии этого мероприятия, иначе последней завершённой. Если прохождений ещё нет, поле можно опустить. Карточка не содержит условий задач или эталонов.

Публикация сразу показывает карточку группе. Клиент переводит обе даты в местное время и показывает часовой пояс. В примере студент видит «25 ноября 2026 года, 10:00–10:30 по Москве». В 09:59 карточка видна с `canStart = false`. В 10:00 студент без прежнего прохождения и без активной сессии может послать `POST /api/tasks/session?assessmentId=320b6de1-755f-4f05-8081-e677fb868d33`. При старте в 10:25 он получает собственный UUID, две задачи и срок приёма новых ответов `deadlineAt = 2026-11-25T07:30:00.000Z`. Для первой позиции сервер случайно выбирает один из двух текстовых вариантов. При дальнейшем чтении студент видит тот же вопрос. С 10:30 карточка показывает `canStart = false`, а по собственному `sessionId` студент по-прежнему может прочитать результат. [Создание и сроки сессии](DOC-08_API_сессий.md#1-создание-сессии), [пример выдачи текстового вопроса и ответа](DOC-08_API_сессий.md#как-передаётся-текстовый-вариант).

### Результаты контрольного мероприятия

`GET /api/assessments/{assessmentId}/results` без тела или параметров возвращает результаты опубликованной работы. Для чтения требуются роль `TEACHER`, авторство работы и действующее назначение её группы. При отсутствии роли ответ 403. Если преподаватель указал неизвестную или чужую работу, черновик либо работу группы, которой он уже не управляет, ответ 404 во всех случаях. Запрос не изменяет результатов.

Ответ 200 содержит `assessmentId` (UUID работы), `groupId` (UUID группы) и массив `sessions`. Каждый элемент — отдельное прохождение в [публичном формате сессии](DOC-08_API_сессий.md#1-создание-сессии), включая собственный UUID прохождения `id`, UUID студента `userId`, время создания `createdAt`, срок `deadlineAt`, состояние `state` и задачи `problems` с сохранёнными вердиктами. Пока никто не начал работу, `sessions` равен `[]`. При разрешённых повторах преподаватель различает прохождения одного студента по `id`. Эталоны, закрытые данные проверки и привязки к кабинету МИФИ в ответ не входят.

Состояния задач и итог сессии определяются на момент чтения по тому же [контракту просрочки](DOC-08_API_сессий.md#3-чтение-состояния-и-восстановление-после-обрыва-связи), что и при чтении студентом. Ведомость не выдаёт устаревшее `NEW` только потому, что планировщик ещё не выполнил очередной проход. Обозначим срок подачи `deadlineAt` через `D`, время получения полного своевременного ответа — `t_in`, его исходный предел обработки — `L = t_in + 60 секунд`. Сохранённый вердикт имеет приоритет: он остаётся в `result` вместе с соответствующим состоянием задачи. Для задачи без вердикта действуют следующие случаи.

| Момент чтения и принятые ответы | Представление задачи в ведомости |
|---|---|
| До `D` | `NEW`, `result = null`; в том числе если обработка прежнего ответа закончилась техническим таймаутом без вердикта |
| В `D` или позднее, без своевременного ответа в допустимой обработке | `FAILED`, `result = null` |
| В `D` или позднее, ответ получен при `t_in < D`, остаётся в обработке и исходный `L` ещё не достигнут | `NEW`, `result = null` |
| В `D` или позднее, наступил `L`, вердикта и другого своевременного ответа в допустимой обработке нет | `FAILED`, `result = null` |

Состояние набора вычисляется по этим же представлениям задач: пока есть открытая задача, набор имеет `NEW`; когда все закрыты, `SOLVED` требует успеха каждой, иначе набор имеет `FAILED`. Ведомость не запускает предметную проверку, не назначает новый срок и не предоставляет преподавателю право отправить ответ за студента.

Например, `D` наступает в 10:30:00, а ближайший фоновый проход ожидается в 10:30:30. При чтении в 10:30:01 задача без ответа уже имеет `FAILED` и `result = null`. Если допустимый полный ответ получен в 10:29:59.900 и ещё обрабатывается, в 10:30:01 задача имеет `NEW`. При отсутствии сохранённого вердикта и другой своевременной обработки ровно в 10:30:59.900 она имеет `FAILED` и `result = null`. Вердикт, сохранённый до этой границы, остаётся доступен при любом последующем чтении. Примеры задают ожидаемое поведение, а не результат испытаний.

## Учётная запись и вход

**Регистрация.** Клиент передаёт `POST /api/auth/registration` с JSON-объектом. Поле `email` содержит адрес электронной почты длиной от 4 до 120 символов, `password` — пароль длиной от 8 до 255 символов. Поле `name` с именем пользователя обязательно. В необязательном поле `surname` можно передать фамилию. Оба поля строковые. Регистрация и вход выполняются по защищённому соединению. Валидность адреса и длина строк проверяются на сервере. Некорректные поля дают 400. Повторная регистрация по занятому адресу даёт 409, существующая учётная запись сохраняется. Успех обозначается HTTP 200. Клиент сразу получает объект с полем `accessJwt` строкового типа.

**Локальный вход.** Для `POST /api/auth/login` передают строки `email` и `password`. При успехе возвращается HTTP 200 и объект с полем `accessJwt`. Неверные учётные данные дают 401. Пароль и его хеш в ответы не входят.

Например, при входе студент передаёт тело запроса в следующем виде.

```json
{"email":"student@example.org","password":"study-example-2026"}
```

**Регистрация и вход через личный кабинет МИФИ.** Для этого варианта клиент передаёт только `{"provider":"MEPHI"}` на `POST /api/auth/registration` или `POST /api/auth/login`. Регистрация создаёт локальный профиль после подтверждения, а вход открывает ранее связанный профиль. Вариант с `provider` нельзя смешивать с полями пароля или локальной регистрации. Некорректное тело даёт 400. Для привязки кабинета к уже существующему профилю вошедший пользователь отправляет `POST /api/users/me/mephi-link` с действительным JWT и без тела. При отсутствии действительного токена ответ 401. Все три начала возвращают 200 и объект с двумя строками — `authRequestId` (UUID обращения) и `continueUrl` (адрес для продолжения подтверждения в браузере). Эти операции ещё не меняют профиль.

**Завершение.** После прохождения подтверждения клиент отправляет на `POST /api/auth/complete` только объект с UUID `authRequestId`. При привязке он также предъявляет JWT того же пользователя. Сервер проверяет достоверное подтверждение личности от `home.mephi.ru`, его связь с исходным обращением, режимом и начавшим его клиентом. Для привязки проверяется также совпадение локального владельца. Один UUID обращения, введённый номер группы или совпавший адрес почты личность не подтверждают. Сервер использует подтверждение однократно. Неверная форма запроса даёт 400. Отсутствующее или недействительное подтверждение, несовпадение клиента или режима, попытка внешнего входа без существующей связи дают 401. Если источник временно недоступен и подтвердить личность нельзя, ответ 503. При отказе нет новой связи или смены владельца.

Во всех трёх режимах успешный ответ на завершение — 200, объект `accessJwt` (строка локального токена), `userId` (UUID локального профиля), `groupId` (UUID учебной группы) и `groupNumber` (строка её подтверждённого номера). При внешней регистрации это новый профиль, при входе — ранее связанный, при привязке — прежний профиль вошедшего пользователя с его историей и правами. Если достоверная внешняя личность установлена, а группу подтвердить не удалось, `groupId` и `groupNumber` равны `null`. Действия вне группы, например личная история и самостоятельные учебные примеры, доступны. Расписание и групповые задания требуют подтверждённой группы. Уже связанная с другим профилем внешняя личность либо повторная внешняя регистрация той же личности даёт 409. В том числе при одновременных запросах у одной внешней личности остаётся только один владелец. Имя, номер группы или роль, указанные пользователем, не дают групповых или преподавательских прав.

## Группы и личная история

**Доступные группы.** `GET /api/users/groups` без параметров и тела возвращает 200 и массив доступных групп. При роли `USER` доступна только собственная подтверждённая группа, при `TEACHER` — закреплённые за преподавателем, при `ADMIN` — все группы. Без доступных групп возвращается `[]`. Поля карточки — `id` (UUID группы), `name` (название) и `users` (массив UUID её участников). Принадлежность студента определяется по подтверждённому номеру группы из личного кабинета МИФИ. Указание группового UUID, номера или имени в запросе клиента не устанавливает членство.

**Закрепление групп за преподавателем.** `GET /api/admin/teachers` без параметров и тела возвращает 200 и массив записей с `teacherId` (UUID профиля с ролью `TEACHER`) и `groupIds` (массив UUID назначенных групп). `PUT /api/admin/teachers/{teacherId}/groups` принимает объект `{"groupIds":[...]}` с полным новым списком UUID. Пустой массив снимает все назначения. При успехе ответ 200 содержит поля `teacherId` и `groupIds` с сохранёнными значениями. Обе операции требуют роль `ADMIN`, для другой роли ответ 403. Неверная форма даёт 400, неизвестный преподаватель или любой неизвестный UUID группы — 404. Назначения изменяются целиком либо сохраняются прежними. Назначение группы не меняет роль пользователя или учебную группу студента. После отзыва прежний преподаватель больше не может публиковать для этой группы или получать результаты её работ.

**История.** `GET /api/users/me/tasks` с ролью `USER` возвращает массив записей решённых задач владельца JWT. Для задачи предметный результат (вердикт) показывает, верен ли её ответ. Параметров запроса нет. Запись содержит UUID задачи `id`, UUID её сессии `sessionId`, строку типа `type`, выданное условие `statement`, состояние `state` и сохранённый предметный результат `result`. Формы этих полей совпадают с представлением задачи в [описании сессии](DOC-08_API_сессий.md#1-создание-сессии). Если у студента ещё нет таких записей, возвращается пустой массив `[]`. Задачи другого студента в ответ не входят, в том числе при совпадающей группе. Для полного состава конкретного набора и чтения сохранённого вердикта предусмотрен [запрос своей сессии](DOC-08_API_сессий.md#3-чтение-состояния-и-восстановление-после-обрыва-связи).

## Шаблоны набора задач для группы

`GET /api/tasks/groups/configurations` принимает обязательный параметр строки запроса `groupId` с UUID группы. Студент с ролью `USER` может читать шаблоны набора задач только своей группы. При отсутствии группы у студента либо при указании чужого UUID шаблоны не выдаются. Некорректная запись UUID даёт 400. Недостаточные права дают 403 без сведений о запрошенной группе.

Ответ 200 содержит массив шаблонов, включая выключенные. Поле `id` — UUID шаблона, `name` — строка его имени, `tasks` — упорядоченный массив устойчивых строковых кодов `type` из каталога, `enabled` — логический признак включения для этой группы. Один тип может встречаться в списке несколько раз. При отсутствии шаблонов возвращается пустой массив. Ниже приведён ответ для группы с одним включённым шаблоном.

```json
[
  {
    "id": "8e30de74-c161-49dd-a4dc-67f91ce6ae20",
    "name": "Sem4",
    "tasks": ["BACKPACK", "EL_GAMAL"],
    "enabled": true
  }
]
```

## Обзор сессий при модерации

`GET /api/moderator/tasks/session` доступен пользователю с ролью `ADMIN`. Параметры и тело запроса отсутствуют. До получения данных сервер проверяет JWT и право административного просмотра. При отсутствии действительного токена возвращается 401, без роли `ADMIN` — 403. Студент видит свой набор через запрос чтения собственной сессии.

При успехе ответ 200 содержит массив сессий всех пользователей. Элемент имеет поля `id`, `assessmentId`, `userId`, `createdAt`, `deadlineAt`, `state` и `problems` в [формате сессии](DOC-08_API_сессий.md#1-создание-сессии). По `userId` администратор различает владельцев, а по `state` сессии и состояниям её задач — незавершённые и законченные наборы. Если сессий нет, возвращается `[]`. Чтение не изменяет состояния.

Для состояний в ответе применяется тот же момент чтения и учёт своевременных ответов, что в [ведомости преподавателя](#результаты-контрольного-мероприятия) и собственной сессии. Фраза «чтение не изменяет состояния» означает отсутствие предметной попытки и нового вердикта; она не разрешает возвращать прежнее `NEW` после срока без действующей своевременной обработки. Закрытые эталоны и приватный контекст проверки в административное представление не входят.

## Типы заданий и авторские упражнения

Тип задания определяет два связанных представления — условие, которое видит студент, и форму решения, которую принимает проверяющий модуль. Состав поддерживаемых типов расширяется при подключении модулей. Известные клиенту примеры — ранцевое задание `BACKPACK`, задача Эль-Гамаля `EL_GAMAL` и текстовое упражнение `CUSTOM_TEXT`. Поля ответа одной формы нельзя переносить на задачу другого типа. Для любого типа попытка завершается, когда сервер сохраняет предметный вердикт. При верном решении результат положительный, при неверном — отрицательный.

При старте сессии для каждой позиции авторского задания сервер случайно выбирает один вариант. Он закрепляется за задачей один раз. Двум студентам может достаться один вариант, но у каждого будет свой UUID задачи и свой результат. Для задания из [примера контрольной](#каталог-типов-и-банк-преподавателя) клиент передаёт объект `{"answer":"8"}`. Сервер отбрасывает пробелы в начале и в конце обеих строк и сравнивает их с учётом регистра и внутренних пробелов. Для вопроса о количестве бит в байте `{"answer":" 8 "}` даёт верный ответ, а `{"answer":"восемь"}` — неверный. Проверяющий использует эталон, закреплённый за предъявленной позицией.

## Ранцевые примеры

В ранцевой задаче заданы последовательности чисел, называемые лёгким и тяжёлым ранцами. Сообщение указывает, какие элементы участвуют в учебном шифровании. Эталон — подготовленный полный пример с правильными параметрами, шифртекстом и расшифрованным сообщением. Обе операции доступны студенту (`USER`) и преподавателю (`TEACHER`) независимо от наличия активной сессии. Редакционная выдача содержит полное решение и не записывается в историю сессий. Правила генерации и проверки параметров приведены в [DOC-06.3](../07_Программные_требования/DOC-06.3_Ранцевые_криптосистемы.md).

**Эталон по варианту.** Для `GET /api/tasks/backpack/editorial` передаётся строковый параметр `type`. Значение `BACKPACK_CODE_SUPER_INCREASING` выбирает супервозрастающую последовательность, в которой каждый элемент больше суммы предшествующих. `BACKPACK_CODE_DEGREES` выбирает последовательность степеней одного основания. Остальные параметры подбирает генератор. При неизвестном варианте эталон другого варианта не выдаётся.

**Эталон с параметрами.** Для `POST /api/tasks/backpack/editorial` передаётся JSON-объект. Значение `type` выбирает вариант по тем же обозначениям. Поле `message` содержит исходное сообщение как массив логических значений. Поле `lightBackpack` — последовательность целых чисел лёгкого ранца, `power` — размерность задачи, `omega` — целый множитель преобразования лёгкого ранца в тяжёлый. Размерность и множитель можно опустить. Если множитель задан, он должен быть взаимно прост с модулем. Некорректный тип, неизвестный вариант или математически непригодные параметры дают 400 с пояснением, эталон отсутствует.

При успехе обе операции возвращают HTTP 200 и объект эталона. В нём `power` — положительное целое число, `type` — строка варианта, `message` и `decodedMessage` — массивы логических значений. Поля `lightBackpack` и `hardBackpack` содержат последовательности лёгкого и тяжёлого ранцев, `omega` и `reverseOmega` — множитель и обратный к нему по модулю `module`. Поле `encodedMessage` — зашифрованное сообщение. В редакционных запросах и ответах целые произвольной длины передаются десятичными строками. Например, выбрав вариант на степенях без собственных параметров, студент получает все величины именно этого варианта. Редакционный пример не расходует попытку решения ни одной задачи.

## Задачи Эль-Гамаля

Для обеих операций нужна роль `USER`. Схема Эль-Гамаля используется здесь как учебная задача о шифровании и расшифровании сообщения. Параметр строки запроса `bitLength` задаёт разрядность — длину генерируемого простого числа в битах. Его значение целое. При его отсутствии используется значение 10. В пути обеих операций пишется `eigamal`. При успехе возвращается HTTP 200. Целые величины произвольной длины в ответе представлены десятичными строками, текстовые пояснения — обычными строками.

**Самостоятельное задание.** `GET /api/tasks/eigamal` возвращает объект с четырьмя целыми величинами — простым модулем `p`, основанием `g`, учебным показателем `x` и сообщением `m`. В учебном примере значения могут быть записаны как `{"p":"23","g":"5","x":"6","m":"13"}`. Клиент показывает их студенту без потери точности. При запросе `GET /api/tasks/eigamal?bitLength=10` возвращается условие для самостоятельного расчёта. Зафиксировать результат по одной из задач выданной сессии можно через [отправку решения](DOC-08_API_сессий.md#2-отправка-решения).

**Пошаговый разбор.** `GET /api/tasks/eigamal/editorial` возвращает исходные `p`, `g`, `x`, `m` и промежуточные величины. `y` — открытый ключ, `k` — одноразовый показатель шифрования. `c1` и `c2` — две части шифртекста, `yk` — промежуточная степень открытого ключа. `s` и `sInverse` — общий секрет и его обратная величина по модулю. В `decryptedMessage` записано восстановленное сообщение. Пояснения представлены строками `yCalculation`, `c1Calculation`, `c2Calculation`, `decryptionCalculation`. По ним можно разобрать получение открытого ключа, шифрование и расшифрование в учебном примере. Редакционные запросы не создают попыток. Для обеих операций нецелое, нулевое или отрицательное значение `bitLength` даёт 400. Если при заданной разрядности математически невозможно сформировать условие, генерация завершается диагностическим отказом.

## Учебная демонстрация со скрытым свойством

Для пользователя с ролью `USER` предусмотрен просмотр готового учебного примера. При успехе сервер возвращает HTTP 200 и JSON-объект с условием, демонстрационным результатом и педагогическим пояснением. В пояснении различаются два исхода. При нарушении конфиденциальности в рамках упражнения стали известны сведения, которые по условию должны были оставаться закрытыми. При ошибке вычисления получено неверное значение. Клиент показывает пояснение вместе с условием и соответствующим ему результатом. Если пример недоступен, сервер возвращает диагностический ответ. Просмотр не открывает сессию и не меняет оценок за ранее выданные задачи.
