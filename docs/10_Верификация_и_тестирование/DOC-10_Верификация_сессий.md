## Предмет и способ проверки

Сессия — личная работа студента с выданным набором задач. Каждая задача имеет своё условие и состояние. Планировщик — часть программы, которая периодически находит задачи с истёкшим сроком и завершает их по правилам системы. Верификация в этой главе означает проверку описанного поведения по требованиям. Верификатор по шагам разбирает карточку с исходными данными, событиями и ожидаемыми результатами. Он устанавливает, целиком ли создан набор, к своей ли задаче отнесён ответ и сохранится ли итог при истечении срока или перезапуске.

Предметный проверяющий — часть программы, которая проверяет решение задачи своего вида. Его вердикт может быть положительным или отрицательным. Когда вердикт зафиксирован, попытка решения завершена. Для разбора поведения сессии правильность учебных ответов задана заранее. Математические алгоритмы проверяют владельцы соответствующих подсистем. Правила составления карточек и чтения их номеров приведены в [основной части плана](DOC-10_План_верификации.md#как-читать-обозначения-и-ответы-системы).

Проверочная карточка имеет обозначение вида [TC-SES-001]. Здесь TC означает проверку, SES — сессии задач, а три цифры различают карточки внутри области. Читатель сопоставляет карточку с [системными требованиями к сессиям](../04_Системные_требования/Сессии_задач.md), [правилами интеграции](../04_Системные_требования/Интеграция.md), [общими программными требованиями](../07_Программные_требования/DOC-06_Программные_требования.md) и [требованиями к подсистеме сессий](../07_Программные_требования/DOC-06.2_Сессии_задач_и_планировщик.md). Тело ответа — данные, которые сервер возвращает клиенту вместе со статусом. Код ответа, состав тела и представление данных определяет [контракт операций](../07_Программные_требования/Контракты_сессий.md).

Для каждого действия прослеживают ответ клиенту (программе, пославшей запрос), состояние задачи, значение её поля `result` с сохранённым вердиктом и состояние сессии. Клиент и сервер обмениваются запросами и ответами по протоколу HTTP. Если одинаковый внешний ответ допускает несколько внутренних исходов, верификатор прослеживает изменения в хранилище. Транзакция объединяет несколько изменений данных, которые сохраняются целиком либо отменяются вместе. Такая отмена называется откатом. Строка в таблице хранилища представляет один записанный объект. Блокировка записи согласует доступ нескольких обработчиков к одним данным, например когда два запроса пытаются создать набор одному студенту.

Для задачи `NEW` означает открытое задание, `SOLVED` — верное решение, `FAILED` — неверное решение или завершение по просрочке. Для сессии `NEW` означает, что остаются задачи без итога. Когда все задачи завершены, сессия получает `SOLVED`, если все решены верно, иначе — `FAILED`. В JSON, текстовом формате передачи структурированных данных, `null` означает отсутствие значения. По полю `result` различают две причины состояния `FAILED`. При неверном решении есть отрицательный вердикт, при просрочке без вердикта значение равно `null`.

### Общие исходные данные

- А и Б — условные учётные записи для разбора, обе с правами студента (роль `USER`). JWT — подписанный токен, по которому сервер подтверждает личность пользователя. Каждый предъявляет свой токен в заголовке `Authorization: Bearer <токен>`. Отклонения указаны в карточках доступа. У А и Б номер учебной группы получен из подтверждённого университетского профиля. Для группы А включён «Практикум» — именованный шаблон с двумя позициями для генерации задач, ранцевой и Эль-Гамаля. Шаблон задаёт виды и порядок задач, а условия формируют при создании набора. Если карточке нужен другой состав, он указан в её условиях.
- Для каждой задачи даны её условие, один верный ответ и один предметно неверный ответ в допустимом формате. Варианты с изменённым полем, размером или участником разбирают отдельно, возвращаясь к исходному состоянию.
- Запись операции содержит метод HTTP и путь. В карточках самостоятельной практики создать набор означает передать `POST /api/tasks/session`, указав имя шаблона в параметре `configuration`. UUID — уникальный идентификатор объекта. Ответ отправляют через `PUT /api/tasks/submit` с UUID конкретной задачи в `statementId`. Сессию читают через `GET /api/tasks/session/{sessionId}`, заменяя `{sessionId}` на UUID набора. Для текста JSON используется кодировка UTF-8. Допустимые поля и их типы перечислены в [схеме данных сессии](../07_Программные_требования/Контракты_сессий.md#представление-сессии-и-задачи).
- Серверное время создания обозначено `t0`. Время приводится в UTC (всемирном координированном времени), буква `Z` в конце обозначает нулевое смещение от UTC. Если карточка не задаёт другого времени, рассматривают самостоятельную практику. Для неё `t0 = 12:00:00.000Z`, общий срок `D = 12:20:00.000Z` того же дня. Для контрольного мероприятия решение заканчивается в более ранний из двух моментов — через 20 минут после личного старта или при закрытии мероприятия. Отдельный пример приведён в [TC-SES-017]. Время `t_in` — момент получения сервером **полного** запроса. Предел фиксации вердикта `L = t_in + 60 секунд`. Время показано без даты для краткости. В ответах сервера проверяют полную дату, время UTC, миллисекунды и суффикс `Z`.
- При успехе код 200 означает выполнение запроса, код 201 — создание сессии. При отказе клиент получает числовой статус HTTP и машинный код причины. В теле ответа `code` обозначает причину, `message` поясняет её человеку, `timestamp` указывает время события, UUID в `requestId` позволяет найти конкретное обращение. В каждой карточке используют только указанные причины отказа. Их значения и соответствующие HTTP-статусы перечислены в [таблице ошибок](../07_Программные_требования/Контракты_сессий.md#коды-и-представление-ошибок).

## Создание сессии

<a id="tc-ses-001"></a>

### TC-SES-001. Создание и сохранение состава

**Исходные условия.** У А нет активной сессии. Для этой карточки «Практикум» содержит три позиции. Первая и третья — ранцевые задачи с разными условиями, вторая — задача Эль-Гамаля. Известны условия, которые вернёт генератор для каждой позиции.

**Действия.** В момент `t0` создать «Практикум». Сопоставить тип и условие каждой задачи с её позицией в шаблоне. Записать UUID в порядке выдачи. Изменить состав и порядок задач шаблона группы, перезапустить приложение и до срока прочитать выданную сессию.

**Ожидаемый результат.** Ответ на создание имеет статус 201. Владелец сессии — А, время создания равно `t0`. Поле `assessmentId` отсылает к контрольному мероприятию и здесь равно `null`. Участие в контрольном мероприятии и его оценка не появляются. Сессия и все три задачи имеют состояние `NEW`, у каждой задачи `result = null`. В списке сохранён исходный порядок типов. Первая и третья позиции содержат отдельные задачи, каждая со своим UUID и своим условием. У всех задач `sessionId` совпадает с `id` сессии. Повторное чтение даёт 200 и возвращает ту же последовательность UUID. На каждой позиции сохранены её тип и условие. Поле `statement` имеет строковый тип. После разбора этой строки как JSON получают исходное условие задачи. Владелец, время создания и срок `D` сохраняются.

<a id="tc-ses-002"></a>

### TC-SES-002. Доступ пользователя к шаблону

**Исходные условия.** Активной сессии нет. Каждый вариант запроса начинается с исходного состояния.

**Действия и ожидаемые результаты.** Аутентификация подтверждает, от какого лица поступил запрос. Запрос создания без действительной аутентификации даёт 401 `UNAUTHENTICATED`, с действительной аутентификацией без роли `USER` — 403 `ACCESS_DENIED`. Для пользователя без подтверждённой группы, отключённого шаблона, имени шаблона другой группы и имени с другим регистром ожидается 404 `CONFIGURATION_NOT_FOUND`. В каждом случае набор отсутствует. При верных полномочиях и имени новый набор принадлежит пользователю, чья личность подтверждена при входе.

<a id="tc-ses-003"></a>

### TC-SES-003. Конкурирующие создания и потеря ответа

**Исходные условия.** У А нет сессии `NEW`. Обе копии запроса содержат одно и то же допустимое имя шаблона.

**Действия.** Разобрать два порядка событий. В первом ответ на создание теряется по пути к клиенту. А повторяет запрос до `D`, пока созданная сессия имеет состояние `NEW`. Во втором оба запроса поступают до того, как первый завершил создание.

**Ожидаемый результат.** Существует одна новая сессия. Один запрос создаёт её со статусом 201, другой получает 409 `ACTIVE_SESSION_EXISTS`. В `details.sessionId` указан UUID единственного созданного набора. Чтение с этим UUID возвращает весь набор пользователю А. При одновременных запросах на создание проверка наличия сессии и вставка нового набора происходят под блокировкой строки одного пользователя в одной транзакции.

<a id="tc-ses-004"></a>

### TC-SES-004. Сбой при создании полного набора

**Исходные условия.** Первое условие уже сформировано. Во втором элементе шаблона задан неподдерживаемый тип. В отдельном варианте оба условия сформированы, но запись набора в хранилище завершается ошибкой.

**Действия.** Запросить создание в каждом варианте. Исправить шаблон либо восстановить запись, повторить исходный запрос.

**Ожидаемый результат.** Первая операция даёт 500 `INTERNAL_ERROR`. Данные незавершённого набора и его задач отсутствуют, ответ 201 не выдан. После устранения причины повтор возвращает 201 с обеими задачами. По описанию транзакции создание записей сессии и задач либо завершается целиком, либо целиком откатывается.

## Приём решения и предметный результат

<a id="tc-ses-005"></a>

### TC-SES-005. Ошибка формы запроса и граница размера

**Исходные условия.** А владеет задачей Эль-Гамаля в состоянии `NEW`. Схема предметного ответа описывает, какие поля обязательны и какого типа должно быть каждое. Поля `k` для Эль-Гамаля (одноразовый показатель) и `power` для ранцевой задачи (размерность) приведены в [схемах решений](../07_Программные_требования/Контракты_сессий.md#предметный-ответ). До `D` достаточно времени для исправления ответа.

**Действия и ожидаемые результаты.**

1. При создании у другого пользователя с доступным шаблоном повторить параметр `configuration`, передать пустое имя, передать одновременно `configuration` и `assessmentId` либо опустить оба параметра. При отправке решения А пропустить `statementId`, повторить его или передать строку, не являющуюся UUID. В каждом варианте ожидается 400 `INVALID_REQUEST`.
2. Для Эль-Гамаля передать пустое тело, ошибочный JSON, тело без `k`, с `k = null`, числом вместо десятичной строки или строкой с ведущим нулём. Для ранцевой задачи проверить вариант с обязательным полем `power` строкового типа. Каждый из этих запросов даёт 400 `INVALID_REQUEST`. Вызов предметного проверяющего отсутствует.
3. Дополнить заведомо верный JSON пробелами после закрывающей скобки до размера 1 048 577 байт. Ожидается 413 `PAYLOAD_TOO_LARGE`. После всех отказов попытка доступна, состояние задачи `NEW`, результат равен `null`.
4. Отправить тот же верный JSON с общим размером ровно 1 048 576 байт. Запрос укладывается в предел, проходит предметную проверку и возвращает 200 с `isOk = true`.

<a id="tc-ses-006"></a>

### TC-SES-006. Выбор проверяющего и итог нескольких задач

**Исходные условия.** А получил набор с двумя задачами. Выданные условия и UUID записаны. Шаблон группы после выдачи изменён. До срока оба ответа успевают получить вердикт.

**Действия.** Отправить допустимые по форме решения для исходных условий. Для первой задачи получить отрицательный вердикт, затем для второй — положительный. Разобрать также одновременное сохранение вердиктов разных задач с каждым из двух возможных порядков фиксации. На отдельном наборе обе задачи решить верно.

**Ожидаемый результат.** Обработчик каждого типа получает своё сохранённое условие и переданное решение. Ответ на каждый вердикт имеет статус 200. Поля `problemId` и `problemType` соответствуют выданной задаче. При ошибочном решении `isOk = false`, `errorMessage` содержит пояснение, задача переходит в `FAILED`. При верном — `isOk = true`, `errorMessage = null`, состояние `SOLVED`. После первого сохранения сессия ещё `NEW`. После обоих сохранившийся итог смешанного набора равен `FAILED`, а набора с двумя верными решениями — `SOLVED`. Результат одновременной записи совпадает с результатом последовательной для тех же двух вердиктов.

**Вариант с пользовательским заданием.** Проверить две отдельные выдачи позиции `CUSTOM_TEXT`. Для разбираемого варианта текст условия — «Назовите столицу России», сохранённый эталон — `Москва`. При чтении условия эталон отсутствует. В первой выдаче отправить `{"answer":"  Москва  "}`. Ожидается `200` с `isOk = true`. Во второй выдаче того же варианта отправить `{"answer":"москва"}`. Ожидается `200` с `isOk = false`. В обоих случаях сохраняется единственный вердикт по UUID задачи соответствующего набора.

<a id="tc-ses-007"></a>

### TC-SES-007. Две посылки на одну задачу

**Исходные условия.** Один допустимый ответ А принят до `D`. Его запись ещё открыта. Верный ответ и второй, неверный, имеют разные значения.

**Действия.** До `D` передать второй ответ, пока обрабатывается первый. Завершить первый положительным вердиктом. Ещё раз до `D` отправить второй ответ и прочитать набор.

**Ожидаемый результат.** Повтор при открытой операции получает 409 `CHECK_IN_PROGRESS`, после сохранения вердикта — 409 `TASK_FINALIZED`. Итог получен для исходного ответа ровно один раз. Сохранённые тело первой операции и положительный результат остаются прежними.

**Одновременное поступление.** В отдельном наборе зарегистрировать два запроса владельца на одну свободную задачу до `D`. Оба тела имеют допустимый формат. Одно решение верно, другое неверно. Подвести оба запроса к началу предметной проверки одновременно. Проверка доступности задачи и закрепление за ней одной операции выполняются как одно неделимое действие. Право начать вычисление получает только эта операция. Пока она выполняется, вторая получает 409 `CHECK_IN_PROGRESS`. Если право получило верное решение, задача становится `SOLVED`, если неверное — `FAILED` с отрицательным результатом. В обоих порядках проверяющему передано только тело выбранной операции. Последующее чтение возвращает единственный соответствующий ему вердикт.

**Отказ одному из двух запросов.** Два ответа владельца поступили до `D`. После `D` при разборе первого обнаружилась ошибка формата. Он получает 400 `INVALID_REQUEST`. Пока второй своевременный ответ ждёт проверки и его собственный предел ещё не достигнут, задача остаётся `NEW`. До этого предела вердикт по второму ответу может быть зафиксирован.

<a id="tc-ses-008"></a>

### TC-SES-008. Принадлежность объекта и порядок отказов

**Исходные условия.** А владеет известной задачей. У Б есть собственная учётная запись с ролью `USER`. Для сравнения взяты UUID отсутствующих задачи и сессии.

**Действия.** Б отправляет решение на задачу А и на отсутствующую задачу. Б читает сессию А и отсутствующую сессию. Повторить обе операции без действительных учётных данных и с учётной записью без роли `USER`. В отдельном варианте Б обращается к задаче А точно в `D`.

**Ожидаемый результат.** Для Б оба обращения к задачам дают 404 `TASK_NOT_FOUND`, оба чтения — 404 `SESSION_NOT_FOUND`. Тот же 404 сохраняется и для чужой задачи в момент `D`. Для обеих операций отсутствие аутентификации даёт 401 `UNAUTHENTICATED`, отсутствие роли — 403 `ACCESS_DENIED`. Проверяющий не вызывается. До срока состояние и результаты сессии А сохраняются, после срока для них действует обычный порядок завершения.

**Просрочка после чужой отправки.** В отдельном наборе у А одна задача `NEW`, свой ответ А не посылал. В 12:19:59.999Z Б отправляет ответ на эту задачу. Сравнить с отправкой Б на отсутствующий UUID в тот же момент. В обоих случаях ожидается 404 `TASK_NOT_FOUND`. В отдельном варианте остановить приложение после получения полного запроса Б, до сверки принадлежности и открытия операции. При обрыве соединения исходный HTTP-ответ неизвестен. После перезапуска за границей `D` открытой операции Б по задаче А нет. Повторное обращение Б даёт 404 `TASK_NOT_FOUND`. Задача А завершается по сроку. После `D` при обращении А за новым набором прежняя задача и её сессия завершаются в `FAILED` с `result = null` у задачи. Создание возвращает 201 с новым UUID сессии.

## Срок сессии и срок обработки ответа

<a id="tc-ses-009"></a>

### TC-SES-009. Своевременный ответ в очереди во время просрочки

**Исходные условия.** У А две задачи `NEW`. Запрос на первую задачу ожидает в очереди, то есть уже зарегистрирован и ждёт освобождения проверяющего. Полный запрос получен в 12:19:59.900Z. Предметная проверка начнётся в 12:20:02.000Z и зафиксирует верный результат в 12:20:04.000Z. По второй задаче ответа нет.

**Действия.** В момент `D` рассмотреть запуск планировщика между получением запроса и запуском проверяющего. До окончания проверки прочитать сессию и запросить новый набор. После фиксации вердикта снова прочитать сессию.

**Ожидаемый результат.** Планировщик сохраняет первую задачу в `NEW`, вторую завершает по сроку в `FAILED` с `result = null`. Чтение видит сессию `NEW`, создание получает 409 `ACTIVE_SESSION_EXISTS`. Фиксация вердикта первой задачи происходит до её предела 12:20:59.900Z, поэтому она становится `SOLVED`, итог сессии — `FAILED`. Время запуска проверяющего и фоновой обработки не меняет `t_in`.

<a id="tc-ses-010"></a>

### TC-SES-010. Полный запрос на границе срока

**Исходные условия.** Одна собственная задача уже имеет сохранённый вердикт, другая остаётся `NEW`. Ближайший плановый проход назначен на 12:20:30.000Z. Для каждого варианта берут исходное состояние.

**Действия.** Начать передачу решения за одну миллисекунду до `D`, передать последний байт в `D`. Повторить вариант с полным запросом в `D + 1 миллисекунда`. Отдельно направить такой запрос к уже завершённой собственной задаче. До фонового прохода прочитать набор. В другом варианте сразу после `D` первым запросом создать новую сессию.

**Ожидаемый результат.** Каждая поздняя отправка получает 410 `SESSION_EXPIRED`, в том числе для завершённой собственной задачи. Отметка клиента и время начала передачи не влияют на допуск. Чтение возвращает прежний вердикт и просроченную задачу в `FAILED` с `result = null`. Итог набора `FAILED`. Новый набор может быть создан после завершения прежнего, если тот уже просрочен и своевременных обработок нет. Повторный фоновый проход не меняет прежних итогов. По расписанию подсистемы плановый период проходов равен 60 секундам.

<a id="tc-ses-011"></a>

### TC-SES-011. Строгая граница фиксации вердикта

**Исходные условия.** Для каждого варианта у А сессия с одной задачей в состоянии `NEW`. Верный ответ принят в 12:05:00.000Z, поэтому `L = 12:06:00.000Z`. Очередь и расчёт занимают часть этого интервала.

**Действия и ожидаемые результаты.** При фиксации в 12:05:59.999Z верный вердикт сохраняется, задача и сессия получают `SOLVED`. Если вычисление закончено раньше, но к 12:06:00.000Z вердикт ещё не записан, операция завершается с 503 `CHECK_TIMEOUT`. То же ожидается при поступлении результата в 12:06:00.001Z. Поздний результат отбрасывается. Задача остаётся `NEW` с `result = null`, поскольку общий срок ещё не наступил. Новый правильный ответ до `D` может получить 200 и завершить задачу.

<a id="tc-ses-012"></a>

### TC-SES-012. Отказ до и после общего срока

**Исходные условия.** У А одна задача. Первый вариант начинается в 12:05:00.000Z. Во втором полный запрос получен в 12:19:59.500Z. Принимающая сторона обнаруживает ошибку формата либо получает отказ проверяющего без вердикта.

**Действия.** Для раннего запроса получить отказ через секунду. Исправить формат либо восстановить доступность проверяющего и послать новый верный ответ до `D`. Для позднего варианта обнаружить отказ в 12:20:00.500Z, затем прочитать задачу и повторить отправку.

**Ожидаемый результат.** Ошибка формата даёт 400 `INVALID_REQUEST`, недоступность проверяющего — 503 `CHECK_UNAVAILABLE`. В первом варианте после отказа видны `NEW` и `result = null`. Исправленный ответ может завершить задачу. Во втором ни один отказ не образует предметного результата. Задача и сессия завершаются по просрочке в `FAILED`, чтение возвращает `result = null`, новый ответ получает 410 `SESSION_EXPIRED`.

## Восстановление и согласованность записи

<a id="tc-ses-013"></a>

### TC-SES-013. Перезапуск с незавершённой операцией

**Исходные условия.** В сессии А одна задача Эль-Гамаля. Назначения полей и исходное условие приведены в [учебном примере Эль-Гамаля](../07_Программные_требования/Контракты_сессий.md#учебный-пример-решения-эль-гамаля). Для этого условия известен верный ответ с полями `y = "8"`, `k = "3"`, `c1 = "10"`, `c2 = "9"`, `decryptedMessage = "13"`. Время получения полного запроса `t_in = 12:19:59.000Z`, предел `L = 12:20:59.000Z`. Открытая запись операции уже сохранена. Приложение останавливается, пока ответ ожидает вызова предметного проверяющего.

**Действия.** В первом варианте восстановить работу в 12:20:30.000Z. Два обработчика восстановления одновременно выбирают ту же открытую запись. Завершить верную проверку в 12:20:58.999Z. Во втором варианте восстановить приложение ровно в 12:20:59.000Z. Для каждого варианта прочитать набор.

**Ожидаемый результат.** Из записи восстанавливаются UUID операции, владелец А, задача, все пять полей ответа с исходными значениями, время получения 12:19:59.000Z и предел 12:20:59.000Z. В первом варианте запись для обработки получает один из двух обработчиков. Он передаёт сохранённое условие и восстановленное тело проверяющему, сохраняет один положительный вердикт. Чтение возвращает задачу и сессию в состоянии `SOLVED`. Во втором варианте запись получает технический исход `CHECK_TIMEOUT`, даже если очередь после запуска свободна. Состояние задачи и сессии — `FAILED` по просрочке, `result = null`. Перезапуск не продлевает ни один из сроков.

<a id="tc-ses-014"></a>

### TC-SES-014. Потеря ответа после сохранения вердикта

**Исходные условия.** У А две задачи. Состояние первой — `SOLVED`. Для второй до срока сохранён предметно неверный ответ, но соединение закрылось до доставки 200.

**Действия.** Перезапустить приложение после фиксации второго вердикта. Считать собственную сессию дважды, в том числе после `D`. Сопоставить содержимое с выданными при создании идентификаторами, условиями и временем.

**Ожидаемый результат.** Оба чтения возвращают 200. Сохранены владелец, `createdAt`, набор условий, типы, UUID и связи задач. У первой задачи `SOLVED` и положительный результат, у второй `FAILED` и отрицательный результат с её UUID, типом и непустым пояснением. Сессия `FAILED`. Ранее закрытая операция не запускается повторно. Чтение не расходует попытку и возвращает один и тот же предметный результат.

<a id="tc-ses-015"></a>

### TC-SES-015. Сбой при фиксации вердикта

**Исходные условия.** У А сессия с одной задачей `NEW`. До `D` и `L` проверяющий передал положительный вердикт. При записи произошёл сбой. Сравнивают два независимых исхода.

**Отказ сообщён клиенту.** После отката фиксации операция закрыта с техническим отказом, клиент получил 500 `INTERNAL_ERROR`. Прочитать сессию и отправить новый ответ до `D`. До новой отправки задача и сессия остаются `NEW`, `result = null`. Первоначальная операция не возобновляется, и её вердикт не может появиться позже. Для новой отправки доступна предметная попытка.

**Работа прервана до выдачи ответа.** После отката в хранилище остаётся открытая запись принятого запроса, клиент не получил ни 200, ни сообщения об отказе. Восстановить приложение до исходного `L`. До восстановления задача и сессия имеют состояние `NEW`, `result = null`. Обработка продолжается по данным той же записи. Если вердикт зафиксирован до `L`, чтение возвращает один положительный результат и состояние `SOLVED` у задачи и сессии. При достижении `L` без фиксации применяется `CHECK_TIMEOUT`. Вердикт, оба состояния и закрытие успешной операции записываются вместе.

<a id="tc-ses-016"></a>

### TC-SES-016. Граница транзакции при одновременном завершении

**Исходные условия.** Две последние задачи одной сессии получили верный и неверный предметные вердикты. Оба обработчика готовы их фиксировать. Варианты внешнего результата описаны в [TC-SES-006].

**Действия.** По описанию подсистемы проследить, какие строки блокирует каждый обработчик во время предметного вычисления и при записи. Разобрать смену очередности двух записей и одновременное обращение планировщика к той же задаче с уже принятым своевременным ответом.

**Ожидаемый результат.** Предметное вычисление вынесено за пределы транзакции фиксации. При записи сначала блокируется строка сессии, затем задачи, затем операции. После получения блокировки обработчик учитывает актуальные состояния. Вердикт, состояния задачи и сессии и закрытие операции фиксируются одной транзакцией. Ни одна очередность не оставляет сессию `NEW` после завершения последней задачи и не позволяет планировщику заместить своевременный вердикт. В обоих вариантах сохраняются оба результата, итог сессии — `FAILED`.

<a id="tc-ses-017"></a>

### TC-SES-017. Общий срок личной сессии внутри контрольного окна

**Условия.** Мероприятие группы опубликовано с `opensAt = 10:00:00.000Z`, `closesAt = 11:00:00.000Z`. Личное время старта обозначено `t0`, срок решения — `D`, фиксация вердикта должна произойти строго до предела `L = t_in + 60 секунд`. Каждый вариант начинают на независимых данных.

**Действия.** Один студент начинает контрольную сессию в 10:05, другой — в 10:55. Для сравнения третий студент начинает самостоятельную практику в 10:55. Прочитать у каждого `deadlineAt` — сохранённое время окончания решения. Во второй контрольной сессии до самого закрытия остаются две задачи. На одну поступает полный ответ в 10:59:59.900Z, на другую — ровно в 11:00:00.000Z. Провести контроль просрочки в 11:00 и рассмотреть положительный вердикт по первому ответу при фиксации в 11:00:02.000Z. Отдельно разобрать отсутствие фиксации именно к исходному пределу 11:00:59.900Z.

**Ожидаемый результат.** Для контроля `D = min(t0 + 20 минут, closesAt)`. В первой контрольной сессии срок равен 10:25. Во второй срок равен 11:00. У начатой в 10:55 практики `D = 11:15`. Повторное чтение, в том числе после перезапуска, возвращает прежние значения. Своевременно зарегистрированный ответ второй контрольной сессии защищён от фоновой просрочки до своего прежнего `L`. При фиксации в 11:00:02 задача получает `SOLVED` со своим вердиктом. Новый ответ на другую задачу, полученный ровно в `D` или позже, получает 410 `SESSION_EXPIRED`. При отсутствии другого своевременного ответа задача завершается в `FAILED` с `result = null`. Если первый вердикт также не зафиксирован до `L`, операция завершается с 503 `CHECK_TIMEOUT`, а задача — по просрочке без предметного результата. Закрытие мероприятия ограничивает приём новых ответов. Оно не сокращает и не продлевает срок фиксации уже зарегистрированного допустимого ответа.
