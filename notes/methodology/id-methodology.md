## 1. Назначение и область применения

Настоящая методика устанавливает единые для всего комплекта документации (DOC-00…DOC-14)
правила: (а) присвоения и ведения идентификаторов требований SR-XXX, программных
требований SWR-XXX, верификационных кейсов TC-XXX и замечаний DEF-XXX; (б) построения
точечных маркеров разделов `[TS.*]`, `[SCMP.*]`, `[SR.*]`, `[SWR.*]`; (в) формулировки
требований; (г) единую терминологию (сквозной глоссарий).

Методика **обязательна к соблюдению всеми авторами** всех документов комплекта с момента
утверждения. Определения глоссария используются дословно во всех документах; расходящиеся
формулировки — предмет замечания ФИ (категория «непротиворечивость»). Контроль соблюдения
несут редакторы документов: СТ и SWR — Анохин, DOC-10 — Кокорев, DOC-09 — Портнов.

Ссылки: перечень и владельцы документов — `Реестр_документов.md`; процессы и ротация ФИ —
`Процессы_и_обязанности.md`.

## 2. Схемы идентификаторов

Идентификаторы требований и кейсов — **плоские сквозные с ведущими нулями** (три знака:
`001`…`999`; при исчерпании диапазона расширение до четырёх знаков оформляет редактор
реестра единым решением для всего префикса). **Без доменных префиксов в самих ID** —
принадлежность домену выражается разделом документа и маркером `[SR.*]`/`[SWR.*]`, а не
номером.

| Префикс | Объект | Формат | Кто присваивает | Где ведётся реестр |
|---|---|---|---|---|
| `SR-` | Системное требование | `SR-001` … `SR-NNN` | Владельцы доменов — для своих разделов `[SR.*]`; сквозную уникальность по всему DOC-05 ведёт редактор СТ (Анохин) | DOC-05 (реестр требований в приложении); дублируются в матрице DOC-09 |
| `SWR-` | Программное требование | `SWR-001` … `SWR-NNN` | Владельцы подсистем — для своих `[SWR.*]`; сквозной реестр по DOC-06 и DOC-06.1–06.6 ведёт редактор DOC-06 (Анохин) | DOC-06 (сводный реестр); детализация в DOC-06.1–06.6 |
| `TC-` | Верификационный кейс | `TC-001` … `TC-NNN` | Владелец DOC-10 (Кокорев) — только на основе уже поставленных SR/SWR; кейсы доменов поставляют владельцы доменов | DOC-10 (план верификации) |
| `DEF-` | Замечание формальной инспекции | `DEF-001` … `DEF-NNN` | Секретарь соответствующей ФИ (по DOC-13.1–13.6) в момент оформления протокола | Сквозной реестр `defects.md` в корне комплекта (единая нумерация для всех ФИ) |

Правила (действуют для всех четырёх префиксов):

1. **Уникальность навсегда.** ID уникален в пределах префикса по всему комплекту и не
   выдаётся повторно ни при каких условиях.
2. **ID удалённого требования не переиспользуется.** Удалённое требование остаётся в
   реестре и в матрице трассировки DOC-09 с пометкой «удалено в v…» (с указанием причины);
   дыры в нумерации допустимы и не заполняются.
3. **Изменение смысла = новый ID.** Если правка меняет проверяемое утверждение (объект,
   условие, меру), заводится новый ID, старый закрывается по правилу 2; переход
   фиксируется в листе регистрации изменений документа и в матрице DOC-09. Правка
   редакционного характера (стиль, опечатки, уточнение формулировки без изменения смысла)
   сохраняет ID.
4. **Присвоение до публикации.** ID присваивается при включении требования в черновик
   раздела владельцем домена; редактор реестра только контролирует уникальность и
   резервирование, самостоятельно требования не нумерует (кроме своих доменов).
5. **TC — только по поставленным требованиям.** Кейс не может получить ID, пока не
   существует SR/SWR, который он проверяет.
6. **DEF — сквозные по комплекту.** Один реестр `defects.md` для всех инспекций;
   атрибуты: документ, категория (по DOC-04), автор, ответственный, статус, дата
   закрытия. Закрытие — до конца спринта, следующего за протоколом ФИ.

## 3. Маркеры разделов

Маркер ставится в заголовке раздела документа и однозначно указывает документ и домен:
`[ДОК.РАЗДЕЛ.ПОДРАЗДЕЛ]` — латиница, верхний регистр, разделитель «точка», глубина не
более трёх уровней.

- `ДОК` ∈ {`TS` — ТЗ (DOC-02), `SCMP` — ПУКПО (DOC-03), `SR` — системные требования
  (DOC-05), `SWR` — программные требования (DOC-06.x)};
- `РАЗДЕЛ` — короткий домен (до 10 символов, из таблиц ниже); `ПОДРАЗДЕЛ` — уточнение,
  при необходимости (например `[SR.AUTH.JWT]`, `[SWR.SESSIONS.SUBMIT]`);
- маркер относится к разделу целиком, включая все его таблицы требований; требования
  внутри раздела нумеруются плоскими ID из п. 2 без повторения кода домена.

Маркеры `[TS.*]` и `[SCMP.*]` строит по той же схеме владелец соответствующего документа
(Кокорев — DOC-02, Самбьюи — DOC-03); примеры: `[TS.OVERVIEW]`, `[TS.CONSTRAINTS]`,
`[SCMP.CI]`, `[SCMP.BUILD]`. Новые доменные коды SR/SWR вводятся только редактором СТ/SWR
(Анохин) и фиксируются в этом файле.

Пример заголовка раздела СТ: `### 4.2 Сессии задач [SR.SESSIONS]` — внутри раздела
требования `SR-014`, `SR-015`, … (без повторения «SESSIONS» в ID).

## 4. Правила формулировки требований

1. **Одно требование = одна атомарная проверяемая формулировка.** Требование проверяется
   одним кейсом TC одного типа (позитивный/негативный) без разделения на случаи.
2. **Каноническая форма** функционального требования: «Система должна <действие> при
   <условие>» («Система должна отклонять запрос `PUT /api/tasks/submit` без JWT кодом
   401»). Для НФТ — с измеримой мерой: «…в течение ≤ N …», «…не более N …».
3. **Запрещены связки «и/или», перечисления и составные требования** внутри одного ID:
   «Система должна A и B» → два требования. Каждое из них получает свой ID и свой TC.
4. **SR не содержит деталей реализации** (структуры БД, классы, имена бинов); это уровень
   SWR. SWR, в свою очередь, не вводит новых функций, отсутствующих в SR.
5. **Термины — только из глоссария (п. 6)**, в единственном написании; эндпоинты,
   состояния и типы — в точности как в коде Системы (см. определения).
6. **Инвариант комплекта:** каждое SR трассируется минимум на одно SWR и минимум на один
   TC; каждое SWR — минимум на одно SR и минимум на один TC. Цепочка SR → SWR → TC
   ведётся в матрице DOC-09 (CSV) и проверяется на каждой контрольной сверке и при
   приёмке 01.12. Нарушение инварианта — блокирующее замечание ФИ.

## 6. Сквозной глоссарий

Определения даны строго в терминах Системы и сверены с кодом `mephi-12/backend`
(пакет `ru.command.mephi12`); все эндпоинты указаны с базовым путём `/api`
(`server.servlet.context-path`).

| Термин | Определение |
|---|---|
| Система | «Платформа для изучения и практики курса по криптографии в МИФИ» (учебный криптотренажёр, репозиторий mephi-12/backend): монолит Kotlin 1.9.25 + Spring Boot 3.4.0 (Web, JPA, Security, Validation) с БД PostgreSQL 17, развёртываемый средствами Docker/docker-compose; REST API — базовый путь `/api`, порт 8083. |
| Пользователь | Учётная запись (сущность `User`): уникальный email, имя, BCrypt-хеш пароля; опционально привязан к одной группе (`User.group`); идентифицируется в запросах по клейму `userId` своего JWT. |
| Студент | Пользователь в роли USER, решающий сессии задач; все операции создания сессий и отправки решений выполняются от имени студента (владельца активного JWT). |
| Администратор | Пользователь, которому при выпуске JWT добавлена authority `ADMIN` (`JwtHelper.generateAccessToken(userId, admin)`). Отдельных административных эндпоинтов в текущей версии нет; роль фиксируется в клеймах `authorities` токена. |
| Модератор | Потребитель эндпоинта `GET /api/moderator/tasks/session` — просмотра сессий задач всех студентов. Отдельного значения роли MODERATOR в коде нет (доступ проходит любой аутентифицированный пользователь с ролью USER); правила доступа к функции модерации — предмет требований `[SR.CONFIG]`. |
| Роль | Значение authority в JWT: `ROLE_USER` (выдаётся каждому при регистрации/логине) и `ADMIN`. `SecurityConfig`: пути `/api/auth/**` и `/api/public/**` открыты, все остальные требуют роль USER. |
| JWT | Access-токен стандарта JSON Web Token (библиотека jjwt), выпускается при регистрации и логине (`JwtHelper`); клеймы: `userId`, `authorities`, `permissions`; срок жизни задаётся переменной окружения `ACCESS_TOKEN_LIFETIME` (в днях); проверяется фильтром `JwtFilter` на каждом запросе. |
| Регистрация | `POST /api/auth/registration` (email, имя, пароль; тело валидируется `@Valid`); пароль хранится только как BCrypt-хеш; успешная регистрация сразу возвращает JWT (`LoginResponse`). |
| Аутентификация | `POST /api/auth/login` по паре email + пароль (сверка BCrypt-хеша) с выдачей JWT; синоним — «логин». |
| Сессия задач | Период решения студентом набора задач (сущность `ProblemSession`): создаётся `POST /api/tasks/session?configuration=<имя конфигурации>` по включённой для группы студента конфигурации; у студента не более одной активной сессии (`sessionState = NEW`, повторное создание отклоняется); время жизни задачи — 20 минут, по истечении задача автоматически проваливается планировщиком автопровала; сессия закрывается, когда не осталось задач в состоянии NEW. |
| Задача | Элемент сессии (сущность `Problem`): JSON-условие (`statement`), тип (`ProblemType`) и состояние (`ProblemState`: NEW «Задание решается», SOLVED «Задание верно решено», FAILED «Задание решено неверно»); проверка решения — `PUT /api/tasks/submit?statementId=<UUID>`; владелец и активность сессии проверяются при отправке. |
| Тип задачи | Значение перечисления `ProblemType`: `BACKPACK_CODE_SUPER_INCREASING` (ранцевая КС на супервозрастающей последовательности), `BACKPACK_CODE_DEGREES` (ранцевая КС на степенях), `BACKPACK` (ранцевая КС в составе сессии), `BACKPACK_BACKDOOR` (бэкдор в ранцевой КС), `EL_GAMAL` (КС Эль-Гамаля). В конфигурациях сессий задачи задаются строковыми квалификаторами «Backpack» и «ElGamal» (`ProblemType.getByQualifier`); типы `BACKPACK_CODE_*` используются редакционными (editorial) генерациями `GET/POST /api/tasks/backpack/editorial`. |
| Ранцевая криптосистема (КС) | Криптосистема Меркля—Хеллмана на задаче о рюкзаке (реализация — `AbstractBackpackProblemSolverService`): лёгкий рюкзак L (супервозрастающая последовательность), модуль n = ΣL + 1, множитель ω, взаимно простой с n; публичный тяжёлый рюкзак H = (L·ω) mod n; шифрование — сумма элементов H по единичным битам сообщения; расшифрование — умножением на ω⁻¹ mod n. |
| Супервозрастающая последовательность | Последовательность, каждый элемент которой строго больше суммы всех предыдущих (`isSuperIncreasing`); в типе `BACKPACK_CODE_SUPER_INCREASING` из неё строится лёгкий рюкзак. |
| Ранцевая КС на степенях | Вариант ранцевой КС (тип `BACKPACK_CODE_DEGREES`, `BackpackDegreesProblemSolverServiceImpl`): лёгкий рюкзак строится из элементов вида p^i (степени основания p > 1), образующих супервозрастающую последовательность. |
| Бэкдор | Секрет, встроенный в публичный ключ ранцевой КС на степенях (`BackpackBackDoorDegreesProblemSolverServiceImpl`, эндпоинт `GET /api/backdoor/editorial`): десятичные записи ω и n «зашиты» в младшие разряды элементов тяжёлого рюкзака (цифра Hᵢ mod 10), что позволяет владельцу секрета восстановить закрытый ключ из открытого. |
| Схема Эль-Гамаля | Криптосистема на мультипликативной группе Z_p*: ключи (p, g, закрытый x, открытый y = g^x mod p), шифрование с сеансовым показателем k, расшифрование через x; реализована `ElGamalService` и utils/mathLibrary (`CryptoRandom`, `PrimeNumbers`, `ModularArithmetic`, `GroupTheory`, `ElGamalUtils`); учебные генерации — `GET /api/tasks/eigamal?bitLength=<N>` (задача) и `GET /api/tasks/eigamal/editorial?bitLength=<N>` (разбор). |
| Конфигурация задач | Сущность `ProblemConfiguration`: имя + упорядоченный список квалификаторов типов задач (`taskServices`), задающий состав и порядок задач в создаваемой сессии; доступность группе — через `UserGroupProblemConfiguration.enabled` (включённые конфигурации группы: `GET /api/tasks/groups/configurations?groupId=<UUID>`). |
| Группа пользователей | Сущность `UserGroup` (учебная группа): объединяет пользователей (`User.group`) и связывается с конфигурациями задач; список групп — `GET /api/users/groups`, привязка себя к группе — `PUT /api/users/me/groups?group=<имя>`. |
| Планировщик автопровала | Фоновый процесс `ProblemAutoFailScheduler` (`@Scheduled(fixedRate = 60 000)` — раз в 60 с): переводит задачи в состоянии NEW старше 20 минут (по `created_at`) в FAILED и закрывает сессии, в которых не осталось задач в состоянии NEW. |

| История решений | Просмотр студентом решённых задач: `GET /api/users/me/tasks`; в текущей версии возвращает все сохранённые сущности `BackpackProblem` (сервис `HistoryService` помечен `@Deprecated` и подлежит замене). |
| Формальная инспекция (ФИ) | Контроль качества документа по процедуре DOC-04 (по Фагану): сессия с ведущим, секретарём и рецензентами (рецензент всегда проверяет чужой домен); по документам приоритета К/В оформляется протокол DOC-13.1–13.6 с решением ПРИНЯТО / ПРИНЯТО С ЗАМЕЧАНИЯМИ / НА ДОРАБОТКУ. |

| Трассировка | Прослеживаемость цепочки SR → SWR → TC: каждое системное требование связано с реализующими его программными требованиями и проверяющими кейсами; ведётся в матрице DOC-09 (CSV-источник, в комплект идёт PDF). |
